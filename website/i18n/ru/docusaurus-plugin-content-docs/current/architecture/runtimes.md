# Рантаймы

Сервис пишется один раз: те же обработчики и та же цепочка монтирования. Работает он на одном из двух исполнителей: многопоточном на tokio или однозадачном на embassy для устройства.
У фасада есть по одной возможности (feature) на каждый, `tokio` и `embassy`. Они складываются: сборка может включить обе.

```toml
# Сервер: tokio входит в возможности по умолчанию.
ruststream = "0.8"

# Устройство с кучей и без операционной системы: только embassy, tokio в сборку не попадает.
ruststream = { version = "0.8", default-features = false, features = ["embassy", "macros", "json"] }

# Устройство без кучи: сборка ничего не выделяет ни при запуске, ни на сообщение.
ruststream = { version = "0.8", default-features = false, features = ["embassy", "memory", "macros", "postcard"] }

# Пакет брокера на tokio: он отключает возможности по умолчанию.
ruststream = { version = "0.8", default-features = false, features = ["tokio"] }
```

## Исполнитель выбирает приложение

`#[ruststream::app]` строит `RustStream`, приложение исполнителя на tokio.
`#[ruststream::app(runtime = embassy)]` строит `EmbeddedApp`, приложение исполнителя на embassy, то есть одну задачу embassy.
Любое другое имя рантайма даёт ошибку компиляции.
Обработчики не несут рантайма: `#[subscriber]` раскрывается в один и тот же код для обоих. Исполнитель сам говорит, что требует от обработчика, в месте, где его монтирует.

## Что каждый исполнитель требует от обработчика

Исполнитель на tokio переносит обработчик между потоками на каждом `.await`, поэтому будущее (future) тела обработчика должно быть `Send`.
Тело, которое держит `Rc` через `.await`, не пройдёт на `include`, который его монтирует. Ошибка называет обработчик.
Исполнитель на embassy опрашивает все обработчики в одной задаче и ничего не требует от будущего, поэтому то же тело монтируется там.
Продолжение, которое выполняется после подтверждения (`and_after`, хук контекста), подчиняется тому же правилу: при включённом tokio его будущее должно быть `Send`, при одном embassy оно не обязано, поэтому продолжение на устройстве может публиковать через локальную шину.

## Один трейт для обоих исполнителей

Брокер реализует один `Publisher`, один `Settle` и один набор трейтов совместимости, и оба исполнителя пользуются ими.
Их будущие (futures) и суперпризнаки требуют `Send` (и `Sync`) при включённом `tokio` и ничего не требуют при одном `embassy`, поэтому брокер на устройстве реализует те же трейты, что и брокер на сервере.
Шаги настроек брокера ограничены `PublishSink<Options = ..>` и работают на любом исполнителе.
Сборка с обеими фичами берёт более строгое ограничение: тип брокера, который держит `Rc`, рядом с tokio не компилируется, а локальная шина памяти семейства делит состояние через потокобезопасные указатели.

## Что предлагает каждый исполнитель

Исполнитель на tokio предлагает `workers(n)`, `threads(n)`, сигналы, метрики, OpenTelemetry и CLI.
Исполнитель на embassy предлагает рабочих постоянного числа (`.pool::<N>()` и `.keyed::<N>()`), хранилище повторов с ёмкостью, заданной в месте монтирования (`.retry_capacity::<CAP>()`), а также остановку и состояние здоровья через `Control` и `Health`.
Возможность, которой нет у одного исполнителя, на нём даёт ошибку компиляции.

Когда отложенному повтору в хранилище embassy не хватает записи, копии негде ждать.
Это такой же сбой публикации, как и любой другой, со своей ошибкой «нет свободной записи»: о нём узнаёт продолжение `.error` обработчика, а без него сбой пишется в журнал, и копия теряется.
Доставка закрыта в любом случае, поэтому обработчик не запускается снова из-за полного хранилища.

## Исполнитель на embassy без кучи

Исполнитель на embassy собирается в двух видах, и одна сборка содержит один из них.
С фичей `alloc` он держит заголовки, полезную нагрузку, продолжения и сбои в куче.
Без неё тот же исполнитель держит их в памяти фиксированного размера и ничего не выделяет ни при запуске, ни на сообщение, поэтому фреймворк работает на устройстве без кучи.
Фичи `tokio`, `json`, `cbor` и `msgpack` включают `alloc`, как и любой крейт графа зависимостей, который его запросит: фичи складываются, и граф с включённым `alloc` целиком собирается в виде с кучей.

Сервис пишется одинаково в обоих видах: `#[subscriber]`, `#[ruststream::app(runtime = embassy)]`, `.then`, `.error`, слоты `Out` и типизированные заголовки.
Различается вид тех частей, размер которых определила бы куча:

| Часть | С `alloc` | Без `alloc` |
|---|---|---|
| Заголовки сообщения | `HeaderMap` | `FixedHeaders`: 8 записей и 256 байт, а `insert` возвращает ошибку, когда карта заполнена |
| Кодек | `Codec`: `json`, `cbor`, `msgpack` | `SliceCodec`: `postcard` и `json-core`, которые кодируют в срез |
| Продолжение (`and_after`, `.then`, `.error`) | лежит в куче | лежит в комнате на 128 байт; больший захват не компилируется |
| Сбои, которые читает `.error` | передаются по значению | заимствуются из фиксированного буфера подписки |
| `ctx.after(..)` | регистрирует | возвращает `Result`, потому что у доставки четыре регистрации |
| Пакет | `Vec` исходов | размером до 16, который задаётся в месте монтирования через `.batch::<N>()` |
| Локальная шина | `LocalMemoryBroker::new()` | `LocalMemoryBus`, который плата объявляет как `static` |
| Диагностика | события `tracing` | `log` или `defmt`, смотря какая из фич включена |

Вид выбирает сборка, поэтому обработчик по нему не ветвится.
Тип из вида с кучей в виде без неё не находится, а превышенная ёмкость даёт ошибку компиляции, которая её называет.
Страница компонента [Встроенный рантайм](../components/application/embedded-runtime.md) показывает целый сервис для устройства в фиксированном виде и все ёмкости, которые называет монтирование.

## Тестирование

`TestApp` запускает приложение на tokio, а `testing::embedded::TestApp` запускает встроенное приложение на хосте с поддельными часами embassy-time.
Оба лежат в фасаде рядом, когда включена возможность `testing`.
Когда включена возможность `testing`, каждый брокер встроенного приложения реализует внутрипроцессный режим, `InProcess`.
`testing::embedded::TestApp` следует виду сборки: без `alloc` он ведёт фиксированный вид, и тестовый бинарник может поставить аллокатор, который отказывает на любое выделение фреймворка.
