    Как написать адаптацию библиотеки брокера¶

    Нормативная версия документации - английская

    Эта страница переведена с английского языковой моделью. При любом расхождении верен английский оригинал.

    Адаптация библиотеки брокера - это отдельный крейт, который реализует трейты ядра. Она подключает ruststream без фич по умолчанию:

    [dependencies]
ruststream = { version = "0.7", default-features = false }

    Так крейт получает трейты и рантайм, но не JSON-кодек: это единственная фича ядра, включённая по умолчанию.

    Эта страница и есть контракт. Работа идёт в четыре шага:

    1. Реализуйте обязательные трейты.
    2. Заведите собственный Config.
    3. Добавьте трейты-совместимости для того, что брокер умеет.
    4. Подтвердите результат обвязкой conformance.

    Полная реализация поверх настоящей клиентской библиотеки разобрана в примере с NATS.

    Обязательные трейты¶

    Контракт требует от брокера этих трейтов:

    • Broker и ConnectedBroker отвечают за подключение и остановку.
    • Subscribe открывает подписку по имени.
    • Subscriber отдаёт поток входящих сообщений.
    • IncomingMessage описывает доставленное сообщение и его подтверждение.
    • Publisher публикует.
    • PublishPolicy - политика, которая конструирует издателя.

    Примеры in-memory брокера на этой странице вырезаны из его исходного кода. Код страницы поэтому меняется вместе с контрактом.

    Broker и ConnectedBroker¶

    Брокер не задаёт ни тип подписчика, ни тип издателя, поэтому одно приложение работает с брокерами разных видов. Сам брокер - это только жизненный цикл.

    Брокер проходит через три состояния, и у каждого свой тип. Переход поглощает self и возвращает следующее состояние. Поэтому вызов не в том порядке не компилируется.

    pub trait Broker: Send + Sync + Sized {
    type Error: std::error::Error + Send + Sync + 'static;
    type Connected: ConnectedBroker;
    async fn connect(self) -> Result<Self::Connected, Self::Error>;
}

pub trait ConnectedBroker: Send + Sync + Sized + 'static {
    type Error: std::error::Error + Send + Sync + 'static;
    type Closed: Send;
    async fn shutdown(self) -> Result<Self::Closed, Self::Error>;
}

    Каждый шаг делает свою работу:

    • new(addrs) только записывает конфигурацию. Он синхронный и не выполняет ввода-вывода.
    • connect(self) выполняет всю сетевую работу. Рантайм вызывает его один раз, на старте. Подключённая форма держит живого клиента, и её операциям не нужно проверять подключение.
    • shutdown(self) освобождает ресурсы. Он не блокирует и не паникует: всякую очистку, которая может вернуть ошибку, делайте здесь и возвращайте Result.

    Closed - свидетель остановки. В него кладут диагностику как обычные данные: итог сброса буферов, счётчики потерь. Если сказать нечего, берут ().

    Остановленный брокер не умеет ни публиковать, ни подписываться, и владелец не вызовет эти методы по ошибке: такой код не компилируется. Дескрипторы, которые разделяют соединение, проверяются во время выполнения. Это издатели, розданные подключённой формой, и клоны разделяемого брокера. После остановки каждый их вызов возвращает ошибку и никогда не завершается успешно.

    Свои задачи брокер запускает в том рантайме, где отработал connect: таймер отложенной повторной доставки, диспетчер ответов, окно фиксации. Для этого подключённая форма запоминает Handle::current() в connect и запускает задачи через этот дескриптор, из какого бы потока ни пришёл вызов:

    pub struct ConnectedExampleBroker {
    runtime: Handle, // captured in `connect`
    // ...
}

impl ConnectedExampleBroker {
    fn requeue_after(&self, delivery: Delivery, delay: Duration) {
        self.runtime.spawn(async move {
            sleep(delay).await;
            delivery.requeue();
        });
    }
}

    Причина в выделенных потоках. Обработчик на таком потоке публикует и подтверждает сообщения из рантайма своего потока. Задача, запущенная там через tokio::spawn, ждёт, пока обработчик закончит вычисление, и останавливается вместе с этим рантаймом, хотя соединение продолжает работать.

    Издателей можно раздавать и до connect, пока приложение собирается. Тогда брокер держит разделяемую ячейку, которую заполняет connect, или разделяемое внутрипроцессное состояние, как in-memory брокер. Ранние дескрипторы обслуживает эта ячейка, а не подключённая форма.

    In-memory брокер реализует весь жизненный цикл в нескольких строках:

    src/memory/mod.rs
    impl<Log: LogMode> Broker for MemoryBroker<Log> {
    type Error = MemoryError;
    type Connected = ConnectedMemoryBroker<Log>;

    /// Connecting is free for an in-process bus. A shut-down bus (a clone lineage may have shut
    /// the shared state down) is revived with a fresh, empty registration map, so the connected
    /// form always starts live; a live bus keeps its registrations.
    ///
    /// The connected form keeps the runtime it was connected on, and a delayed redelivery's timer
    /// runs there whichever thread settles the delivery.
    ///
    /// # Panics
    ///
    /// Panics when polled outside a Tokio runtime, the one thing it has to capture.
    fn connect(self) -> impl Future<Output = Result<Self::Connected, Self::Error>> {
        // Run on the first poll, so the runtime captured is the one the connection runs on, not
        // the one the future happened to be built on.
        lazy(move |_| {
            {
                let mut bus = self
                    .state
                    .subscribers
                    .lock()
                    .expect("memory broker mutex poisoned");
                if let Bus::ShutDown(routing) = *bus {
                    *bus = Bus::Live(Registry::new(routing));
                }
            }
            Ok(ConnectedMemoryBroker {
                state: self.state,
                runtime: Handle::current(),
                mode: PhantomData,
            })
        })
    }
}

/// The connected form of [`MemoryBroker`]: the typed witness that [`Broker::connect`] ran.
///
/// Cheap to clone: the in-memory bus is shared state by nature, so the connected form is a
/// shareable handle on it, exactly like the unconnected broker. Subscriptions (the
/// [`Subscribe`] capability, [`MemorySource`]) resolve against this form, and carry over the
/// broker's log mode: only a [`Retaining`] one opens repositionable subscriptions.
pub struct ConnectedMemoryBroker<Log = Discarding> {
    state: Arc<MemoryState>,
    /// The runtime `connect` ran on, which every task the broker starts runs on.
    runtime: Handle,
    mode: PhantomData<Log>,
}

impl<Log> Clone for ConnectedMemoryBroker<Log> {
    fn clone(&self) -> Self {
        Self {
            state: Arc::clone(&self.state),
            runtime: self.runtime.clone(),
            mode: PhantomData,
        }
    }
}

impl<Log> fmt::Debug for ConnectedMemoryBroker<Log> {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        f.debug_struct("ConnectedMemoryBroker")
            .finish_non_exhaustive()
    }
}

impl<Log: LogMode> ConnectedMemoryBroker<Log> {
    /// Returns a publisher bound to this broker.
    #[must_use]
    pub fn publisher(&self) -> MemoryPublisher {
        MemoryPublisher {
            state: Arc::clone(&self.state),
            txn: Mutex::new(None),
        }
    }

    /// Returns a request / reply-capable publisher bound to this broker.
    ///
    /// See [`MemoryBroker::requester`] for why its operations report [`RequestError`] rather
    /// than [`MemoryError`].
    #[must_use]
    pub fn requester(&self) -> MemoryRequester {
        MemoryRequester::new(Arc::clone(&self.state))
    }
}

impl<Log: LogMode> ConnectedBroker for ConnectedMemoryBroker<Log> {
    type Error = MemoryError;
    type Closed = ClosedMemoryBroker;

    /// Enters the terminal shut-down state: the bus itself flips to its `ShutDown` variant, so
    /// every aliased handle that would touch it (a publisher's publish or transaction commit, a
    /// request) errors with [`MemoryError::ShutDown`]. Consuming `self` makes any further use
    /// of this handle a compile error; the returned witness reports how many subscriber
    /// registrations the teardown dropped.
    fn shutdown(self) -> impl Future<Output = Result<Self::Closed, Self::Error>> {
        let dropped = {
            let mut bus = self
                .state
                .subscribers
                .lock()
                .expect("memory broker mutex poisoned");
            let routing = match &*bus {
                Bus::Live(registry) => registry.routing,
                Bus::ShutDown(routing) => *routing,
            };
            match std::mem::replace(&mut *bus, Bus::ShutDown(routing)) {
                Bus::Live(registry) => registry.len(),
                Bus::ShutDown(_) => 0,
            }
        };
        ready(Ok(ClosedMemoryBroker {
            subscribers_dropped: dropped,
        }))
    }
}

    ClosedMemoryBroker - свидетель остановки с диагностикой: он сообщает, сколько регистраций подписчиков отбросила остановка. Обвязка conformance проверяет весь жизненный цикл, включая ошибки после остановки, а пример с NATS показывает его поверх настоящей клиентской библиотеки.

    Subscribe¶

    Subscribe подписывается по имени: теме, субъекту или очереди. Его вызывает #[subscriber("name")]. Реализуйте трейт на подключённой форме.

    Кроме подписки трейт сообщает адрес для повторов. По нему рантайм публикует копию сообщения, и копия должна вернуться в ту же подписку. Чаще всего адрес - само имя, как у субъекта, топика, стрима и очереди. Фильтр MQTT devices/+/telemetry - исключение: он читает топики всех устройств и не называет ни одного.

    pub trait Subscribe: ConnectedBroker {
    type Subscriber: Subscriber;

    // Кто публикует копии для повторов подписки по имени и кто называет их адрес.
    // AddressedCopies там, где публикация по имени подписки доходит до открытой под
    // ним подписки (субъект, топик, стрим, имя очереди), - тогда имя и есть адрес.
    // NamedCopies там, где это не так: фильтр MQTT читает много топиков и не
    // называет ни одного.
    type Copies: CopyPath;

    async fn subscribe(&self, name: &str) -> Result<Self::Subscriber, Self::Error>;

    // По умолчанию: что регистрация, смонтированная по этому имени, объявила о своих
    // повторах. Отобразите предел и адрес на подписку, которую открывает это имя,
    // если у брокера есть для них механизм.
    fn declare_retry(&self, name: &str, declaration: &RetryDeclaration)
        -> Result<(), DeclareRetryError>;
}

    In-memory брокер реализует его так:

    src/memory/mod.rs
    impl<Log: LogMode> Subscribe for ConnectedMemoryBroker<Log> {
    type Subscriber = MemorySubscriber<Log>;
    // One subject is both ends of the bus here, so a publish under the name a subscription reads
    // reaches that subscription, and the name is the address.
    type Copies = AddressedCopies;

    /// A name with a wildcard token is refused with [`MemoryError::WildcardName`]: this form
    /// reads one name, and [`MemoryPattern`] is the one that reads a pattern.
    fn subscribe(&self, name: &str) -> impl Future<Output = Result<Self::Subscriber, Self::Error>> {
        if has_wildcard(name) {
            return ready(Err(MemoryError::WildcardName {
                name: name.to_owned(),
            }));
        }
        let (tx, rx) = mpsc::unbounded_channel();
        let name = name.to_owned();
        if let Err(err) = self.state.register(&name, tx.clone()) {
            return ready(Err(err));
        }
        ready(Ok(MemorySubscriber::new(
            name,
            rx,
            tx,
            &self.state,
            Some(self.runtime.clone()),
        )))
    }
}

    От type Copies зависит, как повторяет #[subscriber("orders")] на вашем брокере. AddressedCopies означает, что адрес - само имя, и больше ничего писать не нужно. NamedCopies означает, что адрес назовёт место монтирования: через .out_retry(политика).to(имя) или через преобразование публикации для каждой доставки.

    Если подписке мало одного имени, ей нужен собственный дескриптор.

    Subscriber¶

    Подписчик - это Stream входящих сообщений. Обратное давление даёт сам Stream.

    pub trait Subscriber: Send {
    type Message: IncomingMessage;
    type Error: std::error::Error + Send + Sync + 'static;
    fn stream(&mut self) -> impl Stream<Item = Result<Self::Message, Self::Error>> + Send + '_;
}

    stream принимает &mut self. Всё, что подписчик буферизует между опросами, хранится за изменяемым заимствованием, и это даёт безопасность при отмене.

    IncomingMessage¶

    Доставленное сообщение отдаёт полезную нагрузку и заголовки. Его подтверждают через ack или отклоняют через nack. ack поглощает self, поэтому двойной ack - ошибка компиляции.

    pub trait IncomingMessage: Send + Sync {
    fn payload(&self) -> &[u8];
    fn headers(&self) -> &HeaderMap;
    async fn ack(self) -> Result<(), AckError>;
    async fn nack(self, requeue: bool) -> Result<(), AckError>;

    // Defaulted: false. The runtime reads this first and never calls
    // nack_after without it, so override the pair together.
    fn supports_nack_after(&self) -> bool;

    // Defaulted: AckError::Unsupported. Override when the transport has native
    // delayed redelivery (JetStream NAK with delay); handlers reach it through
    // HandlerOutcome::retry_after.
    async fn nack_after(self, delay: Duration) -> Result<(), AckError>;

    // Defaulted: None. Override (with the Partitioned capability) to feed the
    // runtime's keyed lanes, workers(n, by_key) and threads(n, by_key).
    fn partition_key(&self) -> Option<&[u8]>;

    // Defaulted: None. Override where the transport counts its own deliveries
    // (JetStream num_delivered, SQS ApproximateReceiveCount, Pub/Sub
    // delivery_attempt): a registration's max_attempts(..) cap then counts the
    // broker's redeliveries and not only the copies the runtime published.
    // The first delivery of a message answers 1.
    fn redelivery_count(&self) -> Option<u64>;
}

    Методы по умолчанию. Четыре последних метода можно не переопределять. Брокер без них всё равно получает все возможности рантайма:

    • retry_after рантайм выполняет сам. Он отбрасывает доставку, ждёт задержку и публикует копию через издателя повторов регистрации, с увеличенным на единицу заголовком счётчика повторов. Адрес копии называет ваша подписка.
    • Пул воркеров по ключу раздаёт сообщения без ключа по кругу.
    • Предел max_attempts(..) считает попытки по заголовку счётчика повторов.

    Брокеры этого рабочего пространства переопределяют эти методы, поэтому поведение по умолчанию закреплено тестом в ядре:

    src/message.rs
    struct Stub {
    payload: Vec<u8>,
    headers: HeaderMap,
}

impl IncomingMessage for Stub {
    fn payload(&self) -> &[u8] {
        &self.payload
    }

    fn headers(&self) -> &HeaderMap {
        &self.headers
    }

    fn ack(self) -> impl Future<Output = Result<(), AckError>> {
        ready(Ok(()))
    }

    fn nack(self, _requeue: bool) -> impl Future<Output = Result<(), AckError>> {
        ready(Ok(()))
    }
}

let stub = Stub {
    payload: b"body".to_vec(),
    headers: HeaderMap::new(),
};
assert_eq!(stub.payload(), b"body");
// The default partition_key is None (no key).
assert!(stub.partition_key().is_none());
// The default reports no native delayed redelivery, so the runtime uses its fallback.
assert!(!stub.supports_nack_after());
// The default nack_after signals "not honored" rather than silently degrading.
assert!(matches!(
    stub.nack_after(Duration::from_secs(1)).await,
    Err(AckError::Unsupported)
));

    Отложенная доставка. Её переопределяют парой методов. Рантайм сначала спрашивает supports_nack_after. Если переопределить только nack_after, флаг останется false, и метод никто не вызовет.

    Не игнорируйте задержку. nack_after, который делает nack(true) без паузы, превращает retry_after(d) в retry(): сообщение возвращается сразу, и так на каждой попытке. Если транспорт не умеет придержать сообщение, верните AckError::Unsupported: так делает реализация по умолчанию. Получив такой ответ, рантайм выдерживает задержку сам.

    Счётчик попыток. Пока redelivery_count возвращает None, предел читает заголовок фреймворка. Если метод переопределён, предел читает только счётчик брокера, и заголовок к нему не прибавляется.

    Своя задержка. Задержку можно соблюдать и самому, публикуя копию: в очередь ожидания за обменником DLQ или в отдельный топик повторов. Если транспорт попыток не считает, увеличивайте на копии RETRY_COUNT_HEADER из ruststream::runtime. Если считает, заголовок не трогайте: для брокера копия - новое сообщение, и после круга по очереди ожидания доставка придёт к пределу первой попыткой. Опишите это в документации крейта.

    Один счётчик ссылок. Методы доступа отдают заимствования. Поэтому доставке хватает одного счётчика ссылок на всё сообщение, а не по счётчику на поле. Сообщение клиентской библиотеки обычно хранит имя, нагрузку и заголовки тремя подсчитываемыми значениями. Сложите их в один блок под одним Arc. Снаружи оставьте то, что у копий различается: позицию в журнале и число попыток.

    Тогда копия для подписчика, возврат в очередь и повторное воспроизведение стоят одного атомарного инкремента вместо трёх. Разница видна на каждом сообщении, когда поток клиентской библиотеки и задача диспетчера работают на разных ядрах. Так написан MemoryBroker.

    Publisher¶

    pub trait Publisher: Send + Sync {
    /// Как ваш транспорт распоряжается нагрузкой: `Lend`, если он её читает, `Take`, если ваш
    /// клиент оставляет её себе.
    type Payload: PayloadForm;

    type Error: std::error::Error + Send + Sync + 'static;

    /// Настройки вашего брокера на одно сообщение. Все поля необязательные; `()`, если их нет.
    type Options: Clone + Send + Sync + 'static;

    async fn publish(
        &self,
        msg: OutgoingFor<'_, Self::Payload>,
        options: Option<&Self::Options>,
    ) -> Result<(), Self::Error>;

    /// С реализацией по умолчанию: заголовки, которые этот издатель кладёт под каждую публикацию.
    fn base_headers(&self) -> Option<&HeaderMap> { None }
}

    Форма нагрузки. type Payload говорит, что ваш транспорт делает с байтами нагрузки:

    • Lend - транспорт только читает байты: складывает их в свой кадр, пакет или буфер сокета. Так работает почти любой сетевой протокол.
    • Take - клиентская библиотека оставляет нагрузку себе после вызова: принимает Vec<u8>, Bytes или другое собственное значение.

    От объявления зависит, что приходит в publish:

    // Take: буфер, который записал фреймворк, и он ваш.
async fn publish(&self, msg: OutgoingMessage<'_, BytesMut>, options: Option<&()>) -> Result<(), Error>

// Lend: байты там, где они уже лежат, годные на время вызова.
async fn publish(&self, msg: OutgoingMessage<'_, &[u8]>, options: Option<&()>) -> Result<(), Error>

    Lend. Издатель получает &[u8], и освобождать ему нечего. Цикл диспетчеризации одалживает ему один буфер и перезаписывает его для каждого сообщения. Поэтому ответ через ваш брокер не выделяет памяти ни на одной доставке. Ради этого объявление и существует: ядро не может одолжить то, что вы можете оставить себе.

    Take. Издатель получает буфер кодека таким, каким его записали. Vec::from(payload) ничего не стоит, потому что этот буфер и есть вектор. payload.freeze() стоит одного выделения, которое делает владение разделяемым. Копируется только та публикация, которая одалживала чужие байты.

    Сообщение. OutgoingMessage заимствует имя, а нагрузку и заголовки транспорт может забрать без копирования. Прочитать их можно при любом объявлении: msg.payload() отдаёт &[u8], msg.headers() отдаёт &HeaderMap. Транспорт, который поглощает сообщение, забирает адрес, нагрузку и заголовки одним перемещением через msg.into_parts().

    Билдер. Сервис не вызывает publish сам. Он пишет publisher.message(&value).publish(), и билдер выбирает адрес, кодек и заголовки, а затем делает ровно один вызов publish. Реализуйте publish, и весь билдер заработает.

    Настройки. Options - настройки одного сообщения: QoS, приоритет, ключ упорядочивания, срок жизни. Вызов передаёт только те поля, которые изменил. Остальные задала политика, когда конструировала издателя. Ваш publish сводит одно с другим. Там, где настройки некому изменить (ответ обработчика, отложенная переобработка), options равно None, и действуют настройки политики.

    Настройки в тестах. Clone и 'static у Options нужны тестовой обвязке. Она снимает копию настроек через слот Out и отдаёт её тесту тем же типом. Тест проверяет значение, которое получил ваш publish, а не поле протокола. Выведите ещё Debug и PartialEq, и проверка запишется как with_options(&YourOptions { .. }) (проверки по слотам Out).

    Постоянные заголовки. base_headers - постоянные заголовки издателя: арендатор, имя продюсера, идентификатор схемы. Билдер начинает исходящие заголовки с них и кладёт сверху заголовки места вызова, ключ за ключом. На общем ключе остаётся значение места вызова (откуда берутся заголовки).

    Транзакции. Transaction объявляет собственные Options и Payload и тот же base_headers с реализацией по умолчанию. Транзакция - отдельная поверхность публикации. Она может учитывать настройки, которых не учитывает её издатель, а буфер её клиентской библиотеки может оставлять нагрузку себе там, где прямая публикация её только читает. У большинства брокеров в обоих местах стоят типы издателя. Дескриптор без собственных постоянных заголовков оставляет base_headers по умолчанию в обоих местах.

    PublishPolicy¶

    Издатель брокера состоит из двух частей: политики и живого соединения. Политика - это настройки издателя: обменник, таймаут очереди, транзакционный идентификатор. Соединения она не держит, поэтому её можно сконструировать где угодно. Сделайте её отдельным типом.

    На старте политика конструирует живого издателя на подключённой форме. Конструктор - метод pair трейта PublishPolicy:

    pub trait PublishPolicy<C: ConnectedBroker> {
    type Live; // the live publisher (or live wiring form, for combinator stacks)
    async fn pair(self, connected: &C) -> Result<Self::Live, PairError>;
}

    pair. Метод асинхронный и может вернуть ошибку. Брокер, которому нужно инициализировать транзакционного продюсера, делает это здесь. Ошибку оберните в PairError конструктором PairError::new. Политика инстанцирует издателя один раз, поэтому pair не попадает на горячий путь.

    Режимы. Каждому режиму публикации нужна своя пара «политика - живой издатель». Режим выбирают типом политики, а не флагом во время выполнения. Обычная политика конструирует обычного издателя. Шаг билдера transactional_id(..) превращает её в транзакционную политику, и её живой издатель реализует TransactionalPublisher. У обычного издателя транзакционных методов нет вовсе.

    Комбинаторы. Типизированные комбинаторы ядра реализуют PublishPolicy поверх вашей политики. Поэтому пользователь добавляет к ней кодеки и преобразования ещё до того, как она сконструирует издателя.

    Политика по умолчанию. Если обычная политика работает со своими умолчаниями (так почти всегда), реализуйте на подключённой форме DefaultPublish и назовите её там:

    pub trait DefaultPublish: ConnectedBroker {
    type Policy: PublishPolicy<Self> + Default + Send + 'static;
}

    С ней рантайм сам инстанцирует два издателя. Первый публикует ответ обработчика в reply-форме, если регистрация не назвала .out_reply(..). Так работает любая форма аргумента reply макроса #[subscriber], с адресом или без, и b.include(def) компилируется без политики. Второй публикует копию для повтора, если регистрация не назвала .out_retry(..).

    Брокер, издателям которого всегда нужны явные настройки, DefaultPublish не реализует. Его пользователи указывают политику при каждой регистрации обработчика.

    Самый короткий образец - MemoryPublish и MemoryRequest in-memory брокера. Настроек у них нет, поэтому это пустые структуры. Обе половины на этом брокере:

    src/memory/mod.rs
    impl<Log: LogMode> PublishPolicy<ConnectedMemoryBroker<Log>> for MemoryPublish {
    type Live = MemoryPublisher;

    fn pair(
        self,
        connected: &ConnectedMemoryBroker<Log>,
    ) -> impl Future<Output = Result<Self::Live, PairError>> {
        ready(Ok(connected.publisher()))
    }
}

impl<Log: LogMode> DefaultPublish for ConnectedMemoryBroker<Log> {
    type Policy = MemoryPublish;
}

    Источники подписки¶

    Подписке по имени хватает Subscribe. Если подписке нужны настройки вашего брокера (группа консьюмеров, durable-имя, политика доставки), заведите для неё тип-дескриптор. Он реализует SubscriptionSource:

    pub trait SubscriptionSource<C: ConnectedBroker> {
    type Subscriber: Subscriber;

    // Кто публикует копии, из которых состоят повторы этой подписки, и кто называет
    // их адрес: AddressedCopies, NamedCopies или BrokerMoves.
    type Copies: CopyPath;

    fn name(&self) -> &str;
    fn subscribe(self, connected: &C) -> impl Future<Output = Result<Self::Subscriber, C::Error>> + Send;

    // По умолчанию дескриптор без изменений. Прочитайте здесь max_attempts(..) и
    // dead_letter(..) регистрации и примените их к подписке, которую собираетесь
    // открыть, если у брокера есть для них механизм.
    fn declare_retry(self, declaration: &RetryDeclaration) -> Self;

}

// Вторая половина AddressedCopies: адрес - свойство типа, а не ответ, который
// проверяют на старте. Спросите брокер там, где это знает только живое соединение.
pub trait RedeliveryAddressed<C>: SubscriptionSource<C, Copies = AddressedCopies> {
    async fn redelivery_address(&self, connected: &C) -> Result<RedeliveryAddress, C::Error>;
}

    У дескриптора три правила.

    Дайте ему ассоциированный конструктор (OrdersStream::new(..)), а не свободную функцию. Тогда пользователь называет дескриптор прямо в атрибуте: #[subscriber(OrdersStream::new("orders", "workers"))]. Макрос берёт тип из вызова конструктора. Цепочку билдера он тоже принимает (#[subscriber(OrdersStream::new("orders").durable("workers"))]), если каждый метод возвращает Self.

    Тип подписчика объявляет сам источник, в type Subscriber. Поэтому брокер может предложить несколько видов подписки (pub/sub и стримы) с разными подписчиками. А может, как в примере с NATS, обслуживать все виды одним дескриптором, который ветвится внутри.

    Выведите на дескрипторе Clone. Монтирование пересобирает конфигурацию на каждую регистрацию, и с Clone одно определение можно смонтировать сразу на два брокера.

    Кто публикует копию для повтора¶

    Повтор после задержки - это копия сообщения. Её публикует либо сервис, либо сам брокер. Каждый дескриптор объявляет через type Copies, как устроено у него:

    type Copies Копию публикует Адрес называет Где встречается
    AddressedCopies сервис дескриптор субъект, топик, стрим, очередь
    NamedCopies сервис место монтирования субъект с шаблоном, фильтр MQTT, паттерн Pulsar, список топиков
    BrokerMoves сервер или клиентская библиотека - кворумная очередь с x-delivery-limit и x-dead-letter-exchange, подписка Pub/Sub с политикой DLQ, политика redrive в SQS, консьюмер Pulsar с DeadLetterPolicy

    AddressedCopies - у подписки один адрес, и сервис может опубликовать туда обратно. Рядом с SubscriptionSource дескриптор реализует RedeliveryAddressed. Поэтому адрес - свойство типа, и на старте его не проверяют.

    NamedCopies - подписка читает много адресов. Место монтирования называет один из них: через .out_retry(политика).to(имя) или для каждой доставки через преобразование публикации.

    BrokerMoves - сервис ничего не публикует. Поэтому .out_retry(..) на таком дескрипторе не компилируется, и ошибка называет дескриптор.

    В первых двух случаях каждая регистрация получает издателя повторов из политики DefaultPublish брокера. Без DefaultPublish такой дескриптор не компилируется.

    У очереди RabbitMQ своя отложенная доставка есть, только если задан .delay(..). Когда поведение зависит от значения поля, а не от типа, оставьте путь копий открытым.

    Что объявляет регистрация¶

    Место монтирования может объявить предел доставок и адрес DLQ. Дескриптор получает их в declare_retry. Рантайм вызывает этот метод один раз на регистрацию, до subscribe.

    Если у брокера есть политика DLQ, дескриптор включает её здесь. Политике нужны оба значения. Поэтому включайте её, только когда объявлены и предел, и адрес. Если политики нет, оставьте реализацию по умолчанию. Тогда объявление применит рантайм.

    Реализация по умолчанию принимает пустое объявление. Непустое она тоже принимает, если копии публикует сервис. Но на брокере с BrokerMoves она отклоняет непустое объявление на старте. Там его некому применить, и сообщение без предела пережило бы свою политику DLQ. Ошибка называет подписку и место объявления.

    У подписки по голому имени дескриптор - Name из ядра. Своей топологии у него нет. Поэтому объявление получает брокер в Subscribe::declare_retry, в той же точке и для того имени, которое он откроет. Правила те же. Реализуйте метод, если голое имя дотягивается до политики брокера: DLQ в Pub/Sub, redrive в SQS, DeadLetterPolicy у консьюмера Pulsar. В остальных случаях не трогайте его.

    Отображение проверяет retry::broker_moves (проверки повторов).

    Куда публикуется копия для повтора¶

    Если брокер не умеет откладывать доставку, повтор выполняет рантайм. Он ждёт задержку и публикует копию сообщения. Копия должна вернуться в ту же подписку, поэтому её адрес называет дескриптор с AddressedCopies:

    src/memory/mod.rs
    impl<Log: LogMode> SubscriptionSource<ConnectedMemoryBroker<Log>> for MemorySource {
    type Subscriber = MemorySubscriber<Log>;
    // The bus moves nothing on its own, and one subject is both ends of it, so a copy goes back
    // to the subject the subscription reads.
    type Copies = AddressedCopies;

    fn name(&self) -> &str {
        &self.name
    }

    async fn subscribe(
        self,
        connected: &ConnectedMemoryBroker<Log>,
    ) -> Result<Self::Subscriber, MemoryError> {
        Subscribe::subscribe(connected, &self.name).await
    }
}

impl<Log: LogMode> RedeliveryAddressed<ConnectedMemoryBroker<Log>> for MemorySource {
    fn redelivery_address(
        &self,
        _connected: &ConnectedMemoryBroker<Log>,
    ) -> impl Future<Output = Result<RedeliveryAddress, MemoryError>> + Send {
        // One subject is both ends of the bus, and no lookup is needed to say so.
        ready(Ok(RedeliveryAddress::new(self.name.clone())))
    }
}

    Адрес - это имя, по которому публикация доходит до подписки. В NATS это субъект, в Kafka - топик, в Redis - ключ стрима.

    Иногда подписка читает не то имя, в которое публикуют. В NATS JetStream консьюмер читает стрим, а публикуют в субъект. Тогда дескриптор спрашивает субъект стрима у сервера. Рантайм задаёт этот вопрос один раз, на старте.

    Место монтирования может назвать адрес само, через .to(имя). Тогда берётся это имя, и в документе AsyncAPI оно появляется как канал с операцией send. Адрес от дескриптора в документе не повторяется: это канал самой подписки.

    Ответ дескриптора проверяет harness::redelivery_address, остальное - harness::lifecycle (проверки повторов). У NamedCopies адреса нет, и проверять нечего.

    Как назвать вид одной строкой¶

    Вид, который определяется одним именем, реализует ещё и FromName. Его единственный конструктор строит значение из этого имени.

    src/memory/mod.rs
    impl FromName for MemorySource {
    fn from_name(name: impl Into<Cow<'static, str>>) -> Self {
        Self::new(name.into().into_owned())
    }
}

    Тогда законна запись #[subscriber(OrdersStream)]: атрибут называет вид, а значение подставляет точка монтирования. Виду, которому нужно больше одного имени (тема и имя подписки), FromName не реализовать, и такая форма для него не компилируется.

    Настройки в терминах вашего брокера¶

    Стрим, durable-имя и группа консьюмеров - понятия вашего брокера, ядро о них не знает. Чтобы пользователь задавал их в точке монтирования, ядро даёт хук map_source. Он преобразует источник, который собирает точка монтирования. Положите сверху свой трейт и привяжите его к своему типу источника:

    use ruststream::runtime::{Declared, SubscriberBuilder, SubscriberSettings};

pub trait NatsSubscriber {
    fn jetstream(self, stream: impl Into<String>) -> Self;
    fn durable(self, name: impl Into<String>) -> Self;
}

// Четыре слота состояния - это (воркеры, политики отказа, стартовая позиция, размер пакета);
// `Codec` - собственное переопределение кодека регистрации, `()` пока его никто не назвал. Оба
// передаются дальше без изменений.
impl<Def, Workers, Failures, StartPosition, Batch, Codec> NatsSubscriber
    for SubscriberBuilder<Def, SubscribeOptions, (Workers, Failures, StartPosition, Batch), Codec>
where
    Def: Declared,
{
    fn jetstream(self, stream: impl Into<String>) -> Self {
        self.map_source(|source| source.jetstream(stream))
    }

    fn durable(self, name: impl Into<String>) -> Self {
        self.map_source(|source| source.durable(name))
    }
}

    Методы привязаны к типу источника, поэтому на билдере другого брокера их нет. Тем же приёмом расширяется словарь слотов Out ниже.

    Настройка ядра start_at(..) оборачивает дескриптор в StartAt<SubscribeOptions, Position>, и на такой подписке ваших методов не видно. Добавьте для неё второй impl:

    use ruststream::StartAt;
use ruststream::runtime::Fixed;

// Слот стартовой позиции здесь по построению равен `Fixed` - обёртку породил именно
// `start_at(..)`, - да и тип источника другой, поэтому этот impl и предыдущий не пересекаются.
impl<Def, Workers, Failures, Batch, Codec, Position> NatsSubscriber
    for SubscriberBuilder<
        Def,
        StartAt<SubscribeOptions, Position>,
        (Workers, Failures, Fixed, Batch),
        Codec,
    >
where
    Def: Declared,
{
    fn jetstream(self, stream: impl Into<String>) -> Self {
        self.map_source(|source| source.map_inner(|inner| inner.jetstream(stream)))
    }

    fn durable(self, name: impl Into<String>) -> Self {
        self.map_source(|source| source.map_inner(|inner| inner.durable(name)))
    }
}

    StartAt::map_inner отдаёт дескриптор изнутри обёртки и не трогает позицию. Поэтому каждый метод остаётся однострочным.

    Настройки издателя в терминах вашего брокера¶

    Издателя настраивают так же, как подписку. Точка монтирования называет политику через .out(marker, policy):

    • маркер Reply - для ответа обработчика в reply-форме (с аргументом reply макроса #[subscriber]);
    • маркер слота - для слота Out.

    Над политикой этой позиции ядро даёт хук MapPublisher. Ваш трейт вызывает его:

    use ruststream::runtime::MapPublisher;

pub trait NatsPublish {
    fn stream(self, name: impl Into<String>) -> Self;
    fn expect_last_sequence(self, seq: u64) -> Self;
}

impl<T: MapPublisher<Policy = Publish>> NatsPublish for T {
    fn stream(self, name: impl Into<String>) -> Self {
        self.map_publisher(|policy| policy.stream(name))
    }

    fn expect_last_sequence(self, seq: u64) -> Self {
        self.map_publisher(|policy| policy.expect_last_sequence(seq))
    }
}

    В сервисе это выглядит так:

    b.include(confirm).out_reply(Publish).stream("ORDERS");
b.include(mirror).out(Audit, Publish).stream("AUDIT").build();

    Ограничение стоит на политике, а не на цепочке. Поэтому одна реализация работает в позиции ответа, в любом слоте, в роутере и в области брокера.

    map_publisher заменяет политику политикой того же типа. Другой тип политики - другой режим публикации, и его называют в самом .out(marker, policy). Туда же можно сразу передать настроенное значение: .out_reply(Publish::default().stream("ORDERS")).

    Настройки на сообщение в билдере публикации¶

    Некоторые настройки меняются от сообщения к сообщению: ключ упорядочивания, приоритет, QoS. Место вызова задаёт их шагом билдера публикации, а шаг пишет поле вашего Publisher::Options. Издатель при этом ничем не обёрнут. Публикация проходит через запись места монтирования, с её кодеком и преобразованиями.

    Нужны четыре части:

    1. тип настроек, в котором все поля необязательные;
    2. политика, которая хранит умолчания;
    3. живой издатель, который сводит одно с другим;
    4. трейт-расширение над PublishBuilder, ограниченное типом настроек. Ограничение не пускает ваши шаги на билдер издателя другого брокера.
    tests/publish_options.rs
    /// The broker's per-message settings. Every field optional: what a call leaves unset keeps what
/// the policy fixed. `Debug` and `PartialEq` are not part of the contract, they are what a test
/// naming this type needs to assert on it.
#[derive(Debug, Clone, Copy, Default, PartialEq, Eq)]
struct PriorityOptions {
    priority: Option<u8>,
    ttl: Option<u8>,
}

/// The publish policy: pure declaration, constructible anywhere, and the place the defaults are
/// configured.
#[derive(Debug, Clone, Copy, Default)]
struct PriorityPublish {
    priority: u8,
    ttl: u8,
}

impl PriorityPublish {
    fn priority(mut self, priority: u8) -> Self {
        self.priority = priority;
        self
    }

    fn ttl(mut self, ttl: u8) -> Self {
        self.ttl = ttl;
        self
    }
}

/// The live publisher: the connection, plus the defaults the policy carried.
struct PriorityPublisher {
    inner: MemoryPublisher,
    default_priority: u8,
    default_ttl: u8,
}

impl PublishPolicy<ConnectedMemoryBroker> for PriorityPublish {
    type Live = PriorityPublisher;

    async fn pair(self, connected: &ConnectedMemoryBroker) -> Result<Self::Live, PairError> {
        Ok(PriorityPublisher {
            inner: Publish.pair(connected).await?,
            default_priority: self.priority,
            default_ttl: self.ttl,
        })
    }
}

impl Publisher for PriorityPublisher {
    // Forwarded to the bus underneath, which keeps what it is handed.
    type Payload = Take;
    type Error = MemoryError;
    type Options = PriorityOptions;

    async fn publish(
        &self,
        msg: OutgoingMessage<'_, BytesMut>,
        options: Option<&Self::Options>,
    ) -> Result<(), Self::Error> {
        let priority = options
            .and_then(|options| options.priority)
            .unwrap_or(self.default_priority);
        let ttl = options
            .and_then(|options| options.ttl)
            .unwrap_or(self.default_ttl);
        // A real broker hands the resolved values to its client as the protocol fields they are.
        // The in-memory bus has no such field, so this one puts them where a test can read them
        // back.
        let mut headers = msg.headers().clone();
        headers.insert("priority", priority.to_string());
        headers.insert("ttl", ttl.to_string());
        let stamped = OutgoingMessage::new(msg.name(), msg.payload()).with_headers(headers);
        self.inner.publish(stamped, None).await
    }
}

impl TransactionalPublisher for PriorityPublisher {
    async fn begin_transaction(&self) -> Result<(), Self::Error> {
        self.inner.begin_transaction().await
    }

    async fn commit(&self) -> Result<(), Self::Error> {
        self.inner.commit().await
    }

    async fn abort(&self) -> Result<(), Self::Error> {
        self.inner.abort().await
    }
}

/// The steps the broker puts in its prelude. The bound on the sink's options type is what keeps
/// them off a builder over any other broker's publisher.
trait PriorityPublishSteps {
    /// Sends this one message at `priority`, whatever the mount site's default is.
    #[must_use]
    fn priority(self, priority: u8) -> Self;

    /// Sends this one message with `ttl`, whatever the mount site's default is.
    #[must_use]
    fn ttl(self, ttl: u8) -> Self;
}

impl<Sink, Body, Enc, Hdrs, Dest> PriorityPublishSteps
    for PublishBuilder<Sink, Body, Enc, Hdrs, Dest>
where
    Sink: PublishSink<Options = PriorityOptions>,
{
    fn priority(mut self, priority: u8) -> Self {
        self.options_mut()
            .get_or_insert_with(PriorityOptions::default)
            .priority = Some(priority);
        self
    }

    fn ttl(mut self, ttl: u8) -> Self {
        self.options_mut()
            .get_or_insert_with(PriorityOptions::default)

    }
}

    Шаг - единственная форма такой настройки. Свой трейт отправки не подходит: публикацию через ваше значение срез слота не видит, а тест проверяет именно такие настройки, как ключ упорядочивания. Заголовок тоже не подходит: настройка - поле протокола, а в заголовке она хранилась бы байтами, и publish разбирал бы их обратно внутри одного процесса.

    Значение, которое брокер выполнить не может, - ошибка публикации, а не молчаливый откат к умолчанию: вызывающий просил порядок, которого не получит.

    Трейты-совместимости¶

    Обязательные трейты дают брокеру подписку и публикацию. Всё, что брокер умеет сверх этого, описывают трейты-совместимости. Реализуйте только те, что он действительно умеет:

    Трейт Для брокеров, которые умеют
    BatchSubscriber получать сообщения пакетами
    TransactionalPublisher вызывать begin / commit / abort вокруг публикаций на дескрипторе издателя
    OwnedTransactions / Transaction держать на одном дескрипторе сколько угодно транзакций сразу, каждую со своим буфером
    RequestReply делать нативный request-reply
    Partitioned ставить ключ партиционирования на исходящие сообщения
    Seekable / Seeker перемещать живую подписку по воспроизводимому логу
    Positioned сообщать позицию доставки в логе
    DescribeServer сообщать ServerSpec для AsyncAPI

    Ближе всего к обязательному BatchSubscriber. Его просит каждый пакетный обработчик. Транспорт без своего пакетирования собирает пакеты на стороне сервиса, поэтому реализуйте его везде, где можете.

    Сервис пишет эти трейты в ограничениях, а не ваш тип. Тело обработчика ограничивает свой слот совместимостью: Out<impl TransactionalPublisher, Journal> или, на ручном пути, where W: TransactionalPublisher. Точка монтирования один раз, при компиляции, проверяет, что живой издатель политики реализует этот трейт. Больше сервису ничего не нужно.

    Для четырёх совместимостей издателя запись арены за слотом даёт и типизированную форму. Она работает поверх кодека точки монтирования и словаря маркера: билдер публикации, область транзакции, владеющая транзакция, коррелированный запрос.

    Перемотка. Seekable выдаёт дескриптор Seeker раньше, чем stream заимствует подписчика. Поэтому работающую подписку можно переместить извне цикла диспетчеризации.

    • Позиции принадлежат брокеру. Конструкторы вроде KafkaPosition вы объявляете на своём типе, и он же описывает их смысл.
    • Позиция доставки из Positioned::position подчиняется контракту: перемотка на неё повторно доставит ровно это сообщение.
    • Опишите, на что действует перемотка: на экземпляр консьюмера или на общий курсор группы.
    • При перемотке сбрасывайте весь учёт ack, который она делает недействительным.
    • Чтобы тело обработчика могло перематывать, положите позицию и дескриптор перемотки в поля контекста доставки и опубликуйте для них ключи ContextField. Образец - MemoryContext in-memory брокера с ключами Position и SeekHandle. Пакетные формы берут дескриптор перемотки из пакетного контекста, позиции в нём нет.

    Описание сервера. DescribeServer сообщает хост и порт, к которым подключаются сервисы. Документ AsyncAPI публикуют, поэтому учётных данных в нём быть не должно. Если брокер настроен по URL, стройте описание через ServerSpec::from_url. Он оставляет от URL только хост и порт, а схему, имя пользователя с паролем и всё, что идёт после хоста, отбрасывает. Брокер с несколькими адресами берёт каждый через ServerSpec::host_from_url.

    Не срезайте у URL одну схему: пароль останется в документе. Такая ошибка попала в несколько адаптаций библиотек брокеров, прежде чем её закрыл from_url.

    Пакеты: BatchSubscriber¶

    Обработчик, который принимает &[T], получает пакет. Точка монтирования задаёт размер пакета, и рантайм передаёт его в BatchSubscriber::batches(size). Рантайм пакеты не делит и не склеивает: тело видит пакет таким, каким его отдал подписчик. В пакете не больше size сообщений, а меньше - столько, сколько нашлось у транспорта.

    Совместимость нужна каждому подписчику, которого может открыть монтирование. #[subscriber("topic")] подписывается через Subscribe, поэтому тело &[T] в этой форме требует BatchSubscriber от Subscribe::Subscriber. Если подписчик дескриптора и подписчик по имени - один тип, этого достаточно. Если типы разные, реализуйте совместимость на обоих, иначе форма со строковым литералом не компилируется.

    Переведите size в понятие своей клиентской библиотеки: XREADGROUP COUNT, pull-пакет JetStream, лимит poll в Kafka. Остальное устройство пакета (таймаут блокировки, группа консьюмеров, окно предвыборки) остаётся вашим словарём. Его настраивают на источнике подписки через трейт-расширение, и сервис пишет сначала слово ядра, потом ваше: b.include(handler.batch(nonzero!(6)).block(Duration::from_secs(5))).

    Транспорт, который отдаёт сообщения по одному, тоже реализует совместимость. На стороне сервиса пакеты собирает BufferedSubscriber ядра, и его batches соблюдает названный размер. Размер задаёт сервис, а срок, после которого закрывается неполный пакет, выбираете вы. Вынесите срок в дескриптор подписки (.max_wait(Duration::from_millis(25))) и передавайте обёртке при подписке. Тогда сервис настраивает его для каждой подписки. Умолчание в 10 мс рассчитано на внутрипроцессную шину: по сети оно закрывает большинство пакетов на одной доставке. Поэтому адаптации библиотек брокеров выбирают 10-50 мс.

    Остальное в подписчике проходит сквозь обёртку без изменений:

    Прелюдия, которую поставляет ваш крейт¶

    Сервис называет ваши типы в точке монтирования. Для этого ваш крейт поставляет модуль prelude. Он состоит из трёх слоёв, в таком порядке:

    1. pub use ruststream::prelude::*; - чтобы один glob обслуживал весь файл;
    2. ваши типы, которые называет сервис: брокер, источник подписки, Config, ошибка, ключи ContextField, которые читает тело;
    3. ваши политики публикации под общими для всех брокеров именами: Publish, а где есть, ещё TransactionalPublish и Request (pub use crate::KafkaTransactionalPublish as TransactionalPublish;).

    Прелюдия ядра под этими тремя именами ничего не экспортирует. Поэтому точка монтирования на любом брокере читается одинаково, а смена брокера меняет только glob.

    Никогда не называйте политику именем трейта ядра (Publisher, TransactionalPublisher, OwnedTransactions, RequestReply) и ничего не реэкспортируйте под этими именами. В теле с обеими прелюдиями они должны по-прежнему означать трейты ядра.

    К политикам добавьте манифест: трейты совместимостей, которые вы реализуете на живых значениях. Тогда glob приносит вместе с политиками и их операции. В манифест входят трейты потребляющей стороны, до которых тело добирается через ваш брокер: Positioned, Seeker, Transaction и подобные. Четыре совместимости издателя уже есть в прелюдии ядра, повторять их незачем.

    В манифест не входят:

    • трейт, метод которого столкнётся с методом ядра по умолчанию. На практике это Partitioned::partition_key рядом с IncomingMessage::partition_key. Сервис, которому он нужен, импортирует его явно;
    • BatchSubscriber: его вызывает сам фреймворк, и тело не пишет его в ограничениях.

    Разобранный пример - ruststream::memory::prelude.

    Расширение словаря слотов Out¶

    Слот Out даёт телу обработчика живое значение, например издателя. Какое именно, тело не знает: оно пишет только трейт, Out<impl X, Marker>. Для трейтов ядра (Publisher, TransactionalPublisher, OwnedTransactions, RequestReply) это работает сразу, потому что ядро делегирует их само.

    Ваше живое значение может уметь больше или вовсе не быть издателем: кэш продюсеров по партициям, шардирующий роутер. Тогда объявите свою трейт-совместимость и реализуйте её для живого значения.

    Тело держит не само значение, а запись арены Slot - прозрачное окно в него. Вызов метода проходит через окно автоматическим разыменованием, а ограничение по трейту не проходит: функция fn issue<L: Lanes>(lanes: &L) отвергнет запись с ошибкой E0277. Поэтому добавьте рядом со своим трейтом один blanket-impl для Slot, который делегирует через Deref записи. Тогда функции и тела, обобщённые по совместимости, принимают запись как есть, а конкретный тип в коде приложения не появляется:

// Grafted onto the arena entry once, for every marker, delegating through the entry's
// transparent `Deref`: this is how a broker crate extends the slot vocabulary with its own
// traits. A handler body holds the entry, so without this impl the capability is reachable by
// autoderef for a method call but never satisfies a trait bound.
impl<M, W: ShardLanes, E, Pipe, Body> ShardLanes for Slot<M, W, E, Pipe, Body> {
    fn lane(&self, shard: u64) -> (&MemoryPublisher, &'static str) {
        (**self).lane(shard)
    }
}

/// The bound the graft buys: a helper generic over the capability, not over the concrete live
/// type, takes the entry a handler body holds.
async fn sent<L: ShardLanes + Sync>(lanes: &L, event: &Event) -> bool {
    let (publisher, dest) = lanes.lane(event.id);
    publisher.message(event).to(dest).publish().await.is_ok()
}

    Место отправки задаёт одну из двух форм трейта.

    Форма роутера выдаёт издателя и сама ничего не отправляет. Так кэш продюсеров выбирает издателя для шарда и возвращает его. Публикация через такого издателя идёт мимо среза слота, поэтому обвязка не приписывает её слоту, как и буфер завершённой owned-транзакции. Это граница атрибуции и цена выдачи внутреннего издателя. Такую публикацию проверяйте по журналу публикаций брокера.

    Форма шага задаёт одну настройку на сообщение и заканчивается одной публикацией: ключ упорядочивания, приоритет, QoS. Это не трейт-совместимость, а поле Publisher::Options, которое меняет шаг билдера публикации. См. настройки на сообщение в билдере публикации.

    Прелюдия вашего крейта¶

    Прелюдия - единственный ваш импорт в коде сервиса, и её устройство входит в контракт.

    Сервис импортирует вашу прелюдию только в одном файле из двух. На этом держится его переносимость.

    Тело обработчика импортирует только ruststream::prelude::*. Слот оно ограничивает совместимостью ядра: Out<impl Publisher>, Out<impl TransactionalPublisher>, Out<impl OwnedTransactions>, Out<impl RequestReply>. Тело говорит, что ему нужно от издателя, но не какой брокер это даёт.

    Файл монтирования импортирует вашу прелюдию, потому что брокер называют там. Псевдонимы политик (NatsPublish as Publish, KafkaTransactionalPublish as TransactionalPublish, LapinRequest as Request) делают этот файл одинаковым на любом брокере, и смена брокера сводится к смене импорта.

    Исключение одно - настройка на сообщение, потому что её вызывают в теле. Такое тело импортирует вашу прелюдию ради шага и называет ваш тип настроек в ограничении (Out<impl Publisher<Options = MqttOptions>, Telemetry>). Оно привязано к вашему брокеру, и его сигнатура это показывает.

    Явный реэкспорт перекрывает glob без предупреждения. Имя, совпадающее с трейтом ядра, отнимает этот трейт у каждого сервиса с glob-импортом, а ошибка возникает в файле сервиса, не в вашем.

    Закрепите правило пробой за собственным glob-импортом: ограничение из тела должно означать трейт ядра, а имя из точки монтирования - вашу политику.

    // in your crate, behind your own prelude glob
use crate::prelude::*;

// A capability bound a body states: the core trait, not something of yours.
fn _p<T: Publisher>() {}

// A mount-site name: your policy, constructible with no connection in sight.
fn _q() {
    let _: Publish = Publish::default();
}

    Контекст доставки и ключи Ctx¶

    Брокер может знать о доставке больше, чем нагрузку и заголовки: партицию, смещение, номер в стриме. Эти данные он отдаёт типизированным контекстом доставки. Он состоит из двух частей:

    • структура с #[non_exhaustive], которую называет подписчик;
    • типы-ключи ContextField.

    Обработчик получает поле параметром через экстрактор Ctx<K>. Ключи - пустые структуры, поэтому путь доставки обходится без type-map и без выделений в куче.

    /// Per-delivery context of this broker.
#[non_exhaustive]
#[derive(Debug, Clone)]
pub struct MyContext {
    pub partition: i32,
}

/// `Ctx<Partition>` in a handler binds the delivery's partition.
#[derive(Debug, Default, Clone, Copy)]
pub struct Partition;

impl ContextField for Partition {
    type Context = MyContext;
    type Value = i32;
    fn read(self, src: &MyContext) -> i32 {
        src.partition
    }
}

    В наброске ключ читает число, и оно копируется. Позицию, которая не Copy, ключ отдаёт заимствованием: например, идентификатор сообщения в Pulsar или шард Kinesis со строкой последовательности. Для этого Field::Value<'a> обобщён по времени жизни источника. Ключ отдаёт &'a MessageId, а тело читает его через ctx.context(..) и ничего не копирует.

    Экстрактор Ctx<K> работает иначе. Экстракторы связываются до запуска тела, поэтому ContextField::Value должен быть владеющим и 'static: ключ клонирует то, что вернул заимствующий. Обычно один ключ реализует оба трейта.

    Брокер без своих полей доставки берёт ().

    Контекст пакета. Пакет охватывает много доставок, поэтому у пакетной подписки свой контекст:

    1. Соберите вторую структуру из того, что общее для всей подписки: дескриптор перемотки, имя стрима, группа консьюмеров.
    2. Реализуйте на ней BuildBatchContext.
    3. Опубликуйте ключи Field, чтобы пакетное тело читало её через ctx.context(..).

    Рантайм строит одно значение на пакет по его первой доставке.

    Позиция в эту структуру не входит: она принадлежит доставке, и пакет читает её с элементов. Компилятор следит за этим сам. Контекст доставки не реализует BuildBatchContext, поэтому пакетное тело не может его назвать.

    Образец - MemoryBatchContext in-memory брокера: дескриптор перемотки лежит в нём под тем же ключом SeekHandle, что и в контексте доставки. Брокер, которому нечего дать на уровне подписки, ничего не реализует, и контекст пакета остаётся ().

    Middleware на асинхронных краях¶

    Кодек ядра синхронный. Поэтому интеграции с асинхронным вводом-выводом, такие как schema registry или конверт поверх формата передачи, в Codec не ставят. Обработчикам лучше оставаться на кодеке по умолчанию.

    Место таких интеграций - асинхронные края:

    • Входящие сообщения. Перекодируйте полезную нагрузку на пути доставки подписки, до кодека.
    • Исходящие сообщения. Оберните публикацию слоем PublishLayer из ядра и добавьте его на всё приложение через RustStream::publish_layer. Слой асинхронный и может вернуть ошибку. Полезную нагрузку для упаковки в конверт даёт Outgoing::payload_mut.

    Биндинги протокола¶

    В документе AsyncAPI есть место для того, что знает только ваш брокер: долговечность очереди RabbitMQ, группа потребителей Kafka, QoS в MQTT. Спецификация называет это биндингами. Для подписки их заполняет ваш дескриптор:

    tests/asyncapi.rs
    /// A descriptor of the shape a broker crate ships: it reads its own private fields and says
/// what the protocol calls them.
#[derive(Clone)]
struct RabbitQueue {
    name: &'static str,
    durable: bool,
}

impl<C: Subscribe> SubscriptionSource<C> for RabbitQueue {
    type Subscriber = C::Subscriber;
    type Copies = AddressedCopies;

    fn name(&self) -> &str {
        self.name
    }

    async fn subscribe(self, connected: &C) -> Result<Self::Subscriber, C::Error> {
        connected.subscribe(self.name).await
    }

    fn channel_bindings(&self) -> Bindings {
        let body = AmqpChannel {
            is: "queue",
            queue: AmqpQueue {
                name: self.name,
                durable: self.durable,
            },
        };
        Binding::new("amqp", "0.3.0", &body)
            .map(|binding| Bindings::new().with(binding))
            .unwrap_or_default()
    }

    fn operation_bindings(&self) -> Bindings {
        Binding::new("amqp", "0.3.0", &AmqpOperation { ack: true })
            .map(|binding| Bindings::new().with(binding))
            .unwrap_or_default()
    }

    fn message_bindings(&self) -> Bindings {
        let body = AmqpMessage {
            message_type: "order",
        };
        Binding::new("amqp", "0.3.0", &body)
            .map(|binding| Bindings::new().with(binding))
            .unwrap_or_default()
    }
}

    Binding::new(protocol, version, &body) сериализует тело один раз и сам вписывает bindingVersion. Биндинг без версии не отправить.

    Ключ протокола ядро сверяет с закрытым списком спецификации. На неизвестный ключ оно возвращает ошибку, потому что такой документ не прочитал бы ни один инструмент.

    Bindings по умолчанию пуст: дескриптор, который ничего не говорит, документ не меняет.

    Биндинги задаёт дескриптор, поэтому у подписки по голому имени их нет. Брокеру, которому нужны биндинги, нужен тип SubscriptionSource.

    Сервер. Биндинги сервера - поле, а не метод: сервер описывается один раз на брокер. Задайте их через ServerSpec::new(host, protocol).bindings(..) в вашей реализации DescribeServer.

    Содержимое биндинга подчиняется трём правилам:

    1. Значение вычисляется по одному дескриптору. Документ собирается до подключения, поэтому настоящее число партиций топика Kafka, топик за подпиской Pub/Sub и ARN очереди SQS в него не попадают.
    2. Учётные данные в биндинг не попадают, как и в DescribeServer.
    3. Протокол вне списка спецификации записывается расширением Binding::extension("x-kinesis", &body). Законного ключа нет у ZeroMQ, Kinesis и файлового транспорта. Расширение x- стоит на том же уровне и bindingVersion не содержит.

    Второе правило проверяет conformance::harness. Настройте брокер и дескриптор с заранее известным паролем и запустите сканирование:

    tests/conformance_self.rs
    /// The in-memory broker has no network address and no binding, so nothing it describes can leak a
/// password. A broker configured from a URL runs this with the password it was configured with.
#[cfg(feature = "asyncapi")]
#[test]
fn memory_broker_describes_without_credentials() {
    harness::describes_without_credentials(
        &MemoryBroker::new(),
        &MemorySource::new("orders"),
        "hunter2",
    );
}

    Публикация. На стороне публикации те же три уровня заполняют политики. Ответ, слот Out и издатель недоставленных сообщений - всё это PublishPolicy, и каждая политика описывает канал, в который публикует:

    tests/asyncapi.rs
    /// A publish policy of the shape a broker crate ships: an SNS topic is named by its binding's
/// required `name`, and the hook is handed the destination the mount site resolved.
#[derive(Clone, Copy, Default)]
struct TopicPublish;

impl PublishPolicy<ConnectedMemoryBroker> for TopicPublish {
    type Live = MemoryPublisher;

    fn pair(
        self,
        connected: &ConnectedMemoryBroker,
    ) -> impl Future<Output = Result<Self::Live, PairError>> {
        live(connected)
    }

    fn channel_bindings(&self, channel: &str) -> Bindings {
        let body = SnsChannel {
            name: channel.to_owned(),
        };
        one("sns", "0.1.0", &body)
    }

    fn operation_bindings(&self, channel: &str) -> Bindings {
        let body = SnsOperation {
            topic: SnsChannel {
                name: channel.to_owned(),
            },
        };
        one("sns", "0.1.0", &body)
    }

    fn message_bindings(&self, _channel: &str) -> Bindings {
        let body = SnsMessage {
            message_type: "progress",
        };
        one("sns", "0.1.0", &body)
    }
}

    Политика хранит настройки брокера, но не адресата. Адресата каждому методу передаёт точка монтирования:

    • у ответа - имя, объявленное типом ответа, или аргумент reply("dest") макроса #[subscriber];
    • у слота - имя его записи;
    • у сообщения, ушедшего в DLQ, - объявление dead_letter("dlq").

    Отсюда берут имя тема SNS и очередь SQS: в их биндингах name - обязательное поле. Если адресата для каждой доставки называет преобразование, у канала нет адреса, и метод получает запасное имя точки монтирования. Дескриптору такой параметр не нужен: он знает подписку, которую описывает.

    Три правила действуют и здесь, с одним отличием. У ответа нет своей операции send, поэтому operation_bindings политики ответа в документ не попадает. У слота и у адресата недоставленных сообщений эта операция есть.

    Ответ через reply-to. Ваш брокер может направлять ответы через заголовок reply-to. Тогда реализуйте четвёртый метод, reply_address_location: он есть только у ответа и сообщает, откуда клиент читает адрес ответа.

    tests/asyncapi.rs
    /// The reply's own policy: it answers where a client reads the address of an answer.
#[derive(Clone, Copy, Default)]
struct ReplyToPublish;

impl PublishPolicy<ConnectedMemoryBroker> for ReplyToPublish {
    type Live = MemoryPublisher;

    fn pair(
        self,
        connected: &ConnectedMemoryBroker,
    ) -> impl Future<Output = Result<Self::Live, PairError>> {
        live(connected)
    }

    fn channel_bindings(&self, channel: &str) -> Bindings {
        let body = NatsChannel {
            subject: channel.to_owned(),
        };
        one("nats", "0.1.0", &body)
    }

    fn reply_address_location(&self) -> Option<&'static str> {
        Some("$message.header#/reply-to")
    }
}

    Документ показывает канал ответа с address: null, а выражение записывает в reply.address.location операции receive. Выражение действует только там, где точка монтирования поставила преобразование, которое называет адресата для каждой доставки. Иначе ответ уходит на объявленное имя, и документ показывает его.

    Протокол вне списка спецификации не получает биндинга и на стороне публикации. Таков in-memory брокер: ключа memory нет, поэтому MemoryPublish ничего не сообщает и не выдумывает ключ.

    Фича. Хуки включает фича ядра asyncapi. Пробросьте её из своего крейта:

    [features]
asyncapi = ["ruststream/asyncapi"]

    и поставьте #[cfg(feature = "asyncapi")] на каждый метод, который заполняете.

    Конфигурация и умолчания¶

    Config принадлежит вашему крейту: специфичной для брокера конфигурации в ядре нет. Если у поля нет разумного умолчания, не реализуйте Default: пусть пользователь задаст значение явно, а не получит умолчание, которое потом сломается.

    Ошибки¶

    Ошибки крейта описывайте одним перечислением через thiserror, с вариантами по источникам. Публичные перечисления ошибок помечайте #[non_exhaustive]. anyhow в библиотечном крейте не используйте никогда.

    Поддержка тестирования¶

    Сервис тестирует то приложение, которое поставляет: TestApp::start(app()) принимает тот же билдер, что запускает main. Каждый брокер приложения тест подключает внутри процесса, без ввода-вывода. К вашему брокеру тест обращается по рабочему типу: tb.broker::<YourBroker>().

    Поэтому режим работы внутри процесса входит в контракт брокера. Ваш крейт предоставляет его под фичей testing, и состоит он из трёх частей:

    1. InProcess на рабочем брокере. connect_in_process(self) поглощает брокер и возвращает вашу же подключённую форму, за которой стоит внутрипроцессный транспорт без ввода-вывода.
    2. TestableBroker на этой подключённой форме. Через него обвязка вбрасывает сообщение, читает журнал публикаций и устанавливает координатор, который считает сообщения в работе.
    3. register_testable_broker!(YourBroker), который регистрирует и то, и другое.

    У in-memory брокера нет сервера, поэтому его режим внутри процесса - обычный connect:

    src/memory/mod.rs
    // The bus is in-process by nature, so the transition the harness connects through is the ordinary
// `connect`: the connected form a test drives is the one production gets.
#[cfg(feature = "testing")]
impl<Log: LogMode> crate::testing::InProcess for MemoryBroker<Log> {
    fn connect_in_process(
        self,
    ) -> impl Future<Output = Result<Self::Connected, Self::Error>> + Send {
        self.connect()
    }
}

// The harness drives the connected form that transition produces, and run_suite scenarios
// receive it too.
#[cfg(feature = "testing")]
impl<Log: LogMode> crate::testing::TestableBroker for ConnectedMemoryBroker<Log> {
    fn install_coordinator(&self, coordinator: Coordinator) {
        self.state.install_coordinator(coordinator);
    }

    fn inject(&self, message: OutgoingMessage<'_>) {
        let (name, payload, headers) = message.into_parts();
        // Injecting into a shut-down bus is a harness bug (both run_suite and TestApp drive
        // the bus strictly before shutdown), so fail loudly instead of losing the message.
        self.state
            .fanout(name, Bytes::copy_from_slice(payload), headers)
            .expect("inject on a shut-down broker: drive the harness before shutdown");
    }

    /// What the broker holds under `name`: everything published there on a discarding broker
    /// (which records for the length of a harness run), and the retained window on a retaining
    /// one, so an assertion never claims more than the broker keeps.
    fn published(&self, name: &str) -> Vec<RawMessage> {
        self.state
            .log
            .lock()
            .expect("memory broker mutex poisoned")
            .name(name)
            .map(|log| log.messages(name))
            .unwrap_or_default()
    }

    /// The broker's own rule, read from the [`Routing`] it was built with: a name with a
    /// wildcard token is a [`MemoryPattern`] subscription, every other one an exact name.
    fn routes(&self, destination: &str, subscriptions: &[&str]) -> Vec<usize> {
        self.state.routing().routes(destination, subscriptions)
    }

    /// A subscription receives what is published after it opens, on either log mode: a retaining
    /// broker keeps its log for a seek to replay, not for a subscription to start from.
    fn backlog(&self) -> Backlog {
        Backlog::Missed
    }
}

// One registration per log mode: the harness finds a broker by the type the app was built on,
// and the two modes are two types.
#[cfg(feature = "testing")]
crate::register_testable_broker!(MemoryBroker<Discarding>);
#[cfg(feature = "testing")]
crate::register_testable_broker!(MemoryBroker<Retaining>);

    Брокер с сервером строит внутрипроцессный транспорт в connect_in_process и регистрирует рабочий тип:

    tests/in_process.rs
    impl InProcess for Dialling {
    async fn connect_in_process(self) -> Result<Self::Connected, Self::Error> {
        Ok(self
            .bus
            .connect()
            .await
            .expect("the in-memory bus connects without I/O"))
    }
}

register_testable_broker!(Dialling);

    Внутрипроцессный вариант подключённой формы, её подписчика, издателей и доставки существует только под фичей testing. Рабочая сборка сервиса от него не меняется: Cargo не включает фичи dev-зависимостей в рабочий бинарник.

    Транспорт берёт все настройки у брокера, из которого построен: группу по умолчанию, prefetch, объявление топологии и всё остальное, что применяет настоящий брокер. Поэтому тест не может работать с настройками, которых нет в бою.

    Транспорт сообщает координатору, что происходит с сообщениями:

    • Coordinator::enqueued - на каждую постановку в очередь подписчика;
    • Coordinator::consumed - когда доставка завершена или отброшена;
    • Coordinator::schedule_redelivery - на каждую отложенную повторную доставку.

    По первым двум вызовам обвязка определяет, что реакция на сообщение закончилась.

    Тот же тест работает и против настоящего стенда. TestApp::start_live(app()) подключает брокер обычным connect. От вашего крейта ему нужна только подключённая форма с политикой DefaultPublish: через неё обвязка публикует входные сообщения теста. Сторона пользователя описана в разделе Тестирование, а Conformance показывает, как подтвердить режим внутри процесса через run_suite и остальные наборы.

    Как написать транспорт, которому можно верить¶

    Тесты сервиса целиком опираются на внутрипроцессный транспорт. Если он расходится с настоящим брокером, тест проходит на поведении, которого у брокера нет. Поэтому транспорт отклоняет всё, что отклонит или потеряет сервер: публикацию, подтверждение, возврат в очередь, подписку.

    Расхождения встречаются часто. Каждое правило ниже закрывает одно из них и стоит примерно одного теста.

    Прогоняйте наборы ядра и внутри процесса. Наборы написаны против трейтов и не различают, отвечает ли сервер или внутрипроцессный транспорт. Хватит одного #[tokio::test]:

    tests/conformance_self.rs
    /// The suites that read a broker's publish log back - the routing contract's log check and the
/// seeking capability - need a broker that keeps one.
fn replaying() -> MemoryBroker<Retaining> {
    MemoryBroker::retaining(Retention::Messages(nonzero!(64)))
}

#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
async fn memory_broker_passes_conformance_suite() {
    harness::run_suite(replaying).await;
}

    lifecycle тоже запускайте внутри процесса, через harness::InProcessBroker. Он выполняет new -> connect -> подписку -> публикацию -> ack -> shutdown. Затем он проверяет то, что у внутрипроцессного транспорта обычно упускают: издатель, созданный до остановки, после неё возвращает ошибку. Настоящая клиентская библиотека отвечает «нет соединения». Транспорт, у которого публикация - это отправка в канал, примет сообщение.

    tests/conformance_self.rs
    // `make_source` / `make_publisher` must stay closures: their bounds are higher-ranked
// (`Fn(&str) -> _` / `Fn(&B) -> _`), so a bare method path - which binds one concrete lifetime -
// would not type-check.
#[allow(clippy::redundant_closure, clippy::redundant_closure_for_method_calls)]
#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
async fn memory_broker_passes_lifecycle() {

    Добавьте и наборы capabilities::*, по одному на каждую реализованную возможность.

    Возможности совпадают с возможностями настоящего брокера очереди. Внутрипроцессный вариант встроен в рабочие типы, поэтому возможность в обоих режимах - один и тот же тип. Монтирование, которое собирается против брокера, собирается и внутри процесса. Остаётся добиться, чтобы каждая возможность вела себя так же, как у сервера.

    Завершайте доставку так же, как транспорт. Там, где транспорт не подтверждает доставку (отправка без подтверждений, уровень at-most-once), настоящий ack возвращает AckError::Unsupported. Внутрипроцессный транспорт возвращает то же самое. Наборы принимают честный ответ. Если ответить Ok(()) ради набора, обработчик с HandlerOutcome::retry() пройдёт тесты и потеряет сообщение на настоящем брокере очереди.

    Повторяйте работу клиентской библиотеки и не подделывайте работу брокера очереди. Граница проходит по тому, на какой стороне работает механизм:

    • работа клиентской библиотеки или уровня маршрутизации повторяется внутри процесса точно: конкурирующие потребители, распределение по группе, корреляция и маршрутизация ответов, буферизация до фиксации;
    • работа брокера очереди внутри процесса была бы выдумкой: атомарность в кластере, fencing, тайм-ауты на стороне брокера очереди, exactly-once. Тот же тест в режиме TestApp::start_live проходит против сервера, у которого всё это есть.

    Точнее всего повторяйте конкурирующих потребителей: ошибка здесь выглядит как успех. Очередь, которая доставляет каждое сообщение всем подписчикам разом, - уже не очередь. Каждый из двух воркеров на ней обработает весь поток. Тест, который считает обработанные сообщения, увидит сделанную работу и ошибки не заметит.

    Храните то, что хранит настоящий брокер очереди. Уже существующие очередь или журнал держат сообщения, опубликованные до подписки. Поздняя подписка получает их первыми. Очереди, которую подписка объявляет сама, в момент такой публикации ещё нет, и сервер отбрасывает сообщение.

    Если транспорт отбрасывает то, что хранит сервер, тест сервиса, который стартует после своих поставщиков, проходит. В бою тот же сервис сначала разбирает накопившиеся сообщения, которых тест не видел.

    Объявите это поведение в TestableBroker::backlog:

    • Backlog::Missed (по умолчанию) - модель «издатель-подписчик»: подписка получает только то, что опубликовано после неё;
    • Backlog::Delivered - транспорт доставляет опубликованное до подписки, и run_suite это проверяет.

    Если ответ зависит от настройки (журнал читается с самого раннего смещения, потребитель потока доставляет всё), прочитайте её у подключённой формы. in_process::backlog_matches_server сверяет объявление с вашим сервером (см. Conformance).

    Комментируйте каждый пробел: какое утверждение он делает несостоятельным. Пишите не «возможности нет», а какому тесту читатель больше не может верить и что на самом деле закрывает эту проверку:

    // No fencing: a second producer claiming the same transactional id is not rejected here, so a
// test cannot assert the first one is fenced out. `capabilities::transactions` against a real
// server is what covers that.

    Закрепляйте пробел и тестом. Комментарий устареет в тот день, когда кто-нибудь «починит» транспорт и научит его маршрутизировать то, что он намеренно не маршрутизирует. Тест, который утверждает, что обработчик не вызван, в этот день упадёт и сам объяснит причину.

    Опирайтесь на рабочую обвязку брокера. Внутрипроцессный вариант стоит под вашими же источниками подписки и политиками публикации, поэтому сервис проверяет тот файл маршрутов, который поставляет. Проверки, которые настоящий брокер делает при подписке или публикации (отказ от объявления, слишком длинное для протокола имя, заголовок, который нельзя передать), внутри процесса выполняет тот же код.
