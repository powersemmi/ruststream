    Conformance¶

    Нормативная версия документации - английская

    Эта страница переведена с английского языковой моделью. При любом расхождении верен английский оригинал.

    Обвязка conformance доказывает, что брокер соблюдает контракт ядра. Каждый брокер проходит две проверки:

    • harness::run_suite проверяет поверхность маршрутизации в режиме работы внутри процесса. Она строит ваш рабочий брокер и подключает его через InProcess::connect_in_process. Так проверяются гарантии диспетчеризации.
    • harness::lifecycle проверяет последовательность переходов жизненного цикла на настоящем брокере: new -> connect(self) -> подписка -> публикация -> ack -> shutdown(self).

    Обе проверки паникуют с внятным сообщением на первом же нарушении контракта. Подключите фичу conformance в dev-зависимостях:

    [dev-dependencies]
ruststream = { version = "0.7", features = ["conformance"] }

    Фича conformance включает testing. Поэтому один режим работы внутри процесса служит и run_suite, и обвязке TestApp, на которой пишут тесты пользователи.

    Набор проверок маршрутизации¶

    harness::run_suite проверяет гарантии маршрутизации ядра, общие для всех брокеров. Так его прогоняет эталонный in-memory брокер:

    tests/conformance_self.rs
    use ruststream::conformance::harness;

/// The suites that read a broker's publish log back - the routing contract's log check and the
/// seeking capability - need a broker that keeps one.
fn replaying() -> MemoryBroker<Retaining> {
    MemoryBroker::retaining(Retention::Messages(nonzero!(64)))
}

#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
async fn memory_broker_passes_conformance_suite() {
    harness::run_suite(replaying).await;
}

    Фабрика. Подставьте в неё конструктор своего брокера с теми настройками, с которыми его собирает сервис. Фабрика синхронная (Fn() -> B) и строит свежий рабочий брокер для каждого сценария. Поэтому сценарии не видят состояния друг друга.

    Подключение. Каждый сценарий подключает брокер через connect_in_process. Подключённая форма реализует TestableBroker и Subscribe.

    Что остаётся вам. Семантику своего брокера (возобновление с durable-курсора, повторную доставку по таймауту, назначение партиций) вы проверяете сквозным набором тестов против настоящего сервера.

    Совместимости. У каждой совместимости свой набор, они описаны ниже. Только capabilities::batches проверяет, что пакет не больше размера, с которым его открыли, поэтому одного run_suite для пакетов мало.

    Что именно он проверяет¶

    Сценарий Что утверждается
    порядок доставки сообщения доставляются в порядке публикации
    публикация до подписки сообщение, опубликованное до открытия подписки, приходит первым, если брокер объявляет Backlog::Delivered, и не приходит вовсе, если он объявляет Backlog::Missed (по умолчанию); сообщение, опубликованное после, приходит в обоих случаях
    ack поглощает доставку подтверждённое сообщение не доставляется повторно
    nack с requeue доставляет заново nack(requeue = true) доставляет сообщение ещё раз
    nack без requeue отбрасывает после nack(requeue = false) повторной доставки нет
    заголовки передаются заголовки сообщения приходят к подписчику без изменений
    лог публикаций фиксирует публикации published(name) записывает каждое опубликованное сообщение
    лог публикаций фиксирует ваш издатель то, что отправил ваш издатель по умолчанию, лежит в published(name) рядом с тем, что внедрил тест, в порядке публикации и с заголовками (для брокера, зарегистрированного через register_testable_broker!)
    две подписки на одно имя каждое сообщение приходит ровно в те подписки, которые называет TestableBroker::routes, и в каждую по одному разу: при рассылке во все подписки, при конкурирующих потребителях в ту, которую выбирает брокер
    счётчики обвязки сходятся на остановленных часах, так, как их ведёт TestApp: доставка учитывается до возврата из публикации и снимается один раз при завершении, возврат в очередь учитывает её снова, публикация без получателей не учитывается, отложенная повторная доставка учитывается, когда истекает её таймер

    Транспорт без подтверждений. ZeroMQ, MQTT QoS 0, Redis pub/sub и Core NATS не умеют подтверждать доставку. Их ack и nack возвращают AckError::Unsupported, и набор принимает этот ответ везде, где сам завершает доставку. Внутрипроцессный транспорт отвечает так же, как настоящий, и не заявляет подтверждения, которого в бою нет.

    Повторная доставка. Ответ Unsupported на nack(requeue = true) заканчивает этот сценарий: транспорт ничего не забрал обратно, и наблюдать нечего. Остальные сценарии идут как обычно, включая отбрасывание: доставка, которую никто не может завершить, всё равно не приходит снова.

    Ответ на подтверждение. run_suite проверяет ответ на каждое подтверждение отдельно: одна адаптация может отвечать по-разному в зависимости от типа подписки. У Kafka возврат в очередь работает при одном режиме коммитов и недоступен при другом. У MQTT подписка с QoS 1 получает подтверждение, а подписка с QoS 0 - нет.

    Неизменно одно: Ok(()) из nack(requeue = true) означает, что сообщение будет доставлено повторно. На этот ответ опирается механизм повторов рантайма.

    Проверка жизненного цикла¶

    harness::lifecycle проводит настоящий брокер через жизненный цикл так же, как сервис. Проверка не зависит от брокера: она принимает три фабрики.

    use ruststream::conformance::harness;
use ruststream_nats::{NatsBroker, SubscribeOptions};

#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
#[ignore = "needs a running nats-server; set NATS_TEST_URL"]
async fn passes_lifecycle() {
    let url = std::env::var("NATS_TEST_URL").unwrap();
    harness::lifecycle(
        move || NatsBroker::new(url.clone()), // sync construction (no I/O)
        |subject| SubscribeOptions::new(subject), // the broker's SubscriptionSource
        |connected| connected.publisher(), // a publisher from the connected form
    )
    .await;
}
    • make_broker - синхронная (Fn() -> B) и Send + Sync + 'static. Проверка вызывает её в отдельном потоке, который может бросить, поэтому зависший конструктор проваливает проверку, а не вешает её. Замыкание, которое захватывает локальную переменную (например, адрес сервера), пишется с move. Брокер, который строится только асинхронно, сюда не подходит: конструируйте дёшево, а подключайтесь в Broker::connect.
    • make_source строит дескриптор подписки на субъект (путь макро-подписчика).
    • make_publisher создаёт издателя из подключённой формы.

    Проверка идёт на настоящем Broker в пять шагов:

    1. синхронное конструирование без ввода-вывода;
    2. connect, который поглощает self и возвращает типизированную подключённую форму;
    3. подписку через собственный SubscriptionSource брокера;
    4. публикацию, которую подписка получает и подтверждает;
    5. shutdown, который поглощает self и возвращает терминального свидетеля.

    lifecycle выполняет настоящий connect. Запускайте её против живого сервера и включайте только при заданной переменной окружения, например NATS_TEST_URL.

    Каждый шаг проверка выполняет оттуда, откуда к брокеру обращается сервис:

    • Конструктор вызывается в обычном потоке без рантайма Tokio и возвращает управление за секунду. Конструктор, который порождает задачу, вызывает Handle::current или ждёт сети, проверку не проходит. Если конструктор так и не вернул управление, проверка проваливается через эту секунду, а его поток продолжает работать в фоне.
    • Подписка, первая публикация и каждое подтверждение выполняются в однопоточном рантайме на отдельном потоке. Затем проверка останавливает этот рантайм. Подписка продолжает получать сообщения. Издатель первого сообщения публикует ещё раз, из рантайма брокера и из нового рантайма, и оба сообщения доходят. nack(requeue = true), ответивший Ok, возвращает сообщение, а nack(requeue = false) - нет. Так проверка требует, чтобы внутренние задачи брокера выполнялись в рантайме, где он подключился (см. Как написать адаптацию библиотеки брокера).
    • nack_after, если доставка его умеет, откладывает сообщение на 1,5 с. Сообщение возвращается не раньше этого срока и не позже чем через десять секунд после него. Брокер, который пропускает задержку, округляет её вниз или отсчитывает в рантайме вызывающего потока, проверку не проходит.
    • Сроки: connect и shutdown завершаются за десять секунд каждый, а открытие подписки, публикация и подтверждение - за две. Зависший брокер проваливает проверку, а не останавливает её.

    Брокер без семантики ack (Core NATS) проходит проверку, возвращая из ack значение AckError::Unsupported: проверка принимает и его, и успешный ack.

    До последовательности переходов, на отдельном соединении, проверка смотрит, что доносит ваш издатель:

    • тридцать два сообщения, опубликованные одно за другим, приходят в одну подписку, в любом порядке. Секционированный транспорт раскладывает сообщения без ключа по разным секциям, а порядок проверяет keyed_order;
    • ещё четыре сообщения несут заголовки: много записей, пустое значение, значение не в UTF-8 и собственные заголовки фреймворка со счётчиком повторов и контекстом трассировки. Каждый заголовок возвращается байт в байт, иначе публикация с ним возвращает ошибку, и такое сообщение не приходит вовсе, даже после остальных. Заголовок, потерянный или изменённый по пути, проваливает проверку.

    После остановки проверка смотрит на контракт разделяемых дескрипторов. Владелец подключённой формы обратиться к ней не может: такой код не компилируется. Поэтому проверяются дескрипторы:

    • публикация после остановки возвращает ошибку через любого издателя, созданного до неё: ни разу не использованного, использованного только в рантайме брокера и использованного из остановленных рантаймов;
    • доставка, полученная до остановки и возвращённая в очередь после неё, возвращает ошибку или приходит снова.

    Дескриптор подписки, подписчик, издатель и доставка переходят в другие потоки, поэтому все они 'static.

    Остановка и разделяемые дескрипторы¶

    Две проверки смотрят, что происходит при остановке. Им нужен ответ, который знает только ваш брокер, поэтому крейт вызывает каждую из них сам: внутри процесса и против настоящего сервера.

    lifecycle::shutdown_flushes принимает ответ брокера Backlog. Она проверяет, что остановка доводит до конца подтверждение и публикацию, сделанные прямо перед shutdown:

    • подтверждённое сообщение не приходит снова на новом соединении;
    • опубликованное сообщение доходит до другого соединения. При Backlog::Delivered это новое соединение, при Backlog::Missed - подписанное заранее;
    • подтверждение, отправленное после остановки и ответившее Ok, тоже действует;
    • shutdown завершается за десять секунд.

    lifecycle::shared_handle_closes принимает подключённую форму с Clone. После остановки оригинала любое обращение через копию возвращает ошибку. Это касается издателя, созданного из копии до остановки или после, и подписки, которую копия открывает: она получает отказ или сразу завершается.

    shutdown_flushes подключается несколько раз. Поэтому make_broker каждый раз ведёт к одному и тому же брокеру: против сервера - к серверу, внутри процесса - к одному общему миру для всех построенных брокеров. Брокер в памяти в собственном прогоне делит одну шину между копиями:

    tests/conformance_self.rs
    use ruststream::conformance::lifecycle;
use ruststream::testing::Backlog;

// Every broker the factory builds is a clone of one bus, so the second connection reaches what the
// first one published, the way two connections reach one server.
#[allow(clippy::redundant_closure, clippy::redundant_closure_for_method_calls)]
#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
async fn memory_broker_flushes_at_shutdown() {
    let bus = MemoryBroker::new();
    lifecycle::shutdown_flushes(
        move || bus.clone(),
        |name| MemorySource::new(name),
        |broker| broker.publisher(),
        Backlog::Missed,
    )
    .await;
}

// The connected form is a cheap, cloneable handle on the bus.
#[allow(clippy::redundant_closure, clippy::redundant_closure_for_method_calls)]
#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
async fn memory_broker_clones_close_with_the_original() {
    lifecycle::shared_handle_closes(
        MemoryBroker::new,
        |name| MemorySource::new(name),
        |broker| broker.publisher(),
    )
    .await;
}

    Те же наборы внутри процесса¶

    Наборы проверок можно прогнать и без сервера. lifecycle, redelivery_address и наборы для совместимостей подключают брокер через Broker::connect. Оберните рабочий брокер в harness::InProcessBroker, и они подключат его через connect_in_process. Каждый набор выполнится второй раз, на ваших собственных дескрипторах и политиках публикации.

    Прогоняйте оба варианта. Прогон внутри процесса держит честным режим работы внутри процесса, а прогон против сервера проверяет настоящий транспорт.

    В примере брокер, чей connect обращается к серверу, проходит внутри процесса набор маршрутизации и проверку жизненного цикла:

    tests/in_process.rs
    // The routing suite connects the production broker in process.
#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
async fn the_routing_suite_connects_the_broker_in_process() {
    harness::run_suite(Dialling::default).await;
}

// The suites that connect with `connect` run in process through the adapter, over the production
// broker's own descriptor and publisher.
#[allow(clippy::redundant_closure, clippy::redundant_closure_for_method_calls)]
#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
async fn the_ladder_suite_runs_in_process_through_the_adapter() {
    harness::lifecycle(
        || InProcessBroker::new(Dialling::default()),
        |name| MemorySource::new(name),
        |connected| connected.publisher(),
    )
    .await;
}

    Набор проверок подтверждения¶

    settlement::suite проверяет, что каждый способ завершить доставку делает то, что обещает. Набор работает на транспорте брокера, в том числе на живом сервере.

    src/conformance/settlement/tests.rs
    // `make_source` stays a closure: its bound is higher-ranked, so a bare constructor path would bind
// one concrete lifetime and fail to type-check.
#[allow(clippy::redundant_closure)]
#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
async fn the_memory_broker_answers_alike_in_process() {
    // Clones of one broker: the second connection of a check reaches what the first one left.
    let broker = MemoryBroker::new();
    matches_in_process(
        || broker.clone(),
        |name| MemorySource::new(name),
        ConnectedMemoryBroker::publisher,
        // The bus hands an unsettled delivery back at once.
        Duration::ZERO,
    )
    .await;
}
    • make_broker вызывается на каждое соединение, а соединений два. Все брокеры, которые она возвращает, обращаются к одному серверу: на живом сервере к тому же адресу, внутри процесса к клонам одного брокера.
    • make_source открывает одну и ту же подписку на обоих соединениях: durable-потребителя, очередь или группу потребителей, если они у брокера есть. Подписка допускает три доставки в обработке одновременно.
    • Время повторной доставки - срок, после которого брокер повторно доставляет неподтверждённое сообщение. Это ack wait, visibility timeout или ack deadline, заданный дескриптором. Если брокер доставляет такое сообщение повторно только при закрытии соединения, передайте Duration::ZERO.

    Набор проверяет пять способов:

    • ack поглощает доставку: подтверждённое сообщение не доставляется повторно ни за время повторной доставки, ни на новом соединении с той же подпиской;
    • nack без возврата отбрасывает: то же после nack(requeue = false);
    • nack с возвратом возвращает: Ok(()) из nack(requeue = true) приводит сообщение обратно;
    • подтверждение не по порядку: из трёх сообщений в обработке подтверждено третье, а первые два отпущены без подтверждения. Первые два возвращаются: в ту же подписку, в неё же, открытую заново, или на новом соединении с ней;
    • отпущенная доставка: сообщение, отпущенное без подтверждения из рантайма, который сразу останавливается, возвращается.

    Ответ Unsupported. Завершение, ответившее AckError::Unsupported, проверка не ограничивает: транспорт ничего не выполнил, и сообщение может вернуться на своей подписке или на новом соединении. Если nack(requeue = true) отвечает AckError::Unsupported, две последние проверки заканчиваются: такой транспорт ничего не забирает обратно, и повторной доставки не видно.

    Дубликаты. Лог, который фиксирует непрерывный префикс, может вместе с первыми двумя сообщениями доставить повторно и подтверждённое третье. Дубликат проверку проходит, потеря - нет.

    Сверка с сервером. settlement::suite возвращает ответ каждого способа завершения. Пример выше вызывает settlement::matches_in_process: он прогоняет набор против сервера и через harness::InProcessBroker и паникует, если ответы расходятся. Внутрипроцессный транспорт, который заявляет подтверждение, отвергнутое сервером, пропускает в тесте повтор обработчика, а в продакшене теряет сообщение.

    Проверки повторов¶

    type Copies дескриптора говорит, как регистрация повторяет доставку. Два ответа что-то обещают сервису: копию по адресу дескриптора и перекладку силами брокера. conformance::retry проверяет оба обещания.

    Копия по адресу. harness::redelivery_address принимает дескриптор с AddressedCopies и проверяет, что копия по его адресу доходит до подписки:

    1. Проверка открывает по дескриптору две подписки, как две реплики сервиса читают одну подписку.
    2. Она публикует копию по адресу, который называет дескриптор. Копия уходит из однопоточного рантайма, который сразу останавливается: так копию для retry_after публикует обработчик на выделенных потоках.
    3. Копия доходит ровно до одной подписки группы (или до каждой, если транспорт отдаёт каждой подписке всё). Заголовки и RETRY_COUNT_HEADER приходят без изменений.
    4. Проверка дважды возвращает копию в очередь. Каждая повторная доставка сохраняет оба заголовка, а доставка, которая сообщает redelivery_count, насчитывает 1, 2 и 3.

    Если ваша подключённая форма отвечает Subscribe::Copies = AddressedCopies, прогоните проверку ещё раз с голым источником Name. Этот ответ и есть адрес каждой регистрации #[subscriber("orders")].

    src/conformance/retry/tests.rs
    #[allow(clippy::redundant_closure_for_method_calls)]
#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
async fn the_memory_descriptor_passes() {
    redelivery_address(
        MemoryBroker::new,
        |name| MemorySource::new(name),
        |connected| connected.publisher(),
    )
    .await;
}

#[allow(clippy::redundant_closure_for_method_calls)]
#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
async fn the_memory_bare_name_passes() {
    redelivery_address(
        MemoryBroker::new,
        |name| Name::new(name.to_owned()),
        |connected| connected.publisher(),
    )
    .await;
}

    Перекладка брокером. retry::broker_moves принимает дескриптор с BrokerMoves:

    1. Проверка объявляет max_attempts(n) и адрес DLQ.
    2. Она возвращает сообщение в очередь, пока предел не исчерпан.
    3. Сообщение приходит в DLQ ровно один раз и ровно после n доставок.

    Если возврат в очередь отвечает AckError::Unsupported, проверка на этом заканчивается: транспорт ничего не доставляет повторно, и считать нечего. Каждую половину объявления по отдельности брокер отклоняет на старте.

    Передайте n, который ваш брокер принимает. make_source(name) открывает и адрес DLQ, поэтому создаёт всё, что нужно для публикации в name.

    use ruststream::conformance::harness::InProcessBroker;
use ruststream::conformance::retry;
use ruststream::nonzero;
use ruststream_lapin::{LapinBroker, LapinPublish, RabbitQuorumQueue};

#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
async fn a_quorum_queue_dead_letters_at_the_cap() {
    retry::broker_moves(
        || InProcessBroker::new(LapinBroker::new("amqp://localhost:5672").declare_topology(true)),
        |name| RabbitQuorumQueue::new(name),
        |connected| connected.publisher(LapinPublish::default()),
        nonzero!(2u32),
    )
    .await;
}

    Транспорт внутри процесса против сервера¶

    Транспорт внутри процесса должен отвечать так же, как сервер. conformance::in_process сверяет одно с другим. Оба его набора подключают брокер дважды на каждую пробу: через Broker::connect и через connect_in_process. Поэтому запускайте их там же, где проверки против сервера:

    use ruststream::conformance::in_process::{self, Refusal};
use ruststream_nats::{CoreSubject, NatsBroker, NatsPublish};

#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
#[ignore = "needs a running nats-server; set NATS_TEST_URL"]
async fn in_process_matches_the_server() {
    let url = std::env::var("NATS_TEST_URL").unwrap();
    in_process::backlog_matches_server(
        || NatsBroker::new(url.clone()),
        |connected| connected.publisher(NatsPublish),
    )
    .await;
    in_process::refuses_like_the_server(
        || NatsBroker::new(url.clone()),
        |connected| connected.publisher(NatsPublish),
        [
            Refusal::PayloadOver { name: "conformance.payload".to_owned(), limit: 1024 * 1024 },
            Refusal::Publish { name: "conformance.bad subject".to_owned() },
            Refusal::Subscription { source: CoreSubject::new("conformance..empty") },
        ],
    )
    .await;
}

    backlog_matches_server проверяет, что происходит с сообщением, опубликованным до подписки. На обоих транспортах набор публикует сообщение под новым именем, открывает подписку на это имя и публикует ещё одно.

    • При Backlog::Delivered в TestableBroker::backlog первое сообщение приходит первым. При Backlog::Missed оно не приходит вовсе.
    • Если сервер отвергает первую публикацию (очередь или тему никто не объявил), транспорт внутри процесса отвергает её тоже.
    • После этого подписка на обоих транспортах всё равно открывается и получает второе сообщение.

    refuses_like_the_server проверяет, что оба транспорта отказывают одинаково. Набор принимает известные вам отказы, каждый в виде Refusal: полезная нагрузка на байт больше предела, отвергнутое назначение, отвергнутая подписка, подписка, отвергнутая рядом с другой.

    • Каждый отказ дают оба транспорта. Проба, которую сервер принимает, считается ошибкой: она ничего не доказывает.
    • Затем на каждом транспорте открываются две подписки на одно имя и одна на другое. Транспорт в процессе принимает ровно те, которые принимает сервер.

    Что несёт сообщение¶

    Четырём проверкам из conformance::message_shape нужны данные, которые знает только ваш брокер. Поэтому ваш крейт вызывает их сам, против сервера и внутри процесса, как и остальные наборы:

    • keyed_order. Вы передаёте субъект и место ключа: заголовок или поле параметров публикации. Каждая доставка возвращает из partition_key ключ, с которым её опубликовали, а сообщения одного ключа приходят в порядке публикации.
    • publish_options. Вы передаёте субъект, политику публикации, набор случаев и способ прочитать настройку из доставки. Проверка требует трёх вещей:
    • публикация без параметров получает настройку политики;
    • параметры вызова перекрывают её только для этого вызова;
    • значение, которое транспорт не может выполнить, даёт ошибку публикации, и сообщение не приходит, даже после следующей публикации.
    • publishes_without_credentials. Вы передаёте политику публикации, настроенную с паролем. Ни один биндинг, который политика добавляет в документ, не содержит пароля.
    • describes_addresses_without_credentials. Вы передаёте брокер, построенный из нескольких адресов с пользователем и паролем. Описание сервера не содержит этих учётных данных.
    tests/conformance_message_shape.rs
    // `make_source` / `make_publisher` must stay closures: their bounds are higher-ranked, so a bare
// method path, which binds one concrete lifetime, would not type-check.
#[allow(clippy::redundant_closure, clippy::redundant_closure_for_method_calls)]
#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
async fn memory_broker_keeps_keys_and_their_order() {
    message_shape::keyed_order(
        MemoryBroker::new,
        &unique_subject("conformance.keyed"),
        |name| MemorySource::new(name),
        |connected| connected.publisher(),
        // Where a key goes on this broker: a header here, a field of the options elsewhere.
        |key, headers| {
            headers.insert(PARTITION_KEY_HEADER, Bytes::copy_from_slice(key));
            None
        },
    )
    .await;
}

    Транспорт без ключей не вызывает keyed_order: None для него честный ответ.

    Политику для publish_options настройте на значение, отличное от умолчания транспорта. Иначе издатель, который забыл про политику, пройдёт проверку, случайно попав в умолчание.

    Наборы проверок для совместимостей¶

    У каждой трейт-совместимости есть свой набор в conformance::capabilities. Набор доказывает, что реализация соблюдает контракт трейта. Запустите набор для каждой совместимости, которую реализует ваш брокер.

    Наборы принимают фабрики той же формы, что и lifecycle, и выполняют настоящий connect. Поэтому включайте их по той же переменной окружения:

    use ruststream::conformance::capabilities;
use ruststream_nats::{NatsBroker, SubscribeOptions};

#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
#[ignore = "needs a running nats-server; set NATS_TEST_URL"]
async fn passes_request_reply() {
    let url = std::env::var("NATS_TEST_URL").unwrap();
    capabilities::request_reply(
        || NatsBroker::new(url.clone()),
        |subject| SubscribeOptions::new(subject),
        |connected| connected.publisher(), // the RequestReply publisher under test
        |connected| connected.publisher(), // the plain publisher the responder replies through
    )
    .await;
}

    Каждый вызов набора ограничен по времени: зависший брокер проваливает набор, а не останавливает его.

    Ниже наборы и их требования.

    capabilities::request_reply требует RequestReply:

    • запрос доходит до отвечающей стороны с пригодным заголовком reply-to, а соотнесённый ответ завершает запрос;
    • запрос без ответа возвращает ошибку по истечении своего таймаута;
    • запрос, сделанный после того, как предыдущий пришёл из уже остановленного рантайма, всё равно завершается;
    • два одновременных запроса получают каждый свой ответ;
    • ответ, пришедший после таймаута своего запроса, не завершает следующий запрос;
    • запрос после остановки брокера сразу возвращает ошибку.

    capabilities::batches требует BatchSubscriber:

    • каждое опубликованное сообщение приходит в порядке публикации, распределённое по непустым пакетам;
    • если сообщения, которые уже ждут к моменту чтения потока, хотя бы раз за пять попыток попадают в один пакет, элементы этого пакета подтверждаются по отдельности: nack с возвратом в очередь возвращает только этот элемент. Подписка, которая никогда не объединяет их, проходит проверку, и раздельное подтверждение для неё не проверяется;
    • пакет, подтверждённый из уже остановленного рантайма, подтверждается так же.

    capabilities::batch_seeking требует BatchSubscriber и Seekable, сообщения Positioned. Перемотка назад на позицию, снятую с сообщения из пакета, начинает следующие пакеты с этого сообщения, а за ним по порядку идёт всё остальное.

    capabilities::transactions требует TransactionalPublisher:

    • ничто внутри транзакции не видно до commit;
    • commit публикует буфер по порядку, abort его отбрасывает;
    • неверный вызов возвращает ошибку: commit или abort без открытой транзакции, второй begin_transaction при уже открытой (он оставляет её нетронутой);
    • commit из уже остановленного рантайма всё равно публикует буфер;
    • после остановки брокера commit оставшейся открытой транзакции и обычная публикация возвращают ошибку.

    capabilities::owned_transactions требует OwnedTransactions и его Transaction:

    • ничто опубликованное в открытую транзакцию не видно до commit;
    • commit доставляет весь буфер в порядке публикации, abort его отбрасывает;
    • две транзакции, открытые одновременно на одном издателе, завершаются независимо, а сам издатель продолжает публиковать напрямую, пока одна из них открыта;
    • commit из уже остановленного рантайма всё равно публикует буфер;
    • после остановки брокера ошибку возвращают commit, прямая публикация и транзакция, открытая после остановки.

    capabilities::seeking требует Seekable, сообщения Positioned:

    • перемотка назад на позицию, снятую с доставленного сообщения, повторно доставляет именно это сообщение и всё, что идёт за ним, по порядку;
    • перемотка вперёд пропускает доставки, стоявшие в очереди до цели;
    • после перемотки подписка продолжает доставлять новые публикации;
    • новая подписка, которая до первой доставки перематывается на позицию, снятую предыдущей подпиской, начинает с этого сообщения;
    • перемотка из уже остановленного рантайма всё равно срабатывает, а перемотка после остановки брокера возвращает ошибку.

    capabilities::seeking_unknown_position требует Seekable и позицию, которую строит брокер. Перемотка на позицию, которой нет в журнале подписки (вытеснена по сроку хранения или не существовала), возвращает ошибку и не сдвигает подписку: ничего не читается из другого места. Ошибка в потоке не завершает проверку, и она читает следующую доставку.

    Каждый прогон набора берёт новый субъект из conformance::helpers::unique_subject и читает только то, что опубликовал сам. С фиксированным субъектом набор проходит на свежем сервере, но не проходит на втором прогоне у брокера, который хранит оставленное первым: удерживаемый лог воспроизведёт в одну подписку оба прогона, durable-очередь ещё держит ранние сообщения, пространство ключей - ранний тип. Ваш сквозной набор тестов решает ту же проблему тем же способом.

    In-memory брокер реализует все совместимости нативно и проходит все семь наборов прямо в процессе (см. Memory). Это исполняемый эталон того, чего ждёт каждый набор.

    Чеклист автора¶

    Прежде чем публиковать адаптацию библиотеки брокера, проверьте:

    Трейты

    • [ ] Реализованы Broker, ConnectedBroker, Subscribe (или SubscriptionSource), Subscriber, IncomingMessage, Publisher и конструирующая его PublishPolicy.
    • [ ] shutdown выполняет всё освобождение ресурсов, которое может вернуть ошибку, не блокирует и не паникует.
    • [ ] Ack поглощает self, nack учитывает флаг requeue.
    • [ ] Крейт владеет своим Config, а поля без разумного умолчания не получают Default.
    • [ ] Трейты-совместимости реализованы только там, где брокер их действительно поддерживает.
    • [ ] Каждая реализованная совместимость проходит свой набор из conformance::capabilities.

    Режим работы внутри процесса

    • [ ] Режим поставляется под фичей testing: InProcess на брокере, TestableBroker на его подключённой форме и register_testable_broker!(YourBroker).
    • [ ] Внутрипроцессный транспорт берёт все настройки у рабочего брокера и отказывает везде, где отказывает настоящий брокер.

    Проверки

    • [ ] harness::run_suite проходит.
    • [ ] Остальные наборы проходят и внутри процесса через harness::InProcessBroker, и против настоящего сервера.
    • [ ] harness::lifecycle проходит против настоящего сервера и включается по переменной окружения.
    • [ ] lifecycle::shutdown_flushes проходит с ответом брокера Backlog.
    • [ ] lifecycle::shared_handle_closes проходит там, где подключённая форма реализует Clone.
    • [ ] settlement::matches_in_process проходит против настоящего сервера и включается по той же переменной.
    • [ ] harness::redelivery_address проходит для каждого дескриптора с AddressedCopies и для голого Name, если Subscribe::Copies равен AddressedCopies.
    • [ ] retry::broker_moves проходит для каждого дескриптора с BrokerMoves.
    • [ ] Если у транспорта есть ключи или настройки отдельного сообщения, message_shape::keyed_order и message_shape::publish_options проходят внутри процесса и против настоящего сервера.
    • [ ] Сквозной набор тестов покрывает семантику конкретного брокера и включается по той же переменной.

    Публикация

    • [ ] Метаданные Cargo.toml заполнены полностью (description, license, repository, keywords, categories), а CI проверяет --no-default-features и --all-features.
