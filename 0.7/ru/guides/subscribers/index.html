    Подписчики¶

    Нормативная версия документации - английская

    Эта страница переведена с английского. При любом расхождении верен английский оригинал.

    Подписчик связывает обработчик с одной подпиской. Удобный способ объявить его - макрос #[subscriber]; это руководство разбирает контракт обработчика, формы макроса и то, как обработчики монтируются. Про группировку обработчиков по модулям рассказано в Роутинге, а про декодирование полезной нагрузки - в Кодеках.

    Контракт обработчика¶

    Обработчик - это async fn, первый параметр которой - ссылка на декодированную полезную нагрузку:

    examples/subscribers.rs
    use ruststream::runtime::HandlerOutcome;
use ruststream::subscriber;

#[subscriber("orders")]
async fn handle(order: &Order) -> HandlerOutcome {
    println!("got order {}", order.id);
    HandlerOutcome::ack()
}
    examples/manual/subscribers.rs
    /// The handler contract without the attribute: a named type whose `impl Handle<Order>` carries
/// the body. The axes it does not use - the reply, the injections, the broker context, the
/// application state - stay at their defaults, so the impl names only the input.
struct Receive;

impl Handle<Order> for Receive {
    fn handle(
        &self,
        order: &Order,
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<(), HandlerOutcome>> {
        println!("got order {}", order.id);
        ready(Ok(()))
    }
}

    Макрос превращает функцию в значение с тем же именем (здесь handle), которое реализует контракт монтирования. Это значение вы и передаёте в include.

    Приём контекста¶

    Объявите необязательный второй параметр &mut Context, чтобы читать заголовки, имя подписки и общее состояние или публиковать прямо из обработчика:

    examples/subscribers.rs
    #[subscriber("orders")]
async fn with_context(order: &Order, ctx: &mut Context<'_>) -> HandlerOutcome {
    if let Some(id) = ctx.headers().correlation_id() {
        println!("order {} correlates to {id}", order.id);
    }
    HandlerOutcome::ack()
}
    examples/manual/subscribers.rs
    /// The context is a parameter of the trait method, so it is always in reach: nothing declares it.
struct WithContext;

impl Handle<Order> for WithContext {
    fn handle(
        &self,
        order: &Order,
        _outs: &(),
        ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<(), HandlerOutcome>> {
        if let Some(id) = ctx.headers().correlation_id() {
            println!("order {} correlates to {id}", order.id);
        }
        ready(Ok(()))
    }
}

    Тип контекста макрос выводит сам, поэтому имя Context не нужно импортировать, пока оно встречается только в сигнатурах #[subscriber]. Полная поверхность контекста - рабочая копия заголовков, доступ к состоянию, поля брокера, привязанные к конкретной доставке - разобрана в Контексте и состоянии.

    Параметры-экстракторы¶

    Любой следующий параметр, после сообщения и необязательного &mut Context, - это экстрактор: рантайм получает его из доставки до того, как выполнится тело, а неудачная выборка завершает доставку, не запуская тело. Бывает четыре вида:

    • State<T> - поле состояния приложения (выведите FromRef на типе состояния).
    • Ctx<K> - поле брокера для конкретной доставки, читается по своему ключу.
    • Headers<T> - заголовки доставки, разобранные в типизированный контракт; нарушение контракта завершает доставку по политике on_failure(decode = ..) (см. типизированные заголовки).
    • любой тип, реализующий FromContext, - свой экстрактор (auth guard, резолвер в области одного запроса).

    Механика описана в разделах Внедрение зависимостей и Поля контекста как параметры.

    Есть ещё одна форма параметра, и это не экстрактор, а внедрение: Out(out): Out<impl Publisher> получает живого издателя, которого рантайм собирает из политики, прикреплённой в месте include (b.include(handler).out(marker, policy).build()); конкретный тип издателя в сигнатуре не появляется никогда. Необязательная третья позиция объявляет набор сообщений, которые обработчик публикует, - Out<impl Publisher, Marker, (A, B)>, - и тем самым включает типизированный путь публикации по словарю (типизированные заголовки). См. Публикацию изнутри обработчика.

    Подтверждение¶

    Возвращать можно всё, что преобразуется в HandlerOutcome (единица завершения доставки: статус для брокера плюс необязательное продолжение после завершения):

    Возвращаемое значение Что происходит
    HandlerOutcome::ack() подтвердить; брокер удаляет сообщение
    HandlerOutcome::retry() nack с возвратом в очередь (повторная доставка позже)
    HandlerOutcome::retry_after(delay) nack с просьбой доставить повторно не раньше, чем через delay
    HandlerOutcome::drop() nack без возврата в очередь (отбросить или отправить в dead-letter)
    () всегда подтверждает
    Result<(), E> подтверждение при Ok, отбрасывание при Err
    Result<HandlerOutcome, E> внутренний исход при Ok, отбрасывание при Err
    HandlerOutcome::ack().and_after(..) (любой исход) завершить доставку этим исходом, затем выполнить продолжение

    У самого сообщения ack поглощает self, поэтому система типов не даёт сделать ack дважды.

    Продолжения после завершения доставки¶

    HandlerOutcome::ack().and_after(fut) прикрепляет к возвращаемому исходу продолжение: некритичное уведомление, медленную доработку, прогрев кеша. Подходит любой исход (drop().and_after(..) тоже корректен, нейтральное прочтение - «после завершения доставки»):

    examples/post_settle.rs
    /// Ack the order, then fire a non-critical follow-up once it is acknowledged. The continuation is
/// at-most-once: if it is lost or panics, the already-acked order is not redelivered.
#[subscriber("orders")]
async fn handle(order: &Order) -> HandlerOutcome {
    let id = order.id;
    HandlerOutcome::ack().and_after(async move {
        println!("order {id} acked; notifying downstream");
    })
}
    examples/manual/post_settle.rs
    /// Ack the order, then fire a non-critical follow-up once it is acknowledged. The continuation is
/// at-most-once: if it is lost or panics, the already-acked order is not redelivered.
///
/// `and_after` produces a `HandlerOutcome`, the verdict's `Err` side, so the outcome travels as
/// it is (a plain `Ok(())` would ack with no continuation).
struct Notify;

impl Handle<Order> for Notify {
    fn handle(
        &self,
        order: &Order,
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<(), HandlerOutcome>> {
        let id = order.id;
        ready(Err(HandlerOutcome::ack().and_after(async move {
            println!("order {id} acked; notifying downstream");
        })))
    }
}

    Продолжение подчиняется общей семантике post-settle (at-most-once, выполняется только после того, как ack или nack завершил доставку, дорабатывает при мягкой остановке); см. Хуки после завершения доставки.

    В пакете каждый элемент завершается отдельно, поэтому продолжение задаётся поэлементно - такого хук в контексте одного сообщения дать не может:

    examples/post_settle.rs
    /// Per-element settlement: id 0 retries with no continuation, every other order acks and schedules
/// its own follow-up. The continuation rides with the element, so a batch settles each message and
/// its side effect independently.
#[subscriber("orders")]
async fn handle_batch(orders: &[Order]) -> Vec<HandlerOutcome> {
    orders
        .iter()
        .map(|order| {
            if order.id == 0 {
                HandlerOutcome::retry()
            } else {
                let id = order.id;
                HandlerOutcome::ack().and_after(async move {
                    println!("order {id} acked in batch; following up");
                })
            }
        })
        .collect()
}
    examples/manual/post_settle.rs
    /// Per-element settlement: id 0 retries with no continuation, every other order acks and schedules
/// its own follow-up. The continuation rides with the element, so a batch settles each message and
/// its side effect independently.
struct NotifyBatch;

impl Handle<[Order]> for NotifyBatch {
    fn handle(
        &self,
        orders: &[Order],
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<(), Vec<HandlerOutcome>>> {
        ready(Err(orders
            .iter()
            .map(|order| {
                if order.id == 0 {
                    HandlerOutcome::retry()
                } else {
                    let id = order.id;
                    HandlerOutcome::ack().and_after(async move {
                        println!("order {id} acked in batch; following up");
                    })
                }
            })
            .collect()))
    }
}

    Пакетная публикация (пакетный обработчик с publish(..)) завершает всё целиком, одной транзакцией, поэтому поэлементный and_after там не складывается; он работает только в обычной пакетной и одиночной формах.

    Отложенная повторная доставка¶

    retry_after закрывает случай «ещё не готово» (зависимость ещё не появилась, апстрим ограничивает частоту запросов), когда немедленная повторная доставка крутилась бы вхолостую:

    examples/retry.rs
    /// The not-ready-yet case: the upstream has not settled this payment, so an immediate
/// redelivery would just spin. Ask the broker to redeliver no sooner than five seconds from now.
#[subscriber("payments")]
async fn reconcile(payment: &Payment) -> HandlerOutcome {
    if !payment.settled {
        return HandlerOutcome::retry_after(Duration::from_secs(5));
    }
    println!("payment {} settled", payment.id);
    HandlerOutcome::ack()
}
    examples/manual/retry.rs
    /// The not-ready-yet case: the upstream has not settled this payment, so an immediate
/// redelivery would just spin. Ask the broker to redeliver no sooner than five seconds from now.
struct Reconcile;

impl Handle<Payment> for Reconcile {
    fn handle(
        &self,
        payment: &Payment,
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<(), HandlerOutcome>> {
        if !payment.settled {
            return ready(Err(HandlerOutcome::retry_after(Duration::from_secs(5))));
        }
        println!("payment {} settled", payment.id);
        ready(Ok(()))
    }
}

    Внутри рантайм соблюдает задержку так:

    • Брокер с нативной отложенной повторной доставкой (in-memory брокер доставляет повторно по таймеру, брокер на NATS JetStream мог бы послать NAK с задержкой) отдаёт это транспорту напрямую.
    • На брокере без нативной поддержки рантайм планирует отложенную повторную публикацию сообщения в его же исходный субъект через delay, а оригинал отбрасывает. Опубликованная заново копия несёт увеличенный на единицу фреймворковый заголовок со счётчиком повторов (RETRY_COUNT_HEADER); обработчик может его прочитать и ограничить число повторных доставок.

    Включается в пределах области через BrokerScope::retry_via(publisher) (издатель должен указывать на тот же брокер). Без издателя задержка отбрасывается, и сообщение немедленно возвращается в очередь. Отложенная повторная публикация даёт at-most-once на окне задержки: если процесс завершится до срабатывания таймера, копия потеряется.

    Форма batch_retry_after складывается с выборочным завершением пакета: Vec<HandlerOutcome> несёт задержки поэлементно, так что неготовые записи отходят на паузу, не задерживая остальной пакет:

    examples/retry.rs
    /// Selective outcomes carry per-element delays: settled payments ack immediately, pending ones
/// come back in thirty seconds without holding up the rest of the batch.
#[subscriber("payments")]
async fn reconcile_batch(payments: &[Payment]) -> Vec<HandlerOutcome> {
    payments
        .iter()
        .map(|payment| {
            if payment.settled {
                HandlerOutcome::ack()
            } else {
                HandlerOutcome::retry_after(Duration::from_secs(30))
            }
        })
        .collect()
}
    examples/manual/retry.rs
    /// Selective outcomes carry per-element delays: settled payments ack immediately, pending ones
/// come back in thirty seconds without holding up the rest of the batch.
struct ReconcileBatch;

impl Handle<[Payment]> for ReconcileBatch {
    fn handle(
        &self,
        payments: &[Payment],
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<(), Vec<HandlerOutcome>>> {
        ready(Err(payments
            .iter()
            .map(|payment| {
                if payment.settled {
                    HandlerOutcome::ack()
                } else {
                    HandlerOutcome::retry_after(Duration::from_secs(30))
                }
            })
            .collect()))
    }
}

    Выбор источника подписки¶

    Атрибут всегда фиксирует вид подписки: субъект, консьюмер JetStream, поток Redis, канал pub/sub и список - это разные типы. Опустить можно значение, которым вид заполняется: его тогда даёт точка монтирования. Форм четыре, от самой короткой:

    Форма Вид Значение
    #[subscriber] источник по имени из точки монтирования
    #[subscriber(RedisStream)] назван здесь из точки монтирования
    #[subscriber("orders")] источник по имени зафиксировано здесь
    #[subscriber(RedisStream::new("orders").group("w"))] назван здесь зафиксировано здесь

    По имени¶

    #[subscriber("orders")] подписывается по имени. Это работает с любым брокером, реализующим трейт-совместимость Subscribe, - а её реализуют все крейты брокеров семейства: имя отображается в тот вид подписки, который брокер считает у себя основным, а всё, что этому виду нужно сверх имени, настраивается один раз на самом брокере.

    #[subscriber] - тот же источник, но без значения: имя, которое сервис узнаёт только в момент собственного связывания, субъект, собранный из номера шарда, топик, прочитанный из конфигурации:

    examples/subscribers.rs
    /// The by-name source with its value left out: the mount site names the subscription.
#[subscriber]
async fn audit(order: &Order) -> HandlerOutcome {
    println!("auditing order {}", order.id);
    HandlerOutcome::ack()
}
    examples/subscribers.rs
    b.include(audit.name(format!("audit-{shard}")));
    examples/manual/subscribers.rs
    /// A subscription named at the mount site: constructing over `Unnamed` leaves the source
/// unbuilt, and `Unnamed<Name>` is no `SubscriptionSource` at all, so a mount that never calls
/// `.name(..)` does not compile. Naming it is what builds the source.
struct Audit;

impl Handle<Order> for Audit {
    fn handle(
        &self,
        order: &Order,
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<(), HandlerOutcome>> {
        println!("auditing order {}", order.id);
        ready(Ok(()))
    }
}
    examples/manual/subscribers.rs
    b.include(
    subscriber(Unnamed::<Name>::new(), Audit)
        .name(format!("audit-{shard}"))
        .build(),
);

    Там, где виду для существования действительно нужно больше одного имени (источник Pulsar принимает и топик, и имя подписки), FromName не реализуется, и эта форма для него не скомпилируется. Такие виды пишите полностью.

    Дескрипторы, специфичные для брокера¶

    Когда подписке нужны опции конкретного брокера (consumer group, durable-имя, политика доставки), крейт брокера предоставляет тип-дескриптор. Вызывайте его конструктор прямо в декораторе:

    #[subscriber(OrdersStream::new("orders", "workers"))]
async fn handle(order: &Order) -> HandlerOutcome {
    HandlerOutcome::ack()
}

    Тип дескриптора макрос читает из вызова конструктора, поэтому компилятор сверяет дескриптор с тем брокером, на который его смонтировали. Дескриптор - это любой тип, реализующий SubscriptionSource<B>; см. Авторам брокеров.

    Источником может быть и цепочка билдера поверх этого конструктора, так что опции остаются на месте. Например, у брокера с билдером опций обработчик называет конкретный стрим и консьюмер прямо в декораторе:

    #[subscriber(StreamOptions::new("orders").durable("audit"))]
async fn handle(order: &Order) -> HandlerOutcome {
    HandlerOutcome::ack()
}

    Чтобы назвать тип источника, макрос спускается по цепочке до базового Type::new(..), поэтому каждый метод цепочки обязан возвращать Self. Свободные функции отвергаются: их тип макросу не виден.

    Собранный так источник пересобирается для каждого монтирования, поэтому тип-дескриптор брокера реализует Clone. Одно определение можно смонтировать на два брокера.

    Настройки в точке монтирования¶

    Имя, политика воркеров, политики обработки ошибок и стартовая позиция - это значения, поэтому каждое можно задать в атрибуте, в точке монтирования или частично там и там. Атрибут разворачивается ровно в те вызовы, которые вы написали бы руками:

    examples/subscribers.rs
    b.include(
    bill.name("orders")
        .workers(nonzero!(4))
        .on_failure(FailurePolicies::default().with_decode(FailurePolicy::Skip)),
);
    examples/manual/subscribers.rs
    b.include(
    subscriber("orders", Bill)
        .workers(nonzero!(4))
        .on_failure(FailurePolicies::default().with_decode(FailurePolicy::Skip))
        .build(),
);

    Настройка, названная в атрибуте, зафиксирована в типе определения, поэтому точка монтирования не может назвать её повторно - никаких правил приоритета помнить не нужно:

    #[subscriber("orders", workers(4))]
async fn handle(order: &Order) -> HandlerOutcome { HandlerOutcome::ack() }

b.include(handle.name("other"));    // does not compile: the name is already given
b.include(handle.on_failure(..));   // fine: the attribute said nothing about failures

    Методы приходят из трейта SubscriberSettings, который реализует каждое сгенерированное определение; чтобы до них добраться, импортируйте его (или prelude).

    Настройки, специфичные для брокера, передаются тем же путём и в терминах самого брокера. Ядро не может знать, что у подписки есть стрим JetStream или durable-имя консьюмера, поэтому оно даёт один крючок - преобразование над собираемым источником, - а крейт брокера кладёт сверху свой трейт, привязанный к своему типу источника; см. Авторам брокеров. Порядок в цепочке следует из того, что делает каждый шаг: имя идёт первым, потому что оно конструирует источник, дальше настройки брокера его преобразуют, а буфер, о котором ниже, оборачивает результат последним.

    Монтирование обработчиков¶

    Внутри with_broker определение монтируется через include:

    RustStream::new(info).with_broker(broker, |b| {
    b.include(handle);
});

    include декодирует полезную нагрузку кодеком, взятым с самого конкретного уровня, который вы задали: для обработчика, для области или выбранный фичами по умолчанию. См. откуда берётся кодек.

    Чтобы сгруппировать обработчики по модулям и смонтировать их разом, соберите их в Router; см. Роутинг.

    Пакетные подписчики¶

    Обработчик, принимающий срез, потребляет пакеты целиком: он выполняется один раз на каждый пакет, доставленный брокером, - один поход в базу, один массовый вызов API. Форма читается из сигнатуры, поэтому в атрибуте про неё ничего не пишут.

    examples/subscribers.rs
    /// Settles a whole batch of orders in one go: the slice parameter is what says so.
#[subscriber("orders")]
async fn settle(orders: &[Order]) -> HandlerOutcome {
    println!("settling {} orders", orders.len());
    HandlerOutcome::ack()
}
    examples/manual/subscribers.rs
    /// Settles a whole batch of orders in one go: the slice input is what says so, and a single
/// outcome settles every delivery behind the batch.
struct SettleBatch;

impl Handle<[Order]> for SettleBatch {
    fn handle(
        &self,
        orders: &[Order],
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<(), Vec<HandlerOutcome>>> {
        println!("settling {} orders", orders.len());
        ready(Ok(()))
    }
}

    Монтируется он через include, как и любая другая форма. Пакетную форму несёт само определение, а точка монтирования должна дать одно число - размер пакета:

    examples/subscribers.rs
    // The batch size is the one parameter a batch mount owes the broker: at most 64 orders per
// call, whatever the broker builds its batches out of.
b.include(settle.batch(nonzero!(64)));
    examples/manual/subscribers.rs
    /// Batches dispatch per batch rather than per delivery, and the batch input is the whole
/// declaration: the mount demands a batching subscriber of the source, exactly as a `&[T]`
/// handler under `#[subscriber]` would. The batch size is the one parameter a batch mount owes the
/// broker: at most 64 orders per call, whatever the broker builds its batches out of.
fn batch_routes() -> impl RouterDef<MemoryBroker> {
    Router::<MemoryBroker>::new()
        .include(
            subscriber("orders", SettleBatch)
                .batch(nonzero!(64))
                .build(),
        )
        .include(subscriber("orders", Reconcile).batch(nonzero!(64)).build())
}

    batch(n) - единственный пакетный параметр, который несёт фреймворк, и он обязателен: пакетный обработчик без него не компилируется, потому что выдумать за вас размер фреймворку неоткуда. Число уходит прямо в брокер, и тот собирает пакеты под него - XREADGROUP COUNT, pull-пачка JetStream, лимит poll в Kafka, - а тело видит ровно тот пакет, который отдал брокер, и никогда его срез. Пакет бывает короче n, если больше у брокера ничего не было.

    Всё остальное про то, как складывается пакет, - таймаут блокировки, группа консьюмеров, окно предвыборки - это словарь самого брокера, и он цепляется после размера на его источник подписки:

    // на Redis-брокере: размер - слово ядра, `.block(..)` - слово брокера
b.include(reconcile.name("orders").batch(nonzero!(6)).block(Duration::from_secs(5)));

    Размер работает на любой пакетной форме, что бы ещё ни было в сигнатуре: пакет с ответом и пакет, который публикует через слот Out, называют его ровно так же, как обычный. У обработчика одиночного сообщения пакета нет, поэтому там такой вызов тоже не компилируется: сколько доставок такой обработчик берёт разом, задаёт workers(n).

    Пакеты отдаёт любой брокер. Те, чьи клиенты собирают пакеты нативно, дают совместимость BatchSubscriber напрямую (poll в Kafka, pull-консьюмеры JetStream, XREADGROUP в Redis; in-memory брокер тоже), а те, чей транспорт отдаёт по одному сообщению, собирают пакеты на клиенте через адаптер Buffered ядра - внутри крейта брокера. В точке монтирования не видно, какой из двух путей выбран. Как это делает брокер, описано в разделе Пакеты руководства для авторов брокеров.

    От обработчиков одиночных сообщений семантика отличается в нескольких местах:

    • Элементы, которые не удалось декодировать, получают nack поштучно (по политике обработки ошибок декодирования) и до обработчика не доходят; остальные приходят одним срезом.
    • Возвращённое значение завершает весь пакет. Одиночный HandlerOutcome (или () / Result<_, E>) одинаково завершает каждое сообщение: ack() подтверждает все, retry() возвращает в очередь все.
    • Заголовки отдельных сообщений в форме &[T] недоступны, и контекст начинается с пустыми заголовками.
    • Контекст один на пакет, и поля брокера в нём - те, что относятся ко всей подписке: пакетное тело называет пакетный тип контекста брокера (ctx: &mut Context<'_, MemoryBatchContext> для in-memory брокера) и читает его ключи через ctx.context(..). Брокер, которому нечего предложить на уровне подписки, оставляет пакеты на умолчании ().
    • Данным отдельной доставки места там нет, потому что пакет охватывает много доставок: позиция или заголовок едут на самих элементах, и пакет &[Message<H, T>] читает их поэлементно. Это разные типы, поэтому пакетное тело, запросившее контекст отдельной доставки, не компилируется.
    • Глобальные для приложения и роутерные middleware оборачивают обработчики отдельных сообщений и к пакетным регистрациям не применяются.

    Выборочное подтверждение¶

    Частый случай - частичная готовность: часть сообщений пакета обработана, а остальные ещё не готовы и должны быть доставлены повторно, не утаскивая за собой уже удавшиеся. Верните Vec<HandlerOutcome>, чтобы элемент i среза завершился исходом i:

    examples/subscribers.rs
    /// Retries only the entries that are not ready yet; the rest of the batch settles.
#[subscriber("orders")]
async fn reconcile(orders: &[Order]) -> Vec<HandlerOutcome> {
    orders
        .iter()
        .map(|order| {
            if order.id == 0 {
                HandlerOutcome::retry()
            } else {
                HandlerOutcome::ack()
            }
        })
        .collect()
}
    examples/manual/subscribers.rs
    /// Retries only the entries that are not ready yet; the rest of the batch settles. One outcome per
/// element, in the order the slice was handed over.
struct Reconcile;

impl Handle<[Order]> for Reconcile {
    fn handle(
        &self,
        orders: &[Order],
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<(), Vec<HandlerOutcome>>> {
        ready(Err(orders
            .iter()
            .map(|order| {
                if order.id == 0 {
                    HandlerOutcome::retry()
                } else {
                    HandlerOutcome::ack()
                }
            })
            .collect()))
    }
}

    Со стороны брокера семантика ровно та же, что у nack(requeue = true) для одного сообщения: брокеры с повторной доставкой отдельных сообщений поддерживают выборочный повтор нативно, а позиционный брокер деградирует так же, как и на nack одиночного сообщения (крейт такого брокера это описывает). Вернуть вектор, длина которого не совпадает с пакетом, - ошибка в обработчике: несопоставленный остаток отправляется на повторную доставку, а расхождение попадает в лог.

    Перемотка¶

    Переиграть поток после починки бага в обработчике, переобработать с известной точки, перескочить через ядовитый участок: каждый такой случай называет позицию в потоке - ту, с которой подписка открывается, или ту, на которую переезжает живая подписка, не разрываясь. Брокеры поверх воспроизводимого лога (Kafka, потоки Redis, журнал публикаций in-memory брокера) реализуют трейт-совместимость Seekable, владеют типом позиции и публикуют ключи перемотки поверх своего контекста доставки. Брокер без воспроизводимого лога не даёт ни того ни другого, и монтирования ниже на нём не скомпилируются, а не упадут в рантайме.

    Открытие с выбранной позиции¶

    Свежая подписка открывается там, где решит брокер: в хвосте для обычного консьюмера, на сохранённом курсоре для долговечного. Всё, что опубликовано до этой точки, сервис не видит, и это неверный ответ и для журнала аудита, которому нужна вся история, и для монитора, которому нельзя разгребать накопившееся. Где открывается подписка - свойство точки монтирования, а не обработчика, поэтому там она и называется: клаузой start_at(<position>) в атрибуте или шагом настроек .start_at(..):

    examples/seek.rs
    /// The audit trail: its subscription opens at the start of the log, so entries published
/// before the service started are replayed into it.
#[subscriber("audit", start_at(MemoryPosition::start()))]
async fn record(entry: &Job) -> HandlerOutcome {
    println!("audit: entry {}", entry.id);
    HandlerOutcome::ack()
}
    examples/manual/seek.rs
    /// The audit trail: its subscription opens at the start of the log, so entries published
/// before the service started are replayed into it. The position itself is a settings step, so
/// it is named where the handler is mounted, exactly as `workers` or `on_failure` would be.
struct Record;

impl Handle<Job> for Record {
    fn handle(
        &self,
        entry: &Job,
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<(), HandlerOutcome>> {
        println!("audit: entry {}", entry.id);
        ready(Ok(()))
    }
}
    examples/manual/seek.rs
    b.include(
    subscriber(MemorySource::new("audit"), Record)
        .start_at(MemoryPosition::start())
        .build(),
);

    Позиция - значение собственного типа позиций брокера, поэтому назвать можно ровно то, что брокер умеет выразить: in-memory лог даёт MemoryPosition::start() для всей истории, MemoryPosition::end() - для всего начиная со следующей публикации, и MemoryPosition::sequence(n) - для одной записи лога.

    Клауза навязывает позицию при каждом старте; без неё подписка открывается на умолчании брокера. Условное умолчание - применять, только если у брокера нет сохранённого курсора для группы (сброс смещения в Kafka, deliver policy в JetStream), - остаётся на собственном дескрипторе подписки брокера, который выражает его нативно.

    Перемотка из обработчика¶

    Обработчик передвигает собственную подписку через ключи контекста брокера: контекст доставки несёт позицию и живую ручку перемотки (её брокер резолвит один раз, при открытии подписки), а обработчик читает их по ключу - экстрактором Ctx на пути атрибута, вызовом ctx.context(..) над типом контекста брокера на ручном. В месте include ничего прикреплять не нужно:

    examples/seek.rs
    /// Skips forward when the producer marks a poison region: everything queued before the
/// resume point is dropped without touching the subscription itself. The seeker is a broker
/// context field - the `SeekHandle` key reads it off the delivery's context.
#[subscriber("jobs")]
async fn work(job: &Job, Ctx(seeker): Ctx<SeekHandle>) -> HandlerOutcome {
    if job.id == 999 {
        // The poison marker carries the resume point: skip to the fourth log entry.
        if seeker.seek(MemoryPosition::sequence(3)).await.is_err() {
            return HandlerOutcome::retry();
        }
        return HandlerOutcome::ack();
    }
    println!("jobs: processed {}", job.id);
    HandlerOutcome::ack()
}
    examples/seek.rs
    // Both mount plainly: the seek handler's context is built off its own subscription per
// delivery, and the start_at clause seeks the audit one before its first delivery.
let app = RustStream::new(AppInfo::new("seek-demo", "0.1.0")).with_broker(broker, |b| {
    b.include(work);
    b.include(record);
});
    examples/manual/seek.rs
    /// Skips forward when the producer marks a poison region: everything queued before the
/// resume point is dropped without touching the subscription itself.
struct Work;

/// The body behind the attribute's `Ctx(seeker)` parameter: seeking is the broker context axis
/// of `Handle`, so declaring the broker's own `MemoryContext` is the whole declaration - the
/// runtime builds one per delivery off the subscription, and the `SeekHandle` key reads the
/// reposition handle out of it.
impl Handle<Job, (), (), MemoryContext> for Work {
    async fn handle(
        &self,
        job: &Job,
        _outs: &(),
        ctx: &mut Context<'_, MemoryContext>,
    ) -> Result<(), HandlerOutcome> {
        if job.id == 999 {
            // The poison marker carries the resume point: skip to the fourth log entry.
            if ctx
                .context(SeekHandle)
                .seek(MemoryPosition::sequence(3))
                .await
                .is_err()
            {
                return Err(HandlerOutcome::retry());
            }
            return Ok(());
        }
        println!("jobs: processed {}", job.id);
        Ok(())
    }
}
    examples/manual/seek.rs
    // Both mount plainly: the seek body's context is built off its own subscription per
// delivery, and the chained start position seeks the audit one before its first delivery.
let app = RustStream::new(AppInfo::new("seek-demo", "0.1.0")).with_broker(broker, |b| {
    b.include(subscriber(MemorySource::new("jobs"), Work).build());
    b.include(
        subscriber(MemorySource::new("audit"), Record)
            .start_at(MemoryPosition::start())
            .build(),
    );
});

    Пакетное тело перематывает свою подписку так же, только уровнем выше: ручка перемотки относится ко всей подписке, поэтому едет в пакетном контексте брокера, а цель - позиция, с которой продюсер просит продолжить, - едет на элементах самого пакета.

    Что именно захватывает одна перемотка, у брокеров различается: перемещение экземпляра консьюмера (Kafka) двигает только этот экземпляр, а перемещение общего курсора группы (потоки Redis) двигает всю группу. Кроме того, перемотка делает недействительным весь учёт ack, который брокер вёл по этой подписке; и то и другое описывает крейт брокера. Авторы брокеров доказывают контракт набором conformance capabilities::seeking.

    Сырые подписчики¶

    Иногда полезная нагрузка вообще не сериализованное значение: двоичный кадр, чужой формат передачи, который вы разбираете сами. Кодек тут только мешал бы, поэтому тип нагрузки убирает эту ступень с пути:

    обычный путь: брокер -> байты -> кодек -> &Order     -> обработчик
сырой путь:   брокер -> байты ->          &Frame<'_> -> обработчик

    Путь обработки выбирает сам тип нагрузки, а мнемонику дают имена трейтов: Deserialize/Serialize - работу делает кодек фреймворка; Deserialized/Serialized - тип уже сделал её сам. Тип Deserialized - это &[u8] с именем: одно поле, ничего не копируется. #[derive(Deserialized)] на newtype над &'a [u8] - и объявление готово, а параметр &Frame<'_> ставит обработчик на этот путь. Байты приходят ровно в том виде, в каком их отдал брокер, взаймы из его буфера.

    tests/raw_subscriber.rs
    #[subscriber("frames")]
async fn on_frame(frame: &Frame<'_>) -> HandlerOutcome {
    let _ = frame.0;
    HandlerOutcome::ack()
}
    tests/manual_raw_subscriber.rs
    /// The payload view the raw bodies below take, with the pair of impls `#[derive(Deserialized)]`
/// writes: the construction that borrows the delivery's bytes, and the input spelling that
/// routes `&Frame<'_>` onto the codec-free lane.
struct Frame<'a>(&'a [u8]);

impl Deserialized for Frame<'_> {
    type Output<'a> = Frame<'a>;
    type Error = Infallible;

    fn from_payload(payload: &[u8]) -> Result<Frame<'_>, Self::Error> {
        Ok(Frame(payload))
    }
}

impl Input for Frame<'_> {
    type Axis = SoloDeserialized<Frame<'static>>;
}

/// The raw form by hand. `Handle<Frame<'_>>` is what the attribute implements for a
/// `&Frame<'_>` parameter: the input type itself tells the mount to skip the codec, and the
/// adapter lends the delivery's payload rather than decoding it.
struct OnFrame;

impl<'p> Handle<Frame<'p>> for OnFrame {
    fn handle(
        &self,
        frame: &Frame<'p>,
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<(), HandlerOutcome>> {
        let _ = frame.0;
        ready(Ok(()))
    }
}

    Голый параметр &[u8] не компилируется: нагрузка всегда приходит за именованным типом самого сервиса, и ошибка компиляции называет derive как исправление. Вкладка «Вручную» показывает ту пару impl-ов, которую пишет derive: конструкцию и написание, которое направляет тип на этот путь.

    Правило формы от пути не зависит: &T - одно сообщение, &[T] - пакет. Значит, пакет кадров - это &[Frame<'_>], и написание для пакета приходит вместе с derive: второй impl пакетному телу не нужен. Его элементы заимствованы у сообщений самого пакета на время вызова, так что и здесь ничего не копируется, а правила завершения доставки - те же, что и на пакетном пути.

    examples/subscribers.rs
    /// The raw element type: the derive gives the newtype the delivery's bytes, and with them both
/// input spellings, so a batch of frames is `&[Frame<'_>]`.
#[derive(Deserialized)]
struct Frame<'a>(&'a [u8]);

/// A batch of payloads: the batch shape without the decode step.
#[subscriber("frames")]
async fn ingest(frames: &[Frame<'_>]) -> HandlerOutcome {
    let bytes: usize = frames.iter().map(|frame| frame.0.len()).sum();
    println!("ingesting {} frames ({bytes} bytes)", frames.len());
    HandlerOutcome::ack()
}
    examples/manual/subscribers.rs
    /// The raw element type. What `#[derive(Deserialized)]` would write is these two impls: the
/// construction, which borrows the bytes straight out of the delivery, and the `Input`
/// spelling that routes the type onto the self-deserializing lane - the batch spelling
/// (`&[Frame<'_>]`) comes with it. No codec takes part anywhere on this path.
struct Frame<'a>(&'a [u8]);

impl Deserialized for Frame<'_> {
    type Output<'a> = Frame<'a>;
    type Error = Infallible;

    fn from_payload(payload: &[u8]) -> Result<Frame<'_>, Self::Error> {
        Ok(Frame(payload))
    }
}

impl Input for Frame<'_> {
    type Axis = SoloDeserialized<Frame<'static>>;
}

/// A batch of payloads: the batch shape without the decode step.
struct Ingest;

impl<'p> Handle<[Frame<'p>]> for Ingest {
    fn handle(
        &self,
        frames: &[Frame<'p>],
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<(), Vec<HandlerOutcome>>> {
        let bytes: usize = frames.iter().map(|frame| frame.0.len()).sum();
        println!("ingesting {} frames ({bytes} bytes)", frames.len());
        ready(Ok(()))
    }
}

    Конструкция, которая проверяет содержимое (корень flatbuffers, читатель capnp, проверка длины), сообщает о плохой нагрузке через Err из from_payload, и доставку завершает политика on_failure(decode = ..): та же ступень, на которую попадают ошибка декодирования кодека и нарушение типизированного контракта Headers. Всё остальное складывается как обычно: экстракторы, &mut Context, workers(..), on_failure(panic = ..) и внедряемые параметры Out работают на форме одиночной доставки без изменений (пакет кадров параметра Out не принимает), а сам подписчик монтируется тем же include, что и любое другое определение. Кодек области к нему не применяется - этот путь кодек не зовёт вовсе, - и потому это та форма подписчика, которая работает вообще без включённых фич кодеков. Если же для своего формата сериализации вам нужны типизированные обработчики, реализуйте Codec и оставайтесь на типизированном пути.

    Обработчик на этом пути отвечает через ту же клаузу publish("dest"), что и любая другая форма ответа, а способ передачи выбирает тип ответа - по той же мнемонике: ответ с serde::Serialize кодек ответа кодирует, а ответ с #[derive(Serialized)] производит собственные байты и уходит байт в байт, ровно таким, каким его вернул обработчик. Возвращайте ответ напрямую или как Result<Export, HandlerOutcome> - это то же явное управление ack, что и в кодирующей форме.

    Издателя даёт место include: оба способа отправки называют политику одинаково (b.include(relay).out(Reply, Publish)), а если вызова нет вовсе, ответ уходит через политику публикации брокера по умолчанию. Различие в том, что идёт дальше по цепочке: кодируемый ответ принимает .codec(..), .transform(..) и .transactional(), а байты Serialized уходят нетронутыми, поэтому таких шагов там нет. Неудачная публикация ответа даёт доставке nack с возвратом в очередь - ровно как на кодирующем пути:

    tests/raw_subscriber.rs
    #[subscriber("relay-in", publish("relay-out"))]
async fn relay(frame: &Frame<'_>) -> Export {
    let mut reply = frame.0.to_vec();
    reply.reverse();
    Export(reply)
}
    tests/manual_raw_subscriber.rs
    /// The reply type the byte-reply form returns, with the impls `#[derive(Serialized)]` writes
/// for the reply position: the bytes that leave, and the shape that routes them onto the
/// serialized wire.
struct Export(Vec<u8>);

impl Serialized for Export {
    type Error = Infallible;

    fn wire_bytes<'a>(&'a self, _buf: &'a mut BytesMut) -> Result<&'a [u8], Infallible> {
        Ok(&self.0)
    }
}

impl ReplyShape for Export {
    type Body = Self;
    type Headers = ();
    type Wire = SerializedReply;
}

/// The byte-reply form by hand: a body over `Frame<'_>` declaring `Export` as its reply, so
/// bytes in and bytes out. The reply type is what picks the codec-free commit, so the reply
/// leaves as it was returned, and the body's `Err` arm is the reply the attribute lets a
/// handler skip.
struct Relay;

impl<'p> Handle<Frame<'p>, Export> for Relay {
    fn handle(
        &self,
        frame: &Frame<'p>,
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<Export, HandlerOutcome>> {
        let mut reply = frame.0.to_vec();
        reply.reverse();
        ready(Ok(Export(reply)))
    }
}

    Стороны друг друга не ограничивают: тип входа выбирает декодирование, тип ответа - кодирование, и обе диагонали свободно сочетаются. Декодируемый вход с ответом Serialized - это форма шлюза: принимаем структурированные сообщения и отдаём формат передачи, который обработчик собрал сам, а вход при этом декодируется кодеком области и сохраняет свою политику обработки ошибок декодирования:

    tests/raw_subscriber.rs
    /// The gateway shape: a structured message in, a self-produced wire format out.
#[subscriber("gateway-in", publish("gateway-out"))]
async fn gateway(wrap: &Wrap) -> Export {
    Export(wrap.id.to_be_bytes().to_vec())
}
    tests/manual_raw_subscriber.rs
    /// The gateway shape: a structured message in, a self-produced wire format out. Only the
/// body's input parameter changes from the byte-reply form above - `&Wrap` instead of
/// `&Frame<'_>`, which is what selects the decode - so the decode codec is resolved from the
/// mount while the reply still leaves unencoded.
struct Gateway;

impl Handle<Wrap, Export> for Gateway {
    fn handle(
        &self,
        wrap: &Wrap,
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<Export, HandlerOutcome>> {
        ready(Ok(Export(wrap.id.to_be_bytes().to_vec())))
    }
}

    Вторая диагональ читается так же: вход Frame<'_> с ответом Serialize кодирует ответ кодеком ответа, а сам вход кодека не касается вовсе. Два случая, однако, за типом не следуют. Ответ Vec<u8> сырым ответом не считается - это обычное значение Serialize, поэтому оно уходит закодированным, и нагрузке, которая обязана уйти нетронутой, нужен newtype. А ответ на пакет всегда публикуется через кодек ответа: способ передачи Serialized работает для одиночных ответов.

    Пулы воркеров¶

    Цикл диспетчеризации у подписчика последовательный: доставка обрабатывается и завершается до того, как подписчик вытянет следующую, поэтому один медленный обработчик тормозит всю подписку. Клауза workers(n) обрабатывает до n доставок этого подписчика одновременно, каждую в своей задаче на многопоточном рантайме:

    examples/subscribers.rs
    /// Up to 16 orders processed concurrently; global order is lost by design.
#[subscriber("orders", workers(16))]
async fn fan_out(order: &Order) -> HandlerOutcome {
    println!("processing order {}", order.id);
    HandlerOutcome::ack()
}
    examples/manual/subscribers.rs
    /// Up to 16 orders processed concurrently; global order is lost by design. Concurrency belongs to
/// the registration, so it is chained where the handler is mounted.
struct FanOut;

impl Handle<Order> for FanOut {
    fn handle(
        &self,
        order: &Order,
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<(), HandlerOutcome>> {
        println!("processing order {}", order.id);
        ready(Ok(()))
    }
}

fn fan_out_routes() -> impl RouterDef<MemoryBroker> {
    Router::<MemoryBroker>::new()
        .include(subscriber("orders", FanOut).workers(nonzero!(16)).build())
}

    Обратное давление сохраняется: пока n доставок в работе, поток не опрашивается, и это хорошо уживается с ограничениями на стороне брокера вроде max_ack_pending в JetStream. Глобальный порядок обработки при этом теряется, и так задумано: если порядок доставки хоть где-то важен, либо оставайтесь последовательными, либо партиционируйте обработку по ключу:

    examples/subscribers.rs
    /// 16 lanes keyed by the message's partition key: per-key order is preserved.
#[subscriber("orders", workers(16, by_key))]
async fn per_customer(order: &Order) -> HandlerOutcome {
    println!("processing order {}", order.id);
    HandlerOutcome::ack()
}
    examples/manual/subscribers.rs
    /// 16 lanes keyed by the message's partition key: per-key order is preserved. The same slot as the
/// pool, filled with the keyed policy instead.
struct PerCustomer;

impl Handle<Order> for PerCustomer {
    fn handle(
        &self,
        order: &Order,
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<(), HandlerOutcome>> {
        println!("processing order {}", order.id);
        ready(Ok(()))
    }
}

fn per_customer_routes() -> impl RouterDef<MemoryBroker> {
    Router::<MemoryBroker>::new().include(
        subscriber("orders", PerCustomer)
            .workers_by_key(nonzero!(16))
            .build(),
    )
}

    workers(n, by_key) разбивает обработку на n последовательных партиций. Доставка попадает в ту партицию, в которую хешируется её ключ партиционирования, поэтому сообщения с одним ключом никогда не пересекаются и не меняют порядок - внутрипроцессный аналог семантики партиций Kafka. Ключ берётся из partition_key() брокерского сообщения (его дают брокеры, у которых сообщения реализуют трейт-совместимость Partitioned; in-memory брокер читает заголовок partition-key). Сообщения без ключа раскладываются по партициям по кругу. by_key применим к подписчикам одиночных сообщений; пакетные формы берут обычный пул workers(n) из пакетов.

    На остановке подписчик перестаёт вытягивать новые доставки, а воркеры в работе дорабатывают в пределах shutdown_timeout приложения.

    Правила композиции¶

    Возможности подписчика сочетаются друг с другом; ниже - правила на каждом пересечении, и каждое закреплено интеграционным тестом.

    Сочетание Правило
    workers(n) × пакетный обработчик Пул держит в работе до n пакетов. by_key к пакетным формам не применяется: партиционирование упорядочивает одиночные сообщения по ключу, и макрос отвергает такое сочетание на этапе компиляции.
    retry() / retry_after × workers(n) Повторно доставленные сообщения снова попадают в пул и завершаются как любая другая доставка.
    retry() / retry_after × workers(n, by_key) Повторы отрабатывают, но порядок внутри ключа через повтор не гарантируется: возвращённое в очередь сообщение встаёт в поток с конца. Если сообщения ключа обязаны сохранять порядок даже через сбои, обработчик должен поглощать сбой сам, а не слать nack.
    .transactional() × workers(n) Одна транзакция на пакет, ровно как в последовательном цикле. Параллельные пакеты выполняют параллельные независимые транзакции; каждая остаётся атомарной (на пакет: сначала коммит, потом ack).
    размер пакета × workers(n) Пакеты по-прежнему закрываются по batch(n) или, если брокер собирает их на клиенте, по его сроку; пул ограничивает лишь то, сколько закрытых пакетов обрабатывается одновременно, и на границы пакетов не влияет никогда.
    publish(..) × workers(n) Ответы формируются параллельно, поэтому порядок ответов между доставками не гарантируется. Неудачная публикация ответа повторяет только свою доставку.
    middleware × пакетный обработчик Глобальные для приложения и роутерные слои оборачивают обработчики отдельных сообщений и к пакетным регистрациям не применяются (слой на одно сообщение не может обернуть обработчик целого пакета).

    Макрос или вручную¶

    #[subscriber] - это сахар над обобщённым API. Макрос генерирует типизированный обработчик и его метаданные; ту же регистрацию можно написать руками: именованный тип, чей impl Handle несёт тело, привязывается к источнику через subscriber(source, body) и запечатывается вызовом .build(). Обе формы ниже регистрируют один и тот же обработчик.

    examples/subscribers.rs
    use ruststream::subscriber;

#[subscriber("orders")]
async fn handle(order: &Order) -> HandlerOutcome {
    println!("got order {}", order.id);
    HandlerOutcome::ack()
}

// inside with_broker(...):
b.include(handle);
    examples/subscribers.rs
    use ruststream::prelude::*;

// inside with_broker(...):
struct Inline;

impl Handle<Order> for Inline {
    fn handle(
        &self,
        order: &Order,
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<(), HandlerOutcome>> {
        println!("got order {}", order.id);
        ready(Ok(()))
    }
}

b.include(subscriber("orders", Inline).build());

    Ручное тело возвращает Result: сторона Ok несёт то, что произвёл обработчик (ответ или ничего), а сторона Err - завершение доставки, поэтому Ok(()) подтверждает, а Err(HandlerOutcome::retry()) возвращает сообщение в очередь; пакетное тело завершает доставки поэлементно через Err(Vec<HandlerOutcome>). Между subscriber(..) и .build() цепочка принимает те же настройки, что задали бы клаузы атрибута (.name, .workers, .on_failure, .batch), плюс управление документацией: с фичей asyncapi регистрация документируется по умолчанию, .describe(..) задаёт её описание, а .undocumented() выводит её из документа (см. AsyncAPI).

    Браться за ручную форму стоит, когда обработчику нужно состояние, которое макрос выразить не может (обработчик-структура с полями), или когда фича macros выключена. В остальных случаях атрибут дешевле в сопровождении.
