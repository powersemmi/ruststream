    Публикация и ответы¶

    Нормативная версия документации - английская

    Эта страница переведена с английского. При любом расхождении верен английский оригинал.

    Обработчик публикует одним из двух способов. Вернуть ответ - способ короче, и он же верный по умолчанию, когда обработчик отвечает на один адресат. Когда сообщение уходит в другое место или в несколько мест, берите издателя параметром Out. В обоих случаях обработчик никогда не видит неподключённого издателя: регистрации несут политики публикации (чистые объявления), а рантайм связывает их с подключённым брокером на старте.

    Явная публикация - это всегда один и тот же билдер: вход через message(..), выход через publish(). Уходит значение объявленного типа, и способ передачи выбирает сам тип:

    message(&order)   -> кодек -> байты -> брокер    (значение Serialize кодируется)
message(&export)  ->          байты -> брокер    (значение Serialized выдаёт байты само)

    Байты, которые сервис уже держит закодированными, едут как newtype с Serialized: имя превращает их из анонимной нагрузки на канале в запись сгенерированного документа. Позиции, которые обязана заполнить точка вызова, - адресат, типизированные заголовки, кодек - следуют из того, что объявил тип сообщения, поэтому недоопределённая публикация оборачивается ошибкой компиляции, а не сюрпризом во время работы.

    Ответ из обработчика¶

    Назовите адресата ответа через publish(..) и верните значение ответа. Рантайм закодирует его и отправит:

    examples/publishing.rs
    use ruststream::subscriber;

// A `publish(..)` handler that does not read the app state omits the `Context` parameter entirely;
// it stays generic over the state and mounts on an app with any state type.
#[subscriber("requests", publish("responses"))]
async fn respond(req: &Request) -> Response {
    println!("responding to request {}", req.id);
    Response { ok: true }
}
    examples/manual/publishing.rs
    // A `publish(..)` handler is a body producing a reply: the reply type is the second axis of
// `Handle`, and the chain names the subscription, the destination and the publisher the reply
// leaves through.
struct Respond;

impl Handle<Request, Response> for Respond {
    fn handle(
        &self,
        req: &Request,
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<Response, HandlerOutcome>> {
        println!("responding to request {}", req.id);
        ready(Ok(Response { ok: true }))
    }
}

    Монтируется он обычным include. Если больше ничего не сказано, ответ уходит через политику публикации брокера по умолчанию и кодеком по умолчанию; .out(Reply, Publish) называет политику, которую экспортирует прелюдия брокера, а следующие шаги цепочки достраивают связывание ответа: .codec(..) задаёт кодек ответа, .transform(..) - статическое преобразование публикации, .transactional() - одну брокерскую транзакцию на пакет ответов. Каждый шаг занимает свой слот один раз, поэтому второй .codec(..) - ошибка компиляции, а не молчаливая перезапись. Связывание - это объявление: рантайм соединяет его с подключённым брокером на старте.

    Определение никогда не называет издателя. Оно объявляет, чем обработчик отвечает и куда; политика публикации принадлежит брокеру, поэтому её называют там, где называют брокер, - в точке монтирования, тем же вызовом .out(marker, policy), которым связывают слот Out. Reply - это маркер позиции, через которую уходит возвращённое обработчиком значение.

    examples/publishing.rs
    // static, per-reply: the chain names the policy and composes the transform at
// compile time; the runtime pairs it with the connected broker at startup
b.include(respond)
    .out(Reply, Publish)
    .transform(EnvelopeTransform);
// the default reply wiring: the broker's default policy under the default codec
b.include(validate);
    examples/manual/publishing.rs
    // static, per-reply: the chain names the policy and composes the transform at
// compile time; the runtime pairs it with the connected broker at startup
b.include(
    subscriber("requests", Respond)
        .reply()
        .to("responses")
        .build(),
)
.out(Reply, Publish)
.transform(EnvelopeTransform);
// the default reply wiring: the broker's default policy under the default codec
b.include(
    subscriber("validated-requests", Validate)
        .reply()
        .to("responses")
        .build(),
);

    Декодирование входящего запроса следует области (кодек области, заданный через with_broker_codec, иначе кодек по умолчанию); кодек ответа едет на связывании, которое построила цепочка. См. Кодеки.

    Одна клауза обслуживает оба способа отправки, потому что выбор принадлежит типу ответа, а не клаузе. Ответ, реализующий serde::Serialize, кодируется, как выше. Ответ с #[derive(Serialized)] производит собственные байты и уходит байт в байт, поэтому его .out(Reply, ..) берёт политику и больше ничего: кодек на этом пути называть негде, и .codec(..) после него не компилируется. См. сырые подписчики.

    Управление подтверждением¶

    Простая форма ответа всегда публикует и делает ack. Чтобы взять управление на себя, возвращайте Result<Reply, HandlerOutcome>: Ok(reply) публикует и делает ack, Err(outcome) не публикует ничего, а диспетчер действует по возвращённому HandlerOutcome (HandlerOutcome::drop() - отправить в dead-letter, HandlerOutcome::retry() - запросить повторную доставку):

    examples/publishing.rs
    // `Ok` publishes the reply and acks; `Err` publishes nothing and the dispatcher acts on the
// returned HandlerOutcome (here: drop the malformed request instead of replying).
#[subscriber("validated-requests", publish("responses"))]
async fn validate(req: &Request) -> Result<Response, HandlerOutcome> {
    if req.id == 0 {
        return Err(HandlerOutcome::drop());
    }
    Ok(Response { ok: true })
}
    examples/manual/publishing.rs
    // `Ok` publishes the reply and acks; `Err` publishes nothing and the dispatcher acts on the
// returned HandlerOutcome (here: drop the malformed request instead of replying).
struct Validate;

impl Handle<Request, Response> for Validate {
    fn handle(
        &self,
        req: &Request,
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<Response, HandlerOutcome>> {
        if req.id == 0 {
            return ready(Err(HandlerOutcome::drop()));
        }
        ready(Ok(Response { ok: true }))
    }
}

    Форма Result распознаётся по написанной сигнатуре, поэтому её нужно выписать явно (псевдоним типа, прячущий Result, считается обычным типом ответа). Как и любой другой, публикующий обработчик может объявить необязательный второй параметр &mut Context, чтобы прочитать состояние приложения или опубликовать что-то вручную.

    Если не удалась сама публикация ответа (брокер её отверг, соединение потеряно), входящее сообщение получает nack с requeue = true: брокер доставит его повторно, вместо того чтобы молча потерять ответ. Делайте публикующие обработчики идемпотентными относительно повторной доставки.

    Публикация изнутри обработчика¶

    Чтобы публиковать не в единственный ответ, а куда-то ещё (вычисляемый адресат, fan-out, побочные эффекты), принимайте издателя параметром обработчика через Out: шаблон Out(out): Out<impl Publisher> связывает out с живым издателем внутри тела. Сигнатура называет только ту совместимость, которая обработчику нужна, и никогда - тип издателя конкретного брокера: конкретный тип выводится из политики, прикреплённой там, где обработчик включается в приложение, а рантайм связывает их после того, как брокер подключился. Один и тот же обработчик без единой правки монтируется и на боевой брокер, и на его внутрипроцессный тестовый транспорт.

    examples/publishing.rs
    use ruststream::runtime::Out;

// The publisher arrives as a parameter (the Out marker): the source is attached at the include
// site, the runtime pairs it with the connected broker at startup, and the handler always holds
// a live publisher - no registry, no erased lookup, no state plumbing. `Event` declares no
// destination of its own, so the call site names one.
#[subscriber("ingress")]
async fn forward(event: &Event, Out(out): Out<impl Publisher>) -> HandlerOutcome {
    if out.message(event).to("egress").publish().await.is_err() {
        return HandlerOutcome::retry();
    }
    HandlerOutcome::ack()
}
    examples/manual/publishing.rs
    use ruststream::runtime::Out;

// The publisher arrives as an injection: the policy is attached at the include site, the runtime
// pairs it with the connected broker at startup, and the body always holds a live publisher - no
// registry, no erased lookup, no state plumbing. Nothing the mount site chose is named here: one
// parameter stands for the slot's entry, `OutEntry` ties it to the marker, and the body states
// only the capability it needs of the wired publisher - so the same body mounts on a production
// broker and its in-process test transport unchanged, and under a slot transform or an app-wide
// publish layer alike. `Event` declares no destination of its own, so the call site names one.
struct Forward;

impl<Egress> Handle<Event, (), Outs<(Egress,)>> for Forward
where
    Egress: OutEntry<DefaultSlot, Wire: Publisher>,
{
    async fn handle(
        &self,
        event: &Event,
        outs: &Outs<(Egress,)>,
        _ctx: &mut Context<'_>,
    ) -> Result<(), HandlerOutcome> {
        if outs
            .get(DefaultSlot)
            .message(event)
            .to("egress")
            .publish()
            .await
            .is_err()
        {
            return Err(HandlerOutcome::retry());
        }
        Ok(())
    }
}

    message(&value) публикует тем способом, который выбрал тип значения: значение с serde::Serialize кодируется кодеком области (для одного вызова другой кодек называют через .with_codec(..)), а значение с Serialized уходит байт в байт и позиции для кодека не имеет вовсе. Оба заполняют позицию заголовков вызовом .with_headers(..) - объявленный контракт сообщения по ссылке (&meta) или уже собранный HeaderMap по значению, - и оба заканчиваются вызовом publish().

    Точка включения называет источник; для собственного брокера области это его политика публикации:

    examples/publishing.rs
    b.include(forward).out(DefaultSlot, Publish).build();
    examples/manual/publishing.rs
    b.include(subscriber("ingress", Forward).build())
    .out(DefaultSlot, Publish)
    .build();

    Несвязанный слот Out - это ошибка компиляции, а не времени выполнения: регистрация не соберётся, пока у каждого слота нет политики.

    Именованные слоты¶

    Обработчик, принимающий несколько издателей, называет на каждый параметр маркер слота: unit-структуру с выводом OutSlot, записанную вторым типовым аргументом (Out<impl Publisher, Primary>). Точка включения связывает каждый маркер через .out(marker, policy) и фиксирует регистрацию завершающим .build(). Вызовы связывают по маркеру, поэтому их порядок неважен; связать один и тот же слот дважды (или назвать маркер, которого обработчик не объявлял) не скомпилируется, а .build() существует, только когда связаны все слоты, - забытая привязка становится ошибкой компиляции, в типе прикрепления которой назван слот (MissingSlot<Audit>). Единственный безымянный параметр Out<impl Publisher> связывается с неявным DefaultSlot (.out(DefaultSlot, Publish).build()).

    Вызов .transform(..) после .out(..) едет на той позиции, которую этот вызов назвал (см. конвейер публикации), поэтому регистрация, которая и отвечает, и раздаёт копии, называет преобразование на каждой: .out(Reply, Publish).transform(StampSource).out(Audit, Publish).transform(Envelope).

    examples/publishing.rs
    use ruststream::OutSlot;

// A handler with several injected publishers names a slot marker per parameter; the include
// site binds each marker to its own policy, in any order. No broker publisher type appears in
// the signature, so the same handler mounts on a production broker and on its in-process test
// transport unchanged. Each marker lists what may leave through it, which is both what the
// generated document reports and what the publish builder admits.
#[derive(OutSlot)]
#[publishes(Event)]
struct Primary;

#[derive(OutSlot)]
#[publishes(Event)]
struct Shadow;

#[subscriber("mirror")]
async fn mirror(
    event: &Event,
    Out(primary): Out<impl Publisher, Primary>,
    Out(shadow): Out<impl Publisher, Shadow>,
) -> HandlerOutcome {
    if primary
        .message(event)
        .to("mirror-primary")
        .publish()
        .await
        .is_err()
        || shadow
            .message(event)
            .to("mirror-shadow")
            .publish()
            .await
            .is_err()
    {
        return HandlerOutcome::retry();
    }
    HandlerOutcome::ack()
}
    examples/publishing.rs
    // each named slot binds by marker; the call order does not matter, and a
// .transform(..) rides the slot the .out(..) before it bound
b.include(mirror)
    .out(Shadow, Publish)
    .transform(OutboxEnvelope)
    .out(Primary, Publish)
    .build();
    examples/manual/publishing.rs
    use ruststream::OutSlot;

// A body with several injected publishers names a slot marker per parameter; the include site
// binds each marker to its own policy, in any order. Each marker lists what may leave through
// it, which is both what the generated document reports and what the publish builder admits.
struct Primary;

impl OutSlot for Primary {
    const NAME: &'static str = "Primary";

    fn outgoing() -> Vec<OutgoingMessageMetadata> {
        <Event as OutMessages<Self>>::outgoing()
    }
}

impl PublishedThrough<Primary> for Event {}

struct Shadow;

impl OutSlot for Shadow {
    const NAME: &'static str = "Shadow";

    fn outgoing() -> Vec<OutgoingMessageMetadata> {
        <Event as OutMessages<Self>>::outgoing()
    }
}

impl PublishedThrough<Shadow> for Event {}

struct Mirror;

impl<P, S> Handle<Event, (), Outs<(P, S)>> for Mirror
where
    P: OutEntry<Primary, Wire: Publisher>,
    S: OutEntry<Shadow, Wire: Publisher>,
{
    async fn handle(
        &self,
        event: &Event,
        outs: &Outs<(P, S)>,
        _ctx: &mut Context<'_>,
    ) -> Result<(), HandlerOutcome> {
        if outs
            .get(Primary)
            .message(event)
            .to("mirror-primary")
            .publish()
            .await
            .is_err()
            || outs
                .get(Shadow)
                .message(event)
                .to("mirror-shadow")
                .publish()
                .await
                .is_err()
        {
            return Err(HandlerOutcome::retry());
        }
        Ok(())
    }
}
    examples/manual/publishing.rs
    // each named slot binds by marker; the call order does not matter, and a
// .transform(..) rides the slot the .out(..) before it bound
b.include(subscriber("mirror", Mirror).build())
    .out(Shadow, Publish)
    .transform(OutboxEnvelope)
    .out(Primary, Publish)
    .build();

    Совместимость в ограничении можно уточнить: Out<impl OwnedTransactions, Ledger> скомпилируется только с политикой, живой издатель которой поддерживает владеющие транзакции; проверка происходит в точке включения, а диагностика называет недостающую совместимость. Ограничение называет трейт брокерской совместимости - Publisher, TransactionalPublisher, OwnedTransactions, RequestReply или тот, что объявил крейт брокера, - и никогда не называет тип брокера, поэтому тело остаётся брокеро-независимым; на ручном пути то же ограничение стоит на живом значении записи, where L: OutEntry<Ledger, Wire: OwnedTransactions>. Под каждым таким ограничением запись отдаёт типизированную форму этой совместимости (билдер публикации, область транзакции, владеющую транзакцию) поверх кодека точки включения и списка маркера. Маркер слота - это ещё и та идентичность, по которой тестовая обвязка записывает публикации.

    Необязательная третья позиция параметра Out объявляет, что именно шлёт этот обработчик (Out<impl Publisher, Marker, (A, B)>, один тип или enum-набор с #[derive(OutMessages)]); собственный список маркера #[publishes(A, B)] говорит, что слоту разрешено публиковать, - и именно его сгенерированный документ показывает для обработчика, оставившего эту позицию без ограничения. Типизированная публикация типа, которого маркер не называет, - ошибка компиляции, сообщающая о недостающем членстве. Маркер, не перечисливший ничего, не публикует ничего: каждая публикация несёт тип сообщения, поэтому список распространяется на каждую из них. У неявного DefaultSlot единственного безымянного Out<impl Publisher> нет места объявления, где перечислять типы, поэтому он допускает любое объявленное сообщение. См. типизированные заголовки.

    Способ передачи типизированной публикации выбирает тип. Значение с serde::Serialize вызов message(&value) кодирует кодеком, как выше; тип с #[derive(Serialized)] производит собственные байты - держит их у себя или пишет на месте, - и тот же вызов публикует их ровно такими, какие они есть, без кодека на пути. Всё остальное подчиняется обычным правилам: дайте типу #[derive(Outgoing)] и перечислите его в #[publishes(..)], как любую модель. Документ покажет его под собственным именем (без схемы нагрузки - формат тут и есть сами байты), адресат возьмётся из декларации, а словарь, объявленный набор сообщений и позиции заголовков проверяют его так же, как кодируемую модель.

    tests/lanes.rs
    /// A self-carrying model in a slot dictionary: `#[derive(Serialized)]` routes it onto the
/// serialized wire, `#[derive(Outgoing)]` declares where it goes, and `#[publishes(..)]` makes
/// it a member like any encoded model.
#[derive(Outgoing, Serialized)]
#[outgoing(name = "lanes.exports")]
struct WireExport(Vec<u8>);

#[derive(OutSlot)]
#[publishes(WireExport)]
struct Exports;

/// One typed entry serves both wires: the type picks the lane, so `message(&wire)` publishes
/// the bytes as they are - no codec anywhere - to the destination the declaration names.
#[subscriber("lanes.chunks")]
async fn export(frame: &Frame<'_>, Out(out): Out<impl Publisher, Exports>) -> HandlerOutcome {
    let wire = WireExport(frame.0.to_vec());
    if out.message(&wire).publish().await.is_err() {
        return HandlerOutcome::retry();
    }
    HandlerOutcome::ack()
}
    tests/manual_out_slots.rs
    /// A self-carrying model in the slot dictionary, written out: the bytes, the wire spelling
/// that routes a typed publish onto the serialized wire, the declared destination and headers,
/// and the membership - what `#[derive(Serialized)]`, `#[derive(Outgoing)]` and
/// `#[publishes(..)]` would write.
struct WireExport(Vec<u8>);

impl Serialized for WireExport {
    type Error = Infallible;

    fn wire_bytes<'a>(&'a self, _buf: &'a mut BytesMut) -> Result<&'a [u8], Infallible> {
        Ok(&self.0)
    }
}

impl MessageWire for WireExport {
    type Wire = SerializedWire;
}

impl OutgoingDestination for WireExport {
    type Form = FixedName;
    const ADDRESS: &'static str = "slots.exports";
}

impl MessageHeaders for WireExport {
    type Contract = NoHeaders;
}

struct Exports;

impl OutSlot for Exports {
    const NAME: &'static str = "Exports";
}

impl PublishedThrough<Exports> for WireExport {}

/// One typed entry serves both wires: the type picks the lane, so `message(&wire)` publishes
/// the bytes as they are - no codec anywhere - to the destination the declaration names.
struct ExportChunks;

impl<'p, E> Handle<Frame<'p>, (), Outs<(E,)>> for ExportChunks
where
    E: OutEntry<Exports, Wire: Publisher>,
{
    async fn handle(
        &self,
        frame: &Frame<'p>,
        outs: &Outs<(E,)>,
        _ctx: &mut Context<'_>,
    ) -> Result<(), HandlerOutcome> {
        let wire = WireExport(frame.0.to_vec());
        if outs.get(Exports).message(&wire).publish().await.is_err() {
            return Err(HandlerOutcome::retry());
        }
        Ok(())
    }
}

    Объявление адресата сообщения¶

    Тип сообщения объявляет всё, что касается его отправки, одним derive, и все параметры записываются в одной и той же форме key = value. name - это адресат, а headers называет тип контракта (который остаётся обычной serde-структурой, derive её не трогает):

    examples/publishing.rs
    use ruststream::Outgoing;

// What a message says about being sent lives on the type. A fixed name resolves the destination
// for every call site; a name template turns each `{placeholder}` into a setter, so a service
// routing per tenant still declares where the type goes; and the derive alone (like `Event`
// above) leaves the name to the call.
#[derive(Debug, Serialize, Outgoing)]
#[outgoing(name = "orders.confirmed")]
struct OrderConfirmed {
    id: u64,
}

#[derive(Debug, Serialize, Outgoing)]
#[outgoing(name = "orders.{tenant}.placed")]
struct OrderPlaced {
    id: u64,
}

#[derive(OutSlot)]
#[publishes(OrderConfirmed, OrderPlaced)]
struct Orders;

#[subscriber("orders.incoming")]
async fn route(
    event: &Event,
    Out(orders): Out<impl Publisher, Orders, (OrderConfirmed, OrderPlaced)>,
) -> HandlerOutcome {
    // Bound to one name: the destination is already resolved.
    if orders
        .message(&OrderConfirmed { id: event.id })
        .publish()
        .await
        .is_err()
    {
        return HandlerOutcome::retry();
    }
    // Bound to a space of names: one setter per placeholder, and no publish until the last one
    // is bound.
    if orders
        .message(&OrderPlaced { id: event.id })
        .to()
        .tenant("acme")
        .publish()
        .await
        .is_err()
    {
        return HandlerOutcome::retry();
    }
    HandlerOutcome::ack()
}

/// The `tenant` segment of the declared name, named in the compile error of a publish that never
/// bound it. The derive hides it (and the builder below) in a module named after the type; by
/// hand the only requirement is that the names do not collide.
#[derive(Debug, Clone, Copy)]
struct Tenant;

/// One publish whose templated address is being bound, segment by segment. The publish terminal
/// is callable once every placeholder is bound; until then the unbound ones ride in this type, so
/// the compile error names them.
#[must_use = "an address builder does nothing until publish() is awaited"]
struct PlacedAt<Cont, S0> {
    cont: Cont,
    segment_0: S0,
}

impl<Cont> PlacedAt<Cont, MissingSegment<Tenant>> {
    fn start(cont: Cont) -> Self {
        Self {
            cont,
            segment_0: MissingSegment::new(),
        }
    }

    /// Binds the `tenant` segment of the declared name.
    fn tenant(self, value: impl Display) -> PlacedAt<Cont, String> {
        PlacedAt {
            cont: self.cont,
            segment_0: value.to_string(),
        }
    }
}

impl<Cont, S0> PlacedAt<Cont, S0> {
    // Every bound, the segment witness included, sits on the method: on the impl block a publish
    // that forgot a segment reads as "method not found" and loses the guidance the bound carries.
    async fn publish(self) -> Result<(), PublishError<<Cont as PublishAt>::Error>>
    where
        Cont: PublishAt,
        S0: BoundSegment,
    {
        // A templated address is rendered per publish; the fixed form is not.
        let address = format!("orders.{}.placed", self.segment_0);
        PublishAt::publish_at(self.cont, &address).await
    }
}

impl<Cont> TemplateAddress<Cont> for OrderPlaced {
    type Builder = PlacedAt<Cont, MissingSegment<Tenant>>;

    fn begin(cont: Cont) -> Self::Builder {
        PlacedAt::start(cont)
    }
}

struct Orders;

impl OutSlot for Orders {
    const NAME: &'static str = "Orders";

    fn outgoing() -> Vec<OutgoingMessageMetadata> {
        let mut declared = <OrderConfirmed as OutMessages<Self>>::outgoing();
        declared.extend(<OrderPlaced as OutMessages<Self>>::outgoing());
        declared
    }
}

impl PublishedThrough<Orders> for OrderConfirmed {}
impl PublishedThrough<Orders> for OrderPlaced {}

struct Route;

impl<O> Handle<Event, (), Outs<(O,)>> for Route
where
    O: OutEntry<Orders, Wire: Publisher>,
{

        &self,
        event: &Event,
        outs: &Outs<(O,)>,
        _ctx: &mut Context<'_>,

            .await

            .to()

            .publish()
            .await

    Объявление решает, какая позиция адресата остаётся точке вызова:

    • Фиксированное имя разрешает адресата, поэтому писать to(..) негде - и отправить такой тип туда, о чём документ не упоминает, невозможно.
    • Шаблон имени ("orders.{tenant}.placed") открывает to(), который возвращает билдер с одним сеттером на каждую подстановку. publish() скомпилируется, только когда связаны все подстановки, а несвязанная остаётся прямо в типе билдера, поэтому ошибка компиляции сообщает, что адрес не достроен, и называет забытый сегмент. Адрес отрисовывается на каждую публикацию; при фиксированном имени публикация идёт из &'static str.
    • Полное отсутствие name означает, что имя называет точка вызова: .to("orders.archived"), принимая &str или вычисленный String.

    Сообщение, объявившее headers = Meta, публикуется только через .with_headers(&meta): забыть заголовки или передать другой тип не скомпилируется. В сгенерированном документе фиксированное имя становится каналом сообщения, шаблон - шаблонизированным адресом, а его блок параметров заполняется из подстановок; тип, не объявивший адресата, не вносит ничего.

    Публикуемым таким способом значение делает именно derive, включая третий случай. Тип с Serialize, которым владеет другой крейт, вывести Outgoing не может и потому остаётся за пределами билдера: заверните такое значение в newtype с выводом Outgoing или, внутри транзакции, оставайтесь на publish(name, &value) у области.

    examples/publishing.rs
    // the slot lists what it may publish; where each message goes is its own declaration
b.include(route).out(Orders, Publish).build();
    examples/manual/publishing.rs
    // the slot lists what it may publish; where each message goes is its own declaration
b.include(subscriber("orders.incoming", Route).build())
    .out(Orders, Publish)
    .build();

    Параметр сочетается с любой формой подписчика: рядом с экстрактором Ctx, на обработчике, вход которого десериализует себя сам, и на пакетных обработчиках (b.include(f).out(marker, policy).build() - на вход целый пакет, на выход адресаты на каждый элемент). В формах ответа - publish(..) и его пакетном аналоге - ответ становится ещё одной позицией той же цепочки, так что шлюз называет обе и одновременно отвечает по фиксированному адресату и рассылает побочные копии через внедрение:

    Публикация в другой брокер¶

    Когда обработчик потребляет из одного брокера, а публикует в другой (потребляет Kafka, пересылает в Redis), оберните целевой брокер вызовом .bindable() и выпустите связывающий токен ещё до регистрации. Дальше токен и есть источник в точке включения (здесь показано на двух in-memory брокерах, но форма одинакова для любой пары):

    tests/out_injection.rs
    let to_other = other.bind(Publish);
let app = RustStream::new(AppInfo::new("cross", "0.1.0"))
    .with_broker(other, |b| {
        let _ = b; // the target broker may mount its own handlers here
    })
    .with_broker(ingress_broker, |b| {
        b.include(crossing).out(DefaultSlot, to_other).build();
    });
    tests/manual_out_injection.rs
    let to_other = other.bind(Publish);
let app = RustStream::new(AppInfo::new("cross", "0.1.0"))
    .with_broker(other, |b| {
        let _ = b; // the target broker may mount its own handlers here
    })
    .with_broker(ingress_broker, |b| {
        b.include(subscriber("out.crossing", Crossing).build())
            .out(DefaultSlot, to_other)
            .build();
    });

    Токены существуют до того, как отработает хоть один with_broker, поэтому порядок регистрации не имеет значения: двунаправленный мост связывает оба направления заранее.

    Токен делит слот с обёрткой Bindable, из которой он выпущен, поэтому регистрируйте ту же обёртку (with_broker(bindable, ..)), чтобы старт заполнил слот подключённым брокером; токен, брокер которого так и не зарегистрировался, быстро падает на связывании с внятной ошибкой. Та же форма работает и для публикации ответов (.out(Reply, token) на обработчике с publish("dest")), и для пакетных форм. Вне регистрации токен связывает себя сам, как только старт подключил его брокер: running.publisher(token) выдаёт соседней задаче живого издателя - см. Работа рядом с другим сервером. Для самой первой публикации на старте токен не нужен вовсе: b.after_startup(policy, hook) на уровне области запускает хук с уже связанным издателем, как только подписки открыты (см. Жизненный цикл); засев данных в примере публикации выполняется именно на нём.

    Откуда берутся заголовки¶

    Заголовки публикации приходят из двух мест. Место вызова называет их через .with_headers(..) - объявленный контракт сообщения по ссылке или уже собранный HeaderMap по значению, - а сам издатель может подложить снизу собственную основу. Издатель, который несёт один аргумент для целой серии сообщений (арендатор, подсказка о партиции, опция доставки, выражаемая брокером через заголовок), отдаёт этот аргумент из base_headers; так же поступает и открытая от него транзакция.

    Билдер собирает исходящую карту один раз - сначала основа, затем поверх неё, ключ за ключом, заголовки места вызова. Значение ключа определяется в следующем порядке:

    • ключ, названный в месте вызова, берёт значение оттуда;
    • ключ, которого место вызова не касается, берёт значение из основы издателя;
    • издатель без собственной основы оставляет заголовки места вызова ровно такими, как их написали.

    Обе формы сливаются одинаково: карта дописывается запись за записью, а объявленный контракт headers = Meta сериализует свои поля поверх основы, так что сообщение с контрактом несёт ещё и аргумент издателя.

    .with_headers(..) по-прежнему заполняется однажды: второй вызов - ошибка компиляции.

    Ответ собирается так же, хотя .with_headers(..) на нём никто не пишет: издатель, названный местом монтирования для позиции Reply, сначала подкладывает свою основу, а шаги .transform(..) той же цепочки пишут поверх неё. Поэтому опция брокера, которая едет в заголовках, оказывается и в ответе обработчика publish("dest"), и в каждом ответе пакета, и в том, что тело отправляет через слот Out, - обработчик о ней не знает.

    Конвейер публикации¶

    Перед тем как сообщение покинет процесс, работают три вида преобразований, и они сочетаются:

    • Статический PublishTransform на связывании ответа, добавляемый через .transform(..) сразу после .out(Reply, ..). Zero-cost преобразования на конкретного адресата (конверт, фиксированный content type, проставление в ответ trace / correlation id доставки). Они выполняются первыми, ближе всего к значению.
    • Статический OutTransform на одном слоте Out, добавляемый через .transform(..) сразу после .out(marker, policy). Он занимает то же место в порядке, но работает над тем, что уходит через этот слот: конверт outbox, фиксированный content type, метка арендатора. PublishContext он не принимает - публикацию в слот выдаёт само тело обработчика, поэтому доставку оно читает само и само кладёт в сообщение.
    • Статический PublishLayer на приложении, добавляемый через .publish_layer(..). Сквозная функциональность (метрики публикации, обёртка dead-letter), применяемая к каждому опубликованному сообщению вокруг самой отправки, чтобы видеть её результат. Цепочка складывается в конкретный тип, поэтому она становится частью типа приложения. Билдер обычно возвращает impl App и никогда его не выписывает; напишите конкретный RustStream<L, St, PublishStack<MyMiddleware, PublishIdentity>> - и конвейер проступит прямо там, а приложение без publish_layer сохранит умолчание PublishIdentity. Каждый middleware обязан быть Clone (конвейер клонируется в каждый публикующий обработчик), а добавленный последним выполняется самым внешним. Умолчание (middleware нет) - это прямая отправка. Если набор middleware решается во время работы, заверните его в PublishDynStack (публикующий аналог DynStack) и добавьте уже его.

    Статический PublishTransform реализует apply(&mut Outgoing<'_>, &PublishContext<'_, C>); PublishContext - это доступный только на чтение взгляд на доставку, породившую ответ (её канал, входящие заголовки и типизированный контекст брокера на одну доставку, читаемый по ключу Field), поэтому преобразование может перенести значение из входящего сообщения в ответ:

    examples/publishing.rs
    /// A static, per-publisher transform: stamps an envelope header on every outgoing message.
struct EnvelopeTransform;

impl<C> PublishTransform<C> for EnvelopeTransform {
    fn apply(&self, out: &mut Outgoing<'_>, _cx: &PublishContext<'_, C>) {
        out.headers_mut().insert("x-envelope", b"1".to_vec());
    }
}

    Ответы пакетного обработчика проходят мимо стека .transform(..), работающего на каждое сообщение; там преобразование добавляют через .batch_transform(..), переиспользуя помессажный PublishTransform через for_batch(transform). Каждый ответ проходит через него по одному, но PublishContext у них один на всех, и он пакетный, а не доставки: пакет охватывает много доставок, поэтому name() - это подписка, headers() пуст, а context(..) читает пакетный контекст брокера. Преобразованию, которому нужно прочитать сообщение, на которое оно отвечает, место на помессажном пути, где ответ и его доставка - одно и то же.

    OutTransform реализует apply(&mut Outgoing<'_>) и едет на одном слоте:

    examples/publishing.rs
    /// A static, per-slot transform: it stamps what leaves one `Out` slot. There is no
/// `PublishContext` here - the body issues a slot publish itself, so the delivery is the body's
/// own to read and put on the message.
struct OutboxEnvelope;

impl OutTransform for OutboxEnvelope {
    fn apply(&self, out: &mut Outgoing<'_>) {
        out.headers_mut().insert("x-outbox", b"1".to_vec());
    }
}

    PublishLayer реализует сигнатуру вида around/next, поэтому он может замкнуть цепочку накоротко, повторить отправку или просто наблюдать:

    examples/publishing.rs
    /// A static, app-wide publish layer: observes every publish, then passes it on.
#[derive(Clone)]
struct AuditPublish;

impl PublishLayer for AuditPublish {
    async fn on_publish<'a, N: PublishPipeline, P: Publisher>(
        &'a self,
        out: &'a mut Outgoing<'a>,
        next: PublishNext<'a, N, P>,
    ) -> Result<(), Box<dyn Error + Send + Sync>> {
        println!("publishing to {}", out.name());
        next.run(out).await
    }
}

    Оба уровня складываются на приложении:

    examples/publishing.rs
    RustStream::new(AppInfo::new("publishing", "0.1.0"))
    // app-wide layer: wraps every publish a handler makes, replies and Out slots alike
    .publish_layer(AuditPublish)
    .with_broker(broker, |b| {
        // the first publish: runs once connected and subscribed, with the transactional
        // wiring already paired
        b.after_startup(TransactionalPublish, async move |seeder| {
            seed_events(seeder).await.map_err(std::io::Error::other)
        });
        // static, per-reply: the chain names the policy and composes the transform at
        // compile time; the runtime pairs it with the connected broker at startup
        b.include(respond)
            .out(Reply, Publish)
            .transform(EnvelopeTransform);
        // the default reply wiring: the broker's default policy under the default codec
        b.include(validate);
        b.include(forward).out(DefaultSlot, Publish).build();
        // each named slot binds by marker; the call order does not matter, and a
        // .transform(..) rides the slot the .out(..) before it bound
        b.include(mirror)
            .out(Shadow, Publish)
            .transform(OutboxEnvelope)
            .out(Primary, Publish)
            .build();
        // one verb for both positions: .out(Reply, ..) names who publishes the returned
        // value (or leave it out for the default), and .out(<marker>, ..) binds an Out
        // parameter - DefaultSlot for a single unnamed slot
        b.include(gateway).out(DefaultSlot, Publish).build();
        // the slot lists what it may publish; where each message goes is its own declaration
        b.include(route).out(Orders, Publish).build();
        // .batch(n) is the batch size the subscription opens with, which every batch mount
        // owes. .transactional() marks the wiring; the pairing checks that the policy's live
        // publisher is transactional. Without it, each reply publishes independently.
        b.include(confirm.batch(nonzero!(64)))
            .out(Reply, TransactionalPublish)
            .transactional();
    })

    .publish_layer(AuditPublish)
    .with_broker(broker, |b| {

    Общий для приложения слой оборачивает каждую публикацию обработчика: и ответ формы publish(..), и любое сообщение, которое уходит через внедрённый слот Out. Преобразования точки монтирования остаются на том, для чего их назвали: .out(Reply, Publish).transform(StampSource) наращивает стек ответа, .out(Audit, Publish).transform(OutboxEnvelope) - стек этого слота, поэтому регистрация с обеими сторонами пишет оба вызова, а .transform(..) читается как "на позиции перед ним". Порядок на проводе с обеих сторон один: сначала преобразования точки монтирования (ближе всего к закодированному значению), затем общий для приложения middleware, затем отправка.

    Мимо конвейера идут две публикации, и обе обработчик ведёт сам: транзакция, открытая на слоте (begin(), transaction()), отправляет внутрь транзакции брокера, а обмен request / reply (request(..)) ждёт ответа вместо того, чтобы завершиться отправкой. Слоты роутера несут только собственные преобразования, но не общую для приложения цепочку: include_router монтирует маршруты, типы которых сложились раньше самого приложения, поэтому обработчик, публикациям которого из слота нужна эта цепочка, монтируется на области брокера через b.include(..). Полная программа - examples/publishing.rs.

    Пакетные ответы и транзакции¶

    Обработчик #[subscriber("in", publish("out"))], принимающий &[T], потребляет целый декодированный пакет и возвращает ответы на него - шаблон consume-transform-produce. Ok(replies) публикует каждый ответ по имени ответа и делает ack всего пакета; Err(outcome) не публикует ничего и завершает доставку всего пакета значением outcome (всё или ничего: выборочные исходы на каждый элемент с транзакцией не сочетаются):

    examples/publishing.rs
    /// Confirms a whole batch of orders; the replies become visible atomically on commit.
#[subscriber("orders", publish("confirmations"))]
async fn confirm(orders: &[Event]) -> Result<Vec<Event>, HandlerOutcome> {
    if orders.is_empty() {
        return Err(HandlerOutcome::drop()); // nothing published, whole batch settled
    }
    Ok(orders.iter().map(|o| Event { id: o.id }).collect())
}
    examples/manual/publishing.rs
    /// Confirms a whole batch of orders; the replies become visible atomically on commit. The batch
/// input and the reply type are two axes of the one trait: one `Vec` of replies per batch, each
/// published to the destination the chain names, and an `Err` settles the batch element-wise
/// (one outcome per element) without publishing anything.
struct Confirm;

impl Handle<[Event], Vec<Event>> for Confirm {
    fn handle(
        &self,
        orders: &[Event],
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<Vec<Event>, Vec<HandlerOutcome>>> {
        if orders.iter().any(|o| o.id == 0) {
            // nothing published, every element of the batch settled on its own
            return ready(Err(orders.iter().map(|_| HandlerOutcome::drop()).collect()));
        }
        ready(Ok(orders.iter().map(|o| Event { id: o.id }).collect()))
    }
}

    Монтируйте его через include, добавляя в цепочку связывание ответа через .out(Reply, ..):

    Без .transactional() каждый ответ публикуется независимо; сбой в середине пакета отправляет на повтор весь пакет, поэтому при повторной доставке ранее опубликованные ответы могут уйти ещё раз (at-least-once). Шаг .transactional() после .out(Reply, ..) переводит связывание на одну транзакцию брокера на пакет: рантайм начинает транзакцию, публикует все ответы, коммитит и только потом делает ack входящего пакета; любой сбой откатывает транзакцию, поэтому ответы никогда не бывают видны наполовину. Требование транзакционности проверяется там, где связывание поглощается: чтобы его смонтировать, нужна политика, живой издатель которой транзакционен, так что брокер без транзакций попросту не скомпилируется. У ответа на одно сообщение нечего делать атомарным, поэтому .transactional() монтируется только на пакетных формах.

    Ручные транзакции¶

    Вне пути пакетных ответов транзакцией управляют вручную: begin() на любом транзакционном издателе открывает TransactionScope, который владеет транзакцией. Публикации идут через эту область, а commit() / abort() её поглощают - поэтому коммит без начала транзакции, второй коммит или публикация после завершения транзакции оказываются ошибками компиляции, а не сюрпризами во время работы:

    examples/publishing.rs
    /// Seeds the reference events inside one broker transaction: both records become visible
/// together on commit, or not at all. The scope owns the transaction, so a commit without a
/// begin, a second commit, or a publish after settling do not compile. The publisher arrives
/// already paired (the scope's `after_startup` hands it over live), so seeding cannot race the
/// broker connect; the bound names the capability the seeding needs, not the broker's publisher.
async fn seed_events<P>(seeder: P) -> Result<(), Box<dyn Error + Send + Sync>>
where
    P: TransactionalPublisher,
{
    let scope = seeder.begin().await?;
    scope
        .message(&Event { id: 1 })
        .to("events")
        .publish()
        .await?;
    scope
        .message(&Event { id: 2 })
        .to("events")
        .publish()
        .await?;
    scope.commit().await?;
    Ok(())
}

    Область несёт тот же билдер, что и любая другая поверхность (scope.message(&value).publish()), но отправляет в открытую транзакцию, а не прямо брокеру. Значения она кодирует кодеком издателя и отправляет напрямую: преобразования на конкретного издателя и общий для приложения middleware publish_layer принадлежат пути диспетчеризации (они читают породившую доставку) и здесь не выполняются. Если уронить незавершённую область, в лог уйдёт предупреждение, а транзакция брокера на этом хендле останется открытой - всегда завершайте её явно.

    Слот Out открывает ту же область: ограничьте слот через Out<impl TransactionalPublisher, Journal> (на ручном пути - where W: TransactionalPublisher), и begin() на записи вернёт область, которую ведут ровно как выше. Область, открытая на слоте, допускает то же, что и собственный message слота, - список маркера, суженный объявленным набором параметра, - поэтому транзакция не сможет опубликовать то, чего сгенерированный документ никогда не объявлял, а её публикации остаются записанными на слот в тестовой обвязке.

    Область - это заимствующая разновидность транзакции: она занимает единственную транзакцию хендла на стороне брокера, поэтому на одном хендле в каждый момент открыта одна область. Брокеры, у которых транзакция - это буфер клиента, а не состояние продюсера, реализуют ещё и владеющую разновидность, OwnedTransactions: каждый вызов открывает независимую транзакцию с буфером внутри возвращённого TypedTransaction, поэтому один хендл держит сколько угодно транзакций сразу, и завершение одной никогда не задевает другую. message(..).publish() буферизует в это значение, а commit() / abort() его поглощают - та же дисциплина «завершение через поглощение», что и у области, - тогда как потерянное значение просто выбрасывает свой буфер (с предупреждением), а не оставляет открытой транзакцию брокера. Брокеры вроде Kafka, где клиент держит ровно одну транзакцию на продюсера, реализуют только заимствующую разновидность.

    Владеющая разновидность на обеих поверхностях читается одинаково: у издателя, который буферизует транзакции на стороне клиента, есть owned_transaction(), а у слота с ограничением Out<impl OwnedTransactions, Ledger> - transaction(). Оба вызова открывают TypedTransaction, который владеет транзакцией брокера и кодирует кодеком поверхности: let mut txn = publisher.owned_transaction().await?;, затем txn.message(&value).publish().await?; и txn.commit().await?;. Там, где begin() даёт заимствующую область (по одной на хендл), один издатель держит сколько угодно TypedTransaction сразу. (Слово owned стоит в имени потому, что рядом всегда виден собственный OwnedTransactions::transaction брокера.) Буфер владеющей транзакции завершается вне слота, поэтому её публикации попадают в журнал публикаций брокера, а не в собственную запись слота.

    Пакетная публикация¶

    Чтобы опубликовать много сообщений, публикуйте их в цикле: у большинства брокеров (NATS, Kafka) клиент и так объединяет записи, поэтому цикл даёт ту же пропускную способность, что и отдельный пакетный вызов. Там, где у брокера есть настоящий примитив конвейеризации (Redis), его крейт отдаёт этот примитив как совместимость, специфичную для брокера.
