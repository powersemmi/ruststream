    Публикация и ответы¶

    Нормативная версия документации - английская

    Эта страница переведена с английского языковой моделью. При любом расхождении верен английский оригинал.

    Обработчик публикует одним из двух способов. Вернуть ответ - способ короче, и он верен по умолчанию, когда обработчик отвечает по одному объявленному адресату. Издателя параметром Out берут, когда адресат определяется динамически или когда сообщение уходит сразу нескольким адресатам, в том числе в разные брокеры. В обоих случаях обработчик не видит неподключённого издателя: при регистрации вы указываете политику публикации, а она на старте инстанцирует издателя на подключённом брокере.

    Явная публикация - это всегда один и тот же билдер: он начинается с message(..) и заканчивается publish(). Публикуется значение объявленного типа, и способ передачи выбирает сам тип:

    message(&order)   -> кодек -> байты -> брокер    (значение Serialize кодируется)
message(&export)  ->          байты -> брокер    (значение Serialized выдаёт байты само)

    Байты, которые сервис уже держит закодированными, публикуются через newtype с выводом Serialized, и имя вносит их в сгенерированный документ. Тип сообщения объявляет, какие позиции остаются точке вызова: адресат, типизированные заголовки, кодек. Недоопределённая публикация не компилируется.

    Ответ из обработчика¶

    Тип ответа объявляют через #[derive(Outgoing)]. Атрибут #[outgoing(name = "..")] на типе - это адресат. Верните значение ответа и напишите publish у подписчика:

    examples/publishing.rs
    use ruststream::Outgoing;

// The reply type fixes its destination, so the clause names none.
#[derive(Debug, Serialize, Outgoing)]
#[outgoing(name = "receipts")]
struct Receipt {
    id: u64,
}

#[subscriber("receipt-requests", publish)]
async fn issue_receipt(req: &Request) -> Receipt {
    Receipt { id: req.id }
}
    examples/manual/publishing.rs
    // The reply type fixes its destination, so the chain names none.
#[derive(Debug, Serialize, schemars::JsonSchema)]
struct Receipt {
    id: u64,
}

impl OutgoingDestination for Receipt {
    type Form = FixedName;

    const DESTINATION: &'static str = "receipts";
}

impl MessageHeaders for Receipt {
    type Contract = NoHeaders;
}

struct IssueReceipt;

impl Handle<Request, Receipt> for IssueReceipt {
    fn handle(
        &self,
        req: &Request,
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<Receipt, HandlerOutcome>> {
        ready(Ok(Receipt { id: req.id }))
    }
}

    Тип ответа без объявленного имени берёт имя в точке монтирования: publish("responses") в атрибуте, .to("responses") в цепочке. Тип, который задаёт имя сам, публикуется по этому имени, и имя из точки монтирования к нему не применяется.

    examples/publishing.rs
    use ruststream::subscriber;

// A `publish(..)` handler that does not read the app state omits the `Context` parameter entirely;
// it stays generic over the state and mounts on an app with any state type.
#[subscriber("requests", publish("responses"))]
async fn respond(req: &Request) -> Response {
    println!("responding to request {}", req.id);
    Response { ok: true }
}
    examples/manual/publishing.rs
    // A replying handler is a body producing a reply: the reply type is the second axis of
// `Handle`, and the chain names the subscription, the destination and the publisher the reply
// leaves through.
struct Respond;

impl Handle<Request, Response> for Respond {
    fn handle(
        &self,
        req: &Request,
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<Response, HandlerOutcome>> {
        println!("responding to request {}", req.id);
        ready(Ok(Response { ok: true }))
    }
}

    Монтируется такой обработчик обычным include. Если больше ничего не сказано, ответ публикуется через политику публикации брокера по умолчанию и кодек по умолчанию. Вызов .out_reply(Publish) называет политику, которую экспортирует прелюдия брокера, а следующие шаги цепочки достраивают связывание ответа: .codec(..) задаёт кодек ответа, .transform(..) - статическое преобразование публикации, .transactional() - одну брокерскую транзакцию на пакет ответов. Кодек называют один раз: второй .codec(..) - ошибка компиляции.

    Определение обработчика не называет издателя: оно объявляет, чем обработчик отвечает и куда. Политика публикации принадлежит брокеру, поэтому её указывают там же, где брокер, - в точке монтирования, тем же вызовом .out(marker, policy), которым связывают слот Out. Reply - это маркер позиции, через которую публикуется возвращённое обработчиком значение, а Retry - маркер позиции, через которую уходит отложенная копия retry_after (см. отложенную повторную доставку). Для этих двух вызов записывают и короче: .out_reply(policy) - это .out(Reply, policy), а .out_retry(policy) - это .out(Retry, policy).

    examples/publishing.rs
    // the reply type carries the destination, so the mount site adds nothing to it
b.include(issue_receipt);
// static, per-reply: the chain names the policy and composes the transform at
// compile time; the runtime pairs it with the connected broker at startup
b.include(respond)
    .out_reply(Publish)
    .transform(EnvelopeTransform);
// the default reply wiring: the broker's default policy under the default codec
b.include(validate);
    examples/manual/publishing.rs
    // the reply type carries the destination, so the chain adds nothing to it
b.include(subscriber("receipt-requests", IssueReceipt).reply().build());
// static, per-reply: the chain names the policy and composes the transform at

b.include(

        .reply()
        .to("responses")
        .build(),
)

// the default reply wiring: the broker's default policy under the default codec

    subscriber("validated-requests", Validate)
        .reply()
        .to("responses")
        .build(),
);

    Входящий запрос декодируется кодеком области, заданным через with_broker_codec, иначе кодеком по умолчанию. Кодек ответа задаётся связыванием, которое построила цепочка. См. Кодеки.

    Оба способа отправки обслуживает один и тот же publish(..): выбор принадлежит типу ответа. Ответ с serde::Serialize кодируется, как выше. Ответ с #[derive(Serialized)] производит собственные байты и публикуется байт в байт, поэтому его .out_reply(..) берёт только политику: кодек на этом пути называть негде, и .codec(..) после него не компилируется. См. сырые подписчики.

    Управление подтверждением¶

    Простая форма ответа всегда публикует и делает ack. Чтобы взять управление на себя, возвращайте Result<Reply, HandlerOutcome>. Тогда Ok(reply) публикует и делает ack, а Err(outcome) не публикует ничего, и диспетчер действует по возвращённому HandlerOutcome (HandlerOutcome::drop() - отправить в dead-letter, HandlerOutcome::retry() - запросить повторную доставку):

    examples/publishing.rs
    // `Ok` publishes the reply and acks; `Err` publishes nothing and the dispatcher acts on the
// returned HandlerOutcome (here: drop the malformed request instead of replying).
#[subscriber("validated-requests", publish("responses"))]
async fn validate(req: &Request) -> Result<Response, HandlerOutcome> {
    if req.id == 0 {
        return Err(HandlerOutcome::drop());
    }
    Ok(Response { ok: true })
}
    examples/manual/publishing.rs
    // `Ok` publishes the reply and acks; `Err` publishes nothing and the dispatcher acts on the
// returned HandlerOutcome (here: drop the malformed request instead of replying).
struct Validate;

impl Handle<Request, Response> for Validate {
    fn handle(
        &self,
        req: &Request,
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<Response, HandlerOutcome>> {
        if req.id == 0 {
            return ready(Err(HandlerOutcome::drop()));
        }
        ready(Ok(Response { ok: true }))
    }
}

    Форма Result распознаётся по написанной сигнатуре, поэтому выпишите её явно: псевдоним типа, скрывающий Result, считается обычным типом ответа. Публикующий обработчик, как и любой другой, может объявить необязательный второй параметр &mut Context и прочитать состояние приложения или опубликовать что-то вручную.

    Если сама публикация ответа вернула ошибку (брокер отверг её, соединение потеряно), входящее сообщение получает nack с requeue = true, и брокер доставляет его повторно. Делайте публикующие обработчики идемпотентными относительно повторной доставки.

    Публикация изнутри обработчика¶

    Когда адресат определяется динамически или сообщение уходит сразу нескольким адресатам, в том числе в разные брокеры, принимайте издателя параметром обработчика через Out. Шаблон Out(out): Out<impl Publisher> связывает out с живым издателем внутри тела. Сигнатура называет только ту совместимость, которая обработчику нужна, а конкретный тип издателя выводится из политики, указанной в точке монтирования. Один и тот же обработчик без правок монтируется и на боевой брокер, и на его внутрипроцессный тестовый транспорт.

    examples/publishing.rs
    use ruststream::runtime::Out;

// The publisher arrives as a parameter (the Out marker): the source is attached at the include
// site, the runtime pairs it with the connected broker at startup, and the handler always holds
// a live publisher - no registry, no erased lookup, no state plumbing. `Event` declares no
// destination of its own, so the call site names one.
#[subscriber("ingress")]
async fn forward(event: &Event, Out(out): Out<impl Publisher>) -> HandlerOutcome {
    if out.message(event).to("egress").publish().await.is_err() {
        return HandlerOutcome::retry();
    }
    HandlerOutcome::ack()
}
    examples/manual/publishing.rs
    use ruststream::runtime::Out;

// The publisher arrives as an injection: the policy is attached at the include site, the runtime
// pairs it with the connected broker at startup, and the body always holds a live publisher - no
// registry, no erased lookup, no state plumbing. Nothing the mount site chose is named here: one
// parameter stands for the slot's entry, `OutEntry` ties it to the marker, and the body states
// only the capability it needs of the wired publisher - so the same body mounts on a production
// broker and its in-process test transport unchanged, and under a slot transform or an app-wide
// publish layer alike. `Event` declares no destination of its own, so the call site names one.
struct Forward;

impl<Egress> Handle<Event, (), Outs<(Egress,)>> for Forward
where
    Egress: OutEntry<DefaultSlot, Wire: Publisher>,
{
    async fn handle(
        &self,
        event: &Event,
        outs: &Outs<(Egress,)>,
        _ctx: &mut Context<'_>,
    ) -> Result<(), HandlerOutcome> {
        if outs
            .get(DefaultSlot)
            .message(event)
            .to("egress")
            .publish()
            .await
            .is_err()
        {
            return Err(HandlerOutcome::retry());
        }
        Ok(())
    }
}

    Вызов message(&value) публикует тем способом, который выбрал тип значения. Значение с serde::Serialize кодируется кодеком области; для одного вызова другой кодек называют через .with_codec(..). Значение с Serialized публикуется байт в байт и позиции для кодека не имеет. У обоих способов есть позиция заголовков: вызов .with_headers(..) принимает объявленный контракт сообщения по ссылке (&meta) или уже собранный HeaderMap по значению. Публикация заканчивается вызовом publish().

    Точка монтирования называет источник; для собственного брокера области это его политика публикации:

    examples/publishing.rs
    b.include(forward).out(DefaultSlot, Publish).build();
    examples/manual/publishing.rs
    b.include(subscriber("ingress", Forward).build())
    .out(DefaultSlot, Publish)
    .build();

    Несвязанный слот Out - это ошибка компиляции: регистрация не собирается, пока у каждого слота нет политики.

    Именованные слоты¶

    Обработчик, принимающий несколько издателей, называет на каждый параметр маркер слота: пустую структуру с выводом OutSlot, записанную вторым типовым аргументом (Out<impl Publisher, Primary>). Точка монтирования связывает каждый маркер вызовом .out(marker, policy) и фиксирует регистрацию завершающим .build(). Вызовы связывают по маркеру, поэтому их порядок неважен. Связать один и тот же слот дважды или назвать маркер, которого обработчик не объявлял, - ошибка компиляции. Сам .build() существует, только когда связаны все слоты, поэтому забытая привязка тоже не компилируется, и слот назван прямо в типе (MissingSlot<Audit>). Единственный безымянный параметр Out<impl Publisher> связывается с неявным DefaultSlot (.out(DefaultSlot, Publish).build()).

    Вызов .transform(..) после .out(..) относится к той позиции, которую назвал этот .out(..) (см. конвейер публикации), поэтому регистрация, которая и отвечает, и раздаёт копии, называет преобразование на каждой: .out_reply(Publish).transform(StampSource).out(Audit, Publish).transform(Envelope).

    examples/publishing.rs
    use ruststream::OutSlot;

// A handler with several injected publishers names a slot marker per parameter; the include
// site binds each marker to its own policy, in any order. No broker publisher type appears in
// the signature, so the same handler mounts on a production broker and on its in-process test
// transport unchanged. Each marker lists what may leave through it, which is both what the
// generated document reports and what the publish builder admits.
#[derive(OutSlot)]
#[publishes(Event)]
struct Primary;

#[derive(OutSlot)]
#[publishes(Event)]
struct Shadow;

#[subscriber("mirror")]
async fn mirror(
    event: &Event,
    Out(primary): Out<impl Publisher, Primary>,
    Out(shadow): Out<impl Publisher, Shadow>,
) -> HandlerOutcome {
    if primary
        .message(event)
        .to("mirror-primary")
        .publish()
        .await
        .is_err()
        || shadow
            .message(event)
            .to("mirror-shadow")
            .publish()
            .await
            .is_err()
    {
        return HandlerOutcome::retry();
    }
    HandlerOutcome::ack()
}
    examples/publishing.rs
    // each named slot binds by marker; the call order does not matter, and a
// .transform(..) rides the slot the .out(..) before it bound
b.include(mirror)
    .out(Shadow, Publish)
    .transform(OutboxEnvelope)
    .out(Primary, Publish)
    .build();
    examples/manual/publishing.rs
    use ruststream::OutSlot;

impl OutSlot for Primary {

struct Mirror;

impl<P, S> Handle<Event, (), Outs<(P, S)>> for Mirror

        event: &Event,
        outs: &Outs<(P, S)>,

            .message(event)
            .to("mirror-primary")
            .publish()
            .await
            .is_err()
            || outs
                .get(Shadow)
                .message(event)
                .to("mirror-shadow")
                .publish()
                .await

        }
        Ok(())
    }
}

b.include(subscriber("mirror", Mirror).build())

    Совместимость в ограничении можно уточнить: Out<impl OwnedTransactions, Ledger> скомпилируется только с политикой, живой издатель которой поддерживает владеющие транзакции. Ограничение проверяется в точке монтирования, и ошибка компиляции называет недостающую совместимость. Ограничение называет трейт брокерской совместимости - Publisher, TransactionalPublisher, OwnedTransactions, RequestReply или тот, что объявил крейт брокера, - а не тип брокера, поэтому тело не зависит от брокера. На ручном пути то же ограничение стоит на живом значении записи, where L: OutEntry<Ledger, Wire: OwnedTransactions>. Под каждым таким ограничением запись отдаёт типизированную форму этой совместимости (билдер публикации, область транзакции, владеющую транзакцию) поверх кодека точки монтирования и списка маркера. Маркер слота служит и тем именем, по которому тестовая обвязка записывает публикации.

    Необязательная третья позиция параметра Out объявляет, что именно публикует этот обработчик: Out<impl Publisher, Marker, (A, B)>, один тип или enum-набор с #[derive(OutMessages)]. Собственный список маркера #[publishes(A, B)] задаёт, что слоту разрешено публиковать, и для обработчика, оставившего третью позицию без ограничения, сгенерированный документ показывает именно его. Типизированная публикация типа, которого маркер не называет, - ошибка компиляции. Маркер, не перечисливший ничего, не публикует ничего: у каждой публикации есть тип сообщения, поэтому список распространяется на все публикации. У неявного DefaultSlot единственного безымянного Out<impl Publisher> нет места объявления, где перечислять типы, поэтому он допускает любое объявленное сообщение. См. типизированные заголовки.

    Тип с #[derive(Serialized)] публикуется в слот байт в байт, без кодека на пути. Всё остальное подчиняется обычным правилам: дайте типу #[derive(Outgoing)] и перечислите его в #[publishes(..)], как любую модель. Документ покажет его под собственным именем и без схемы нагрузки, потому что формат тут и есть сами байты. Адресат берётся из объявления, а словарь, объявленный набор сообщений и позиции заголовков проверяют такой тип так же, как кодируемую модель.

    Объявление адресата сообщения¶

    Тип сообщения объявляет всё, что касается его отправки, одним derive, и параметры записываются в форме key = value. Параметр name - это адресат, а headers называет тип контракта заголовков; сам контракт остаётся обычной serde-структурой, derive её не трогает:

    examples/publishing.rs
    use ruststream::Outgoing;

// What a message says about being sent lives on the type. A fixed name resolves the destination
// for every call site; a name template turns each `{placeholder}` into a setter, so a service
// routing per tenant still declares where the type goes; and the derive alone (like `Event`
// above) leaves the name to the call.
#[derive(Debug, Serialize, Outgoing)]
#[outgoing(name = "orders.confirmed")]
struct OrderConfirmed {
    id: u64,
}

#[derive(Debug, Serialize, Outgoing)]
#[outgoing(name = "orders.{tenant}.placed")]
struct OrderPlaced {
    id: u64,
}

#[derive(OutSlot)]
#[publishes(OrderConfirmed, OrderPlaced)]
struct Orders;

#[subscriber("orders.incoming")]
async fn route(
    event: &Event,
    Out(orders): Out<impl Publisher, Orders, (OrderConfirmed, OrderPlaced)>,
) -> HandlerOutcome {
    // Bound to one name: the destination is already resolved.
    if orders
        .message(&OrderConfirmed { id: event.id })
        .publish()
        .await
        .is_err()
    {
        return HandlerOutcome::retry();
    }
    // Bound to a space of names: one setter per placeholder, and no publish until the last one
    // is bound.
    if orders
        .message(&OrderPlaced { id: event.id })
        .to()
        .tenant("acme")
        .publish()
        .await
        .is_err()
    {
        return HandlerOutcome::retry();
    }
    HandlerOutcome::ack()
}

/// The `tenant` segment of the declared name, named in the compile error of a publish that never
/// bound it. The derive hides it (and the builder below) in a module named after the type; by
/// hand the only requirement is that the names do not collide.
#[derive(Debug, Clone, Copy)]
struct Tenant;

/// One publish whose templated address is being bound, segment by segment. The publish terminal
/// is callable once every placeholder is bound; until then the unbound ones ride in this type, so
/// the compile error names them.
#[must_use = "an address builder does nothing until publish() is awaited"]
struct PlacedAt<Cont, S0> {
    cont: Cont,
    segment_0: S0,
}

impl<Cont> PlacedAt<Cont, MissingSegment<Tenant>> {
    fn start(cont: Cont) -> Self {
        Self {
            cont,
            segment_0: MissingSegment::new(),
        }
    }

    /// Binds the `tenant` segment of the declared name.
    fn tenant(self, value: impl Display) -> PlacedAt<Cont, String> {
        PlacedAt {
            cont: self.cont,
            segment_0: value.to_string(),
        }
    }
}

impl<Cont, S0> PlacedAt<Cont, S0> {
    // Every bound, the segment witness included, sits on the method: on the impl block a publish
    // that forgot a segment reads as "method not found" and loses the guidance the bound carries.
    async fn publish(self) -> Result<(), PublishError<<Cont as PublishAt>::Error>>
    where
        Cont: PublishAt,
        S0: BoundSegment,
    {
        // A templated address is rendered per publish; the fixed form is not.
        let address = format!("orders.{}.placed", self.segment_0);
        PublishAt::publish_at(self.cont, &address).await
    }
}

impl<Cont> TemplateAddress<Cont> for OrderPlaced {
    type Builder = PlacedAt<Cont, MissingSegment<Tenant>>;

    fn begin(cont: Cont) -> Self::Builder {
        PlacedAt::start(cont)
    }
}

struct Orders;

impl OutSlot for Orders {
    const NAME: &'static str = "Orders";
    type Destination = Reads;

    fn outgoing() -> Vec<OutgoingMessageMetadata> {
        let mut declared = <OrderConfirmed as OutMessages<Self>>::outgoing();
        declared.extend(<OrderPlaced as OutMessages<Self>>::outgoing());
        declared
    }
}

impl PublishedThrough<Orders> for OrderPlaced {}

    Объявление решает, какая позиция адресата остаётся точке вызова:

    • Фиксированное имя задаёт адресата, поэтому писать to(..) негде: такой тип публикуется только по адресу из объявления.
    • Шаблон имени ("orders.{tenant}.placed") открывает to(), который возвращает билдер с одним сеттером на каждую подстановку. Вызов publish() компилируется, только когда связаны все подстановки, а несвязанная остаётся прямо в типе билдера, поэтому ошибка компиляции сообщает, что адрес не достроен, и называет забытый сегмент. Адрес собирается заново на каждую публикацию, а фиксированное имя публикация берёт из &'static str.
    • Отсутствие name означает, что имя называет точка вызова: .to("orders.archived") принимает &str или вычисленный String.

    Сообщение, объявившее headers = Meta, публикуется только через .with_headers(&meta): забытые заголовки или другой тип не компилируются. В сгенерированном документе фиксированное имя становится каналом сообщения, а шаблон - адресом с параметрами, блок которых заполняется из подстановок. Тип, не объявивший адресата, в документ не попадает.

    Публикуемым через билдер значение делает именно derive, включая третий случай. Тип с Serialize из чужого крейта вывести Outgoing не может: такое значение можно завернуть в newtype с выводом Outgoing или, внутри транзакции, опубликовать через publish(name, &value) у области.

    examples/publishing.rs
    // the slot lists what it may publish; where each message goes is its own declaration
b.include(route).out(Orders, Publish).build();
    examples/manual/publishing.rs
    // the slot lists what it may publish; where each message goes is its own declaration
b.include(subscriber("orders.incoming", Route).build())
    .out(Orders, Publish)
    .build();

    Параметр Out сочетается с любой формой подписчика: рядом с экстрактором Ctx, на обработчике, который десериализует вход сам, и на пакетных обработчиках (b.include(f).out(marker, policy).build() - на вход целый пакет, на выход адресаты на каждый элемент). В формах ответа, publish(..) и его пакетном аналоге, ответ становится ещё одной позицией той же цепочки. Поэтому шлюз называет обе позиции и одновременно отвечает по фиксированному адресату и рассылает побочные копии через внедрённого издателя:

    Публикация в другой брокер¶

    Когда обработчик потребляет из одного брокера, а публикует в другой (потребляет Kafka, пересылает в Redis), оберните целевой брокер вызовом .bindable() и выпустите связывающий токен ещё до регистрации. Дальше токен служит источником в точке монтирования. Форма одинакова для любой пары брокеров, здесь она показана на двух in-memory брокерах:

    .with_broker(other, |b| {
        let _ = b; // the target broker may mount its own handlers here
    })
    .with_broker(ingress_broker, |b| {
        b.include(crossing).out(DefaultSlot, to_other).build();
    });
    tests/manual_out_injection.rs
    let to_other = other.bind(Publish);

    .with_broker(other, |b| {

    Токены существуют до того, как отработает хоть один with_broker, поэтому порядок регистрации не имеет значения: двунаправленный мост связывает оба направления заранее.

    Токен делит слот с обёрткой Bindable, из которой он выпущен, поэтому регистрируйте ту же обёртку (with_broker(bindable, ..)), чтобы старт заполнил слот подключённым брокером. Токен, брокер которого так и не зарегистрировался, возвращает внятную ошибку сразу на связывании. Та же форма работает и для публикации ответов (.out_reply(token) на обработчике с publish("dest")), и для пакетных форм.

    Вне регистрации токен связывает себя сам, как только старт подключил его брокер: running.publisher(token) выдаёт соседней задаче живого издателя - см. Работа рядом с другим сервером. Для самой первой публикации на старте токен не нужен вовсе: b.after_startup(policy, hook) на уровне области запускает хук с уже связанным издателем, как только подписки открыты (см. Жизненный цикл). На нём выполняется и начальное заполнение данными в примере публикации.

    Откуда берутся заголовки¶

    Заголовки публикации складываются из двух источников. Место вызова задаёт их через .with_headers(..): объявленным контрактом сообщения по ссылке или готовым HeaderMap по значению. Издатель может добавить к ним собственную основу: в base_headers он хранит заголовки, одинаковые в каждом его сообщении (арендатор, имя продюсера, идентификатор схемы). Так же поступает и транзакция, открытая от этого издателя.

    Билдер собирает исходящие заголовки один раз: сначала основу, затем поверх неё, ключ за ключом, заголовки места вызова. Значение ключа определяется в следующем порядке:

    • ключ, названный в месте вызова, берёт значение оттуда;
    • ключ, которого место вызова не касается, берёт значение из основы издателя;
    • издатель без собственной основы оставляет заголовки места вызова ровно такими, как их написали.

    Обе формы сливаются одинаково: готовый HeaderMap дописывается запись за записью, а объявленный контракт headers = Meta сериализует свои поля поверх основы, поэтому сообщение с контрактом получает и основу издателя.

    .with_headers(..) заполняется однажды: второй вызов - ошибка компиляции.

    Ответ собирается так же, хотя .with_headers(..) на нём не пишут: издатель, созданный политикой, которую точка монтирования назвала для позиции Reply, кладёт свою основу первой, а шаги .transform(..) той же цепочки пишут поверх неё. Поэтому заголовок из основы издателя оказывается и в ответе обработчика publish("dest"), и в каждом ответе пакета, и в том, что тело отправляет через слот Out, - обработчик о нём не знает.

    Брокер позволяет одному сообщению отличаться от следующего не только полезной нагрузкой: QoS, приоритет, ключ упорядочивания, срок жизни. Это собственные настройки брокера, а не заголовки, и в публикацию они приходят из двух мест.

    Одно место - политика публикации: умолчания вы задаёте в точке монтирования, и каждое сообщение через этот слот уходит с ними:

}

    Остальное в публикации по-прежнему принадлежит точке монтирования: кодек, который назвала запись, её преобразования и слот, на который обвязка запишет отправку. Шаги есть на любой поверхности публикации - на слоте Out, на транзакции, открытой от него, на обычном издателе из состояния приложения или из стартового хука.

    В тесте вы можете прочитать настройки, с которыми ушла публикация через слот Out, включая те, что брокер превращает в поле протокола, а не в заголовок: см. проверки слотов Out.

    Тело, которое меняет настройку, импортирует прелюдию этого брокера ради шага и называет тип настроек брокера в ограничении (Out<impl Publisher<Options = MqttOptions>, Telemetry>). Это единственное место, где тело обработчика импортирует что-то помимо прелюдии фреймворка, и сигнатура тогда называет брокер, к которому привязан обработчик. Какие шаги существуют - отвечает документация вашего брокера.

    Конвейер публикации¶

    Опубликованное сообщение проходит два уровня, прежде чем покинуть процесс, и они сочетаются:

    • Статический PublishTransform на одной позиции, добавляемый через .transform(..) сразу после того .out(..), который эту позицию назвал. Zero-cost преобразования на конкретного адресата: конверт, фиксированный content type, trace / correlation id доставки в ответе, конверт outbox или метка арендатора на слоте. Они выполняются ближе всего к значению, до общего для приложения конвейера.
    • Статический PublishLayer на приложении, добавляемый через .publish_layer(..). Сквозная функциональность (метрики публикации, обёртка dead-letter), применяемая к каждому опубликованному сообщению вокруг самой отправки, чтобы видеть её результат. Цепочка складывается в конкретный тип и становится частью типа приложения: билдер обычно возвращает impl App и никогда его не выписывает, а конкретный RustStream<L, St, PublishStack<MyMiddleware, PublishIdentity>> показывает конвейер прямо в записи типа; приложение без publish_layer сохраняет умолчание PublishIdentity. Каждый middleware обязан быть Clone (конвейер клонируется в каждый публикующий обработчик), а добавленный последним выполняется самым внешним. Умолчание (middleware нет) - это прямая отправка. Набор middleware, который определяется во время работы, можно завернуть в PublishDynStack (публикующий аналог DynStack) и добавить уже его.

    Что преобразование объявляет¶

    Преобразование объявляет три вещи: что оно читает, что оно пишет и что ему разрешено делать с адресатом.

    Преобразование читает вид контекста этой позиции - тот самый K в apply(&mut Outgoing<'_>, &mut Option<Options>, &K::View<'_>), который выбирает точка монтирования:

    позиция вид что читает преобразование
    ответ, после .out_reply(..) ForReply<C> PublishContext<'_, C>: доставка, на которую отвечают
    слот Out, после .out(marker, policy) ForSlot SlotContext<'_>: имя самого слота

    Пишет преобразование Options - настройки брокера на сообщение. Преобразование, которое ни одной из них не касается, обобщено по этому типу и монтируется над издателем любого брокера; преобразование, которое настройку задаёт, называет тип своего брокера и монтируется только над издателем этого брокера.

    Разрешённое задаёт type Destination: Reads для преобразования, которое адресата не трогает, и Names для того, которое его задаёт. Эту строку пишет каждая реализация, и почти каждая пишет Reads.

    Преобразование, которое ничего не читает и ничего не пишет, обходится одной реализацией на все виды и все типы настроек и монтируется на любой позиции:

    examples/publishing.rs
    /// A static, per-publisher transform: stamps an envelope header on every outgoing message. It
/// reads no context, so one impl serves every position - a reply and an `Out` slot alike.
struct EnvelopeTransform;

impl<K: ContextKind, Options> PublishTransform<K, Options> for EnvelopeTransform {
    type Destination = Reads;

    fn apply(&self, out: &mut Outgoing<'_>, _options: &mut Option<Options>, _cx: &K::View<'_>) {
        out.headers_mut().insert("x-envelope", b"1".to_vec());
    }
}

    ForReply даёт доступ только на чтение к доставке, породившей ответ: к её каналу, входящим заголовкам и типизированному контексту брокера на одну доставку, читаемому по ключу Field. Поэтому преобразование может перенести значение из входящего сообщения в ответ. Этот вид задаёт и место преобразования: смонтировать его на слоте - ошибка компиляции в точке монтирования.

    ForSlot отдаёт имя слота и больше ничего. Публикацию в слот делает само тело обработчика, поэтому оно может прочитать свой Context и положить в сообщение всё нужное из доставки.

    examples/publishing.rs
    /// A static, per-slot transform: it stamps what leaves one `Out` slot. A slot position hands its
/// transforms a `SlotContext`, which names the slot and nothing else: the body issues a slot
/// publish itself, so the delivery is the body's own to read and put on the message.
struct OutboxEnvelope;

impl<K: ContextKind, Options> PublishTransform<K, Options> for OutboxEnvelope {
    type Destination = Reads;

    fn apply(&self, out: &mut Outgoing<'_>, _options: &mut Option<Options>, _cx: &K::View<'_>) {
        out.headers_mut().insert("x-outbox", b"1".to_vec());
    }
}

    Названный тип настроек брокера закрепляет место преобразования так же, как названный вид:

    tests/publish_options.rs
    /// A transform that writes this broker's per-message settings. It names the options type, so it
/// mounts over this broker's publisher and nowhere else; the position it reads is still free, so
/// it goes on a reply and on a slot alike.
struct Expedite;

impl<K: ContextKind> PublishTransform<K, PriorityOptions> for Expedite {
    type Destination = Reads;

    fn apply(
        &self,
        _out: &mut Outgoing<'_>,
        options: &mut Option<PriorityOptions>,
        _cx: &K::View<'_>,
    ) {
        options.get_or_insert_with(PriorityOptions::default).ttl = Some(2);
    }
}

    На слоте позиция настроек начинается с копии того, что задали шаги места вызова, поэтому преобразование этот вызов дополняет: оно заполняет настройку, которую вызов не тронул, и перекрывает ту, которую вызов назвал. У ответа места вызова нет, поэтому там настройки задаёт только преобразование.

    Ответы пакетного обработчика идут мимо стека .transform(..), который работает на каждое сообщение. Преобразование для них добавляют через .batch_transform(..), а PublishTransform, написанный на одно сообщение, переиспользуют через for_batch(transform).

    Ответы проходят через преобразование по одному, но PublishContext у них общий, и относится он к пакету, а не к доставке: пакет охватывает много доставок, поэтому name() - это подписка, headers() пуст, а context(..) читает пакетный контекст брокера. Преобразованию, которое читает входящее сообщение, место на пути одного сообщения, где ответ и его доставка - одно и то же.

    Как преобразование задаёт адресата¶

    Адресат сообщения объявлен: на типе сообщения через #[outgoing(name = "..")], в точке монтирования через publish("dest") или в месте вызова слота через .to(..). У некоторых ответов объявлять нечего. В запросе AMQP очередь для ответа указана в заголовке reply-to, а ROUTER в ZeroMQ адресует каждый ответ тому участнику, который спросил.

    Преобразование с Destination = Names задаёт имя само:

    examples/publishing.rs
    /// A transform declaring `Names`: it sets the destination, so it mounts only where the position
/// offers that right. This one answers where the request asked to be answered, and leaves the name
/// alone for a request that asked for nothing - which is when the mount site's own destination
/// stands.
struct ReplyTo;

impl<C, Options> PublishTransform<ForReply<C>, Options> for ReplyTo {
    type Destination = Names;

    fn apply(
        &self,
        out: &mut Outgoing<'_>,
        _options: &mut Option<Options>,
        cx: &PublishContext<'_, C>,
    ) {
        if let Some(to) = cx.headers().get("reply-to")
            && let Ok(to) = std::str::from_utf8(to)
        {
            out.set_name(to.to_owned());
        }
    }
}

/// `Response` declares no destination, so this position offers the naming right; the clause's
/// `"answers"` is the fallback and what the generated document reports.
#[subscriber("asks", publish("answers"))]
async fn answer(req: &Request) -> Response {
    println!("answering ask {}", req.id);
    Response { ok: true }
}

    На цепочку его добавляют как любое другое:

    examples/publishing.rs
    // `Response` leaves its destination open, so this position offers the naming right and
// `ReplyTo` may take it; the steps run in the order written
b.include(answer).out_reply(Publish).transform(ReplyTo);

    Позиция даёт это право только там, где адресат не объявлен, а в остальных случаях вызов .transform(..) не компилируется. Тип ответа с #[outgoing(name = "receipts")] права не даёт, и ошибка компиляции называет этот тип. Ответы пакета права тоже не дают: пакет отвечает многим доставкам сразу, и ни одна из них не говорит, куда уходит ответ. Право выдаётся один раз, поэтому второе задающее преобразование на той же позиции не компилируется.

    publish("answers") в точке монтирования остаётся объявленным адресатом ответа. Это имя попадает в сгенерированный документ, и туда же уходит ответ, если преобразование имя не изменило.

    Слот даёт это право только тогда, когда каждый тип в списке #[publishes(..)] его маркера оставляет адресата открытым. Тело по-прежнему пишет .to(..) на каждой публикации, а задающее преобразование переписывает это имя. Маркер без списка допускает любое объявленное сообщение, в том числе те, что задают адресата сами, поэтому права он не даёт никогда. Неявный DefaultSlot одиночного безымянного Out<impl Publisher> - один из таких маркеров. Отзывается только право задавать адресата: обычное преобразование такой слот принимает как любой другой.

    Слот, отдавший право, даёт только обычную отправку: транзакция и цикл запрос / ответ доходят до брокера мимо пути публикации слота, поэтому обработчик, который просит любую из них, не компилируется.

    PublishLayer реализует сигнатуру вида around/next, поэтому он может прервать цепочку, повторить отправку или просто наблюдать:

    examples/publishing.rs
    /// A static, app-wide publish layer: observes every publish, then passes it on.
#[derive(Clone)]
struct AuditPublish;

impl PublishLayer for AuditPublish {
    async fn on_publish<'a, N: PublishPipeline, P: Publisher>(
        &'a self,
        out: &'a mut Outgoing<'a>,
        next: PublishNext<'a, N, P>,
    ) -> Result<(), Box<dyn Error + Send + Sync>> {
        println!("publishing to {}", out.name());
        next.run(out).await
    }
}

    Преобразования точки монтирования действуют там, где их назвали: .out_reply(Publish).transform(StampSource) наращивает стек ответа, .out(Audit, Publish).transform(OutboxEnvelope) - стек этого слота. Регистрация с обеими сторонами пишет оба вызова, а .transform(..) относится к позиции, названной перед ним. В конвейере первыми выполняются преобразования позиции, в том порядке, в каком их написала цепочка, затем общий для приложения middleware, затем отправка.

    Мимо конвейера идут две публикации, и обе обработчик ведёт сам: транзакция, открытая на слоте (begin(), transaction()), отправляет внутрь транзакции брокера, а обмен request / reply (request(..)) ждёт ответа вместо того, чтобы завершиться отправкой.

    На слотах роутера работают только собственные преобразования, но не общая для приложения цепочка: include_router монтирует маршруты, типы которых сложились раньше самого приложения. Обработчик, публикации которого из слота должны пройти эту цепочку, монтируют на области брокера через b.include(..). Полная программа - examples/publishing.rs.

    Пакетные ответы и транзакции¶

    Обработчик #[subscriber("in", publish("out"))], принимающий &[T], потребляет целый декодированный пакет и возвращает ответы на него - шаблон consume-transform-produce. Ok(replies) публикует каждый ответ объявленному адресату и делает ack всего пакета; Err(outcome) не публикует ничего и завершает доставку всего пакета значением outcome (всё или ничего: выборочные исходы на каждый элемент с транзакцией не сочетаются):

    examples/publishing.rs
    /// Confirms a whole batch of orders; the replies become visible atomically on commit.
#[subscriber("orders", publish("confirmations"))]
async fn confirm(orders: &[Event]) -> Result<Vec<Event>, HandlerOutcome> {
    if orders.is_empty() {
        return Err(HandlerOutcome::drop()); // nothing published, whole batch settled
    }
    Ok(orders.iter().map(|o| Event { id: o.id }).collect())
}
    examples/manual/publishing.rs
    /// Confirms a whole batch of orders; the replies become visible atomically on commit. The batch
/// input and the reply type are two axes of the one trait: one `Vec` of replies per batch, each
/// published to the destination the chain names, and an `Err` settles the batch element-wise
/// (one outcome per element) without publishing anything.
struct Confirm;

impl Handle<[Event], Vec<Event>> for Confirm {
    fn handle(
        &self,
        orders: &[Event],
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<Vec<Event>, Vec<HandlerOutcome>>> {
        if orders.iter().any(|o| o.id == 0) {
            // nothing published, every element of the batch settled on its own
            return ready(Err(orders.iter().map(|_| HandlerOutcome::drop()).collect()));
        }
        ready(Ok(orders.iter().map(|o| Event { id: o.id }).collect()))
    }
}

    Без .transactional() каждый ответ публикуется независимо. Сбой в середине пакета отправляет на повтор весь пакет, поэтому при повторной доставке ранее опубликованные ответы могут уйти ещё раз (at-least-once).

    Шаг .transactional() после .out_reply(..) переводит связывание на одну транзакцию брокера на пакет: рантайм начинает транзакцию, публикует все ответы, фиксирует её и только потом делает ack входящего пакета. Любой сбой откатывает транзакцию, поэтому ответы никогда не бывают видны наполовину.

    Смонтировать такое связывание можно только с политикой, живой издатель которой транзакционен, поэтому с брокером без транзакций программа не скомпилируется. В ответе на одно сообщение нет пакета, который нужно сделать атомарным, поэтому .transactional() есть только на пакетных формах.

    Ручные транзакции¶

    Вне пути пакетных ответов транзакцией управляют вручную: begin() на любом транзакционном издателе открывает TransactionScope, который владеет транзакцией. Публикации идут через эту область, а commit() / abort() её поглощают, поэтому фиксация без начатой транзакции, вторая фиксация или публикация после завершения - ошибки компиляции, а не сюрпризы во время работы:

    examples/publishing.rs
    /// Seeds the reference events inside one broker transaction: both records become visible
/// together on commit, or not at all. The scope owns the transaction, so a commit without a
/// begin, a second commit, or a publish after settling do not compile. The publisher arrives
/// already paired (the scope's `after_startup` hands it over live), so seeding cannot race the
/// broker connect; the bound names the capability the seeding needs, not the broker's publisher.
async fn seed_events<P>(seeder: P) -> Result<(), Box<dyn Error + Send + Sync>>
where
    P: TransactionalPublisher,
{
    let scope = seeder.begin().await?;
    scope
        .message(&Event { id: 1 })
        .to("events")
        .publish()
        .await?;
    scope
        .message(&Event { id: 2 })
        .to("events")
        .publish()
        .await?;
    scope.commit().await?;
    Ok(())
}

    У области тот же билдер, что и у любой другой поверхности (scope.message(&value).publish()), но отправляет он в открытую транзакцию, а не прямо брокеру. Значения область кодирует кодеком издателя и отправляет напрямую: преобразования на конкретного издателя и общий для приложения middleware publish_layer принадлежат пути диспетчеризации (они читают породившую доставку) и здесь не выполняются. Область, уничтоженная незавершённой, пишет предупреждение в лог и оставляет транзакцию брокера на этом дескрипторе открытой - завершайте её явно.

    Слот Out открывает ту же область: ограничьте слот через Out<impl TransactionalPublisher, Journal> (на ручном пути - where W: TransactionalPublisher), и begin() на записи вернёт область, которую ведут ровно как выше.

    Область, открытая на слоте, принимает то же, что и собственный message слота: список маркера, суженный объявленным набором параметра. Поэтому транзакция не опубликует того, чего сгенерированный документ не объявлял, а её публикации в тестовой обвязке записываются на слот.

    Область - это заимствующая разновидность транзакции: она занимает единственную транзакцию дескриптора на стороне брокера, поэтому на одном дескрипторе в каждый момент открыта одна область.

    Брокеры, у которых транзакция - это буфер клиента, а не состояние продюсера, реализуют ещё и владеющую разновидность, OwnedTransactions: каждый вызов открывает независимую транзакцию с буфером внутри возвращённого TypedTransaction, поэтому один дескриптор держит сколько угодно транзакций сразу, и завершение одной никогда не задевает другую. message(..).publish() буферизует в это значение, а commit() / abort() его поглощают - та же дисциплина «завершение через поглощение», что и у области, - тогда как уничтоженное значение просто выбрасывает свой буфер (с предупреждением) и не оставляет транзакцию брокера открытой. Брокеры вроде Kafka, где клиент держит ровно одну транзакцию на продюсера, реализуют только заимствующую разновидность.

    Владеющая разновидность на обеих поверхностях читается одинаково: у издателя, который буферизует транзакции на стороне клиента, есть owned_transaction(), а у слота с ограничением Out<impl OwnedTransactions, Ledger> - transaction(). Оба вызова открывают TypedTransaction, который владеет транзакцией брокера и кодирует кодеком поверхности: let mut txn = publisher.owned_transaction().await?;, затем txn.message(&value).publish().await?; и txn.commit().await?;. Там, где begin() даёт заимствующую область (по одной на дескриптор), один издатель держит сколько угодно TypedTransaction сразу. Буфер владеющей транзакции завершается вне слота, поэтому её публикации попадают в журнал публикаций брокера, а не записываются на слот.

    Пакетная публикация¶

    Много сообщений публикуйте в цикле: у большинства брокеров (NATS, Kafka) клиент сам объединяет записи, поэтому цикл даёт ту же пропускную способность, что и отдельный пакетный вызов. Там, где у брокера есть настоящий примитив конвейеризации (Redis), его крейт отдаёт этот примитив как совместимость, специфичную для брокера.
