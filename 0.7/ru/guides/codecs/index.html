    Кодеки и сериализация¶

    Нормативная версия документации - английская

    Эта страница переведена с английского. При любом расхождении верен английский оригинал.

    Кодек превращает байты из сети в вашу типизированную полезную нагрузку и обратно. Это отдельный шов, не связанный с брокером: на стороне потребления конвейер выглядит как байты -> Codec -> типизированная полезная нагрузка -> обработчик, а на стороне публикации тот же путь проходится в обратном порядке. Кодек фиксируется в точке монтирования обработчика, поэтому на пути доставки он ничего не стоит.

    Встроенные кодеки¶

    Кодек Фича Подключает Формат передачи
    JsonCodec json (по умолчанию) serde_json JSON
    MsgpackCodec msgpack rmp-serde MessagePack
    CborCodec cbor ciborium CBOR

    Фичи кодеков строго аддитивны: включайте столько, сколько нужно. От типов сообщений требуется только вывести serde::Deserialize (и Serialize, если тип уходит в ответах).

    Кодек по умолчанию¶

    DefaultCodec - это псевдоним, выбираемый по фичам: json, если он включён, иначе cbor, иначе msgpack. Именно его берут include(def) и цепочка ответа, остановившаяся на .out(Reply, policy), когда кодек нигде не назван; ни тот, ни другая не принимают аргумент-кодек.

    Когда не включена ни одна фича кодека, кодировать и декодировать нечем, поэтому всё, чему потребовался бы кодек по умолчанию, оборачивается ошибкой компиляции - и она перечисляет выходы: включить фичу кодека, назвать кодек явно или перевести сообщение на байтовый путь обработки. Байтовым путям кодек не нужен никогда: вход Deserialized строит себя из байтов доставки, а значение Serialized производит свои байты само. Сервис, который говорит только на собственных форматах передачи, работает вообще без фичи кодека и ничего при этом не теряет.

    Двоичные протоколы - не кодеки¶

    Позиция кодека означает «значение, которое кодирует кодек, выбранный точкой монтирования». Сгенерированное сообщение Protobuf в эту позицию не встаёт: оно и есть своя кодировка и владеет раскладкой байтов от начала до конца. В позиции кодека одно монтирование отправило бы Order в JSON, а другое - в Protobuf; ровно эту путаницу байтовые пути и предотвращают. Поэтому двоичный протокол едет по байтовым путям, и между типом и проводом ничего не разрешается.

    Сгенерированный код не правят руками, но украшать то, что он выдаёт, умеет любой генератор. prost-build принимает message_attribute, поэтому весь рецепт - две строки конфигурации сборки:

    // build.rs
prost_build::Config::new()
    .message_attribute(".", "#[derive(ruststream::Serialized, ruststream::Deserialized)]")
    .message_attribute(".", "#[wire(prost)]")
    .compile_protos(&["proto/orders.proto"], &["proto"])?;

    Дальше каждое сообщение схемы приходит уже на путях, как будто его выписали руками. Вкладка «Вручную» - то же сообщение с раскрытыми деривами: два импла путей, выбранные ими способы передачи и декларация исходящего:

    examples/protobuf.rs
    #[derive(Clone, PartialEq, prost::Message, Outgoing, Serialized, Deserialized)]
#[outgoing(name = "orders")]
#[wire(prost)]
struct Order {
    #[prost(uint64, tag = "1")]
    id: u64,
    #[prost(string, tag = "2")]
    sku: String,
}
    examples/manual/protobuf.rs
    /// What `prost-build` emits from the schema. On the macro path a `message_attribute` line adds
/// `#[derive(Outgoing, Serialized, Deserialized)]` and `#[wire(prost)]` to it; here the impls
/// below take their place, and the struct is what the generator wrote and nothing more.
#[derive(Clone, PartialEq, prost::Message)]
struct Order {
    #[prost(uint64, tag = "1")]
    id: u64,
    #[prost(string, tag = "2")]
    sku: String,
}

// `#[derive(Serialized)]` under `#[wire(encode = ..)]`: the format's own encoder writes into the
// buffer the publish path already carries, and the value lends what it wrote - so the message is
// encoded once and nothing intermediate is allocated. The error is the format's, named here
// because a hand-written impl can see it (the derive cannot, and erases it instead).
impl Serialized for Order {
    type Error = prost::EncodeError;

    fn wire_bytes<'a>(&'a self, buf: &'a mut BytesMut) -> Result<&'a [u8], Self::Error> {
        prost::Message::encode(self, &mut *buf)?;
        Ok(&buf[..])
    }
}

// The two spellings that route the type onto the serialized wire. They carry no bytes of their
// own: what differs between a byte bag and a generated message is `wire_bytes`, not where the
// value may be used, so the derive writes these two the same way for both.
impl MessageWire for Order {
    type Wire = SerializedWire;
}

impl ReplyShape for Order {
    type Body = Self;
    type Headers = ();
    type Wire = SerializedReply;
}

// `#[derive(Deserialized)]` under `#[wire(decode = ..)]`, plus the `Input` spelling that routes
// `&Order` onto the self-deserializing lane. `Output<'a>` is `Self` because a generated message
// owns its fields; a zero-copy reader names its own borrowing view there instead.
impl Deserialized for Order {
    type Output<'a> = Self;
    type Error = prost::DecodeError;

    fn from_payload(payload: &[u8]) -> Result<Self, Self::Error> {
        prost::Message::decode(payload)
    }
}

impl Input for Order {
    type Axis = SoloDeserialized<Self>;
}

// `#[derive(Outgoing)]` with `#[outgoing(name = "orders")]`: where the type goes, what header
// contract it declares, and what it contributes to the generated document. `with_serialized`
// records the lane, which is what the derive's probe reports for a type carrying its own bytes.
impl OutgoingDestination for Order {
    type Form = FixedName;
    const ADDRESS: &'static str = "orders";
}

impl MessageHeaders for Order {
    type Contract = NoHeaders;
}

impl<M: OutSlot> OutMessages<M> for Order {
    fn outgoing() -> Vec<OutgoingMessageMetadata> {
        vec![
            OutgoingMessageMetadata::new(Self::ADDRESS, std::any::type_name::<Self>())
                .with_serialized(true),
        ]
    }
}

    Обработчик не называет кодек ни на входе, ни на выходе: для этого типа кодек не разрешается вовсе.

    examples/protobuf.rs
    #[subscriber("orders")]
async fn handle(order: &Order) -> HandlerOutcome {
    println!("order {} of {}", order.id, order.sku);
    HandlerOutcome::ack()
}
    examples/manual/protobuf.rs
    /// The definition value `#[subscriber("orders")]` would have minted. The body reads the model
/// type, not bytes: the lane decoded the payload with the message's own reader before the call.
struct Receive;

impl Handle<Order> for Receive {
    fn handle(
        &self,
        order: &Order,
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<(), HandlerOutcome>> {
        println!("order {} of {}", order.id, order.sku);
        ready(Ok(()))
    }
}

    #[wire(prost)] - сокращение для двух путей одного генератора. Общая форма называет функции сама: #[wire(encode = <path>, decode = <path>)], где encode - это fn(&Self, &mut BytesMut), возвращающая либо ничего, либо Result, а decode - fn(&[u8]) -> Result<Self, E>. Cap'n Proto, FlatBuffers и самодельный кадр едут по тому же механизму, и отдельная фича cargo на каждый формат не нужна: этот крейт вызывает то, что назвал атрибут, и ни от одного из них не зависит, а сервис зависит от того, который использует. Формат, который не укладывается ни в одну из этих форм, пишется так же, как вкладка «Вручную» пишет этот: wire_bytes и from_payload - методы публичных трейтов, поэтому весь путь доступен вообще без фичи macros.

    Тип модели остаётся виден там, где это важно. Его называет точка монтирования, его перечисляет словарь слота Out, о нём сообщает сгенерированный документ AsyncAPI - и все три поверхности newtype с заранее закодированными байтами прячет за мешком байтов. Эти сервисы - examples/protobuf.rs и examples/manual/protobuf.rs.

    Откуда берётся кодек декодирования¶

    Кодек декодирования фиксируется во время компиляции. include не принимает кодек аргументом: он разрешает его по самому конкретному уровню, на котором вы кодек задали, от самого узкого к самому широкому.

    На один обработчик¶

    Переопределить одно монтирование:

    router.with_codec(CborCodec).include(handle);

    examples/codecs.rs
    // name the codec for this one handler by mounting it through a router
b.include_router(Router::new().with_codec(JsonCodec).include(handle));
    examples/manual/codecs.rs
    // one handler on a codec of its own: the override sits on the definition, so no
// router is needed to keep the choice from reaching the neighbours
b.include(subscriber("orders", Receive).codec(JsonCodec).build());

    На область¶

    Задать один кодек для всех обработчиков в области with_broker:

    examples/codecs.rs
    use ruststream::codec::CborCodec;

RustStream::new(info)
    .with_broker_codec(MemoryBroker::new(), CborCodec, |b| {
        b.include(handle); // decodes with CborCodec
        b.include(audit); // also CborCodec
    })
    examples/manual/codecs.rs
    use ruststream::codec::CborCodec;

// Every subscription in the scope decodes with CBOR: the scope codec is the default the
// `include` family reads off the mount site, so no registration repeats it.
RustStream::new(info)
    .with_broker_codec(MemoryBroker::new(), CborCodec, |b| {
        b.include(subscriber("orders", Receive).build());
        b.include(subscriber("audit", Audit).build());
    })

    По умолчанию¶

    Когда ни один из уровней выше кодек не назвал, include берёт DefaultCodec.

    Сторона публикации¶

    Издатели подчиняются тем же правилам: .out(Reply, policy) кодирует ответы кодеком по умолчанию, а .out(Reply, policy).codec(codec) называет кодек явно - как и .out(marker, policy).codec(codec) для одного слота Out. Декодирование входящего запроса следует области (кодек области, заданный через with_broker_codec, или Router::with_codec цепочки роутера, иначе кодек по умолчанию), а кодек ответа едет на связывании, которое построила цепочка, - так что форматы запроса и ответа спокойно расходятся.

    Кодек - свойство монтирования, а не типа сообщения: один и тот же тип декодируется как JSON на одной подписке и как CBOR на другой, а точка монтирования - единственное место, где это сказано.

    Ошибки декодирования¶

    Когда декодирование не удалось, судьбу сообщения решает политика отказа; по умолчанию сообщение отбрасывается (nack без возврата в очередь). Политика задаётся для каждого подписчика клаузой on_failure(decode = ..):

    examples/codecs.rs
    use ruststream::subscriber;

/// A payload that fails to decode is redelivered instead of dropped.
#[subscriber("orders", on_failure(decode = retry))]
async fn strict(order: &Order) -> HandlerOutcome {
    println!("strictly decoded order {}", order.id);
    HandlerOutcome::ack()
}
    examples/manual/codecs.rs
    // A payload that fails to decode is redelivered instead of dropped. The policy is a
// setting on the same chain, the counterpart of `on_failure(decode = retry)` on the
// declaration.
b.include(
    subscriber("orders", Strict)
        .on_failure(FailurePolicies::default().with_decode(FailurePolicy::Retry))
        .build(),
);

    Значения политики (Drop, Retry, RetryAfter(..), Skip, FailFast), умолчания и оговорки про повторы описаны в разделе Политика отказов. Примеры с кодеками выше взяты из examples/codecs.rs.

    Свои кодеки¶

    Кодек - это любой тип, реализующий трейт Codec, поэтому можно подставить свой и передать его всюду, куда идёт встроенный кодек. Обобщите его по другому кодеку - и он станет составным: внутренний кодек задаёт формат полезной нагрузки, а обёртка только преобразует байты вокруг него. Кодек ниже обрамляет вывод внутреннего двухбайтовым заголовком с версией - ту же форму принимают и конверт для schema registry, и шифрующая обёртка.

    examples/custom_codec.rs
    /// The marker byte that says these bytes are an envelope at all.
const MAGIC: u8 = 0xE1;
/// The envelope layout this build writes, and the only one it reads.
const VERSION: u8 = 1;

/// A codec that frames another codec's output: `inner` decides the payload format, the envelope
/// only puts a versioned header in front of it.
///
/// The version is a constant on purpose. Resolving it against a schema registry would need async
/// I/O, and a codec is synchronous - that integration goes on the async edges instead.
#[derive(Debug, Clone, Copy, Default)]
struct Envelope<C> {
    inner: C,
}

impl<C> Envelope<C> {
    const fn new(inner: C) -> Self {
        Self { inner }
    }
}

impl<C: Codec> Codec for Envelope<C> {
    fn encode<T: Serialize>(&self, value: &T) -> Result<BytesMut, CodecError> {
        let payload = self.inner.encode(value)?;
        let mut framed = BytesMut::with_capacity(2 + payload.len());
        framed.extend_from_slice(&[MAGIC, VERSION]);
        framed.extend_from_slice(&payload);
        Ok(framed)
    }

    fn decode<T: DeserializeOwned>(&self, bytes: &[u8]) -> Result<T, CodecError> {
        // The inner codec's failure already is a `CodecError` and travels up with `?`; only the
        // envelope's own failures need wrapping, and they carry their own error type as the
        // source so the message names the layer that rejected the payload.
        let payload = open(bytes).map_err(|err| CodecError::Decode(Box::new(err)))?;
        self.inner.decode(payload)
    }
}

/// Strips the header, naming which of its two bytes was wrong.
fn open(bytes: &[u8]) -> Result<&[u8], EnvelopeError> {
    match bytes {
        [MAGIC, VERSION, payload @ ..] => Ok(payload),
        [MAGIC, version, ..] => Err(EnvelopeError::Version(*version)),
        [magic, _, ..] => Err(EnvelopeError::Magic(*magic)),
        _ => Err(EnvelopeError::Truncated(bytes.len())),
    }
}

/// What the envelope rejects on its own, as opposed to what the inner codec rejects.
#[derive(Debug, Error)]
enum EnvelopeError {
    #[error("too short to carry an envelope header: {0} byte(s)")]
    Truncated(usize),
    #[error("not an envelope: leading byte {0:#04x}")]
    Magic(u8),
    #[error("envelope version {0} is not the version this build reads")]
    Version(u8),
}

    Обе стороны обёртки сообщают об ошибках через CodecError. Сбой внутреннего кодека - это уже CodecError, и он уходит наверх через ? без изменений. Сбой самой обёртки становится CodecError::Decode (или CodecError::Encode) и несёт ваш собственный тип ошибки как источник, поэтому сообщение называет слой, отвергнувший полезную нагрузку, и причину: decode failed: not an envelope: leading byte 0x7b.

    Свой кодек монтируется на тех же трёх уровнях, что и встроенный, - здесь все три сразу, чтобы область, цепочка и ответ читались каждый своей строкой:

    examples/custom_codec.rs
    RustStream::new(info).with_broker_codec(
    MemoryBroker::new(),
    // per scope: every handler mounted here decodes through the envelope
    Envelope::new(JsonCodec),
    |b| {
        b.include(handle);
        // per chain: this router names its own codec for what it mounts
        b.include_router(
            Router::new()
                .with_codec(Envelope::new(CborCodec))
                .include(audit),
        );
        // per reply: the reply leaves under the envelope, the request still arrives under
        // the scope codec
        b.include(bill)
            .out(Reply, Publish)
            .codec(Envelope::new(JsonCodec));
    },
)
    examples/manual/custom_codec.rs
    RustStream::new(info).with_broker(MemoryBroker::new(), |b| {
    // per subscription: the codec is a step on the definition, so two handlers on one broker
    // frame their payloads differently without a scope or a router to separate them
    b.include(
        subscriber("orders", Receive)
            .codec(Envelope::new(JsonCodec))
            .build(),
    );
    b.include(
        subscriber("audit", Audit)
            .codec(Envelope::new(CborCodec))
            .build(),
    );
    // per publisher: the reply leaves under the envelope, the request still arrives under the
    // subscription's own codec. The in-memory broker hands out a live publisher synchronously;
    // a networked broker resolves one at startup instead, and the handler reads it off the
    // application state.
    let receipts = b.broker().publisher();
    b.include(
        subscriber(
            "billing",
            Bill {
                receipts,
                codec: Envelope::new(JsonCodec),
            },
        )
        .codec(Envelope::new(JsonCodec))
        .build(),
    );
})

    Синхронная граница¶

    Codec::encode и Codec::decode синхронны, и это задаёт границу того, что может находиться в кодеке: только то, что уже решают константа и байты под рукой, - как тег версии выше. Интеграция, которой для сериализации нужен ввод-вывод (разрешить идентификатор схемы в реестре, взять ключ из KMS), сюда не помещается, а блокирующий вызов внутри кодека останавливает задачу доставки.

    Место таких интеграций - асинхронные края: перекодируйте входящие полезные нагрузки на пути доставки подписки, до того как их увидит кодек, а исходящие обрамляйте через PublishLayer. Оба края асинхронны и умеют вернуть ошибку. Ту же границу со стороны брокера описывает раздел Авторам брокеров.
