    Типизированные заголовки¶

    Нормативная версия документации - английская

    Эта страница переведена с английского. При любом расхождении верен английский оригинал.

    Заголовки сообщения едут как нетипизированная карта name -> bytes, это HeaderMap. Когда приложение несёт в них настоящий контракт (идентификаторы, порядковые номера, итоговые счётчики), объявить этот контракт может одна структура - и она сразу питает три поверхности: извлечение в рантайме на стороне потребления, билдер публикации на стороне отправки и схему заголовков в сгенерированном AsyncAPI-документе.

    Контракт¶

    Контракт заголовков - это плоская структура: каждое поле называет заголовок, а значения - скаляры (числа, булевы значения, строки, сырые байты, перечисления без данных) или их Option. По проводу каждое значение передаётся строкой: фреймворк разбирает "3" в поле u32 и так же записывает его обратно, а схемы по-прежнему описывают логические типы.

    examples/typed_headers.rs
    #[derive(Serialize, Deserialize, JsonSchema)]
struct ChunkMeta {
    task_id: u64,
    chunk_no: u32,
    chunks_total: u32,
}

#[derive(Serialize, Deserialize, JsonSchema)]
struct DoneMeta {
    task_id: u64,
    duration_ms: u64,
}

    Имена полей - это имена на проводе; для имён, которые не годятся как идентификаторы Rust, используйте #[serde(rename = "x-task-id")]. Поле Option равно None, когда заголовка нет; отсутствие заголовка, объявленного не через Option, - нарушение контракта.

    Приём: экстрактор Headers¶

    Headers<T> - это параметр-экстрактор: рантайм разбирает заголовки доставки в T до того, как выполнится тело, поэтому обработчик начинает с проверенных типизированных значений. Нарушение (отсутствующий заголовок, неразбираемое значение) до тела не доходит: доставка завершается по политике on_failure(decode = ..) подписчика - той же, что покрывает не декодируемую полезную нагрузку (по умолчанию drop), - после WARN, называющего подписку и тип контракта.

    examples/typed_headers.rs
    /// The body keeps the chunk as bytes, so the input is a type of its own rather than a decoded
/// model: the derive gives the newtype the delivery's payload as it arrives.
#[derive(Deserialized)]
struct Chunk<'a>(&'a [u8]);

#[subscriber("chunks.raw")]
async fn convert(
    chunk: &Chunk<'_>,
    Headers(meta): Headers<ChunkMeta>,
    Out(events): Out<impl Publisher, Events, (ChunkDone, Progress)>,
) -> HandlerOutcome {
    let percent = u8::try_from(meta.chunk_no * 100 / meta.chunks_total.max(1)).unwrap_or(100);
    if events
        .message(&Progress { percent })
        .publish()
        .await
        .is_err()
    {
        return HandlerOutcome::retry();
    }

    let done = ChunkDone {
        output_key: format!("chunks/{}/{}.part", meta.task_id, meta.chunk_no),
    };
    let done_meta = DoneMeta {
        task_id: meta.task_id,
        duration_ms: chunk.0.len() as u64,
    };
    if events
        .message(&done)
        .with_headers(&done_meta)
        .publish()
        .await
        .is_err()
    {
        return HandlerOutcome::retry();
    }
    HandlerOutcome::ack()
}
    examples/manual/typed_headers.rs
    // The raw input type. What `#[derive(Deserialized)]` would write is these two impls: the
// construction, which borrows the delivery's bytes, and the `Input` spelling that routes
// `&Chunk<'_>` onto the self-deserializing lane.
struct Chunk<'a>(&'a [u8]);

impl Deserialized for Chunk<'_> {
    type Output<'a> = Chunk<'a>;
    type Error = Infallible;

    fn from_payload(payload: &[u8]) -> Result<Chunk<'_>, Self::Error> {
        Ok(Chunk(payload))
    }
}

impl Input for Chunk<'_> {
    type Axis = SoloDeserialized<Chunk<'static>>;
}

#[derive(Clone, Copy)]
struct Convert;

impl<'p, E> Handle<Chunk<'p>, (), Outs<(E,)>> for Convert
where
    E: OutEntry<Events, Wire: Publisher>,
{
    async fn handle(
        &self,
        chunk: &Chunk<'p>,
        outs: &Outs<(E,)>,
        ctx: &mut Context<'_>,
    ) -> Result<(), HandlerOutcome> {
        // Read the policy before the extraction takes the mutable borrow.
        let policy = ctx.decode_policy();
        let Headers(meta) = Headers::<ChunkMeta>::extract(&mut *ctx, policy)?;
        let events = outs.get(Events);

        let percent = u8::try_from(meta.chunk_no * 100 / meta.chunks_total.max(1)).unwrap_or(100);
        if events
            .message(&Progress { percent })
            .publish()
            .await
            .is_err()
        {
            return Err(HandlerOutcome::retry());
        }

        let done = ChunkDone {
            output_key: format!("chunks/{}/{}.part", meta.task_id, meta.chunk_no),
        };
        let done_meta = DoneMeta {
            task_id: meta.task_id,
            duration_ms: chunk.0.len() as u64,
        };
        if events
            .message(&done)
            .with_headers(&done_meta)
            .publish()
            .await
            .is_err()
        {
            return Err(HandlerOutcome::retry());
        }
        Ok(())
    }
}

    Headers сочетается с телом, которое десериализует себя само (&Frame<'_> рядом с его типизированными заголовками), и с любым другим экстрактором.

    В пакетном обработчике заголовки остаются своими у каждой доставки, поэтому пакет спаривает каждый элемент с его контрактом: вход - &[Message<H, T>], и element.headers лежит рядом с element.body. Соответствие гарантировано конструкцией: элемент, у которого не удалось получить полезную нагрузку или заголовки, завершается по той же политике on_failure(decode = ..) и до обработчика не доходит - ровно как на пути одиночного сообщения. Параметр Headers<..> здесь отвергается, а ошибка называет парный вход.

    examples/typed_headers.rs
    #[subscriber("chunks.bulk")]
async fn bulk(reports: &[Message<ChunkMeta, Progress>]) -> HandlerOutcome {
    for report in reports {
        let meta = &report.headers;
        println!(
            "task {}: chunk {} of {} at {}%",
            meta.task_id, meta.chunk_no, meta.chunks_total, report.body.percent,
        );
    }
    HandlerOutcome::ack()
}
    examples/manual/typed_headers.rs
    struct Bulk;

impl Handle<[Message<ChunkMeta, Progress>]> for Bulk {
    fn handle(
        &self,
        reports: &[Message<ChunkMeta, Progress>],
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<(), Vec<HandlerOutcome>>> {
        for report in reports {
            let meta = &report.headers;
            println!(
                "task {}: chunk {} of {} at {}%",
                meta.task_id, meta.chunk_no, meta.chunks_total, report.body.percent,
            );
        }
        ready(Ok(()))
    }
}

    Монтирование читается так же, как у любой другой формы, и на обеих поверхностях: b.include(bulk) в области брокера, Router::include на пути роутера. Тип контракта едет в оси входа, поэтому обычный пакетный маршрут декодирует его рядом с каждой полезной нагрузкой.

    Когда по одному каналу идут сообщения, у которых заголовки различаются в зависимости от вида события, стандартный экстрактор туда лучше не пускать: напишите свой на трейте [FromContext] - прочитайте заголовок-дискриминатор из нетипизированной карты ([HeaderMap::get_str]), а затем соберите тот контракт, которого требует этот вид. Объединение форм объявите на входном типе (см. следующий раздел), чтобы документ по-прежнему показывал контракт целиком.

    Объявление контракта на типе сообщения¶

    #[derive(Outgoing)] принимает headers = Meta рядом с адресатом: контракт становится частью типа. Билдер публикации после этого требует ровно эти заголовки, а AsyncAPI-документ рисует схему рядом с полезной нагрузкой везде, где встречается тип. Про половину с адресатом см. публикацию.

    examples/typed_headers.rs
    #[derive(Outgoing, Serialize, Deserialize, JsonSchema)]
#[outgoing(name = "chunks.done", headers = DoneMeta)]
struct ChunkDone {
    output_key: String,
}

#[derive(Outgoing, Serialize, Deserialize, JsonSchema)]
#[outgoing(name = "chunks.progress")]
struct Progress {
    percent: u8,
}
    examples/manual/typed_headers.rs
    #[derive(Serialize, Deserialize, JsonSchema)]
struct ChunkDone {
    output_key: String,
}

impl OutgoingDestination for ChunkDone {
    type Form = FixedName;
    const ADDRESS: &'static str = "chunks.done";
}

impl MessageHeaders for ChunkDone {
    type Contract = WithHeaders<DoneMeta>;
}

impl MessageInfo for ChunkDone {
    const NAME: &'static str = "ChunkDone";
}

impl ContainsMessage<Self, SlotPos<0>> for ChunkDone {}

impl<M: OutSlot> OutMessages<M> for ChunkDone {
    fn outgoing() -> Vec<OutgoingMessageMetadata> {
        vec![
            OutgoingMessageMetadata::new(Self::ADDRESS, type_name::<Self>())
                .with_message_name(Some(Self::NAME))
                .with_payload_schema(Some(schema_of::<Self>()))
                .with_headers_schema(Some(schema_of::<DoneMeta>())),
        ]
    }
}

#[derive(Serialize, Deserialize, JsonSchema)]
struct Progress {
    percent: u8,
}

impl OutgoingDestination for Progress {
    type Form = FixedName;
    const ADDRESS: &'static str = "chunks.progress";
}

// No `headers = ..` in the declaration: the publish builder demands no contract for this type.
impl MessageHeaders for Progress {
    type Contract = NoHeaders;
}

impl MessageInfo for Progress {
    const NAME: &'static str = "Progress";
}

impl ContainsMessage<Self, SlotPos<0>> for Progress {}

impl<M: OutSlot> OutMessages<M> for Progress {
    fn outgoing() -> Vec<OutgoingMessageMetadata> {
        vec![
            OutgoingMessageMetadata::new(Self::ADDRESS, type_name::<Self>())
                .with_message_name(Some(Self::NAME))
                .with_payload_schema(Some(schema_of::<Self>())),
        ]
    }
}

    Публикация: контракт в точке вызова¶

    Маркер слота Out перечисляет типы сообщений, которые слот вправе публиковать:

    examples/typed_headers.rs
    #[derive(OutSlot)]
#[publishes(ChunkDone, Progress)]
struct Events;
    examples/manual/typed_headers.rs
    struct Events;

impl OutSlot for Events {
    const NAME: &'static str = "Events";

    fn outgoing() -> Vec<OutgoingMessageMetadata> {
        let mut entries = <ChunkDone as OutMessages<Self>>::outgoing();
        entries.extend(<Progress as OutMessages<Self>>::outgoing());
        entries
    }
}

impl PublishedThrough<Events> for ChunkDone {}
impl PublishedThrough<Events> for Progress {}

    Необязательная третья позиция параметра Out объявляет набор сообщений, которые публикует этот обработчик:

    • Out<impl Publisher, Events> (или явный ()) - без ограничений: любое объявленное сообщение;
    • Out<impl Publisher, Events, (ChunkDone, Progress)> - список прямо на месте;
    • Out<impl Publisher, Events, ChunkDone> - один объявленный тип (тип с #[derive(Outgoing)] объявляет сам себя);
    • Out<impl Publisher, Events, ConvertSends> - перечисление с #[derive(OutMessages)], каждый вариант которого оборачивает одну модель: переиспользуемый именованный набор (само перечисление - декларация на уровне типов, его никогда не конструируют).

    Дальше тело публикует через билдер (обработчик выше), а компилятор следит за всей декларацией целиком:

    • message(..) с типом вне объявленного набора не компилируется: обработчик публикует то, что объявил, и ничего кроме;
    • тип, объявивший headers = Meta, публикуется только через .message(&value).with_headers(&meta): забыть заголовки или передать не тот их тип - ошибка компиляции;
    • адресат берётся из собственной декларации типа, поэтому фиксированное имя в точке вызова не требует ничего, а шаблонное требует свои подстановки;
    • позиция совместимости, как всегда, статически сверяется с политикой в точке монтирования: Out<impl TransactionalPublisher, Events, (ChunkDone, Progress)> требует политику, у которой живой издатель транзакционный, и объявленные публикации выполняются внутри области, которую открывает запись, под той же декларацией.

    Полезная нагрузка, которую сервис уже держит закодированной, или чужой тип, на который декларацию не повесить (голый Vec<Frame>), уходит в newtype, который выводит и Outgoing, и Serialized. Такой newtype - полноправный член словаря: адресата и заголовки он объявляет как любая модель и публикуется через ту же типизированную точку входа, out.message(&export), - способ отправки выбирает тип, поэтому байты уходят байт в байт, а позиции заголовков работают без изменений.

    Контракт заполняет эту позицию один раз. То, что добавляет сам издатель, подкладывается снизу: издатель, несущий один аргумент для каждого отправляемого сообщения, отдаёт его как основу, а поля контракта сериализуются поверх этой основы поле за полем; см. откуда берутся заголовки.

    Форма ответа¶

    Обработчику с publish("dest") дополнительная декларация не нужна: документ питается собственным контрактом типа ответа, а адресат уже указан в атрибуте.

    examples/typed_headers.rs
    #[derive(Deserialize, JsonSchema)]
struct StatusRequest {
    task_id: u64,
}

// The reply is sent where the `publish(..)` clause says, so the type declares no name of its
// own - only the contract that travels with it.
#[derive(Outgoing, Serialize, JsonSchema)]
#[outgoing(headers = DoneMeta)]
struct StatusReply {
    done: bool,
}

#[subscriber("jobs.status-requests", publish("jobs.status"))]
async fn status(req: &StatusRequest) -> StatusReply {
    StatusReply {
        done: req.task_id.is_multiple_of(2),
    }
}
    examples/manual/typed_headers.rs
    #[derive(Deserialize, JsonSchema)]
struct StatusRequest {
    task_id: u64,
}

// The reply is sent where `reply_name` says, so the type declares no name of its own - the
// `CallerName` form - only the contract that travels with it.
#[derive(Serialize, JsonSchema)]
struct StatusReply {
    done: bool,
}

impl OutgoingDestination for StatusReply {
    type Form = CallerName;
}

impl MessageHeaders for StatusReply {
    type Contract = WithHeaders<DoneMeta>;
}

impl MessageInfo for StatusReply {
    const NAME: &'static str = "StatusReply";
}

struct Status;

impl Handle<StatusRequest, StatusReply> for Status {
    fn handle(
        &self,
        req: &StatusRequest,
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<StatusReply, HandlerOutcome>> {
        ready(Ok(StatusReply {
            done: req.task_id.is_multiple_of(2),
        }))
    }
}

    В рантайме заголовки ответа остаются там же, где были: их выставляет PublishTransform на издателе ответа, а [HeaderMap::insert_typed] сериализует значение контракта в карту изнутри трансформа.

    Что показывает документ¶

    С фичей asyncapi build_spec рисует:

    • схему заголовков каждого принимаемого сообщения - из параметра Headers<T> обработчика или из контракта #[message(headers(..))] входного типа, когда обработчик извлекает заголовки вручную;
    • по операции send на каждое объявленное исходящее сообщение - ответ каждой формы publish(..) и каждый тип сообщения, объявленный слотом, - и у каждой из них свои схемы полезной нагрузки и заголовков.

    Схемы описывают логические типы полей (task_id: integer), тогда как на проводе значения - это строковые заголовки.

    Тестирование¶

    Внутрипроцессная обвязка прогоняет весь путь целиком: with_headers(&meta) на билдере вброса отправляет доставку с типизированным контрактом, а журнал публикаций показывает заголовки, которые породила типизированная публикация.

    examples/typed_headers.rs
    let meta = ChunkMeta {
    task_id: 7,
    chunk_no: 3,
    chunks_total: 12,
};
tb.broker::<MemoryBroker>()
    .message(&RawChunk(vec![0; 16]))
    .with_headers(&meta)
    .to("chunks.raw")
    .publish()
    .await?;

let done = tb
    .broker::<MemoryBroker>()
    .published::<ChunkDone>("chunks.done")
    .assert_called_once();
println!("published: {:?}", done.decoded()[0].output_key);
println!(
    "task_id header: {:?}",
    done.messages()[0].headers().get_str("task_id")
);
