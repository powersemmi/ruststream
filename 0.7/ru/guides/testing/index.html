    Тестирование¶

    Нормативная версия документации - английская

    Эта страница переведена с английского. При любом расхождении верен английский оригинал.

    Сервисы RustStream тестируются на двух уровнях:

    1. Внутрипроцессные юнит-тесты гоняют ваши настоящие обработчики, middleware и кодеки через обвязку TestApp: без сервера, без docker, без сети (connect у внутрипроцессного брокера не делает ввода-вывода). Это путь по умолчанию, и он покрывает логику обработчика от начала до конца: декодирование, диспетчеризацию, исход (ack / nack / drop / паника / ошибка декодирования) и все сообщения, которые публикует обработчик.
    2. Интеграционные тесты идут против настоящего брокера, включаются переменной окружения и покрывают семантику, которая есть только у настоящего сервера (durable-консьюмеры, таймеры повторной доставки, партиции).

    Что обвязка моделирует, а что нет

    Обвязка гоняет внутрипроцессный транспорт брокера: публикация разводит сообщение по подписчикам, у которых совпал субъект, прогоняет ваш обработчик по настоящему пути диспетчеризации и записывает исход вместе со всеми публикациями вниз по потоку. Она не моделирует durable-курсоры JetStream, повторную доставку по ack_wait, max_ack_pending, retention, офсеты и consumer-группы Kafka, обменники и dead-letter-маршрутизацию RabbitMQ. Это забота настоящего брокера; проверяйте это в интеграционном наборе.

    Что такое MemoryBroker и что он не заменяет, сказано на его собственной странице: брокер в памяти.

    Юнит-тестирование сервиса через TestApp¶

    TestApp берёт собранное приложение RustStream, подключает его брокеры (для внутрипроцессной шины это без ввода-вывода), монтирует обработчики и записывает каждую доставку. Вы публикуете вход, и публикация доводит всю реакцию (обработчик, его публикации вниз по потоку, любой каскад между брокерами) до полной остановки, прежде чем вернуть управление, - а дальше вы проверяете.

    Тестируемый обработчик (в настоящем сервисе он лежит в вашем модуле обработчиков, а тест его импортирует):

    tests/doc_testing_memory.rs
    use ruststream::prelude::*;
use serde::{Deserialize, Serialize};

#[derive(Debug, Deserialize, Outgoing, Serialize, PartialEq)]
struct Order {
    id: u64,
    quantity: u32,
}

#[derive(Debug, Deserialize, Serialize, PartialEq)]
struct Confirmation {
    id: u64,
    accepted: bool,
}

#[subscriber("orders", publish("confirmations"))]
async fn confirm(order: &Order) -> Confirmation {
    Confirmation {
        id: order.id,
        accepted: order.quantity > 0,
    }
}
    tests/manual_doc_testing_memory.rs
    use std::future::{Future, ready};

use ruststream::prelude::*;
use schemars::JsonSchema;
use serde::{Deserialize, Serialize};

#[derive(Debug, Deserialize, Serialize, PartialEq, JsonSchema)]
struct Order {
    id: u64,
    quantity: u32,
}

// `#[derive(Outgoing)]` with no `name`, by hand: the destination stays with the call site, which
// is what lets the test publish this type with `.to("orders")`.
impl OutgoingDestination for Order {
    type Form = CallerName;
}

impl MessageHeaders for Order {
    type Contract = NoHeaders;
}

#[derive(Debug, Deserialize, Serialize, PartialEq, JsonSchema)]
struct Confirmation {
    id: u64,
    accepted: bool,
}

/// The reply body without the attribute: the reply type sits in the `Handle` impl's second
/// position, and the subscription source and the reply destination are named where the definition
/// is built.
struct Confirm;

impl Handle<Order, Confirmation> for Confirm {
    fn handle(
        &self,
        order: &Order,
        _outs: &(),
        _ctx: &mut Context<'_>,
    ) -> impl Future<Output = Result<Confirmation, HandlerOutcome>> {
        ready(Ok(Confirmation {
            id: order.id,
            accepted: order.quantity > 0,
        }))
    }
}

    Сам тест:

    tests/doc_testing_memory.rs
    use ruststream::memory::prelude::*;
use ruststream::testing::TestApp;

#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
async fn confirms_valid_orders() {
    // The app under test: production wiring, in-memory broker.
    let app = RustStream::new(AppInfo::new("orders-test", "0.0.0")).with_broker(
        MemoryBroker::new(),
        |b| {
            b.include(confirm).out(Reply, Publish);
        },
    );

    // Start the harness (no connect, no server) and publish an order; the publish drives the
    // handler to a standstill before it returns.
    let tb = TestApp::start(app).await.expect("start harness");
    tb.broker::<MemoryBroker>()
        .message(&Order { id: 1, quantity: 2 })
        .to("orders")
        .publish()
        .await
        .expect("publish");

    // The handler decoded the order, acked, and published a confirmation.
    tb.broker::<MemoryBroker>()
        .subscriber("orders")
        .assert_called_once()
        .with(&Order { id: 1, quantity: 2 })
        .settled(HandlerOutcome::ack());
    tb.broker::<MemoryBroker>()
        .published::<Confirmation>("confirmations")
        .assert_called_once()
        .with(&Confirmation {
            id: 1,
            accepted: true,
        });
}

    Как адресовать брокеры¶

    tb.broker::<MemoryBroker>() адресует брокер по типу; tb.broker_named("ingress") - по метке из with_broker_labeled, когда сервис монтирует несколько брокеров и их субъекты пересекаются. Внеобластной tb.message(&value).to(name) - удобство для приложений с одним брокером: он сообщает TestError::Ambiguous, если зарегистрирован больше чем один брокер.

    Вход приходит через тот же билдер публикации, которым публикует сам сервис: message(&value) отправляет значение с #[derive(Outgoing)] тем способом, который выбрал его тип, with_headers(&meta) прикрепляет типизированный контракт заголовков, а to(name) называет субъект, когда тип значения его не объявляет. Байты, которые моделью не являются, - недекодируемая нагрузка для политики декодирования или вход обработчика, который десериализует байты сам, - едут через ту же точку входа в newtype с #[derive(Outgoing, Serialized)], поэтому тест называет то, что вбрасывает, а не роняет анонимные байты на субъект.

    Проверки обработчика¶

    tb.broker::<B>().subscriber(name) возвращает текучий билдер по тому, что получил этот обработчик:

    Метод Что проверяет
    assert_called_once() / assert_called(n) / assert_not_called() число вызовов
    with(&value) единственная доставка последнего вызова декодируется в value (кодеком по умолчанию)
    with_raw(bytes) единственная сырая нагрузка последнего вызова
    settled(HandlerOutcome::ack()) чем завершилось всё, что нёс последний вызов
    assert_batch_sizes(&[2, 1]) какие пакеты получило тело, в порядке прихода
    assert_outcome(Outcome::Drop) классифицированный исход (ack / nack / drop / ошибка декодирования / паника)
    panicked() обработчик упал в панику на последнем вызове
    assert_last_failed_to_decode() полезная нагрузка не декодировалась

    Считают эти проверки ВЫЗОВ обработчика, а не сообщение. Обработчик одиночных сообщений вызывается на каждую доставку, поэтому одно совпадает с другим; пакетный обработчик вызывается на пакет, поэтому assert_called_once() означает, что пришёл один пакет любого размера, settled(..) охватывает каждый его элемент, а received_raw() по-прежнему перечисляет элементы поштучно. Две проверки, называющие одну ожидаемую нагрузку (with, with_raw), сообщают размер пакета, а не молча проверяют один его элемент. Элемент, который политика декодирования отвергла до тела, эта политика и завершает: в пакете, который увидел обработчик, его нет.

    Пакет доходит до тела целиком - поэтому один пакет и есть один вызов. Где проходят границы пакетов, решает брокер в ответ на batch(n) точки монтирования, и assert_batch_sizes как раз это показывает: журнал из трёх записей, переигранный при batch(2), доходит до тела как [2, 1] - два вызова, потому что брокер собрал два пакета. Обработчик одиночных сообщений вызывается на каждую доставку, поэтому тот же прогон даёт [1, 1, 1].

    Как набрать пакет длиннее одного элемента

    tb.message(&value).publish() доводит всю реакцию до покоя прежде, чем вернуть управление, а успокоившаяся реакция закрывает пакет брокера, который собирает пакеты на клиенте. Поэтому вызовы по одному сообщению дают по пакету на сообщение, и в каждом ровно один элемент, какой бы размер ни назвала точка монтирования. Возьмите хендл продюсера у брокера до сборки приложения, опубликуйте через него всю серию (по пути ничего не успокаивается) и один раз доведите реакцию до покоя через tb.settle(). Брокера с нативной пакетной доставкой это не касается: там границу пакета определяет он сам.

    tb.broker::<B>().published::<T>(name) проверяет то, что обработчик опубликовал дальше, читая журнал публикаций брокера: .assert_called_once() / .assert_called(n) / .assert_not_called() фиксируют число публикаций, .with(&Receipt { id: 1 }) / .with_raw(bytes) - последнюю нагрузку, .with_header("x-app", b"1") - заголовок, который проставил на выходе middleware публикации или PublishTransform.

    Помимо готовых проверок, сами сообщения можно достать и проверить по-своему: subscriber(name).received::<T>() / .received_raw() отдают то, что получил обработчик, а published::<T>(name).decoded() / .messages() - каждое сообщение, опубликованное в канал; и то и другое по порядку.

    Ещё два представления сохраняют то, что теряет плоский список. subscriber(name).batches::<T>() / .batches_raw() группирует доставки по ВЫЗОВУ - один вложенный вектор на вызов, - поэтому тест фиксирует, как поток нарезан на пакеты; received::<T>() эту границу стирает. subscriber(name).outcomes() отдаёт классифицированный исход каждого вызова по порядку - с ним сравнивают последовательность передоставки (nack, затем ack на повторе), тогда как settled(..) и assert_outcome(..) читают только последний вызов.

    Декодирующие помощники (with, received, decoded) работают кодеком по умолчанию. Если обработчик или издатель смонтирован с другим кодеком (with_broker_codec, Router::with_codec), передайте его явно через варианты _with / with_codec - subscriber(name).with_codec(&CborCodec, &expected), .received_with(&CborCodec), published::<T>(name).with_codec(&CborCodec, &expected), .decoded_with(&CborCodec), - а with_raw / received_raw / messages кодека не касаются.

    Сообщение, которое сериализует себя само¶

    Между значением на байтовом пути и проводом не стоит ничего, а в каждой типизированной проверке выше стоит кодек: with(&value), received::<T>() и их варианты _with(codec) декодируют кодеком, а тип с Serialized / Deserialized кодек не разрешает вовсе. Тест на этом пути опирается на две проверки, кодека не касающиеся, - with_raw(bytes) для нагрузки и received_raw() для чтения доставки обратно, - а остальное даёт собственный формат типа:

    tests/self_serialising.rs
    /// Asserting on a value that serializes itself. The harness's typed assertions decode with a
/// codec, and this lane has none, so both ends of the test speak the type's own format: the
/// expected payload is the frame the writer produces, and a delivery is read back with the
/// reader the type already declares.
#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
async fn a_self_serialising_message_is_asserted_on_its_own_bytes() {
    let app =
        RustStream::new(AppInfo::new("wire", "0.1.0")).with_broker(MemoryBroker::new(), |b| {
            b.include(count);
        });
    let tb = TestApp::start(app).await.expect("harness start");

    tb.message(&Tick { seq: 9 })
        .publish()
        .await
        .expect("inject");

    let broker = tb.broker::<MemoryBroker>();
    let ticks = broker.subscriber("wire.ticks");
    // `from_payload` is the same reader the lane ran on the way in, so the test asserts on the
    // model type without a codec and without repeating the frame layout.
    let received = ticks.received_raw();
    let decoded = Tick::from_payload(&received[0]).expect("a tick frame");
    assert_eq!(decoded, Tick { seq: 9 });

    // The bytes themselves, where the wire format is what the test is pinning.
    ticks
        .assert_called_once()
        .with_raw(&[0, 0, 0, 9])
        .settled(HandlerOutcome::ack());

    tb.shutdown().await.expect("graceful shutdown");
}

    Ожидаемые байты приходят из формата, а не из харнесса: самодельный кадр достаточно короток, чтобы выписать его целиком, а сгенерированное сообщение выдаёт свои байты само, поэтому для сообщения prost это with_raw(&order.encode_to_vec()). Чтение доставки обратно - это Deserialized::from_payload поверх владеющих Bytes, которые вернул received_raw(): тот же читатель, который путь запускал на входе, так что проверка идёт против типа модели и без кодека. Сторона публикации делится так же: published::<T>(name).with_raw(bytes) и .messages() кодека не касаются, а .with(&value) и .decoded() - касаются.

    Проверки слотов Out¶

    Слот Out обработчика служит заодно его тестовой идентичностью: tb.out::<Marker>() возвращает ровно те сообщения, которые опубликованы через этот внедрённый издателя, - вместе с адресатами и заголовками, по всем брокерам сразу - и с тем же набором проверок, что у published (assert_called_once, with_raw, messages; для типизированного with добавьте в цепочку .decoded_as::<T>()). Взгляд через слот добавляет только атрибуцию: те же сообщения видит и поканальный журнал публикаций брокера.

    tests/out_slots.rs
    tb.broker::<MemoryBroker>()
    .message(&Wire::of(b"frame"))
    .to("slots.in")
    .publish()
    .await
    .expect("publish");

let encoded = tb.out::<Encoded>().assert_called_once().with_raw(b"frame");
let recorded = &encoded.messages()[0];
assert_eq!(recorded.name(), "slots.encoded");
assert_eq!(
    recorded.headers().get("source"),
    Some(b"slots.in".as_slice()),
);
tb.out::<Audit>()
    .assert_called_once()
    .with_raw(5u64.to_be_bytes().as_slice());

    Публикации, которые уходят из задачи обработчика (порождённая соседняя задача, буфер завершённой собственной транзакции), слоту не приписываются: проверяйте их по журналу публикаций брокера.

    Политика ошибок, паника и остановка¶

    Обвязка выполняет диспетчеризацию под настоящей FailurePolicy приложения, поэтому негативный тест здесь полноправен. При умолчании panic = fail_fast паника обработчика роняет сервис ровно так же, как в бою:

    tests/testing_harness.rs
    // The panicking delivery still drives to quiescence (the message is dropped, unsettled).
tb.broker::<MemoryBroker>()
    .message(&Order { id: 0 })
    .to("orders")
    .publish()
    .await
    .unwrap();

tb.broker::<MemoryBroker>()
    .subscriber("orders")
    .assert_called_once()
    .panicked();
tb.assert_shut_down();
assert!(matches!(
    tb.run_result(),
    Err(ruststream::runtime::RustStreamError::Dispatch(_))
));
// A publish after the fail-fast shutdown is rejected.
assert!(matches!(
    tb.broker::<MemoryBroker>()
        .message(&Order { id: 1 })
        .to("orders")
        .publish()
        .await,
    Err(PublishError::Publish(TestError::ShutDown))
));

    При on_failure(panic = skip) паника завершается через ack, потребление продолжается, и tb.assert_running() держится. run_result() возвращает то же, что вернул бы настоящий run: Ok, пока всё здорово, и ошибку, как только сбой в режиме fail-fast остановил сервис.

    Чтобы ловить панику, нужна раскрутка стека

    Обвязка работает через catch_unwind рантайма, поэтому намеренная паника не убивает тестовый поток. Сборка, скомпилированная с panic = "abort", панику обработчика поймать не может.

    Отложенная повторная доставка (retry_after)¶

    Обработчик, вернувший retry_after(delay), планирует отложенную повторную доставку. publish записывает немедленное завершение NackAfter и возвращает управление, а сама повторная доставка запускается отдельно - сдвигом остановленных часов:

    tests/testing_harness.rs
    #[subscriber("delayed")]
async fn delayed_retry(order: &Order, ctx: &mut Context<'_, (), Counter>) -> HandlerOutcome {
    let _ = order;
    if ctx.state().seen.fetch_add(1, Ordering::SeqCst) == 0 {
        HandlerOutcome::retry_after(std::time::Duration::from_secs(30))
    } else {
        HandlerOutcome::ack()
    }
}

#[tokio::test(start_paused = true)]
async fn retry_after_redelivers_after_advancing_time() {
    let seen = Arc::new(AtomicU32::new(0));
    let state_seen = Arc::clone(&seen);
    let app = RustStream::new(AppInfo::new("svc", "0.1.0"))
        .on_startup(move |()| {
            let seen = state_seen;
            async move { Ok::<_, std::convert::Infallible>(Counter { seen }) }
        })
        .with_broker(MemoryBroker::new(), |b| b.include(delayed_retry));
    let tb = TestApp::start(app).await.unwrap();

    // The publish records the immediate NackAfter settlement and returns; the redelivery is pending.
    tb.message(&Order { id: 1 })
        .to("delayed")
        .publish()
        .await
        .unwrap();
    tb.broker::<MemoryBroker>()
        .subscriber("delayed")
        .assert_called_once()
        .settled(HandlerOutcome::retry_after(std::time::Duration::from_secs(
            30,
        )));
    assert_eq!(seen.load(Ordering::SeqCst), 1);

    // Advancing past the delay fires the redelivery and drives it to settle.
    tb.advance(std::time::Duration::from_secs(30))
        .await
        .unwrap();
    tb.broker::<MemoryBroker>()
        .subscriber("delayed")
        .assert_called(2)
        .settled(HandlerOutcome::ack());
    assert_eq!(seen.load(Ordering::SeqCst), 2);

    /// A handler bound to one state type: naming `Counter` in the state position of the `Handle` impl
/// is what the attribute's `ctx: &mut Context<'_, (), Counter>` parameter declares. The mount reads
/// the state off the impl, so the definition is built the same way as a stateless one.
struct DelayedRetry;

impl Handle<Order, (), (), (), Counter> for DelayedRetry {
    fn handle(
        &self,
        _order: &Order,
        _outs: &(),
        ctx: &mut Context<'_, (), Counter>,
    ) -> impl Future<Output = Result<(), HandlerOutcome>> {
        if ctx.state().seen.fetch_add(1, Ordering::SeqCst) == 0 {
            return ready(Err(HandlerOutcome::retry_after(Duration::from_secs(30))));
        }
        ready(Ok(()))
    }
}

    Интеграционные тесты против настоящего брокера¶

    Поведение, которое зависит от семантики настоящего брокера, вынесено в отдельный набор, включаемый переменной окружения, - чтобы обычный cargo test оставался быстрым и офлайновым:
