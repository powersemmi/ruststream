    Контекст и состояние¶

    Нормативная версия документации - английская

    Эта страница переведена с английского языковой моделью. При любом расхождении верен английский оригинал.

    Всё, кроме полезной нагрузки, обработчик получает через два объекта с разным временем жизни:

    Уровень Тип Время жизни Содержит
    Приложение тип состояния S всё время работы сервиса разделяемые ресурсы: пулы, клиенты, конфигурацию
    Доставка Context<'_, C, S> одно сообщение имя канала, рабочую копию заголовков, типизированный контекст брокера на одну доставку C (читается по ключу) и типизированное разделяемое состояние S

    Состояние создаётся один раз, на старте. Его тип вы выбираете сами. Context создаётся заново на каждую доставку и передаётся как &mut по цепочке middleware в обработчик. Middleware и обработчик работают с одним и тем же объектом, поэтому обработчик видит всё, что добавил в него middleware.

    Уровень приложения: типизированное состояние¶

    Разделяемое состояние приложения - это одно типизированное значение S: ваша структура или (), если состояние сервису не нужно. Создаёт его хук on_startup, и тип возвращённого значения становится типом состояния приложения.

    examples/context.rs
    // `on_startup` fixes the app's state type to `AppConfig`; `.layer` then grows the global stack.
#[ruststream::app]
fn app() -> RustStream<Stack<RequestId, Identity>, AppConfig> {
    RustStream::new(AppInfo::new("context", "0.1.0"))
        .on_startup(async move |()| {
            Ok::<_, std::convert::Infallible>(AppConfig {
                reject_zero_ids: true,
            })
        })
        .layer(RequestId)
        .with_broker(MemoryBroker::new(), |b| {
            b.include(handle);
        })
}
    examples/manual/context.rs
    // `on_startup` fixes the app's state type to `AppConfig`; `.layer` then grows the global stack.
// `include` mounts the constructed definition: the source resolves at startup, and the scope codec
// (here the default) decodes.
fn app() -> RustStream<Stack<RequestId, Identity>, AppConfig> {
    RustStream::new(AppInfo::new("context", "0.1.0"))
        .on_startup(async move |()| {
            Ok::<_, Infallible>(AppConfig {
                reject_zero_ids: true,
            })
        })
        .layer(RequestId)
        .with_broker(MemoryBroker::new(), |b| {
            b.include(subscriber("orders", Receive).build());
        })
}

// `#[ruststream::app]` is what would have written this main (and given it a CLI); `run` itself is
// an ordinary method, so the macro-free service calls it.
#[tokio::main]
async fn main() -> Result<(), Box<dyn Error>> {
    app().run().await?;
    Ok(())
}

    Тип состояния проверяется во время компиляции. Обработчик, который читает состояние, называет его последним типовым параметром Context (Context<'_, C, S>) и монтируется только на приложение с тем же типом состояния. Обработчик, который тип состояния не называет, обобщён по нему и монтируется на любое приложение.

    У обработчиков с publish(..) то же правило и одна особенность. Тот, кто состояние не читает, опускает параметр Context целиком и всё равно монтируется на приложение с состоянием. Тот, кто Context объявил, но тип состояния не назвал, закрепляет за состоянием (). Назовите тип состояния явно, чтобы смонтировать такой обработчик на приложение с состоянием.

    Состояние обработчик читает через ctx.state(): метод возвращает &S. Состояние находится в совместном владении, поэтому все обработчики работают с одним значением. Значение, которое должно меняться во время работы, хранят через внутреннюю изменяемость: AtomicU64, ассоциативный массив под мьютексом.

    Данные в пределах одной доставки, а не всего сервиса, хранит контекст на одну доставку. Хук старта описан в разделе Жизненный цикл.

    examples/context.rs
    /// Shared configuration: produced once at startup, read by every handler as the typed app state.
#[derive(Debug)]
struct AppConfig {
    reject_zero_ids: bool,
}

    Внедрение зависимостей: параметры-экстракторы¶

    Зависимость всегда доступна через ctx.state().field, но обработчик может принять её и параметром.

    Экстрактор - это параметр обработчика, тип которого реализует FromContext. Экстракторы идут после сообщения и после необязательного параметра &mut Context. Рантайм вычисляет значение экстрактора из доставки до того, как выполнится тело обработчика. Экстрактор, вернувший отказ, завершает доставку своим исходом, и тело не выполняется.

    Чтобы внедрить часть состояния, выведите на состоянии FromRef и объявите в обработчике параметр State<T>. State<T> работает с полем любого типа (T: FromRef<S>), в том числе с типом из другого крейта: издателем брокера, пулом клиентов:

    examples/from_context.rs
    #[derive(FromRef)]
struct AppState {
    create_order: CreateOrder,
}
    examples/manual/from_context.rs
    struct AppState {
    create_order: CreateOrder,
}

impl FromRef<AppState> for CreateOrder {
    fn from_ref(state: &AppState) -> Self {
        state.create_order.clone()
    }
}

    Обработчик принимает State<FieldType> параметром:

    examples/from_context.rs
    #[subscriber("orders")]
async fn handle(order: &Order, State(create_order): State<CreateOrder>) -> HandlerOutcome {
    create_order.execute(order);
    HandlerOutcome::ack()
}
    examples/manual/from_context.rs
    /// The handler body: `#[subscriber("orders")]` generates this struct and this impl.
struct Receive;

impl Handle<Order, (), (), (), AppState> for Receive {
    async fn handle(
        &self,
        order: &Order,
        _outs: &(),
        ctx: &mut Context<'_, (), AppState>,
    ) -> Result<(), HandlerOutcome> {
        // One binding per extractor parameter, in declaration order, before the body: this is
        // what the attribute emits for `State(create_order): State<CreateOrder>`. A rejection
        // settles the delivery by its `HandlerOutcome` and the body never runs.
        let State(create_order) =
            match <State<CreateOrder> as FromContext<(), AppState>>::from_context(ctx).await {
                Ok(value) => value,
                Err(rejection) => return Err(HandlerOutcome::from(rejection)),
            };

        create_order.execute(order);
        Ok(())
    }
}

// The state a body extracts from is the last axis of its own `impl Handle`, so
// `subscriber(source, body)` mounts it unchanged: the mount reads `AppState` off the impl and
// checks it against the app's.

    Два поля состояния не могут иметь один тип: внедрение идёт по типу. Поле, которое внедрять не нужно или тип которого уже занят другим полем, вы можете исключить атрибутом #[from_ref(skip)].

    Экстрактор, который делает больше, чем чтение состояния, вы реализуете сами через FromContext: так пишут проверку доступа, отклоняющую доставку, или поиск зависимости в пределах одного запроса. Такой экстрактор получает &mut Context и может читать заголовки, поля брокера или черновое значение, оставленное middleware. Чтобы завершить доставку, он возвращает Rejection.

    Уровень доставки: Context¶

    Обработчик #[subscriber] объявляет контекст вторым параметром после полезной нагрузки; обработчику, которому хватает самого сообщения, этот параметр не нужен. Тип подставляет сам макрос, поэтому импорт Context не нужен, пока этот тип встречается только в сигнатурах обработчиков:

    examples/context.rs
    #[subscriber("orders")]
async fn handle(order: &Order, ctx: &mut Context<'_, (), AppConfig>) -> HandlerOutcome {
    // 1. The channel the message arrived on.
    println!("received on {}", ctx.name());

    // 2. The headers working copy - including what middleware added on the way in.
    if let Some(id) = ctx.headers().get("x-request-id") {
        println!("request {}", String::from_utf8_lossy(id));
    }

    // 3. The typed app-level shared state, borrowed through state().
    let config = ctx.state();
    if config.reject_zero_ids && order.id == 0 {
        return HandlerOutcome::drop();
    }

    // 4. A post-settle hook: fires after the broker has acked this message, off the delivery
    //    path, so slow follow-up work never gates the ack or the next delivery. At-most-once:
    //    a lost hook does not redeliver.
    let id = order.id;
    ctx.after_ack(async move {
        println!("order {id} acked; sending the confirmation");
    });

    HandlerOutcome::ack()
}
    examples/manual/context.rs
    /// The handler body: `#[subscriber("orders")]` generates this struct and this impl. The axes the
/// attribute would infer are spelled out - no reply, no injections, `()` for the broker's
/// per-delivery context, `AppConfig` for the application state.
struct Receive;

impl Handle<Order, (), (), (), AppConfig> for Receive {
    fn handle(
        &self,
        order: &Order,
        _outs: &(),
        ctx: &mut Context<'_, (), AppConfig>,
    ) -> impl Future<Output = Result<(), HandlerOutcome>> {
        // 1. The channel the message arrived on.
        println!("received on {}", ctx.name());

        // 2. The headers working copy - including what middleware added on the way in.
        if let Some(id) = ctx.headers().get("x-request-id") {
            println!("request {}", String::from_utf8_lossy(id));
        }

        // 3. The typed app-level shared state, borrowed through state().
        let config = ctx.state();
        if config.reject_zero_ids && order.id == 0 {
            return ready(Err(HandlerOutcome::drop()));
        }

        // 4. A post-settle hook: fires after the broker has acked this message, off the delivery
        //    path, so slow follow-up work never gates the ack or the next delivery. At-most-once:
        //    a lost hook does not redeliver.
        let id = order.id;
        ctx.after_ack(async move {
            println!("order {id} acked; sending the confirmation");
        });

        ready(Ok(()))
    }
}

// The state a body reads is the last axis of its own `impl Handle`, so `subscriber(source, body)`
// mounts it unchanged: the mount checks the impl's state type against the app's.

    Что даёт контекст:

    Метод Возвращает Зачем
    name() &str канал или субъект, по которому пришло сообщение
    headers() &HeaderMap рабочая копия заголовков сообщения
    headers_mut() &mut HeaderMap та же копия, чтобы middleware её дополнял
    state() &S типизированное разделяемое состояние приложения
    context(KEY) KEY::Value поле брокера по ключу времени компиляции
    set(KEY, v) () черновое значение на одну доставку, для middleware
    after(outcome).then(fut) () хук после завершения доставки с отбором по исходу
    after_ack(fut) / after_settle(fut) () сахар: хук после ack и хук после любого завершения

    Контекст на одну доставку¶

    Кроме разделяемого состояния приложения контекст хранит типизированный контекст брокера на одну доставку - собственные метаданные доставки: идентификатор потока, смещение, дескриптор доставки.

    Обработчик читает их по ключу времени компиляции. Ключ - это селектор, который экспортирует брокер; ctx.context(KEY) возвращает значение поля прямо из контекста, без сериализации в байтовые заголовки. На пути доставки такое чтение ничего не стоит. Ключ, которого нет у брокера этой подписки, - ошибка компиляции.

    examples/context_field.rs
    use ruststream::Field;

// A broker crate ships its per-delivery context and the keys that read its fields; an application
// reads a field by key from a handler taking `&mut Context<'_, Delivery>`.
struct Delivery {
    offset: u64,
}

#[derive(Clone, Copy)]
struct Offset;

impl Field<Delivery> for Offset {
    type Value<'a> = u64;
    fn get(self, d: &Delivery) -> u64 {
        d.offset
    }
}

    У брокера без полей на доставку тип контекста - (), значение по умолчанию: обработчик, который не называет тип контекста и не принимает экстрактор Ctx, видит Context<'_>.

    Middleware может передать типизированное черновое значение обработчику ниже по цепочке: correlation id, пользователя, которого слой аутентифицировал. По записываемому ключу (FieldMut) слой вызывает ctx.set(KEY, value), а обработчик читает значение через ctx.context(KEY). Следующая доставка этих значений не увидит.

    Пакетный обработчик получает один контекст на весь пакет, и в нём лежат только поля брокера уровня подписки: дескриптор перемотки, имя потока. Данных отдельной доставки там нет - пакет охватывает много доставок, поэтому позиция и заголовок хранятся на его элементах.

    Тело пакетного обработчика объявляет этот тип своим типом контекста (ctx: &mut Context<'_, MemoryBatchContext> на in-memory брокере) и читает поля через ctx.context(..). Типы контекста доставки и пакета разные, поэтому пакетное тело с контекстом доставки не компилируется. У брокера без полей уровня подписки тип пакетного контекста - ().

    Поля контекста как параметры¶

    Поле контекста может прийти и аргументом обработчика, как State<T> внедряет часть состояния: экстрактор Ctx<K> связывает значение, которое читает ключ K. Параметр &mut Context при этом не нужен: макрос #[subscriber] выводит тип контекста подписки из первого ключа Ctx в сигнатуре.

    examples/ctx_extractor.rs
    // The broker's per-delivery context, built once per delivery; here it carries the payload
// size, standing in for an offset, a partition, or a delivery tag a real broker exposes.
struct DeliveryMeta {
    payload_len: usize,
}

impl BuildContext<MemoryMessage> for DeliveryMeta {
    fn build(msg: &MemoryMessage) -> Self {
        Self {
            payload_len: msg.payload().len(),
        }
    }
}

// The key: `ContextField` names the context it reads and yields an owned value, which is what
// lets it work as an extractor. Broker crates ship these next to their `Field` keys.
#[derive(Clone, Copy, Default)]
struct PayloadLen;

impl ContextField for PayloadLen {
    type Context = DeliveryMeta;
    type Value = usize;
    fn read(self, src: &DeliveryMeta) -> usize {
        src.payload_len
    }
}
    examples/ctx_extractor.rs
    // The field arrives as an argument; no `&mut Context` parameter, no context type named - the
// macro projects it from the key.
#[subscriber("orders")]
async fn audit(order: &Order, Ctx(len): Ctx<PayloadLen>) -> HandlerOutcome {
    println!("order {} arrived as {len} bytes", order.id);
    HandlerOutcome::ack()
}
    examples/manual/ctx_extractor.rs
    /// The handler body: `#[subscriber("orders")]` generates this struct and this impl.
struct Audit;

// The context type is written down rather than inferred: the attribute projected it from the key
// as `<PayloadLen as ContextField>::Context`, which is this broker context.
impl Handle<Order, (), (), DeliveryMeta> for Audit {
    async fn handle(
        &self,
        order: &Order,
        _outs: &(),
        ctx: &mut Context<'_, DeliveryMeta>,
    ) -> Result<(), HandlerOutcome> {
        // What the attribute emits for a `Ctx(len): Ctx<PayloadLen>` parameter: the field is
        // resolved off the delivery context before the body runs, and binds by the same pattern.
        let Ctx(len) =
            match <Ctx<PayloadLen> as FromContext<DeliveryMeta, ()>>::from_context(ctx).await {
                Ok(value) => value,
                Err(rejection) => return Err(HandlerOutcome::from(rejection)),
            };

        println!("order {} arrived as {len} bytes", order.id);
        Ok(())
    }
}

// `subscriber` reads the broker context off the `Handle` impl, so naming `DeliveryMeta` there is
// the whole declaration: nothing repeats it at the mount, and `include` builds that context per
// delivery.

    Три особенности этой формы:

    • Экстрактор отдаёт значение во владение: он связывается до того, как выполнится тело обработчика, и заимствовать из контекста не может. Ключ, который отдаёт заимствованное значение (имя как &str), читается через ctx.context(KEY), если параметр ctx объявлен.
    • Если обработчик берёт и параметр &mut Context<'_, C>, каждый ключ Ctx обязан читать тот же самый C.
    • Вывод типа синтаксический: макрос распознаёт запись Ctx<K> - любой путь, оканчивающийся на Ctx, с одним типовым аргументом. За псевдонимом типа макрос эту запись не видит, и тип контекста становится ().

    Рабочая копия заголовков¶

    Каждая доставка копирует входящие заголовки в контекст, и ctx.headers() возвращает эту копию, а не заголовки самого сообщения брокера. Копия - черновик для всей цепочки диспетчеризации: middleware раньше по цепочке может записать в неё значения через headers_mut(), а обработчик читает результат:

    examples/context.rs
    /// A layer that stamps a request id onto the context headers before the handler runs.
#[derive(Clone)]
struct RequestId;

struct WithRequestId<H>(H);

impl<H> Layer<H> for RequestId {
    type Handler = WithRequestId<H>;
    fn layer(&self, inner: H) -> WithRequestId<H> {
        WithRequestId(inner)
    }
}

static NEXT_REQUEST: AtomicU64 = AtomicU64::new(1);

// The layer is state-agnostic: it threads the context `C` and state `S` through unchanged, so it
// wraps a handler whatever typed state the app declares.
impl<M: Send + Sync, C: Send, S: Send + Sync, H: Handler<M, C, S>> Handler<M, C, S>
    for WithRequestId<H>
{
    async fn handle(&self, msg: &M, ctx: &mut Context<'_, C, S>) -> HandlerOutcome {
        if ctx.headers().get("x-request-id").is_none() {
            let id = format!("req-{}", NEXT_REQUEST.fetch_add(1, Ordering::Relaxed));
            ctx.headers_mut().insert("x-request-id", id.into_bytes());
        }
        self.0.handle(msg, ctx).await
    }
}

// The app-global stack wraps every handler through `BlanketLayer`: the mount site hides the
// handler's concrete type, so the wrap happens through this generic method instead.
impl BlanketLayer for RequestId {
    fn apply<M, C, S, H>(&self, handler: H) -> impl Handler<M, C, S> + 'static
    where
        M: Send + Sync + 'static,
        C: Send + 'static,
        S: Send + Sync + 'static,
        H: Handler<M, C, S> + 'static,
    {
        WithRequestId(handler)
    }
}

    Слой, смонтированный глобально, выполняется перед каждым обработчиком, поэтому handle выше всегда находит x-request-id:

    examples/context.rs
    // `on_startup` fixes the app's state type to `AppConfig`; `.layer` then grows the global stack.
#[ruststream::app]
fn app() -> RustStream<Stack<RequestId, Identity>, AppConfig> {
    RustStream::new(AppInfo::new("context", "0.1.0"))
        .on_startup(async move |()| {
            Ok::<_, std::convert::Infallible>(AppConfig {
                reject_zero_ids: true,
            })
        })
        .layer(RequestId)
        .with_broker(MemoryBroker::new(), |b| {
            b.include(handle);
        })
}
    examples/manual/context.rs

            Ok::<_, Infallible>(AppConfig {
                reject_zero_ids: true,
            })
        })
        .layer(RequestId)
        .with_broker(MemoryBroker::new(), |b| {
            b.include(subscriber("orders", Receive).build());
        })
}

// `#[ruststream::app]` is what would have written this main (and given it a CLI); `run` itself is
// an ordinary method, so the macro-free service calls it.
#[tokio::main]
async fn main() -> Result<(), Box<dyn Error>> {
    app().run().await?;
    Ok(())
}

    У копии две границы:

    • Изменения остаются внутри доставки: сообщение брокера и доставки других подписчиков их не видят.
    • Исходящие сообщения эту копию не получают: ответ и ручная публикация начинают с пустых заголовков. Метаданные исходящего сообщения задают в конвейере публикации, через PublishTransform или PublishLayer.

    Публикация из обработчика¶

    Помимо формы ответа publish(..), обработчик может публиковать через слот Out. Издателя для этого не кладут в состояние, а принимают параметром обработчика: шаблон Out(out): Out<impl Publisher> связывает out с живым издателем внутри тела.

    Политику вы указываете при включении обработчика в приложение. Из неё выводится конкретный тип издателя, и она же инстанцирует его на подключённом брокере.

    Всё, что публикуется через слот, проходит тот же конвейер публикации, что и ответ: общая для приложения цепочка publish_layer под собственными шагами слота .out(marker, policy).transform(..). Полный шаблон с примером кода - в разделе Публикация изнутри обработчика.

    Хуки после завершения доставки¶

    На контексте вы можете зарегистрировать побочный эффект, который сработает после завершения доставки: некритичное уведомление, медленную дополнительную работу, прогрев кеша. На решение об ack и на повторную доставку такой эффект не влияет.

    examples/context.rs
    #[subscriber("orders")]
async fn handle(order: &Order, ctx: &mut Context<'_, (), AppConfig>) -> HandlerOutcome {
    // 1. The channel the message arrived on.
    println!("received on {}", ctx.name());

    // 2. The headers working copy - including what middleware added on the way in.
    if let Some(id) = ctx.headers().get("x-request-id") {
        println!("request {}", String::from_utf8_lossy(id));
    }

    // 3. The typed app-level shared state, borrowed through state().
    let config = ctx.state();
    if config.reject_zero_ids && order.id == 0 {
        return HandlerOutcome::drop();
    }

    // 4. A post-settle hook: fires after the broker has acked this message, off the delivery
    //    path, so slow follow-up work never gates the ack or the next delivery. At-most-once:
    //    a lost hook does not redeliver.
    let id = order.id;
    ctx.after_ack(async move {
        println!("order {id} acked; sending the confirmation");
    });

    HandlerOutcome::ack()
}
    examples/manual/context.rs
    /// The handler body: `#[subscriber("orders")]` generates this struct and this impl. The axes the
/// attribute would infer are spelled out - no reply, no injections, `()` for the broker's
/// per-delivery context, `AppConfig` for the application state.
struct Receive;

impl Handle<Order, (), (), (), AppConfig> for Receive {
    fn handle(
        &self,
        order: &Order,
        _outs: &(),
        ctx: &mut Context<'_, (), AppConfig>,
    ) -> impl Future<Output = Result<(), HandlerOutcome>> {
        // 1. The channel the message arrived on.
        println!("received on {}", ctx.name());

        // 2. The headers working copy - including what middleware added on the way in.
        if let Some(id) = ctx.headers().get("x-request-id") {
            println!("request {}", String::from_utf8_lossy(id));
        }

        // 3. The typed app-level shared state, borrowed through state().
        let config = ctx.state();
        if config.reject_zero_ids && order.id == 0 {
            return ready(Err(HandlerOutcome::drop()));
        }

        // 4. A post-settle hook: fires after the broker has acked this message, off the delivery
        //    path, so slow follow-up work never gates the ack or the next delivery. At-most-once:
        //    a lost hook does not redeliver.
        let id = order.id;
        ctx.after_ack(async move {
            println!("order {id} acked; sending the confirmation");
        });

        ready(Ok(()))
    }
}

// The state a body reads is the last axis of its own `impl Handle`, so `subscriber(source, body)`
// mounts it unchanged: the mount checks the impl's state type against the app's.

    Обработчик выше заканчивается вызовом ctx.after_ack(..). Продолжение выполняется только после того, как брокер сделал ack сообщения, и вне пути доставки, поэтому не задерживает ни ack, ни следующую доставку.

    Три формы, и они складываются:

    • ctx.after(outcome).then(fut) - выполняется, только если доставка завершилась исходом outcome. Исходы сопоставляются по виду, видов четыре: ack(), drop() (nack без возврата в очередь), retry() (nack с возвратом в очередь) и retry_after() (совпадает при любой задержке). Хук на drop() не сработает, когда доставка завершилась через retry(), и наоборот.
    • ctx.after_ack(fut) - сахар для ctx.after(HandlerOutcome::ack()).then(fut).
    • ctx.after_settle(fut) - выполняется после завершения доставки при любом исходе.

    Продолжение можно прикрепить и к возвращаемому значению: .and_after(fut) есть у любого исхода, и так пакетный обработчик получает продолжение на каждый элемент. Эта форма описана в разделе Продолжения после завершения доставки; всё сказанное ниже относится к обеим.

    Регистрации накапливаются, и выполняются все подходящие - вне пути доставки, в отслеживаемом наборе задач.

    Семантика хуков - at-most-once: доставка завершается раньше, чем запустится любой хук, поэтому паника в хуке или аварийное завершение процесса не приводит к повторной доставке. Не кладите в хук работу, потеря которой обязана вызвать повторную доставку: завершите доставку подходящим исходом и дайте брокеру повторить попытку.

    Плавная остановка дожидается незавершённых хуков в пределах shutdown_timeout, прерванная остановка может их потерять.

    На пакетном пути Context один на пакет, поэтому хук выполняется после завершения всего пакета. Исходы у пакета свои на каждый элемент, поэтому отбор по исходу здесь не определён: срабатывают только хуки after_settle, а after(..) и after_ack на пакете игнорируются.

    Контекст в middleware¶

    Любая форма middleware получает тот же &mut Context, что и обработчик:

    • Статический слой - через Handler::handle(&self, msg, ctx), как в примере выше.
    • Динамический middleware - через DynMiddleware::handle(&self, input, ctx, next): он читает или дополняет контекст, а затем вызывает next.run(input, ctx).

    Сами формы middleware описаны в разделе Middleware. Полная программа этой страницы - examples/context.rs.
