    Контекст и состояние¶

    Нормативная версия документации - английская

    Эта страница переведена с английского. При любом расхождении верен английский оригинал.

    Всё, до чего обработчик может дотянуться помимо своей полезной нагрузки, приходит через два объекта с разным временем жизни:

    Уровень Тип Время жизни Содержит
    Приложение тип состояния S всё время работы сервиса разделяемые ресурсы: пулы, клиенты, конфигурацию
    Доставка Context<'_, C, S> одно сообщение имя канала, рабочую копию заголовков, типизированный контекст брокера на одну доставку C (читается по ключу) и типизированное разделяемое состояние S

    Состояние создаётся один раз, на старте, и хранится как одно типизированное значение, которое вы выбираете сами. Context строится заново для каждой доставки и протягивается как &mut через цепочку middleware в обработчик, поэтому middleware и обработчик видят (и могут обогащать) один и тот же взгляд на текущее сообщение.

    Уровень приложения: типизированное состояние¶

    Разделяемое состояние приложения - это одно типизированное значение S (ваша структура или (), если сервису состояние не нужно). Его создаёт хук on_startup: возвращённое хуком значение и становится состоянием, фиксируя тип состояния приложения.

    examples/context.rs
    // `on_startup` fixes the app's state type to `AppConfig`; `.layer` then grows the global stack.
#[ruststream::app]
fn app() -> RustStream<Stack<RequestId, Identity>, AppConfig> {
    RustStream::new(AppInfo::new("context", "0.1.0"))
        .on_startup(async move |()| {
            Ok::<_, std::convert::Infallible>(AppConfig {
                reject_zero_ids: true,
            })
        })
        .layer(RequestId)
        .with_broker(MemoryBroker::new(), |b| b.include(handle))
}
    examples/manual/context.rs
    // `on_startup` fixes the app's state type to `AppConfig`; `.layer` then grows the global stack.
// `include` mounts the constructed definition: the source resolves at startup, and the scope codec
// (here the default) decodes.
fn app() -> RustStream<Stack<RequestId, Identity>, AppConfig> {
    RustStream::new(AppInfo::new("context", "0.1.0"))
        .on_startup(async move |()| {
            Ok::<_, Infallible>(AppConfig {
                reject_zero_ids: true,
            })
        })
        .layer(RequestId)
        .with_broker(MemoryBroker::new(), |b| {
            b.include(subscriber("orders", Receive).build());
        })
}

// `#[ruststream::app]` is what would have written this main (and given it a CLI); `run` itself is
// an ordinary method, so the macro-free service calls it.
#[tokio::main]
async fn main() -> Result<(), Box<dyn Error>> {
    app().run().await?;
    Ok(())
}

    Тип состояния проверяется во время компиляции: обработчик #[subscriber], который читает состояние, называет его третьим типовым параметром Context (Context<'_, C, S>), и рантайм даст смонтировать такой обработчик только на приложение с совпадающим типом состояния. Обработчик, который тип состояния не называет, обобщён по нему и монтируется на любое приложение. Обработчики с publish(..) подчиняются тому же правилу с одной оговоркой: тот, кто состояние игнорирует, опускает параметр Context целиком и всё равно монтируется на приложение с состоянием, а вот тот, кто Context объявил, но тип состояния не назвал, прибивает состояние к (), - поэтому, чтобы смонтировать такой обработчик на приложение с состоянием, тип состояния нужно назвать явно.

    Обработчики берут состояние взаймы через ctx.state(): он возвращает &S, то самое типизированное состояние, - без поиска по ключу и без Option, который пришлось бы разворачивать. Пока сервис работает, состояние разделяется за Arc, так что обработчики получают дешёвые общие ссылки, а не копии; если разделяемое значение должно меняться во время работы, инструмент - внутренняя изменяемость (AtomicU64, карта под мьютексом). Для данных в пределах одного сообщения, а не всего сервиса, есть контекст на одну доставку. Контракт хука старта описан в разделе Жизненный цикл.

    examples/context.rs
    /// Shared configuration: produced once at startup, read by every handler as the typed app state.
#[derive(Debug)]
struct AppConfig {
    reject_zero_ids: bool,
}

    Внедрение зависимостей: параметры-экстракторы¶

    Дотянуться до зависимости через ctx.state().field можно всегда, но обработчик может принять её и параметром. Любой параметр обработчика после сообщения (и после необязательного &mut Context) с типом, реализующим FromContext, - это экстрактор: рантайм разрешает его из доставки до того, как выполнится тело, а неудачная выборка завершает доставку сообщения по HandlerOutcome из отказа, так и не запустив тело.

    Чтобы внедрить кусок состояния, выведите на состоянии FromRef и принимайте в обработчике State<T> - реализацию экстрактора писать руками не нужно. State<T> разрешается для поля любого типа (T: FromRef<S>), включая типы из других крейтов - издатель брокера, пул клиентов:

    examples/from_context.rs
    #[derive(FromRef)]
struct AppState {
    create_order: CreateOrder,
}
    examples/manual/from_context.rs
    struct AppState {
    create_order: CreateOrder,
}

impl FromRef<AppState> for CreateOrder {
    fn from_ref(state: &AppState) -> Self {
        state.create_order.clone()
    }
}

    Обработчик принимает State<FieldType> и никуда не тянется через ctx.state():

    examples/from_context.rs
    #[subscriber("orders")]
async fn handle(order: &Order, State(create_order): State<CreateOrder>) -> HandlerOutcome {
    create_order.execute(order);
    HandlerOutcome::ack()
}
    examples/manual/from_context.rs
    /// The handler body: `#[subscriber("orders")]` generates this struct and this impl.
struct Receive;

impl Handle<Order, (), (), (), AppState> for Receive {
    async fn handle(
        &self,
        order: &Order,
        _outs: &(),
        ctx: &mut Context<'_, (), AppState>,
    ) -> Result<(), HandlerOutcome> {
        // One binding per extractor parameter, in declaration order, before the body: this is
        // what the attribute emits for `State(create_order): State<CreateOrder>`. A rejection
        // settles the delivery by its `HandlerOutcome` and the body never runs.
        let State(create_order) =
            match <State<CreateOrder> as FromContext<(), AppState>>::from_context(ctx).await {
                Ok(value) => value,
                Err(rejection) => return Err(HandlerOutcome::from(rejection)),
            };

        create_order.execute(order);
        Ok(())
    }
}

// The state a body extracts from is the last axis of its own `impl Handle`, so
// `subscriber(source, body)` mounts it unchanged: the mount reads `AppState` off the impl and
// checks it against the app's.

    Поле, которое внедрять не нужно или тип которого уже занят другим полем, отказывается от внедрения через #[from_ref(skip)]; два поля не могут иметь один тип, иначе внедрение по типу стало бы неоднозначным. Для своего экстрактора, который делает больше, чем чтение состояния (auth guard, отклоняющий доставку, резолвер в пределах запроса), реализуйте FromContext напрямую: он занимает &mut Context, поэтому может читать заголовки, поля брокера или черновое значение, оставленное middleware, и вернуть Rejection, чтобы завершить доставку.

    Уровень доставки: Context¶

    Обработчик #[subscriber] подключается к контексту, объявив второй параметр после полезной нагрузки; если обработчику ничего, кроме сообщения, не нужно, параметр опускают. Тип разрешает сам макрос, поэтому импортировать Context не требуется, пока он встречается только в сигнатурах обработчиков:

    examples/context.rs
    #[subscriber("orders")]
async fn handle(order: &Order, ctx: &mut Context<'_, (), AppConfig>) -> HandlerOutcome {
    // 1. The channel the message arrived on.
    println!("received on {}", ctx.name());

    // 2. The headers working copy - including what middleware added on the way in.
    if let Some(id) = ctx.headers().get("x-request-id") {
        println!("request {}", String::from_utf8_lossy(id));
    }

    // 3. The typed app-level shared state, borrowed through state().
    let config = ctx.state();
    if config.reject_zero_ids && order.id == 0 {
        return HandlerOutcome::drop();
    }

    // 4. A post-settle hook: fires after the broker has acked this message, off the delivery
    //    path, so slow follow-up work never gates the ack or the next delivery. At-most-once:
    //    a lost hook does not redeliver.
    let id = order.id;
    ctx.after_ack(async move {
        println!("order {id} acked; sending the confirmation");
    });

    HandlerOutcome::ack()
}
    examples/manual/context.rs
    /// The handler body: `#[subscriber("orders")]` generates this struct and this impl. The axes the
/// attribute would infer are spelled out - no reply, no injections, `()` for the broker's
/// per-delivery context, `AppConfig` for the application state.
struct Receive;

impl Handle<Order, (), (), (), AppConfig> for Receive {
    fn handle(
        &self,
        order: &Order,
        _outs: &(),
        ctx: &mut Context<'_, (), AppConfig>,
    ) -> impl Future<Output = Result<(), HandlerOutcome>> {
        // 1. The channel the message arrived on.
        println!("received on {}", ctx.name());

        // 2. The headers working copy - including what middleware added on the way in.
        if let Some(id) = ctx.headers().get("x-request-id") {
            println!("request {}", String::from_utf8_lossy(id));
        }

        // 3. The typed app-level shared state, borrowed through state().
        let config = ctx.state();
        if config.reject_zero_ids && order.id == 0 {
            return ready(Err(HandlerOutcome::drop()));
        }

        // 4. A post-settle hook: fires after the broker has acked this message, off the delivery
        //    path, so slow follow-up work never gates the ack or the next delivery. At-most-once:
        //    a lost hook does not redeliver.
        let id = order.id;
        ctx.after_ack(async move {
            println!("order {id} acked; sending the confirmation");
        });

        ready(Ok(()))
    }
}

// The state a body reads is the last axis of its own `impl Handle`, so `subscriber(source, body)`
// mounts it unchanged: the mount checks the impl's state type against the app's.

    Что даёт контекст:

    Метод Возвращает Зачем
    name() &str канал / субъект, по которому пришло сообщение
    headers() &HeaderMap рабочая копия заголовков сообщения
    headers_mut() &mut HeaderMap та же копия, чтобы middleware её обогащал
    state() &S типизированное разделяемое состояние приложения, взятое напрямую
    context(KEY) KEY::Value поле брокера, читаемое по ключу времени компиляции
    set(KEY, v) () записать черновое значение на одну доставку (для middleware)
    after(outcome).then(fut) () хук после завершения доставки, привязанный к исходу завершения
    after_ack(fut) / after_settle(fut) () сахар для хуков после завершения доставки (после ack / после любого завершения)

    Контекст на одну доставку¶

    Кроме разделяемого состояния приложения контекст несёт типизированный контекст брокера на одну доставку, и читается он по ключу времени компиляции, ничего не стоя на пути доставки. Ключ - это селектор, который экспортирует брокер; ctx.context(KEY) читает поле прямо из контекста, поэтому обработчик получает родные метаданные доставки (идентификатор потока, смещение, дескриптор доставки), а брокеру не приходится сериализовать их в чисто байтовые заголовки. Ключ, которого нет у брокера этой подписки, - ошибка компиляции, а не промах во время работы.

    examples/context_field.rs
    use ruststream::Field;

// A broker crate ships its per-delivery context and the keys that read its fields; an application
// reads a field by key from a handler taking `&mut Context<'_, Delivery>`.
struct Delivery {
    offset: u64,
}

#[derive(Clone, Copy)]
struct Offset;

impl Field<Delivery> for Offset {
    type Value<'a> = u64;
    fn get(self, d: &Delivery) -> u64 {
        d.offset
    }
}

    Брокер без полей на доставку берёт () - значение по умолчанию, поэтому обработчик #[subscriber], который не называет тип контекста и не принимает экстрактор Ctx, видит Context<'_>. Middleware умеет ещё и передавать типизированное черновое значение обработчику ниже по цепочке: по записываемому ключу (FieldMut) слой делает ctx.set(KEY, value), а обработчик читает значение обратно через ctx.context(KEY): correlation id, аутентифицированный пользователь, которого разрешил слой, - и всё это без сериализации в заголовки. Контекст строится заново на каждую доставку, поэтому значения одной доставки никогда не протекают в следующую.

    Пакетный обработчик получает один контекст на пакет, и в этом контексте лежат только те поля брокера, которые относятся ко всей подписке, - ручка перемотки, имя потока. Пакетное тело называет этот тип своим типом контекста (ctx: &mut Context<'_, MemoryBatchContext> на in-memory брокере) и читает его через ctx.context(..). Данные отдельной доставки туда не попадают: пакет охватывает много доставок, поэтому позиция или заголовок едут на элементах. Типы контекста доставки и пакета разные, поэтому пакетное тело, запросившее контекст доставки, не компилируется, а брокер, которому нечего дать на уровне подписки, оставляет пакеты на умолчании ().

    Поля контекста как параметры¶

    Поле может прийти и аргументом обработчика - так же, как State<T> внедряет часть состояния: экстрактор Ctx<K> связывает значение, которое читает ключ K. Параметр &mut Context обработчику вообще не нужен: макрос #[subscriber] выводит тип контекста подписки из первого ключа Ctx в сигнатуре.

    examples/ctx_extractor.rs
    // The broker's per-delivery context, built once per delivery; here it carries the payload
// size, standing in for an offset, a partition, or a delivery tag a real broker exposes.
struct DeliveryMeta {
    payload_len: usize,
}

impl BuildContext<MemoryMessage> for DeliveryMeta {
    fn build(msg: &MemoryMessage) -> Self {
        Self {
            payload_len: msg.payload().len(),
        }
    }
}

// The key: `ContextField` names the context it reads and yields an owned value, which is what
// lets it work as an extractor. Broker crates ship these next to their `Field` keys.
#[derive(Clone, Copy, Default)]
struct PayloadLen;

impl ContextField for PayloadLen {
    type Context = DeliveryMeta;
    type Value = usize;
    fn read(self, src: &DeliveryMeta) -> usize {
        src.payload_len
    }
}
    examples/ctx_extractor.rs
    // The field arrives as an argument; no `&mut Context` parameter, no context type named - the
// macro projects it from the key.
#[subscriber("orders")]
async fn audit(order: &Order, Ctx(len): Ctx<PayloadLen>) -> HandlerOutcome {
    println!("order {} arrived as {len} bytes", order.id);
    HandlerOutcome::ack()
}
    examples/manual/ctx_extractor.rs
    /// The handler body: `#[subscriber("orders")]` generates this struct and this impl.
struct Audit;

// The context type is written down rather than inferred: the attribute projected it from the key
// as `<PayloadLen as ContextField>::Context`, which is this broker context.
impl Handle<Order, (), (), DeliveryMeta> for Audit {
    async fn handle(
        &self,
        order: &Order,
        _outs: &(),
        ctx: &mut Context<'_, DeliveryMeta>,
    ) -> Result<(), HandlerOutcome> {
        // What the attribute emits for a `Ctx(len): Ctx<PayloadLen>` parameter: the field is
        // resolved off the delivery context before the body runs, and binds by the same pattern.
        let Ctx(len) =
            match <Ctx<PayloadLen> as FromContext<DeliveryMeta, ()>>::from_context(ctx).await {
                Ok(value) => value,
                Err(rejection) => return Err(HandlerOutcome::from(rejection)),
            };

        println!("order {} arrived as {len} bytes", order.id);
        Ok(())
    }
}

// `subscriber` reads the broker context off the `Handle` impl, so naming `DeliveryMeta` there is
// the whole declaration: nothing repeats it at the mount, and `include` builds that context per
// delivery.

    Три вещи, которые стоит знать:

    • Значения владеемые: экстрактор связывается до того, как выполнится тело обработчика, поэтому занять значение у контекста он не может. Ключи, отдающие заимствованные значения (имя как &str), по-прежнему читаются через ctx.context(KEY), если параметр ctx объявлен.
    • Если параметр &mut Context<'_, C> тоже присутствует, каждый ключ Ctx обязан читать тот же самый C.
    • Вывод типа синтаксический: макрос распознаёт буквальную форму Ctx<K> (любой путь, оканчивающийся на Ctx, с одним типовым аргументом). Псевдоним типа её прячет, и тип контекста откатывается к ().

    Рабочая копия заголовков¶

    ctx.headers() - это не само сообщение брокера: каждая доставка копирует входящие заголовки в рабочую копию, которая хранится в контексте. Тем самым копия становится черновиком для цепочки диспетчеризации: middleware раньше по цепочке проставляет в неё значения через headers_mut(), а обработчик читает уже обогащённый результат:

    examples/context.rs
    /// A layer that stamps a request id onto the context headers before the handler runs.
#[derive(Clone)]
struct RequestId;

struct WithRequestId<H>(H);

impl<H> Layer<H> for RequestId {
    type Handler = WithRequestId<H>;
    fn layer(&self, inner: H) -> WithRequestId<H> {
        WithRequestId(inner)
    }
}

static NEXT_REQUEST: AtomicU64 = AtomicU64::new(1);

// The layer is state-agnostic: it threads the context `C` and state `S` through unchanged, so it
// wraps a handler whatever typed state the app declares.
impl<M: Send + Sync, C: Send, S: Send + Sync, H: Handler<M, C, S>> Handler<M, C, S>
    for WithRequestId<H>
{
    async fn handle(&self, msg: &M, ctx: &mut Context<'_, C, S>) -> HandlerOutcome {
        if ctx.headers().get("x-request-id").is_none() {
            let id = format!("req-{}", NEXT_REQUEST.fetch_add(1, Ordering::Relaxed));
            ctx.headers_mut().insert("x-request-id", id.into_bytes());
        }
        self.0.handle(msg, ctx).await
    }
}

// The app-global stack wraps every handler through `BlanketLayer`: the mount site hides the
// handler's concrete type, so the wrap happens through this generic method instead.
impl BlanketLayer for RequestId {
    fn apply<M, C, S, H>(&self, handler: H) -> impl Handler<M, C, S> + 'static
    where
        M: Send + Sync + 'static,
        C: Send + 'static,
        S: Send + Sync + 'static,
        H: Handler<M, C, S> + 'static,
    {
        WithRequestId(handler)
    }
}

    Смонтированный глобально слой выполняется перед каждым обработчиком, поэтому handle выше всегда находит x-request-id:

    examples/context.rs
    // `on_startup` fixes the app's state type to `AppConfig`; `.layer` then grows the global stack.
#[ruststream::app]
fn app() -> RustStream<Stack<RequestId, Identity>, AppConfig> {
    RustStream::new(AppInfo::new("context", "0.1.0"))
        .on_startup(async move |()| {
            Ok::<_, std::convert::Infallible>(AppConfig {
                reject_zero_ids: true,
            })
        })
        .layer(RequestId)
        .with_broker(MemoryBroker::new(), |b| b.include(handle))
}

    Две границы, о которых стоит помнить:

    • Изменения не выходят за пределы доставки: само сообщение брокера и доставки других подписчиков остаются нетронутыми.
    • Исходящие сообщения эту копию не наследуют. Ответы и ручные публикации начинают с чистых заголовков; исходящие метаданные вешайте в конвейере публикации - через PublishTransform или PublishLayer.

    Публикация из обработчика¶

    Чтобы публиковать изнутри обработчика (помимо формы ответа publish(..)), не кладите издателя в состояние: принимайте его параметром обработчика через Out - шаблон Out(out): Out<impl Publisher> связывает out с живым издателем внутри тела. Политика прикрепляется там, где обработчик включается в приложение, конкретный тип издателя выводится из неё, а рантайм связывает их после того, как брокер подключился. Всё, что уходит через слот, едет по тому же конвейеру публикации, что и ответ: общая для приложения цепочка publish_layer под собственными шагами слота .out(marker, policy).transform(..). Полный шаблон и его фрагмент - в разделе Публикация изнутри обработчика.

    Хуки после завершения доставки¶

    Иногда обработчику нужен побочный эффект, который сработает после того, как доставка сообщения завершена, - некритичное уведомление, медленная дополнительная работа, прогрев кеша, - и при этом не влияет ни на решение об ack, ни на повторную доставку. Зарегистрируйте такой эффект на контексте:

    examples/context.rs
    #[subscriber("orders")]
async fn handle(order: &Order, ctx: &mut Context<'_, (), AppConfig>) -> HandlerOutcome {
    // 1. The channel the message arrived on.
    println!("received on {}", ctx.name());

    // 2. The headers working copy - including what middleware added on the way in.
    if let Some(id) = ctx.headers().get("x-request-id") {
        println!("request {}", String::from_utf8_lossy(id));
    }

    // 3. The typed app-level shared state, borrowed through state().
    let config = ctx.state();
    if config.reject_zero_ids && order.id == 0 {
        return HandlerOutcome::drop();
    }

    // 4. A post-settle hook: fires after the broker has acked this message, off the delivery
    //    path, so slow follow-up work never gates the ack or the next delivery. At-most-once:
    //    a lost hook does not redeliver.
    let id = order.id;
    ctx.after_ack(async move {
        println!("order {id} acked; sending the confirmation");
    });

    HandlerOutcome::ack()
}
    examples/manual/context.rs
    /// The handler body: `#[subscriber("orders")]` generates this struct and this impl. The axes the
/// attribute would infer are spelled out - no reply, no injections, `()` for the broker's
/// per-delivery context, `AppConfig` for the application state.
struct Receive;

impl Handle<Order, (), (), (), AppConfig> for Receive {
    fn handle(
        &self,
        order: &Order,
        _outs: &(),
        ctx: &mut Context<'_, (), AppConfig>,
    ) -> impl Future<Output = Result<(), HandlerOutcome>> {
        // 1. The channel the message arrived on.
        println!("received on {}", ctx.name());

        // 2. The headers working copy - including what middleware added on the way in.
        if let Some(id) = ctx.headers().get("x-request-id") {
            println!("request {}", String::from_utf8_lossy(id));
        }

        // 3. The typed app-level shared state, borrowed through state().
        let config = ctx.state();
        if config.reject_zero_ids && order.id == 0 {
            return ready(Err(HandlerOutcome::drop()));
        }

        // 4. A post-settle hook: fires after the broker has acked this message, off the delivery
        //    path, so slow follow-up work never gates the ack or the next delivery. At-most-once:
        //    a lost hook does not redeliver.
        let id = order.id;
        ctx.after_ack(async move {
            println!("order {id} acked; sending the confirmation");
        });

        ready(Ok(()))
    }
}

// The state a body reads is the last axis of its own `impl Handle`, so `subscriber(source, body)`
// mounts it unchanged: the mount checks the impl's state type against the app's.

    Обработчик выше заканчивается вызовом ctx.after_ack(..): продолжение выполняется, только когда брокер сделал ack сообщения, и вне пути доставки, поэтому оно никогда не задерживает ни ack, ни следующую доставку.

    Три формы, и все складываются:

    • ctx.after(outcome).then(fut) - выполняется, только если доставка сообщения завершилась исходом outcome, причём сопоставление идёт по виду. Четыре вида различаются: ack(), drop() (nack без возврата в очередь), retry() (nack с возвратом в очередь) и retry_after() (совпадает независимо от задержки). Drop и retry - разные механики, поэтому хук, привязанный к drop(), не сработает, когда доставка завершилась через retry(), и наоборот.
    • ctx.after_ack(fut) - сахар для ctx.after(HandlerOutcome::ack()).then(fut).
    • ctx.after_settle(fut) - выполняется после завершения доставки, каким бы ни был исход.

    Обработчик может прикрепить продолжение и через возвращаемое значение: любой исход несёт его вызовом .and_after(fut) - именно так пакетный обработчик получает продолжения на каждый элемент. Эта форма описана в разделе Продолжения после завершения доставки; семантика ниже относится к обеим.

    Несколько регистраций накапливаются, и выполняются все подходящие - в отслеживаемом наборе задач вне пути доставки. Семантика здесь at-most-once: доставка сообщения уже завершена до того, как запустится любой хук, поэтому хук, который упал в панику или потерялся при аварийном завершении процесса, никогда не приводит к повторной доставке. Не кладите в хук работу, потеря которой обязана вызвать повторную доставку сообщения: завершите доставку подходящим исходом и дайте брокеру повторить попытку. Плавная остановка дожидается хуков в полёте (в пределах shutdown_timeout); прерванная остановка может их потерять.

    На пакетном пути Context один на пакет, поэтому хук выполняется после того, как завершена доставка всего пакета. У пакета исходы свои на каждый элемент, поэтому отбор по исходу здесь не определён: срабатывают только хуки after_settle (формы с отбором - after(..) и after_ack - на пакете игнорируются).

    Контекст в middleware¶

    Каждая форма middleware получает тот же &mut Context, который увидит обработчик:

    • Handler::handle(&self, msg, ctx) у статического слоя - как в примере выше.
    • Динамический DynMiddleware::handle(&self, input, ctx, next) - посмотреть или обогатить, а затем вызвать next.run(input, ctx).

    Сами формы middleware разобраны в разделе Middleware. Полная программа для этой страницы - examples/context.rs.
