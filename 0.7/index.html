    The same consumer, twice

    Write the handler, not the loop

    Both programs read orders from Kafka, decode them and print the id. On the left the client is driven by hand; on the right the runtime drives it.

    The raw loopThe RustStream way
    src/main.rs · rdkafkaBy hand
    use rdkafka::Message;
    use rdkafka::config::ClientConfig;
    use rdkafka::consumer::{CommitMode, Consumer, StreamConsumer};
    use serde::Deserialize;

    #[derive(Debug, Deserialize)]
    struct Order {
        id: u64,
    }

    #[tokio::main]
    async fn main() -> Result<(), Box<dyn std::error::Error>> {
        let consumer: StreamConsumer = ClientConfig::new()
            .set("bootstrap.servers", "localhost:9092")
            .set("group.id", "orders-svc")
            .set("enable.auto.commit", "false")
            .create()?;
        consumer.subscribe(&["orders"])?;

        loop {
            let msg = tokio::select! {
                _ = tokio::signal::ctrl_c() => break,
                msg = consumer.recv() => match msg {
                    Ok(msg) => msg,
                    Err(err) => {
                        eprintln!("kafka error: {err}");
                        continue;
                    }
                },
            };
            match msg.payload().map(serde_json::from_slice::<Order>) {
                Some(Ok(order)) => println!("got order {}", order.id),
                Some(Err(err)) => eprintln!("bad payload: {err}"),
                None => eprintln!("empty message"),
            }
            if let Err(err) = consumer.commit_message(&msg, CommitMode::Async) {
                eprintln!("commit failed: {err}");
            }
        }
        Ok(())
    }
    • Client settings and commit mode, by hand
    • Decoding and every error branch, by hand
    • Signals and shutdown, by hand
    • All of it again for the next topic and the next broker
    src/main.rs · ruststream-rdkafka
    use ruststream_rdkafka::prelude::*;
    use serde::Deserialize;

    #[derive(Debug, Deserialize)]
    struct Order {
        id: u64,
    }

    #[subscriber("orders")]
    async fn handle(order: &Order) -> HandlerOutcome {
        println!("got order {}", order.id);
        HandlerOutcome::ack()
    }

    #[ruststream::app]
    fn app() -> impl App {
        RustStream::new(AppInfo::new("orders", "0.1.0")).with_broker(
            KafkaBroker::new(["localhost:9092"]).default_group("orders-svc"),
            |b| {
                b.include(handle);
            },
        )
    }

    Architecture

    The path of a message

    A delivery goes from the broker through the subscription and the codec to your handler, and the reply goes back the same way. Each part is a type the compiler checks.

    HandlerAn async function under #[subscriber]; what it returns settles the delivery or becomes the reply.
    1. BrokerA broker crate wraps one client and is held to the contract that the conformance suite checks; the core depends on no broker.
    2. SubscriptionA subscription names what to consume and is resolved once, at startup, against the connected broker.
    3. CodecThe codec turns the payload into the handler type: JSON, MessagePack or CBOR chosen at compile time, or raw bytes with no codec at all.
    4. MiddlewareConsume and publish layers wrap every delivery: logging, metrics, tracing or your own.
    5. HandlerAn async function under #[subscriber]; what it returns settles the delivery or becomes the reply.
    6. ReplyA reply type derives Outgoing and declares where it goes; the runtime encodes it and publishes it.
    7. PublisherA publish policy paired with the connected broker; a handler also publishes through typed Out slots.
    8. AsyncAPIThe same declarations generate an AsyncAPI 3.1 document, so the document cannot drift from the code.
    9. TestAppTests start the production app with the broker in process and drive the real dispatch, with no server.
    Design

    What the framework commits to

    • 01

      A core with no broker in it

      The core is traits and types. Each broker is its own crate, held to the contract by the conformance suite.

    • 02

      Broker settings stay with the broker

      Each broker crate owns its Config. A client upgrade changes that crate, not the framework.

    • 03

      Misuse does not compile

      ack(self) consumes the delivery, so a second ack is a compile error. Out-of-order lifecycle calls fail the same way.

    • 04

      Subscribers are streams

      A subscriber is a Stream, so back-pressure comes with it. The runtime builds handlers on top of it.

    • 05

      Generic, with no dyn in the contract

      The contract uses associated types and native async fn in trait. The runtime erases types only where a service needs it.

    • 06

      Capabilities, not a fat interface

      Batches, transactions, request-reply, partitions and seeking are separate traits. A broker implements the ones it supports.

    //! The landing-page example: a one-handler service with no runtime boilerplate.
    //!
    //! ```text
    //! cargo run --example quickstart --features macros,memory,json,logging -- run
    //! ```

    use ruststream::memory::prelude::*;
    use serde::Deserialize;

    #[derive(Debug, Deserialize)]
    struct Order {
        id: u64,
    }

    #[subscriber("orders")]
    async fn handle(order: &Order) -> HandlerOutcome {
        tracing::info!(order.id, "got order");
        HandlerOutcome::ack()
    }

    #[ruststream::app]
    fn app() -> RustStream {
        RustStream::new(AppInfo::new("orders", "0.1.0")).with_broker(MemoryBroker::new(), |b| {
            b.include(handle);
        })
    }
    examples/manual/quickstart.rs
    //! The landing-page example written without the `macros` feature: the handler is a named type
    //! with an `impl Handle`, mounted with the `subscriber` constructor, and `main` is the one
    //! `#[ruststream::app]` would generate.
    //!
    //! ```text
    //! cargo run --example manual_quickstart --no-default-features --features memory,json,logging -- run
    //! ```

    use std::future::ready;
    use std::process::ExitCode;

    use ruststream::memory::prelude::*;
    use ruststream::runtime::cli::run_main;
    use serde::Deserialize;

    #[derive(Debug, Deserialize, schemars::JsonSchema)]
    struct Order {
        id: u64,
    }

    /// The handler: `#[subscriber("orders")]` generates this type and this impl. Every axis of the
    /// form - the reply, the injections, the broker context, the application state - is a defaulted
    /// parameter of `Handle`, so a plain body names none of them.
    struct Receive;

    impl Handle<Order> for Receive {
        fn handle(
            &self,
            order: &Order,
            _outs: &(),
            _ctx: &mut Context<'_>,
        ) -> impl Future<Output = Result<(), HandlerOutcome>> {
            tracing::info!(order.id, "got order");
            ready(Ok(()))
        }
    }

    fn app() -> RustStream {
        RustStream::new(AppInfo::new("orders", "0.1.0")).with_broker(MemoryBroker::new(), |b| {
            b.include(subscriber("orders", Receive).build());
        })
    }

    fn main() -> ExitCode {
        run_main(app)
    }

    #[ruststream::app] generates main with all the runtime boilerplate: cargo run -- run starts the service, and cargo run -- asyncapi gen prints its AsyncAPI document.
