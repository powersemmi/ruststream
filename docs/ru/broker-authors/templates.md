# Контракт шаблонов

Как крейту поставлять заготовку для [`cargo generate`](https://github.com/cargo-generate/cargo-generate),
которая не расходится с его API. Для скаффолдинга этот контракт - то же, чем для кода является
[обвязка conformance](conformance.md): шаблон - это собираемый в CI артефакт, который принадлежит
крейту, чей брокер он связывает, а не набор строк, поддерживаемых вручную в CLI ядра. Ядро
поставляет только in-memory `templates/memory`; шаблоны для своих транспортов держит каждый крейт
брокера.

## Форма

Шаблон - это каталог, который рендерит `cargo generate`:

```
templates/<name>/
├── cargo-generate.toml   # манифест: описание, объявленные плейсхолдеры
├── Cargo.toml            # name = "{{project-name}}"; пины ruststream + крейта брокера
└── src/
    ├── main.rs           # билдер #[ruststream::app]
    ├── orders.rs         # обработчики #[subscriber]
    └── routes.rs         # Router, собирающий обработчики
```

- Плейсхолдеры записываются на Liquid-синтаксисе cargo-generate; `{{project-name}}` (значение
  `--name`) встроен, поэтому минимальный шаблон не объявляет ни одного.
- `Cargo.toml` пинит `ruststream` на поддерживаемую минорную версию, а крейт брокера - на его
  собственную.
- Один шаблон на транспорт или топологию брокера (например, `nats` против `nats-js` или
  `redis-stream` / `redis-pubsub` / `redis-list`) - по той же модели «один вид на шаблон».

Исходники шаблона несут плейсхолдеры `{{...}}`, поэтому до рендера они не являются валидными
Rust/TOML и должны оставаться вне cargo-воркспейса крейта (`exclude = ["templates"]`).

## Сборка в CI (собственно контракт)

CI каждого владеющего репозитория рендерит все свои шаблоны и компилирует их против запиненных
версий, поэтому изменение API, ломающее заготовку, роняет CI того репозитория, где и место
исправлению, а не первый `cargo build` у пользователя. Задача о расхождении:

1. ставит `cargo-generate`,
2. рендерит шаблон во временный каталог (`cargo generate --path templates/<name> --name smoke`),
3. запускает `cargo check` на отрендеренном проекте.

Пока поддерживаемая версия `ruststream` не опубликована, задача подкладывает в отрендеренный проект
`[patch.crates-io]`, указывающий на локальный чекаут (та самая раскладка с соседними чекаутами,
которой CI брокеров уже пользуется), - так заготовка компилируется против неопубликованной версии.

## Только аддитивное написание

Блоки под фичи только ДОБАВЛЯЮТ: никаких `{% else %}` и никаких отрицательных веток
`{% if not flag %}`. Тогда рендер без флагов - строгое подмножество рендера со всеми фичами, и один
`cargo check` со всеми фичами на шаблон ловит любое расхождение с API: спрятаться в выключенной
ветке нечему. Комбинации с выключенными флагами - забота статического написания (висящий `use`,
незаполненный слот), их проверяют локально, а не в CI.

## Кому что принадлежит

- Ядру (`ruststream`) принадлежит только `templates/memory` (брокер в процессе, который оно и
  поставляет), поэтому `cargo generate` по умолчанию работает офлайн и без зависимости от брокера.
- Каждому крейту брокера принадлежат шаблоны для его транспортов, и задачу о расхождении он гоняет в
  своём CI.
- Это разделение держит специфичный для брокера API вне CLI ядра: ядро ничего не знает про
  дескрипторы брокера, а шаблон живёт рядом с крейтом, который их определяет.
