# Conformance

Обвязка conformance доказывает, что брокер соблюдает контракт ядра. У неё две точки входа, и обе
паникуют с внятным сообщением на первом же нарушении контракта:

- `harness::run_suite` проверяет **поверхность маршрутизации** в
  [режиме работы внутри процесса](index.md#test-support): строит ваш рабочий брокер и подключает его
  через `InProcess::connect_in_process`.
- `harness::lifecycle` проверяет **последовательность переходов жизненного цикла** целиком на
  настоящем брокере.

Запускайте обе: `run_suite` - ради гарантий диспетчеризации, `lifecycle` - чтобы убедиться, что
`new` -> `connect(self)` -> подписка -> публикация -> ack -> `shutdown(self)` работает на реальном
транспорте.

```toml
[dev-dependencies]
ruststream = { version = "0.7", features = ["conformance"] }
```

Фича `conformance` включает `testing`, поэтому один и тот же режим работы внутри процесса, который
поставляет ваш крейт, годится и для `run_suite` здесь, и для обвязки
[`TestApp`](https://docs.rs/ruststream/latest/ruststream/testing/index.html), которую пишут пользователи.

## Набор проверок маршрутизации

`harness::run_suite` принимает синхронную фабрику (`Fn() -> B`). Фабрика строит свежий рабочий
брокер для каждого сценария, поэтому сценарии не видят состояния друг друга. Каждый сценарий
подключает брокер через `connect_in_process` и работает с подключённой формой, которая реализует
`TestableBroker` и `Subscribe`. Ниже приведён прогон набора у эталонного in-memory брокера.
Подставьте в фабрику конструктор своего брокера с теми настройками, с которыми его собирает сервис:

```rust
use ruststream::conformance::harness;

--8<-- "tests/conformance_self.rs:run_suite"
```

### Что именно он проверяет

| Сценарий | Что утверждается |
|---|---|
| порядок доставки | сообщения доставляются в порядке публикации |
| публикация до подписки | сообщение, опубликованное до открытия подписки, приходит первым, если брокер объявляет `Backlog::Delivered`, и не приходит вовсе, если он объявляет `Backlog::Missed` (по умолчанию); сообщение, опубликованное после, приходит в обоих случаях |
| ack поглощает доставку | подтверждённое сообщение не доставляется повторно |
| nack с requeue доставляет заново | `nack(requeue = true)` доставляет сообщение ещё раз |
| nack без requeue отбрасывает | после `nack(requeue = false)` повторной доставки нет |
| заголовки передаются | заголовки сообщения приходят к подписчику без изменений |
| лог публикаций фиксирует публикации | `published(name)` записывает каждое опубликованное сообщение |
| лог публикаций фиксирует ваш издатель | то, что отправил ваш издатель по умолчанию, лежит в `published(name)` рядом с тем, что внедрил тест, в порядке публикации и с заголовками (для брокера, зарегистрированного через `register_testable_broker!`) |
| две подписки на одно имя | каждое сообщение приходит ровно в те подписки, которые называет `TestableBroker::routes`, и в каждую по одному разу: при рассылке во все подписки, при конкурирующих потребителях в ту, которую выбирает брокер |
| счётчики обвязки сходятся | на остановленных часах, так, как их ведёт `TestApp`: доставка учитывается до возврата из публикации и снимается один раз при завершении, возврат в очередь учитывает её снова, публикация без получателей не учитывается, отложенная повторная доставка учитывается, когда истекает её таймер |

Транспорт, который не умеет подтверждать (ZeroMQ, MQTT `QoS 0`, Redis pub/sub, Core NATS),
возвращает `AckError::Unsupported` из `ack` и `nack`. Набор принимает такой ответ везде, где сам
завершает доставку. Внутрипроцессный транспорт обязан отвечать ровно так же, как настоящий, и не
заявлять о подтверждении, которого в бою нет. Исключение одно - сценарий повторной доставки: ответ
`Unsupported` на `nack(requeue = true)` завершает этот сценарий, потому что транспорт ничего не
забирает обратно и наблюдать нечего. Остальные сценарии проверяются как обычно, включая
отбрасывание: доставка, которую никто не может завершить, всё равно не приходит снова.

Набор читает ответ у доставки, а не у брокера. Поэтому ответ может различаться по подпискам и
сообщениям, как у самого транспорта: возврат в очередь бывает совещательным при одном режиме
коммитов и перематывающим при другом, подтверждение доступно на одном уровне качества обслуживания
и недоступно на другом. Смысл успеха не меняется: `Ok(())` из `nack(requeue = true)` обещает, что
сообщение вернётся, и путь повторов в рантайме читает этот ответ так же.

Эти сценарии - гарантии маршрутизации ядра, которые обязан соблюдать каждый брокер. Семантику
конкретного брокера (возобновление с durable-курсора, повторную доставку по таймауту, назначение
партиций) проверяет ваш собственный сквозной набор тестов против настоящего сервера.

У каждой совместимости свой набор, они описаны ниже. Ваш крейт вызывает наборы для тех
совместимостей, которые реализует. Только `capabilities::batches` проверяет, что пакет не больше
размера, с которым его открыли, поэтому одного `run_suite` для пакетов мало.

## Проверка жизненного цикла

`harness::lifecycle` проходит **последовательность переходов жизненного цикла** на настоящем
`Broker`:

1. синхронное конструирование без I/O;
2. `connect`, который поглощает `self` и возвращает типизированную подключённую форму;
3. подписка через собственный `SubscriptionSource` брокера;
4. публикация, которую подписка получает и подтверждает;
5. `shutdown`, который поглощает `self` и возвращает терминального свидетеля.

Каждый шаг выполняется оттуда, откуда к брокеру обращается сервис:

- Конструктор вызывается в обычном потоке без рантайма Tokio и обязан вернуть управление за
  секунду. Конструктор, который порождает задачу, вызывает `Handle::current` или ждёт сети, не
  проходит проверку. Если конструктор так и не вернул управление, проверка проваливается через эту
  секунду, а его поток продолжает работать в фоне.
- Подписка, первая публикация и каждое подтверждение выполняются в однопоточном рантайме на
  отдельном потоке. Проверка останавливает этот рантайм, прежде чем идти дальше. Подписка обязана
  продолжать получать сообщения. Издатель первого сообщения публикует ещё раз, из рантайма брокера и
  из нового рантайма, и оба сообщения обязаны дойти. `nack(requeue = true)`, ответивший `Ok`,
  обязан вернуть сообщение, а `nack(requeue = false)` не должен. Так проверка требует, чтобы
  внутренние задачи брокера выполнялись в рантайме, где он подключился (см.
  [Как написать брокер](index.md)).
- Если доставка умеет `nack_after`, проверка откладывает её на 1,5 с. Сообщение обязано вернуться не
  раньше этого срока и не позже чем через десять секунд после него. Брокер, который пропускает
  задержку, округляет её вниз или отсчитывает в рантайме вызывающего потока, проверку не проходит.
- `connect` и `shutdown` обязаны завершиться за десять секунд каждый, а открытие подписки,
  публикация и подтверждение - за две.

До последовательности переходов, на отдельном соединении, проверка смотрит, что доносит ваш
издатель. Тридцать два сообщения, опубликованные одно за другим, должны все прийти в одну подписку,
в любом порядке: секционированный транспорт раскладывает сообщения без ключа по разным секциям, а
порядок проверяет `keyed_order`. Ещё четыре сообщения несут заголовки: много записей, пустое
значение, значение не в UTF-8 и собственные заголовки фреймворка со счётчиком повторов и контекстом
трассировки. Каждый заголовок возвращается байт в байт, иначе публикация с ним обязана вернуть
ошибку. Сообщение с неудавшейся публикацией не приходит вовсе, даже после остальных. Заголовок,
потерянный или изменённый по пути, проваливает проверку. Подключение, подписка и каждая публикация
ограничены по времени, поэтому зависший брокер проваливает проверку, а не останавливает её.

Владелец подключённой формы не может обратиться к ней после остановки: такой код не компилируется.
Во время выполнения проверяется **контракт разделяемых дескрипторов**. После остановки публикация
обязана вернуть ошибку через любого издателя, созданного до неё: ни разу не использованного,
использованного только в рантайме брокера и использованного из остановленных рантаймов. Доставка,
полученная до остановки и возвращённая в очередь после неё, обязана вернуть ошибку или прийти снова.

Дескриптор подписки, подписчик, издатель и доставка переходят в другие потоки, поэтому все они
`'static`.

Проверка принимает три фабрики, и благодаря им она не зависит от брокера:

<!-- inline-rust: worked lifecycle check against the external ruststream-nats crate; its real gated suite lives in that repo, so it has no compiled home here -->
```rust
use ruststream::conformance::harness;
use ruststream_nats::{NatsBroker, SubscribeOptions};

#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
#[ignore = "needs a running nats-server; set NATS_TEST_URL"]
async fn passes_lifecycle() {
    let url = std::env::var("NATS_TEST_URL").unwrap();
    harness::lifecycle(
        move || NatsBroker::new(url.clone()), // sync construction (no I/O)
        |subject| SubscribeOptions::new(subject), // the broker's SubscriptionSource
        |connected| connected.publisher(), // a publisher from the connected form
    )
    .await;
}
```

- **`make_broker`** - **синхронная** (`Fn() -> B`) и `Send + Sync + 'static`. Проверка вызывает её
  в отдельном потоке, который может бросить, поэтому зависший конструктор проваливает проверку, а
  не вешает её. Замыкание, которое захватывает локальную переменную (например, адрес сервера),
  пишется с `move`. Брокер, который строится только асинхронно, сюда не подходит: конструируйте
  дёшево, а подключайтесь в `Broker::connect`.
- **`make_source`** строит дескриптор подписки на субъект (путь макро-подписчика).
- **`make_publisher`** создаёт издателя из подключённой формы.

Брокер без семантики ack (Core NATS) проходит проверку, возвращая из `ack` значение
`AckError::Unsupported`: проверка принимает и его, и успешный ack. `lifecycle` выполняет настоящий
`connect`, поэтому запускайте её против живого сервера и включайте только при заданной переменной
окружения, например `NATS_TEST_URL`.

## Остановка и разделяемые дескрипторы

Двум проверкам жизненного цикла нужен ответ, который знает только ваш брокер. Поэтому крейт
вызывает каждую из них сам, внутри процесса и против настоящего сервера:

| Проверка | Принимает | Проверяет |
|---|---|---|
| `lifecycle::shutdown_flushes` | ответ брокера `Backlog` | остановка доводит до конца подтверждение и публикацию, сделанные прямо перед `shutdown`. Подтверждённое сообщение не возвращается на новом соединении. Опубликованное доходит до другого соединения: нового при `Backlog::Delivered`, подписанного заранее при `Backlog::Missed`. Подтверждение после остановки, ответившее `Ok`, тоже обязано действовать. `shutdown` завершается за десять секунд |
| `lifecycle::shared_handle_closes` | подключённую форму с `Clone` | после остановки оригинала любое обращение через копию возвращает ошибку: издатель, созданный из неё до остановки или после, и подписка, которую она открывает (отказ или немедленное завершение) |

`shutdown_flushes` подключается несколько раз, поэтому `make_broker` каждый раз ведёт к одному и
тому же брокеру: к серверу, а внутри процесса к одному общему миру для всех построенных брокеров.
Брокер в памяти в собственном прогоне делит одну шину между копиями:

```rust
use ruststream::conformance::lifecycle;
use ruststream::testing::Backlog;

--8<-- "tests/conformance_self.rs:shutdown_flushes"
```

## Те же наборы внутри процесса

`lifecycle`, `redelivery_address` и наборы для совместимостей подключают брокер через
`Broker::connect`. Если обернуть рабочий брокер в `harness::InProcessBroker`, они подключат его через
`connect_in_process`. Тогда каждый набор проходит второй раз, без сервера, на ваших собственных
дескрипторах и политиках публикации.

Прогоняйте оба варианта. Проход внутри процесса держит честным режим работы внутри процесса, проход
против сервера проверяет настоящий транспорт. Ниже брокер, чей `connect` обращается к серверу,
проходит внутри процесса и набор маршрутизации, и проверку жизненного цикла:

```rust

```

## Набор проверок подтверждения

`settlement::suite` проверяет, что каждый способ завершить доставку делает то, что обещает, на
транспорте брокера, в том числе на живом сервере:

| Проверка | Что утверждается |
|---|---|
| ack поглощает доставку | подтверждённое сообщение не возвращается ни за время повторной доставки, ни на новом соединении с той же подпиской |
| nack без возврата отбрасывает | то же после `nack(requeue = false)` |
| nack с возвратом возвращает | `Ok(())` из `nack(requeue = true)` приводит сообщение обратно |
| подтверждение не по порядку | из трёх сообщений в обработке подтверждено третье, а первые два отпущены без подтверждения; первые два возвращаются: в ту же подписку, в неё же, открытую заново, или на новом соединении с ней |
| отпущенная доставка | сообщение, отпущенное без подтверждения из рантайма, который сразу останавливается, возвращается |

Завершение, ответившее `AckError::Unsupported`, проверка не ограничивает: транспорт ничего не
выполнил, и сообщение может вернуться на своей подписке или на новом соединении. Две последние
проверки заканчиваются, если `nack(requeue = true)` отвечает `AckError::Unsupported`: такой
транспорт ничего не забирает обратно, и повторной доставки не видно. Лог, который фиксирует
непрерывный префикс, может вместе с первыми двумя сообщениями снова доставить и подтверждённое
третье. Дубликат проверку проходит, потеря - нет.

```rust
--8<-- "src/conformance/settlement/tests.rs:matches_in_process"
```

- **`make_broker`** вызывается на каждое соединение, а проверка подключается дважды. Поэтому каждый
  возвращённый брокер обращается к одному серверу: на живом сервере к тому же адресу, внутри
  процесса к клонам одного брокера.
- **`make_source`** открывает одну и ту же подписку на обоих соединениях: durable-потребителя,
  очередь или группу потребителей, если они у брокера есть. Подписка допускает три доставки в
  обработке одновременно.
- **Время повторной доставки** - срок, за который брокер возвращает никем не завершённую доставку:
  ack wait, visibility timeout или ack deadline, заданный дескриптором. Брокер, который возвращает
  такую доставку только при закрытии соединения, передаёт `Duration::ZERO`.

`settlement::suite` возвращает ответ каждого способа завершения. `settlement::matches_in_process`
прогоняет набор против сервера и через `harness::InProcessBroker` и паникует, если ответы
расходятся. Внутрипроцессный транспорт, который заявляет подтверждение, отвергнутое сервером,
пропускает в тесте повтор обработчика, а в продакшене теряет сообщение.

## Проверки повторов {#retry-checks}

`type Copies` дескриптора говорит, как регистрация повторяет доставку. `conformance::retry`
проверяет каждый ответ, который что-то обещает сервису.

`harness::redelivery_address` принимает дескриптор с `AddressedCopies`. Проверка открывает по нему
две подписки, как две реплики сервиса читают одну подписку, и публикует копию по адресу, который
называет дескриптор. Копия уходит из однопоточного рантайма, который сразу после этого
останавливается: именно так копию для `retry_after` публикует обработчик на выделенных потоках.
Копия обязана дойти ровно до одной подписки группы (или до каждой, если транспорт отдаёт каждой
подписке всё) и прийти с заголовками и `RETRY_COUNT_HEADER` без изменений. Затем проверка дважды
возвращает её в очередь. Каждая повторная доставка сохраняет оба заголовка, а доставка, которая
сообщает `redelivery_count`, обязана насчитать 1, 2 и 3.

Если ваша подключённая форма отвечает `Subscribe::Copies = AddressedCopies`, прогоните проверку
второй раз с голым источником `Name`: этот ответ и есть адрес каждой регистрации
`#[subscriber("orders")]`.

```rust
--8<-- "src/conformance/retry/tests.rs:redelivery_address"
```

`retry::broker_moves` принимает дескриптор с `BrokerMoves`. Проверка объявляет `max_attempts(n)` и
адрес мёртвых писем, возвращает сообщение в очередь, пока предел не исчерпан, и ждёт его по адресу
мёртвых писем ровно один раз и ровно после `n` доставок. Если возврат в очередь отвечает
`AckError::Unsupported`, проверка на этом заканчивается: транспорт ничего не доставляет повторно, и
считать нечего. Каждую половину объявления по отдельности брокер обязан отклонить на старте.
Передайте `n`, который ваш брокер принимает. `make_source(name)` открывает и адрес мёртвых писем,
поэтому создаёт всё, что нужно для публикации в `name`.

<!-- inline-rust: worked dead-letter check against the external ruststream-lapin crate; its real suite lives in that repo, so it has no compiled home here -->
```rust
use ruststream::conformance::harness::InProcessBroker;
use ruststream::conformance::retry;
use ruststream::nonzero;
use ruststream_lapin::{LapinBroker, LapinPublish, RabbitQuorumQueue};

#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
async fn a_quorum_queue_dead_letters_at_the_cap() {
    retry::broker_moves(
        || InProcessBroker::new(LapinBroker::new("amqp://localhost:5672").declare_topology(true)),
        |name| RabbitQuorumQueue::new(name),
        |connected| connected.publisher(LapinPublish::default()),
        nonzero!(2u32),
    )
    .await;
}
```

## Транспорт внутри процесса против сервера

`conformance::in_process` сверяет то, что объявляет ваш транспорт внутри процесса, с тем, что делает
сервер. Оба набора подключают брокер дважды на каждую пробу, через `Broker::connect` и через
`connect_in_process`, поэтому запускайте их там же, где проверки против сервера:

<!-- inline-rust: worked check against the external ruststream-nats crate; its real gated suite lives in that repo, so it has no compiled home here -->
```rust
use ruststream::conformance::in_process::{self, Refusal};
use ruststream_nats::{CoreSubject, NatsBroker, NatsPublish};

#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
#[ignore = "needs a running nats-server; set NATS_TEST_URL"]
async fn in_process_matches_the_server() {
    let url = std::env::var("NATS_TEST_URL").unwrap();
    in_process::backlog_matches_server(
        || NatsBroker::new(url.clone()),
        |connected| connected.publisher(NatsPublish),
    )
    .await;
    in_process::refuses_like_the_server(
        || NatsBroker::new(url.clone()),
        |connected| connected.publisher(NatsPublish),
        [
            Refusal::PayloadOver { name: "conformance.payload".to_owned(), limit: 1024 * 1024 },
            Refusal::Publish { name: "conformance.bad subject".to_owned() },
            Refusal::Subscription { source: CoreSubject::new("conformance..empty") },
        ],
    )
    .await;
}
```

- **`backlog_matches_server`** на обоих транспортах публикует сообщение под новым именем,
  открывает подписку на это имя и публикует ещё одно. Первое сообщение приходит первым, если
  `TestableBroker::backlog` объявляет `Backlog::Delivered`, и не приходит вовсе, если он объявляет
  `Backlog::Missed`. Если сервер отвергает первую публикацию (очередь или тему никто не объявил),
  транспорт внутри процесса обязан её отвергнуть тоже. После этого на обоих транспортах подписка
  всё равно обязана открыться и получить второе сообщение.
- **`refuses_like_the_server`** принимает известные вам отказы, каждый в виде `Refusal`: полезная
  нагрузка на байт больше предела, отвергнутое назначение, отвергнутая подписка, подписка,
  отвергнутая рядом с другой. Каждый отказ должны дать оба транспорта. Проба, которую сервер
  принимает, считается ошибкой: она ничего не доказывает. Затем на каждом транспорте открываются
  две подписки на одно имя и одна на другое. Транспорт в процессе обязан принять ровно те, которые
  принимает сервер.


## Что несёт сообщение

Четырём проверкам из `conformance::message_shape` нужны данные, которые знает только ваш брокер,
поэтому ваш крейт вызывает их сам, против сервера и внутри процесса, как и остальные наборы:

| Проверка | Что вы передаёте | Что проверяется |
|---|---|---|
| `keyed_order` | субъект и место ключа: заголовок или поле параметров публикации | каждая доставка возвращает из `partition_key` ключ, с которым её опубликовали, а сообщения одного ключа приходят в порядке публикации |
| `publish_options` | субъект, политику публикации, набор случаев и способ прочитать настройку из доставки | публикация без параметров получает настройку политики; параметры вызова перекрывают её только для этого вызова; значение, которое транспорт не может выполнить, даёт ошибку публикации, и сообщение не приходит, даже после следующей публикации |
| `publishes_without_credentials` | политику публикации, настроенную с паролем | ни одна привязка, которую политика добавляет в документ, не содержит пароля |
| `describes_addresses_without_credentials` | брокер, построенный из нескольких адресов с пользователем и паролем | описание сервера не содержит этих учётных данных |

Транспорт без ключей не вызывает `keyed_order`: `None` для него честный ответ. Политику для
`publish_options` настройте на значение, отличное от умолчания транспорта: тогда издатель, который
забыл про политику, не пройдёт проверку, случайно попав в умолчание.

```rust
--8<-- "tests/conformance_message_shape.rs:keyed_order"
```

## Наборы проверок для совместимостей {#capability-suites}

Для каждой трейт-совместимости, которую реализует ваш брокер, запустите её набор из
`conformance::capabilities`: он доказывает, что реализация соблюдает контракт трейта. Наборы
принимают фабрики той же формы, что и `lifecycle`, и выполняют настоящий `connect`, поэтому
включайте их по той же переменной окружения. Каждый вызов набора ограничен по времени: зависший
брокер проваливает набор, а не останавливает его.

| Набор | Требует | Что утверждается |
|---|---|---|
| `capabilities::request_reply` | `RequestReply` | запрос доходит до отвечающей стороны с пригодным заголовком `reply-to`, соотнесённый ответ завершает запрос, а запрос без ответа возвращает ошибку по истечении своего таймаута; запрос, сделанный после того, как предыдущий пришёл из уже остановленного рантайма, всё равно завершается; два одновременных запроса получают каждый свой ответ, ответ, пришедший после таймаута своего запроса, не завершает следующий запрос, а запрос после остановки брокера сразу возвращает ошибку |
| `capabilities::batches` | `BatchSubscriber` | каждое опубликованное сообщение приходит в порядке публикации, распределённое по непустым пакетам; если сообщения, которые уже ждут к моменту чтения потока, хотя бы раз за пять попыток попадают в один пакет, элементы этого пакета подтверждаются по отдельности (`nack` с возвратом в очередь возвращает только этот элемент); подписка, которая никогда не объединяет их, проходит проверку, и раздельное подтверждение для неё не проверяется; пакет, подтверждённый из уже остановленного рантайма, подтверждается так же |
| `capabilities::batch_seeking` | `BatchSubscriber` и `Seekable`, сообщения `Positioned` | перемотка назад на позицию, снятую с сообщения из пакета, начинает следующие пакеты с этого сообщения, а за ним по порядку идёт всё остальное |
| `capabilities::transactions` | `TransactionalPublisher` | ничто внутри транзакции не видно до `commit`, `commit` публикует буфер по порядку, `abort` его отбрасывает; неверный вызов возвращает ошибку - `commit` / `abort` без открытой транзакции, второй `begin_transaction` при уже открытой (он обязан оставить её нетронутой); `commit` из уже остановленного рантайма всё равно публикует буфер, а после остановки брокера `commit` оставшейся открытой транзакции и обычная публикация возвращают ошибку |
| `capabilities::owned_transactions` | `OwnedTransactions` и его `Transaction` | ничто опубликованное в открытую транзакцию не видно до `commit`, `commit` доставляет весь буфер в порядке публикации, `abort` его отбрасывает, две транзакции, открытые одновременно на одном издателе, завершаются независимо, а сам издатель продолжает публиковать напрямую, пока одна из них открыта; `commit` из уже остановленного рантайма всё равно публикует буфер, а после остановки брокера ошибку возвращают `commit`, прямая публикация и транзакция, открытая после остановки |
| `capabilities::seeking` | `Seekable`, сообщения `Positioned` | перемотка назад на позицию, снятую с доставленного сообщения, повторно доставляет именно это сообщение и всё, что идёт за ним, по порядку; перемотка вперёд пропускает доставки, стоявшие в очереди до цели; после перемотки подписка продолжает доставлять новые публикации; новая подписка, которая до первой доставки перематывается на позицию, снятую предыдущей подпиской, начинает с этого сообщения, перемотка из уже остановленного рантайма всё равно срабатывает, а перемотка после остановки брокера возвращает ошибку |
| `capabilities::seeking_unknown_position` | `Seekable` и позиция, которую строит брокер | перемотка на позицию, которой нет в журнале подписки (вытеснена по сроку хранения или не существовала), возвращает ошибку и не сдвигает подписку: ничего не читается из другого места; ошибка в потоке не завершает проверку, и она читает следующую доставку |

<!-- inline-rust: worked request-reply capability check against the external ruststream-nats crate; its real gated suite lives in that repo, so it has no compiled home here -->
```rust
use ruststream::conformance::capabilities;
use ruststream_nats::{NatsBroker, SubscribeOptions};

#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
#[ignore = "needs a running nats-server; set NATS_TEST_URL"]
async fn passes_request_reply() {
    let url = std::env::var("NATS_TEST_URL").unwrap();
    capabilities::request_reply(
        || NatsBroker::new(url.clone()),
        |subject| SubscribeOptions::new(subject),
        |connected| connected.publisher(), // the RequestReply publisher under test
        |connected| connected.publisher(), // the plain publisher the responder replies through
    )
    .await;
}
```

Каждый прогон набора берёт новый субъект из `conformance::helpers::unique_subject` и читает только
то, что опубликовал сам. Фиксированный субъект проходит на свежем сервере, но не проходит на втором
прогоне у брокера, который хранит оставленное первым: удерживаемый лог воспроизведёт в одну
подписку оба прогона, durable-очередь ещё держит ранние сообщения, пространство ключей - ранний
тип. Ваш сквозной набор тестов решает ту же проблему тем же способом.

In-memory брокер реализует все совместимости нативно и проходит все семь наборов прямо в процессе
(см. [Memory](../brokers/memory.md#capabilities)). Это исполняемый эталон того, чего ждёт каждый
набор.

## Чеклист автора

Прежде чем публиковать крейт брокера, проверьте:

- [ ] Реализованы `Broker`, `ConnectedBroker`, `Subscribe` (или `SubscriptionSource`), `Subscriber`,
      `IncomingMessage`, `Publisher` и конструирующая его `PublishPolicy`.
- [ ] `shutdown` выполняет всё освобождение ресурсов, которое может вернуть ошибку, и не блокирует
      и не паникует.
- [ ] Ack поглощает `self`, nack учитывает флаг `requeue`.
- [ ] Крейт владеет своим `Config`, а поля без разумного умолчания не получают `Default`.
- [ ] Трейты-совместимости реализованы только там, где брокер их действительно поддерживает, и
      каждая реализованная совместимость проходит свой набор из `conformance::capabilities`.
- [ ] Режим работы внутри процесса поставляется под фичей `testing`: `InProcess` на брокере,
      `TestableBroker` на его подключённой форме и `register_testable_broker!(YourBroker)`.
      Внутрипроцессный транспорт берёт все настройки у рабочего брокера и отказывает везде, где
      отказывает настоящий брокер.
- [ ] `harness::run_suite` проходит (поверхность маршрутизации), а остальные наборы проходят и
      внутри процесса через `harness::InProcessBroker`, и против настоящего сервера.
- [ ] `harness::lifecycle` проходит против настоящего сервера и включается по переменной окружения:
      синхронный `new`, поглощающий `connect`, подписка, ack, поглощающий `shutdown` и ошибка
      разделяемого дескриптора после него.
- [ ] `lifecycle::shutdown_flushes` проходит с ответом брокера `Backlog`, а
      `lifecycle::shared_handle_closes` проходит там, где подключённая форма реализует `Clone`.
- [ ] `settlement::matches_in_process` проходит против настоящего сервера и включается по той же
      переменной: ack, nack, подтверждение не по порядку и отпущенная доставка значат одно и то же
      на сервере и внутри процесса.
- [ ] `harness::redelivery_address` проходит для каждого дескриптора с `AddressedCopies` и для
      голого `Name`, если `Subscribe::Copies` равен `AddressedCopies`. `retry::broker_moves`
      проходит для каждого дескриптора с `BrokerMoves`.
- [ ] Если у транспорта есть ключи или настройки отдельного сообщения, `message_shape::keyed_order`
      и `message_shape::publish_options` проходят внутри процесса и против настоящего сервера.
- [ ] Сквозной набор тестов покрывает семантику конкретного брокера и включается по той же
      переменной.
- [ ] Метаданные `Cargo.toml` заполнены полностью (`description`, `license`, `repository`,
      `keywords`, `categories`), а CI проверяет `--no-default-features` и `--all-features`.

Контракт трейтов описан в разделе [Как написать брокер](index.md).
