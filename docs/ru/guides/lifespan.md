# Жизненный цикл и разделяемое состояние

Большинству сервисов нужны общие для всех обработчиков ресурсы, которые создаются один раз на
старте: пул соединений с базой, HTTP-клиент, разобранная конфигурация. RustStream даёт для них одно
типизированное разделяемое состояние и выполняет хуки жизненного цикла в фиксированных точках вокруг
рабочего цикла.

## Разделяемое состояние

Состояние приложения - одно типизированное значение, которое возвращает хук `on_startup`. Любой
обработчик или middleware одалживает состояние через `ctx.state()`.

Раздел [Контекст и состояние](context.md#application-level-typed-state) описывает правила
монтирования, проверяемые во время компиляции, внедрение `State<T>` и контекст каждой доставки для
данных в области сообщения. Ниже - хуки, которые состояние создают и освобождают.

## Хуки жизненного цикла {#lifecycle-hooks}

Всё, что требует `async`-работы (подключить пул, аккуратно его закрыть), выполняется в хуке.
Рабочий цикл обрамляют четыре хука:

```text
on_startup(prev) -> S            # до подключения брокеров; создайте async-ресурсы и состояние
  -> брокеры подключаются, открываются подписки
after_startup(Arc<S>)            # обработчики живы; опубликуйте первое сообщение, сообщите о готовности
  ... работаем ...
  -> запрошена остановка (сигнал или завершился future из run_until)
on_shutdown(Arc<S>)              # брокеры ещё подключены
  -> брокеры останавливаются, обработчики в полёте дорабатывают
after_shutdown(Arc<S>)           # финальная уборка
```

- **`on_startup`** получает предыдущее состояние **по значению** (`()` при первом вызове) и
  возвращает новое, поэтому его future может владеть ресурсами между точками `await`: подключить
  пул, собрать структуру состояния, вернуть её. Последующие хуки получают состояние в совместное
  владение, как `Arc<S>`. Вызвать `on_startup` можно только до первого `with_broker`: обработчики
  регистрируются уже под произведённый им тип состояния, поэтому обратный порядок не компилируется.
  Остальные хуки жизненного цикла регистрируйте после него: хук, зарегистрированный раньше,
  захватил бы неверный тип состояния, и `on_startup` в этом случае паникует.
- **`after_startup`** выполняется, когда подписки уже открыты, а обработчики живы. Первое сообщение
  публикуйте формой уровня области `b.after_startup(policy, hook)`: момент тот же, а хук получает
  живого издателя, которого политика инстанцирует на подключённом брокере. Хук уровня приложения
  остаётся для сигнала о готовности и работы, не связанной с брокером; так его использует
  [руководство по тестированию](testing.md). Здесь же место для первых сообщений, которые приложение
  потребляет само: опубликованное до этого момента сообщение не дойдёт ни до одного подписчика.
- **`on_shutdown`** выполняется, когда остановка началась, а брокеры ещё подключены.
- **`after_shutdown`** выполняется после остановки брокеров, для финальной асинхронной уборки.

Ошибка в хуке старта прерывает запуск сервиса. Хук остановки только логирует свою ошибку, поэтому
остановка всегда доходит до конца. Хуки одного вида выполняются в порядке регистрации.

## Как передать соединение с базой

Типичный случай: открыть пул до начала работы, отдать его каждому обработчику, закрыть при
остановке. `Database` ниже - заглушка вместо любого асинхронного ресурса: `sqlx::PgPool` или
HTTP-клиент подставляются так же, отличаются только вызовы `connect` / `close`:

=== "Макросы"

    ```rust
    --8<-- "examples/lifespan.rs:hooks"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/lifespan.rs:hooks"
    ```

Тип ошибки хука выводится из возвращаемого `Result`; достаточно, чтобы он реализовал
`std::error::Error + Send + Sync`. Ресурс реализует `Send + Sync`, поэтому все параллельные
обработчики одалживают один общий экземпляр через `ctx.state()` и не настраивают соединение заново
на каждое сообщение:

=== "Макросы"

    ```rust
    --8<-- "examples/lifespan.rs:handler"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/lifespan.rs:handler"
    ```

Запускаемая программа -
[`examples/lifespan.rs`](https://github.com/powersemmi/ruststream/blob/main/examples/lifespan.rs).

## Работа рядом с другим сервером

`run` владеет всем процессом: он ставит обработчики сигналов и возвращает управление только после
того, как сервис остановился.

Сервис, который делит процесс с другим сервером на переднем плане (обычно с HTTP-фреймворком),
запускает сторону обмена сообщениями через `start`. Метод `start` выполняет ту же последовательность
старта и завершается, когда подписки открыты, поэтому ошибку запуска вы получите раньше, чем хозяин
процесса начнёт принимать трафик. Обработчиков сигналов `start` не ставит: чем остановить сервис,
решает хозяин. Дальнейшим жизненным циклом управляет возвращённый дескриптор `RunningApp`:

```rust
--8<-- "tests/app_start.rs:handle"
```

- `stopping()` возвращает владеющий future, который завершается, когда сервис остановился сам по
  отказу в режиме fail-fast. Его можно подставить в штатную остановку хозяина
  (`with_graceful_shutdown` в axum), чтобы процесс перестал обслуживать запросы, как только сторона
  обмена сообщениями остановилась.
- `shutdown()` - это явная штатная остановка: хуки `on_shutdown`, ожидание обработчиков в полёте и
  продолжений после завершения доставки (в пределах [таймаута остановки](#shutdown-timeout)),
  остановка брокеров в порядке, обратном порядку регистрации, затем хуки `after_shutdown`. Причину
  отказа в режиме fail-fast `shutdown()` возвращает ошибкой.

Дескриптор помечен `#[must_use]`: уничтожить его, не вызвав `shutdown`, - значит отсоединить сервис
без штатной остановки. `run` и `run_until` построены на том же пути start/shutdown, поэтому все три
формы проходят одну последовательность старта и остановки.

## Таймаут остановки {#shutdown-timeout}

По умолчанию после запроса остановки `run` ждёт завершения обработчиков в полёте неограниченно
долго. Ограничить это ожидание можно через `shutdown_timeout`, как в примере выше. Обработчики,
которые не успели к его истечению, прерываются:

<!-- inline-rust: isolates the shutdown_timeout call; the full chain is compiled in lifespan.rs:hooks, shown earlier on this page -->
```rust
use std::time::Duration;

RustStream::new(info)
    .shutdown_timeout(Duration::from_secs(10))
    .with_broker(broker, |b| { b.include(handle); });
```
