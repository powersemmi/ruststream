# Жизненный цикл и общее состояние

Почти любому сервису нужны ресурсы, которые создаются один раз на старте и общие для всех
обработчиков: пул к базе, HTTP-клиент, разобранная конфигурация. RustStream даёт одно типизированное
общее состояние и хуки жизненного цикла, которые выполняются в фиксированных точках вокруг рабочего
цикла.

## Общее состояние

Состояние приложения - одно типизированное значение, которое производит хук `on_startup`: что хук
вернул, то и становится состоянием, фиксируя тип состояния приложения. Любой обработчик или
middleware одалживает его через `ctx.state()`. Полная история про состояние - правила монтирования,
проверяемые во время компиляции, внедрение `State<T>` и контекст на каждую доставку для данных в
области сообщения - изложена в разделе
[Контекст и состояние](context.md#application-level-typed-state); эта страница - про хуки, которые
состояние создают и разбирают.

## Хуки жизненного цикла {#lifecycle-hooks}

Всё, что требует `async`-работы (подключить тот самый пул, аккуратно его закрыть), уходит в хук.
Рабочий цикл обрамляют четыре хука:

```text
on_startup(prev) -> S            # до подключения брокеров; создайте async-ресурсы и состояние
  -> брокеры подключаются, открываются подписки
after_startup(Arc<S>)            # обработчики живы; опубликуйте первое сообщение, сообщите о готовности
  ... работаем ...
  -> запрошена остановка (сигнал или завершился future из run_until)
on_shutdown(Arc<S>)              # брокеры ещё подключены
  -> брокеры останавливаются, обработчики в полёте дорабатывают
after_shutdown(Arc<S>)           # финальная уборка
```

- **`on_startup`** получает предыдущее состояние **по значению** (`()` при первом вызове) и
  возвращает новое, поэтому его future может владеть ресурсами между точками `await`: подключить
  пул, собрать структуру состояния, вернуть её. Возвращённый тип и становится типом состояния приложения.
  Ошибка в `on_startup` прерывает старт. Последующие хуки получают состояние как разделяемый
  `Arc<S>`. `on_startup` существует только до первого `with_broker`: обработчики регистрируются
  против производимого им типа состояния, поэтому обратный порядок не соберётся. Остальные хуки
  жизненного цикла регистрируйте после него (хук, зарегистрированный раньше, замкнулся бы на неверный
  тип состояния; если такой уже есть, `on_startup` паникует).
- **`after_startup`** выполняется, когда подписки уже открыты, а обработчики живы. Для публикации
  первого сообщения предпочитайте форму уровня области `b.after_startup(policy, hook)`: момент тот
  же, но хук получает уже сведённого живого издателя, и ничего не приходится вытаскивать наружу из
  замыкания связывания. Хук уровня приложения остаётся для сигнала о готовности и работы, не
  связанной с брокером ([руководство по тестированию](testing.md) использует его как признак
  «обработчики живы»). Ошибка в любом из них прерывает старт. Это же и единственно верный по доставке
  момент для затравочных сообщений, которые приложение потребляет само: публикация до открытия
  подписок не найдёт ни одного подписчика.
- **`on_shutdown`** выполняется, когда остановка началась, а брокеры ещё подключены.
- **`after_shutdown`** выполняется после того, как брокеры остановлены, - для финальной асинхронной
  уборки.

Хуки старта при ошибке прерывают сервис; хуки остановки только логируют свою ошибку, поэтому
остановка всегда доходит до конца. Хуки одного вида выполняются в порядке регистрации.

## Как передать соединение с базой

Типичный случай: открыть пул до начала работы, раздать его каждому обработчику, закрыть на выходе.
`Database` ниже - заглушка вместо любого асинхронного ресурса: `sqlx::PgPool` или HTTP-клиент встают
на то же место, отличаются только вызовы `connect` / `close`:

=== "Макросы"

    ```rust
    --8<-- "examples/lifespan.rs:hooks"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/lifespan.rs:hooks"
    ```

Тип ошибки хука выводится из возвращаемого `Result`; от него требуется только реализовать
`std::error::Error + Send + Sync`. Ресурс `Send + Sync`, поэтому все параллельные обработчики
одалживают один общий экземпляр через `ctx.state()` - никакой настройки соединения на каждое
сообщение:

=== "Макросы"

    ```rust
    --8<-- "examples/lifespan.rs:handler"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/lifespan.rs:handler"
    ```

Запускаемая программа -
[`examples/lifespan.rs`](https://github.com/powersemmi/ruststream/blob/main/examples/lifespan.rs).

## Работа рядом с другим сервером

`run` владеет всем процессом: он ставит обработчики сигналов и возвращает управление только после
того, как сервис остановился. Сервис, который делит процесс с другим сервером на переднем плане
(обычно с HTTP-фреймворком), поднимает сторону обмена сообщениями через `start`. Тот выполняет ту же
последовательность старта и завершается, когда подписки открыты, - так что сбой на старте всплывёт
раньше, чем хозяин процесса начнёт принимать трафик, - и не ставит ни одного обработчика сигналов:
чем остановить сервис, решает хозяин. Дальнейшим жизненным циклом управляет возвращённый хендл
`RunningApp`:

```rust
--8<-- "tests/app_start.rs:handle"
```

- `stopping()` возвращает владеющий future, который завершается, когда сервис сворачивается сам из-за
  отказа в режиме fail-fast; подставьте его в штатную остановку хозяина (`with_graceful_shutdown` в
  axum), чтобы процесс перестал обслуживать запросы, как только сторона обмена сообщениями умерла.
- `shutdown()` - это явная штатная остановка: хуки `on_shutdown`, слив обработчиков в работе и
  продолжений после завершения доставки (ограниченный [таймаутом остановки](#shutdown-timeout)),
  остановка
  брокеров в порядке, обратном порядку регистрации, затем хуки `after_shutdown`. Причина fail-fast
  всплывает здесь как ошибка.

Хендл помечен `#[must_use]`: уронить его, не вызвав `shutdown`, значит отсоединить сервис без всякой
штатной остановки. `run` и `run_until` построены на том же пути start/shutdown, поэтому все три формы
делят одну последовательность старта и остановки.

## Таймаут остановки {#shutdown-timeout}

По умолчанию после запроса остановки `run` ждёт завершения обработчиков в полёте сколько угодно
долго. Ограничьте это ожидание через `shutdown_timeout`, как в примере выше; обработчики, всё ещё
работающие по его истечении, прерываются:

<!-- inline-rust: isolates the shutdown_timeout call; the full chain is compiled in lifespan.rs:hooks, shown earlier on this page -->
```rust
use std::time::Duration;

RustStream::new(info)
    .shutdown_timeout(Duration::from_secs(10))
    .with_broker(broker, |b| b.include(handle));
```
