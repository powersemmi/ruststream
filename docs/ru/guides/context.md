# Контекст и состояние

Всё, до чего обработчик может дотянуться помимо своей полезной нагрузки, приходит через два объекта
с разным временем жизни:

| Уровень | Тип | Время жизни | Содержит |
|---|---|---|---|
| Приложение | тип состояния `S` | всё время работы сервиса | разделяемые ресурсы: пулы, клиенты, конфигурацию |
| Доставка | `Context<'_, C, S>` | одно сообщение | имя канала, рабочую копию заголовков, типизированный контекст брокера на одну доставку `C` (читается по ключу) и типизированное разделяемое состояние `S` |

Состояние создаётся один раз, на старте, и хранится как одно типизированное значение, которое вы
выбираете сами. `Context` строится заново для каждой доставки и протягивается как `&mut` через
цепочку middleware в обработчик, поэтому middleware и обработчик видят (и могут обогащать) один и
тот же взгляд на текущее сообщение.

## Уровень приложения: типизированное состояние {#application-level-typed-state}

Разделяемое состояние приложения - это одно типизированное значение `S` (ваша структура или `()`,
если сервису состояние не нужно). Его создаёт хук `on_startup`: возвращённое хуком значение и
становится состоянием, фиксируя тип состояния приложения.

```rust
--8<-- "examples/context.rs:app"
```

Тип состояния проверяется во время компиляции: обработчик `#[subscriber]`, который читает состояние,
называет его третьим типовым параметром `Context` (`Context<'_, C, S>`), и рантайм даст смонтировать
такой обработчик только на приложение с совпадающим типом состояния. Обработчик, который тип
состояния не называет, обобщён по нему и монтируется на любое приложение. Обработчики с `publish(..)`
подчиняются тому же правилу с одной оговоркой: тот, кто состояние игнорирует, опускает параметр
`Context` целиком и всё равно монтируется на приложение с состоянием, а вот тот, кто `Context`
объявил, но тип состояния не назвал, прибивает состояние к `()`, - поэтому, чтобы смонтировать такой
обработчик на приложение с состоянием, тип состояния нужно назвать явно.

Обработчики берут состояние взаймы через `ctx.state()`: он возвращает `&S`, то самое типизированное
состояние, - без поиска по ключу и без `Option`, который пришлось бы разворачивать. Пока сервис
работает, состояние разделяется за `Arc`, так что обработчики получают дешёвые общие ссылки, а не
копии; если разделяемое значение должно меняться во время работы, инструмент - внутренняя
изменяемость (`AtomicU64`, карта под мьютексом). Для данных в пределах одного сообщения, а не всего
сервиса, есть [контекст на одну доставку](#per-delivery-context). Контракт хука старта описан в
разделе [Жизненный цикл](lifespan.md).

```rust
--8<-- "examples/context.rs:state"
```

## Внедрение зависимостей: параметры-экстракторы {#injecting-dependencies-extractor-parameters}

Дотянуться до зависимости через `ctx.state().field` можно всегда, но обработчик может принять её и
параметром. Любой параметр обработчика после сообщения (и после необязательного `&mut Context`) с
типом, реализующим `FromContext`, - это **экстрактор**: рантайм разрешает его из доставки до того,
как выполнится тело, а неудачная выборка завершает доставку сообщения по `HandlerResult` из отказа, так
и не запустив тело.

Чтобы внедрить кусок состояния, выведите на состоянии `FromRef` и принимайте в обработчике
`State<T>` - реализацию экстрактора писать руками не нужно. `State<T>` разрешается для поля любого
типа (`T: FromRef<S>`), включая типы из других крейтов - издатель брокера, пул клиентов:

```rust
--8<-- "examples/from_context.rs:state"
```

Обработчик принимает `State<FieldType>` и никуда не тянется через `ctx.state()`:

```rust
--8<-- "examples/from_context.rs:handler"
```

Поле, которое внедрять не нужно или тип которого уже занят другим полем, отказывается от внедрения
через `#[from_ref(skip)]`; два поля не могут иметь один тип, иначе внедрение по типу стало бы
неоднозначным. Для своего экстрактора, который делает больше, чем чтение состояния (auth guard,
отклоняющий доставку, резолвер в пределах запроса), реализуйте `FromContext` напрямую: он занимает
`&mut Context`, поэтому может читать заголовки, поля брокера или черновое значение, оставленное
middleware, и вернуть `Rejection`, чтобы завершить доставку.

## Уровень доставки: `Context`

Обработчик `#[subscriber]` подключается к контексту, объявив второй параметр после полезной
нагрузки; если обработчику ничего, кроме сообщения, не нужно, параметр опускают. Тип разрешает сам
макрос, поэтому импортировать `Context` не требуется, пока он встречается только в сигнатурах
обработчиков:

```rust
--8<-- "examples/context.rs:handler"
```

Что даёт контекст:

| Метод | Возвращает | Зачем |
|---|---|---|
| `name()` | `&str` | канал / субъект, по которому пришло сообщение |
| `headers()` | `&HeaderMap` | рабочая копия заголовков сообщения |
| `headers_mut()` | `&mut HeaderMap` | та же копия, чтобы middleware её обогащал |
| `state()` | `&S` | типизированное разделяемое состояние приложения, взятое напрямую |
| `context(KEY)` | `KEY::Value` | [поле брокера](#per-delivery-context), читаемое по ключу времени компиляции |
| `set(KEY, v)` | `()` | записать [черновое значение](#per-delivery-context) на одну доставку (для middleware) |
| `after(outcome).then(fut)` | `()` | [хук после завершения доставки](#post-settle-hooks), привязанный к исходу завершения |
| `after_ack(fut)` / `after_settle(fut)` | `()` | сахар для хуков после завершения доставки (после ack / после любого завершения) |

Обработчики-замыкания (ручная форма `typed(codec, |msg, ctx| ...)`) всегда принимают контекст вторым
аргументом.

## Контекст на одну доставку {#per-delivery-context}

Кроме разделяемого состояния приложения контекст несёт типизированный контекст брокера на одну
доставку, и читается он по **ключу времени компиляции**, ничего не стоя на пути доставки. Ключ - это
селектор, который экспортирует брокер; `ctx.context(KEY)` читает поле прямо из контекста, поэтому
обработчик получает родные метаданные доставки (идентификатор потока, смещение, дескриптор доставки),
а брокеру не приходится сериализовать их в чисто байтовые заголовки. Ключ, которого нет у брокера
этой подписки, - ошибка компиляции, а не промах во время работы.

```rust
--8<-- "examples/context_field.rs:field"
```

Тип контекста строит из сообщения `BuildContext`, который рантайм вызывает по разу на доставку;
брокер без полей на доставку берёт `()` - значение по умолчанию (поэтому обработчик `#[subscriber]`,
который не называет тип контекста и не принимает [экстрактор `Ctx`](#context-fields-as-parameters),
видит `Context<'_>`). Middleware умеет ещё и передавать типизированное черновое значение обработчику
ниже по цепочке: по записываемому ключу (`FieldMut`) слой делает `ctx.set(KEY, value)`, а
обработчик читает значение обратно через `ctx.context(KEY)`: correlation id, аутентифицированный
пользователь, которого разрешил слой, - и всё это без сериализации в заголовки. Контекст строится
заново на каждую доставку, поэтому значения одной доставки никогда не протекают в следующую.

## Поля контекста как параметры {#context-fields-as-parameters}

Поле может прийти и аргументом обработчика - так же, как `State<T>` внедряет часть состояния:
экстрактор `Ctx<K>` связывает значение, которое читает ключ `K`. Параметр `&mut Context` обработчику
вообще не нужен: макрос `#[subscriber]` выводит тип контекста подписки из первого ключа `Ctx` в
сигнатуре.

```rust
--8<-- "examples/ctx_extractor.rs:key"
```

```rust
--8<-- "examples/ctx_extractor.rs:handler"
```

Три вещи, которые стоит знать:

- Значения владеемые: экстрактор связывается до того, как выполнится тело обработчика, поэтому занять
  значение у контекста он не может. Ключи, отдающие заимствованные значения (имя как `&str`),
  по-прежнему читаются через `ctx.context(KEY)`, если параметр ctx объявлен.
- Если параметр `&mut Context<'_, C>` тоже присутствует, каждый ключ `Ctx` обязан читать тот же
  самый `C`.
- Вывод типа синтаксический: макрос распознаёт буквальную форму `Ctx<K>` (любой путь, оканчивающийся
  на `Ctx`, с одним типовым аргументом). Псевдоним типа её прячет, и тип контекста откатывается к
  `()`.

## Рабочая копия заголовков {#the-headers-working-copy}

`ctx.headers()` - это не само сообщение брокера: каждая доставка копирует входящие заголовки в
рабочую копию, которая хранится в контексте. Тем самым копия становится черновиком для цепочки
диспетчеризации: middleware раньше по цепочке проставляет в неё значения через `headers_mut()`, а
обработчик читает уже обогащённый результат:

```rust
--8<-- "examples/context.rs:enrich"
```

Смонтированный глобально слой выполняется перед каждым обработчиком, поэтому `handle` выше всегда
находит `x-request-id`:

```rust
--8<-- "examples/context.rs:app"
```

Две границы, о которых стоит помнить:

- Изменения не выходят за пределы доставки: само сообщение брокера и доставки других подписчиков
  остаются нетронутыми.
- Исходящие сообщения эту копию не наследуют. Ответы и ручные публикации начинают с чистых
  заголовков; исходящие метаданные вешайте в
  [конвейере публикации](publishing.md#the-publish-pipeline) - через `PublishTransform` или
  `PublishLayer`.

## Публикация из обработчика

Чтобы публиковать изнутри обработчика (помимо формы ответа `publish(..)`), не кладите издателя в
состояние: принимайте его параметром обработчика через `Out` - шаблон
`Out(out): Out<impl Publisher>` связывает `out` с живым издателем внутри тела. Политика
прикрепляется там, где обработчик включается в приложение, конкретный тип издателя выводится из
неё, а рантайм связывает их после того, как брокер подключился. Полный шаблон и его фрагмент - в
разделе
[Публикация изнутри обработчика](publishing.md#publishing-from-inside-a-handler).

## Хуки после завершения доставки {#post-settle-hooks}

Иногда обработчику нужен побочный эффект, который сработает *после* того, как доставка сообщения
завершена, - некритичное уведомление, медленная дополнительная работа, прогрев кеша, - и при
этом не влияет ни на решение об ack, ни на повторную доставку. Зарегистрируйте такой эффект на
контексте:

```rust
--8<-- "examples/context.rs:handler"
```

Обработчик выше заканчивается вызовом `ctx.after_ack(..)`: продолжение выполняется, только когда
брокер сделал ack сообщения, и вне пути доставки, поэтому оно никогда не задерживает ни ack, ни
следующую доставку.

Три формы, и все складываются:

- `ctx.after(outcome).then(fut)` - выполняется, только если доставка сообщения завершилась исходом
  `outcome`, причём сопоставление идёт **по виду**. Четыре вида различаются: `Ack`, `drop()` (nack
  без возврата в очередь), `retry()` (nack с возвратом в очередь) и `retry_after()` (совпадает
  независимо от задержки). Drop и retry - разные механики, поэтому хук, привязанный к `drop()`, не
  сработает, когда доставка завершилась через `retry()`, и наоборот.
- `ctx.after_ack(fut)` - сахар для `ctx.after(HandlerResult::Ack).then(fut)`.
- `ctx.after_settle(fut)` - выполняется после завершения доставки, каким бы ни был исход.

Обработчик может прикрепить продолжение и через возвращаемое значение: любой исход превращается в
`Settle` вызовом `.and_after(fut)` - именно так пакетный обработчик получает продолжения на каждый
элемент. Эта форма описана в разделе
[Продолжения после завершения доставки](subscribers.md#post-settle-continuations); семантика ниже
относится к обеим.

Несколько регистраций накапливаются, и выполняются все подходящие - в отслеживаемом наборе задач вне
пути доставки. Семантика здесь **at-most-once**: доставка сообщения уже завершена до того, как
запустится любой хук, поэтому хук, который упал в панику или потерялся при аварийном завершении
процесса, никогда не приводит к повторной доставке. Не кладите в хук работу, потеря которой обязана
вызвать повторную доставку сообщения: завершите доставку подходящим исходом и дайте брокеру
повторить попытку. Плавная остановка дожидается хуков в полёте (в пределах `shutdown_timeout`);
прерванная остановка может их потерять.

На пакетном пути `Context` один на *пакет*, поэтому хук выполняется после того, как завершена
доставка всего пакета. У пакета исходы свои на каждый элемент, поэтому отбор по исходу здесь не определён:
срабатывают только хуки `after_settle` (формы с отбором - `after(..)` и `after_ack` - на пакете
игнорируются).

## Контекст в middleware

Каждая форма middleware получает тот же `&mut Context`, который увидит обработчик:

- `Handler::handle(&self, msg, ctx)` у статического слоя - как в примере выше.
- Динамический `DynMiddleware::handle(&self, input, ctx, next)` - посмотреть или обогатить, а затем
  вызвать `next.run(input, ctx)`.

Сами формы middleware разобраны в разделе [Middleware](middleware.md). Полная программа для этой
страницы -
[`examples/context.rs`](https://github.com/powersemmi/ruststream/blob/main/examples/context.rs).
