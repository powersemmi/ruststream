# Контекст и состояние

Всё, кроме полезной нагрузки, обработчик получает через два объекта с разным временем жизни:

| Уровень | Тип | Время жизни | Содержит |
|---|---|---|---|
| Приложение | тип состояния `S` | всё время работы сервиса | разделяемые ресурсы: пулы, клиенты, конфигурацию |
| Доставка | `Context<'_, C, S>` | одно сообщение | имя канала, рабочую копию заголовков, типизированный контекст брокера на одну доставку `C` (читается по ключу) и типизированное разделяемое состояние `S` |

Состояние создаётся один раз, на старте. Его тип вы выбираете сами. `Context` создаётся заново на
каждую доставку и передаётся как `&mut` по цепочке middleware в обработчик. Middleware и обработчик
работают с одним и тем же объектом, поэтому обработчик видит всё, что добавил в него middleware.

## Уровень приложения: типизированное состояние {#application-level-typed-state}

Разделяемое состояние приложения - это одно типизированное значение `S`: ваша структура или `()`,
если состояние сервису не нужно. Создаёт его хук `on_startup`, и тип возвращённого значения
становится типом состояния приложения.

=== "Макросы"

    ```rust
    --8<-- "examples/context.rs:app"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/context.rs:app"
    ```

Тип состояния проверяется во время компиляции. Обработчик, который читает состояние, называет его
последним типовым параметром `Context` (`Context<'_, C, S>`) и монтируется только на приложение с тем
же типом состояния. Обработчик, который тип состояния не называет, обобщён по нему и монтируется на
любое приложение.

У обработчиков с `publish(..)` то же правило и одна особенность. Тот, кто состояние не читает,
опускает параметр `Context` целиком и всё равно монтируется на приложение с состоянием. Тот, кто
`Context` объявил, но тип состояния не назвал, закрепляет за состоянием `()`. Назовите тип состояния
явно, чтобы смонтировать такой обработчик на приложение с состоянием.

Состояние обработчик читает через `ctx.state()`: метод возвращает `&S`. Состояние находится в
совместном владении, поэтому все обработчики работают с одним значением. Значение, которое должно
меняться во время работы, хранят через внутреннюю изменяемость: `AtomicU64`, ассоциативный массив
под мьютексом.

Данные в пределах одной доставки, а не всего сервиса, хранит
[контекст на одну доставку](#per-delivery-context). Хук старта описан в разделе
[Жизненный цикл](lifespan.md).

```rust
--8<-- "examples/context.rs:state"
```

## Внедрение зависимостей: параметры-экстракторы {#injecting-dependencies-extractor-parameters}

Зависимость всегда доступна через `ctx.state().field`, но обработчик может принять её и параметром.

**Экстрактор** - это параметр обработчика, тип которого реализует `FromContext`. Экстракторы идут
после сообщения и после необязательного параметра `&mut Context`. Рантайм вычисляет значение
экстрактора из доставки до того, как выполнится тело обработчика. Экстрактор, вернувший отказ,
завершает доставку своим исходом, и тело не выполняется.

Чтобы внедрить часть состояния, выведите на состоянии `FromRef` и объявите в обработчике параметр
`State<T>`. `State<T>` работает с полем любого типа (`T: FromRef<S>`), в том числе с типом из
другого крейта: издателем брокера, пулом клиентов:

=== "Макросы"

    ```rust
    --8<-- "examples/from_context.rs:state"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/from_context.rs:state"
    ```

Обработчик принимает `State<FieldType>` параметром:

=== "Макросы"

    ```rust
    --8<-- "examples/from_context.rs:handler"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/from_context.rs:handler"
    ```

Два поля состояния не могут иметь один тип: внедрение идёт по типу. Поле, которое внедрять не нужно
или тип которого уже занят другим полем, вы можете исключить атрибутом `#[from_ref(skip)]`.

Экстрактор, который делает больше, чем чтение состояния, вы реализуете сами через `FromContext`: так
пишут проверку доступа, отклоняющую доставку, или поиск зависимости в пределах одного запроса. Такой
экстрактор получает `&mut Context` и может читать заголовки, поля брокера или черновое значение,
оставленное middleware. Чтобы завершить доставку, он возвращает `Rejection`.

## Уровень доставки: `Context`

Обработчик `#[subscriber]` объявляет контекст вторым параметром после полезной нагрузки;
обработчику, которому хватает самого сообщения, этот параметр не нужен. Тип подставляет сам макрос,
поэтому импорт `Context` не нужен, пока этот тип встречается только в сигнатурах обработчиков:

=== "Макросы"

    ```rust
    --8<-- "examples/context.rs:handler"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/context.rs:handler"
    ```

Что даёт контекст:

| Метод | Возвращает | Зачем |
|---|---|---|
| `name()` | `&str` | канал или субъект, по которому пришло сообщение |
| `headers()` | `&HeaderMap` | рабочая копия заголовков сообщения |
| `headers_mut()` | `&mut HeaderMap` | та же копия, чтобы middleware её дополнял |
| `state()` | `&S` | типизированное разделяемое состояние приложения |
| `context(KEY)` | `KEY::Value` | [поле брокера](#per-delivery-context) по ключу времени компиляции |
| `set(KEY, v)` | `()` | [черновое значение](#per-delivery-context) на одну доставку, для middleware |
| `after(outcome).then(fut)` | `()` | [хук после завершения доставки](#post-settle-hooks) с отбором по исходу |
| `after_ack(fut)` / `after_settle(fut)` | `()` | сахар: хук после ack и хук после любого завершения |

## Контекст на одну доставку {#per-delivery-context}

Кроме разделяемого состояния приложения контекст хранит типизированный контекст брокера на одну
доставку - собственные метаданные доставки: идентификатор потока, смещение, дескриптор доставки.

Обработчик читает их по **ключу времени компиляции**. Ключ - это селектор, который экспортирует
брокер; `ctx.context(KEY)` возвращает значение поля прямо из контекста, без сериализации в байтовые
заголовки. На пути доставки такое чтение ничего не стоит. Ключ, которого нет у брокера этой
подписки, - ошибка компиляции.

```rust
--8<-- "examples/context_field.rs:field"
```

У брокера без полей на доставку тип контекста - `()`, значение по умолчанию: обработчик, который не
называет тип контекста и не принимает [экстрактор `Ctx`](#context-fields-as-parameters), видит
`Context<'_>`.

Middleware может передать типизированное черновое значение обработчику ниже по цепочке: correlation
id, пользователя, которого слой аутентифицировал. По записываемому ключу (`FieldMut`) слой вызывает
`ctx.set(KEY, value)`, а обработчик читает значение через `ctx.context(KEY)`. Следующая доставка
этих значений не увидит.

[Пакетный обработчик](subscribers.md#batch-subscribers) получает один контекст на весь пакет, и в
нём лежат только поля брокера уровня *подписки*: дескриптор перемотки, имя потока. Данных отдельной
доставки там нет - пакет охватывает много доставок, поэтому позиция и заголовок хранятся на его
элементах.

Тело пакетного обработчика объявляет этот тип своим типом контекста
(`ctx: &mut Context<'_, MemoryBatchContext>` на in-memory брокере) и читает поля через
`ctx.context(..)`. Типы контекста доставки и пакета разные, поэтому пакетное тело с контекстом
доставки не компилируется. У брокера без полей уровня подписки тип пакетного контекста - `()`.

## Поля контекста как параметры {#context-fields-as-parameters}

Поле контекста может прийти и аргументом обработчика, как `State<T>` внедряет часть состояния:
экстрактор `Ctx<K>` связывает значение, которое читает ключ `K`. Параметр `&mut Context` при этом не
нужен: макрос `#[subscriber]` выводит тип контекста подписки из первого ключа `Ctx` в сигнатуре.

```rust
--8<-- "examples/ctx_extractor.rs:key"
```

=== "Макросы"

    ```rust
    --8<-- "examples/ctx_extractor.rs:handler"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/ctx_extractor.rs:handler"
    ```

Три особенности этой формы:

- Экстрактор отдаёт значение во владение: он связывается до того, как выполнится тело обработчика,
  и заимствовать из контекста не может. Ключ, который отдаёт заимствованное значение (имя как
  `&str`), читается через `ctx.context(KEY)`, если параметр `ctx` объявлен.
- Если обработчик берёт и параметр `&mut Context<'_, C>`, каждый ключ `Ctx` обязан читать тот же
  самый `C`.
- Вывод типа синтаксический: макрос распознаёт запись `Ctx<K>` - любой путь, оканчивающийся на
  `Ctx`, с одним типовым аргументом. За псевдонимом типа макрос эту запись не видит, и тип
  контекста становится `()`.

## Рабочая копия заголовков {#the-headers-working-copy}

Каждая доставка копирует входящие заголовки в контекст, и `ctx.headers()` возвращает эту копию, а не
заголовки самого сообщения брокера. Копия - черновик для всей цепочки диспетчеризации: middleware
раньше по цепочке может записать в неё значения через `headers_mut()`, а обработчик читает
результат:

```rust
--8<-- "examples/context.rs:enrich"
```

Слой, смонтированный глобально, выполняется перед каждым обработчиком, поэтому `handle` выше всегда
находит `x-request-id`:

=== "Макросы"

    ```rust
    --8<-- "examples/context.rs:app"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/context.rs:app"
    ```

У копии две границы:

- Изменения остаются внутри доставки: сообщение брокера и доставки других подписчиков их не видят.
- Исходящие сообщения эту копию не получают: ответ и ручная публикация начинают с пустых заголовков.
  Метаданные исходящего сообщения задают в
  [конвейере публикации](publishing.md#the-publish-pipeline), через `PublishTransform` или
  `PublishLayer`.

## Публикация из обработчика

Помимо формы ответа `publish(..)`, обработчик может публиковать через слот `Out`. Издателя для этого
не кладут в состояние, а принимают параметром обработчика: шаблон `Out(out): Out<impl Publisher>`
связывает `out` с живым издателем внутри тела.

Политику вы указываете при включении обработчика в приложение. Из неё выводится конкретный тип
издателя, и она же инстанцирует его на подключённом брокере.

Всё, что публикуется через слот, проходит тот же
[конвейер публикации](publishing.md#the-publish-pipeline), что и ответ: общая для приложения цепочка
`publish_layer` под собственными шагами слота `.out(marker, policy).transform(..)`. Полный шаблон с
примером кода - в разделе
[Публикация изнутри обработчика](publishing.md#publishing-from-inside-a-handler).

## Хуки после завершения доставки {#post-settle-hooks}

На контексте вы можете зарегистрировать побочный эффект, который сработает *после* завершения
доставки: некритичное уведомление, медленную дополнительную работу, прогрев кеша. На решение об ack
и на повторную доставку такой эффект не влияет.

=== "Макросы"

    ```rust
    --8<-- "examples/context.rs:handler"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/context.rs:handler"
    ```

Обработчик выше заканчивается вызовом `ctx.after_ack(..)`. Продолжение выполняется только после
того, как брокер сделал ack сообщения, и вне пути доставки, поэтому не задерживает ни ack, ни
следующую доставку.

Три формы, и они складываются:

- `ctx.after(outcome).then(fut)` - выполняется, только если доставка завершилась исходом `outcome`.
  Исходы сопоставляются **по виду**, видов четыре: `ack()`, `drop()` (nack без возврата в очередь),
  `retry()` (nack с возвратом в очередь) и `retry_after()` (совпадает при любой задержке). Хук на
  `drop()` не сработает, когда доставка завершилась через `retry()`, и наоборот.
- `ctx.after_ack(fut)` - сахар для `ctx.after(HandlerOutcome::ack()).then(fut)`.
- `ctx.after_settle(fut)` - выполняется после завершения доставки при любом исходе.

Продолжение можно прикрепить и к возвращаемому значению: `.and_after(fut)` есть у любого исхода, и
так пакетный обработчик получает продолжение на каждый элемент. Эта форма описана в разделе
[Продолжения после завершения доставки](subscribers.md#post-settle-continuations); всё сказанное
ниже относится к обеим.

Регистрации накапливаются, и выполняются все подходящие - вне пути доставки, в отслеживаемом наборе
задач.

Семантика хуков - **at-most-once**: доставка завершается раньше, чем запустится любой хук, поэтому
паника в хуке или аварийное завершение процесса не приводит к повторной доставке. Не кладите в хук
работу, потеря которой обязана вызвать повторную доставку: завершите доставку подходящим исходом и
дайте брокеру повторить попытку.

Плавная остановка дожидается незавершённых хуков в пределах `shutdown_timeout`, прерванная остановка
может их потерять.

На пакетном пути `Context` один на *пакет*, поэтому хук выполняется после завершения всего пакета.
Исходы у пакета свои на каждый элемент, поэтому отбор по исходу здесь не определён: срабатывают
только хуки `after_settle`, а `after(..)` и `after_ack` на пакете игнорируются.

## Контекст в middleware

Любая форма middleware получает тот же `&mut Context`, что и обработчик:

- Статический слой - через `Handler::handle(&self, msg, ctx)`, как в примере выше.
- Динамический middleware - через `DynMiddleware::handle(&self, input, ctx, next)`: он читает или
  дополняет контекст, а затем вызывает `next.run(input, ctx)`.

Сами формы middleware описаны в разделе [Middleware](middleware.md). Полная программа этой
страницы -
[`examples/context.rs`](https://github.com/powersemmi/ruststream/blob/main/examples/context.rs).
