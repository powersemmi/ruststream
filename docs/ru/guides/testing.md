# Тестирование

Сервисы RustStream тестируются на двух уровнях:

1. **Внутрипроцессные юнит-тесты** запускают ваши настоящие обработчики, middleware и кодеки в
   обвязке [`TestApp`](#unit-testing-a-service-with-testapp): без сервера, без docker, без сети.
   Это путь по умолчанию, и он покрывает логику обработчика целиком: декодирование,
   диспетчеризацию, исход (ack / nack / drop / паника / ошибка декодирования) и всё, что
   обработчик публикует дальше.
2. **Интеграционные тесты** работают с настоящим брокером, включаются переменной окружения и
   покрывают семантику, которая есть только у настоящего сервера: durable-консьюмеры, таймеры
   повторной доставки, партиции.

!!! warning "Что покрывает внутрипроцессный транспорт"
    Обвязка работает на **внутрипроцессном транспорте** брокера: доставляет публикацию
    подписчикам, у которых совпал субъект, выполняет обработчик на настоящем пути диспетчеризации
    и записывает исход вместе со всеми публикациями вниз по потоку. Семантику хранения и повторной
    доставки задаёт настоящий сервер; проверяйте её в
    [интеграционном наборе](#integration-tests-against-a-real-broker).

    Что такое `MemoryBroker`, сказано на его собственной странице:
    [брокер в памяти](../brokers/memory.md).

## Юнит-тестирование сервиса через `TestApp` {#unit-testing-a-service-with-testapp}

`TestApp` берёт собранное приложение `RustStream`, подключает его брокеры, монтирует обработчики и
записывает каждую доставку. Внутрипроцессная шина подключается без ввода-вывода. Вы публикуете
вход. Публикация доводит до конца всю реакцию - обработчик, его публикации вниз по потоку, каскад
между брокерами - и только потом возвращает управление. Дальше вы проверяете результат.

Тестируемый обработчик (в настоящем сервисе он лежит в вашем модуле обработчиков, а тест его
импортирует):

=== "Макросы"

    ```rust
    --8<-- "tests/doc_testing_memory.rs:handler"
    ```

=== "Вручную"

    ```rust
    --8<-- "tests/manual_doc_testing_memory.rs:handler"
    ```

Сам тест:

=== "Макросы"

    ```rust
    --8<-- "tests/doc_testing_memory.rs:test"
    ```

=== "Вручную"

    ```rust
    --8<-- "tests/manual_doc_testing_memory.rs:test"
    ```

!!! info "Этот тест выполняется в CI репозитория"
    Код выше включён из
    [`tests/doc_testing_memory.rs`](https://github.com/powersemmi/ruststream/blob/main/tests/doc_testing_memory.rs),
    а `cargo test --all-features` запускает его на каждое изменение, поэтому пример не может
    устареть незаметно.

Включите фичу `testing` в dev-зависимостях:

```toml
[dev-dependencies]
ruststream = { version = "0.7", features = ["testing", "memory", "macros", "json"] }
```

### Как адресовать брокеры

`tb.broker::<MemoryBroker>()` адресует брокер по типу. `tb.broker_named("ingress")` адресует его по
метке из [`with_broker_labeled`](asyncapi.md), когда сервис монтирует несколько брокеров и их
субъекты пересекаются. В приложении с одним брокером брокер можно не называть вовсе:
`tb.message(&value).to(name)` работает без него и возвращает `TestError::Ambiguous`, если
зарегистрирован больше одного брокера.

Вход подаётся через тот же билдер публикации, которым публикует сам сервис. `message(&value)`
отправляет значение с `#[derive(Outgoing)]` тем способом, который выбрал его тип,
`with_headers(&meta)` прикрепляет типизированный контракт заголовков, а `to(name)` называет субъект,
когда тип значения его не объявляет.

Байты, которые моделью не являются, проходят через ту же точку входа в newtype с
`#[derive(Outgoing, Serialized)]`. Так подают недекодируемую полезную нагрузку для политики
декодирования и вход обработчика, который
[десериализует байты сам](subscribers.md#raw-subscribers): тест называет то, что подаёт.

### Проверки обработчика

`tb.broker::<B>().subscriber(name)` возвращает билдер проверок по тому, что получил этот
обработчик:

| Метод | Что проверяет |
|---|---|
| `assert_called_once()` / `assert_called(n)` / `assert_not_called()` | число вызовов |
| `with(&value)` | единственная доставка последнего вызова декодируется в `value` (кодеком по умолчанию) |
| `with_raw(bytes)` | единственная сырая полезная нагрузка последнего вызова |
| `settled(HandlerOutcome::ack())` | чем завершилось всё, что пришло в последнем вызове |
| `assert_batch_sizes(&[2, 1])` | какие пакеты получило тело, в порядке поступления |
| `assert_outcome(Outcome::Drop)` | классифицированный исход (ack / nack / drop / ошибка декодирования / паника) |
| `panicked()` | обработчик завершился паникой на последнем вызове |
| `assert_last_failed_to_decode()` | полезная нагрузка не декодировалась |

Эти проверки считают ВЫЗОВ обработчика, а не сообщение. Обработчик одиночных сообщений вызывается
на каждую доставку, поэтому вызов и сообщение совпадают. Пакетный обработчик вызывается на пакет:
`assert_called_once()` означает один пакет любого размера, `settled(..)` охватывает каждый его
элемент, а `received_raw()` перечисляет элементы поштучно.

`with` и `with_raw` называют одну ожидаемую полезную нагрузку, поэтому на пакете такая проверка не
проходит и сообщает его размер. Элемент, отвергнутый политикой декодирования до тела, завершает та
же политика, и в пакете обработчика его нет.

Границы пакетов задаёт брокер в ответ на [`batch(n)`](subscribers.md#batch-subscribers) точки
монтирования, и `assert_batch_sizes` показывает именно их: журнал из трёх записей, переигранный при
`batch(2)`, доходит до тела как `[2, 1]`. Тот же прогон на обработчике одиночных сообщений даёт
`[1, 1, 1]`.

!!! note "Как набрать пакет длиннее одного элемента"
    `tb.message(&value).publish()` доводит реакцию до конца прежде, чем вернуть управление, а
    завершённая реакция закрывает пакет у брокера, который собирает пакеты на клиенте. Поэтому
    публикация по одному сообщению даёт по пакету на сообщение, и в каждом ровно один элемент,
    какой бы размер ни назвала точка монтирования. Возьмите дескриптор издателя у брокера до
    сборки приложения и опубликуйте через него всю серию: по пути реакция не завершается. Потом
    доведите её до конца один раз, через `tb.settle()`. Брокера с собственной пакетной доставкой
    это не касается: там границу пакета определяет он сам.

`tb.broker::<B>().published::<T>(name)` читает журнал публикаций брокера и проверяет то, что
обработчик опубликовал дальше: `.assert_called_once()` / `.assert_called(n)` /
`.assert_not_called()` - число публикаций, `.with(&Receipt { id: 1 })` / `.with_raw(bytes)` -
последнюю полезную нагрузку, `.with_header("x-app", b"1")` - заголовок, который проставил
middleware публикации или [`PublishTransform`](publishing.md).

Сами сообщения тоже доступны, если проверка нужна своя: `subscriber(name).received::<T>()` /
`.received_raw()` возвращают то, что получил обработчик, а `published::<T>(name).decoded()` /
`.messages()` - каждое сообщение, опубликованное в канал. Оба списка идут в порядке поступления.

Ещё два представления сохраняют то, что теряет плоский список. `subscriber(name).batches::<T>()` /
`.batches_raw()` группируют доставки по ВЫЗОВУ, по одному вложенному вектору на вызов: тест видит,
как поток разбит на пакеты, а `received::<T>()` эту границу стирает. `subscriber(name).outcomes()`
возвращает классифицированный исход каждого вызова по порядку - по нему сверяют последовательность
повторной доставки (nack, затем ack на повторе), тогда как `settled(..)` и `assert_outcome(..)`
читают только последний вызов.

Декодирующие методы (`with`, `received`, `decoded`) работают кодеком по умолчанию. Если обработчик
или издатель смонтирован с другим кодеком (`with_broker_codec`, `Router::with_codec`), передайте
его явно вариантами `_with` / `with_codec`: `subscriber(name).with_codec(&CborCodec, &expected)`,
`.received_with(&CborCodec)`, `published::<T>(name).with_codec(&CborCodec, &expected)`,
`.decoded_with(&CborCodec)`. Методы `with_raw` / `received_raw` / `messages` кодек не используют.

### Сообщение, которое сериализует себя само {#a-message-that-serializes-itself}

Значение на [байтовом пути](codecs.md#binary-protocols-are-not-codecs) передаётся без кодека, а
каждая типизированная проверка выше кодек использует: `with(&value)`, `received::<T>()` и их
варианты `_with(codec)` декодируют им, а тип с `Serialized` / `Deserialized` кодек не разрешает
вовсе. Тест на этом пути опирается на две проверки без кодека: `with_raw(bytes)` для полезной
нагрузки и `received_raw()` для чтения доставки обратно. Остальное даёт собственный формат типа:

```rust
--8<-- "tests/self_serialising.rs:assertions"
```

Ожидаемые байты берутся из формата, а не из обвязки: самодельный кадр достаточно короток, чтобы
выписать его целиком, а сгенерированное сообщение выдаёт свои байты само - для сообщения `prost`
это `with_raw(&order.encode_to_vec())`. Доставку читают обратно через `Deserialized::from_payload`
поверх владеющих `Bytes`, которые вернул `received_raw()`: это тот же читатель, что разбирал вход,
поэтому проверка сверяется с типом модели и без кодека. Сторона публикации устроена так же:
`published::<T>(name).with_raw(bytes)` и `.messages()` кодек не используют, а `.with(&value)` и
`.decoded()` используют.

### Проверки слотов Out {#asserting-on-out-slots}

По слоту [`Out`](publishing.md#named-slots) обработчик опознаётся и в тесте.
`tb.out::<Marker>()` возвращает ровно те сообщения, которые опубликованы через этого внедрённого
издателя, вместе с адресатами и заголовками и сразу по всем брокерам. Набор проверок тот же, что у
`published`: `assert_called_once`, `with_raw`, `messages`; для типизированного `with` добавьте в
цепочку `.decoded_as::<T>()`. Слот добавляет атрибуцию: те же сообщения видит и поканальный журнал
публикаций брокера.

```rust
--8<-- "tests/out_slots.rs:slot_capture"
```

Публикации, которые уходят за пределы задачи обработчика (порождённая соседняя задача, буфер
завершённой собственной транзакции), слоту не приписываются: проверяйте их по журналу публикаций
брокера.

Вместе с сообщением слот записывает и
[настройки брокера на сообщение](publishing.md#broker-settings-per-message), с которыми оно
опубликовано. Поэтому вы можете проверить и ту настройку, которую брокер кладёт в поле протокола, а
не в заголовок. `with_options` называет тип настроек брокера и сверяет значение;
`assert_options_default` утверждает, что на этой публикации ни один шаг не задал настройку и
применились умолчания политики:

=== "Макросы"

    ```rust
    --8<-- "tests/publish_options.rs:options_assert"
    ```

=== "Вручную"

    ```rust
    --8<-- "tests/manual_publish_options.rs:options_assert"
    ```

Обе проверки читают последнюю публикацию, как и `with_header`. Настройки записывает только слот.
Журнал публикаций брокера видит сообщение уже после того, как брокер их применил, поэтому запрос
настроек у `published::<T>(name)` паникует. Издатель из стартового хука или из состояния приложения
не принадлежит ни одному слоту, и его настройки не записывает никто.

### Политика ошибок, паника и остановка

Обвязка выполняет диспетчеризацию под настоящей `FailurePolicy` приложения, поэтому негативный тест
здесь полноценный сценарий. При умолчании `panic = fail_fast` паника обработчика останавливает
сервис ровно так же, как в бою:

```rust
--8<-- "tests/testing_harness.rs:panic"
```

При `on_failure(panic = skip)` паника завершается через ack, потребление продолжается, и
`tb.assert_running()` проходит. `run_result()` возвращает то же, что вернул бы настоящий
[`run`](lifespan.md): `Ok`, пока сервис работает, и ошибку, как только сбой в режиме fail-fast его
остановил.

!!! note "Чтобы ловить панику, нужна раскрутка стека"
    Обвязка опирается на `catch_unwind` рантайма, поэтому намеренная паника не завершает тестовый
    поток. Сборка с `panic = "abort"` панику обработчика поймать не может.

### Отложенная повторная доставка (`retry_after`)

Обработчик, который вернул `retry_after(delay)`, планирует отложенную повторную доставку. `publish`
записывает немедленный исход `NackAfter` и возвращает управление, а саму повторную доставку вы
запускаете отдельно, сдвигом остановленных часов:

=== "Макросы"

    ```rust
    --8<-- "tests/testing_harness.rs:retry_after"
    ```

=== "Вручную"

    ```rust
    --8<-- "tests/manual_testing_harness.rs:retry_after"
    ```

## Интеграционные тесты против настоящего брокера {#integration-tests-against-a-real-broker}

Поведение, которое зависит от семантики настоящего брокера, вынесите в отдельный набор и включайте
его переменной окружения. Тогда обычный `cargo test` остаётся быстрым и не требует сети:

<!-- inline-rust: integration-test skeleton with a pseudocode body; it drives a real NatsBroker (external crate) behind an env gate, so it has no compiled home here -->
```rust title="tests/integration_nats.rs"
fn test_url() -> Option<String> {
    std::env::var("NATS_TEST_URL").ok()
}

#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
async fn durable_consumer_resumes_after_restart() {
    let Some(url) = test_url() else {
        eprintln!("skipping: set NATS_TEST_URL to run");
        return;
    };
    // connect NatsBroker::new(url), drive the real JetStream consumer ...
}
```

Запускайте его явно на живом сервере:

```bash
docker run -d -p 4222:4222 nats:latest -js
NATS_TEST_URL=nats://127.0.0.1:4222 cargo test --test integration_nats
```

Логику обработчика проверяет внутрипроцессный путь, семантику брокера - настоящий сервер. Держите
оба набора над одними и теми же модулями обработчиков, чтобы у боевого кода был один источник
истины.

!!! note "Пишете крейт брокера?"
    Внутрипроцессный транспорт и контракт `TestableBroker`, на которых `TestApp` работает с
    брокером, - это забота автора брокера. Они описаны в
    [Авторам брокеров: поддержка тестов](../broker-authors/index.md#test-support) и
    [Conformance](../broker-authors/conformance.md).
