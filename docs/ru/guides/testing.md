# Тестирование

Сервисы RustStream тестируются на двух уровнях:

1. **Внутрипроцессные юнит-тесты** гоняют ваши настоящие обработчики, middleware и кодеки через
   обвязку [`TestApp`](#unit-testing-a-service-with-testapp): без сервера, без docker, без сети
   (`connect` у внутрипроцессного брокера не делает ввода-вывода). Это путь по умолчанию, и он
   покрывает логику обработчика от начала до конца: декодирование, диспетчеризацию, исход
   (ack / nack / drop / паника / ошибка декодирования) и все сообщения, которые публикует обработчик.
2. **Интеграционные тесты** идут против настоящего брокера, включаются переменной окружения и
   покрывают семантику, которая есть только у настоящего сервера (durable-консьюмеры, таймеры
   повторной доставки, партиции).

!!! warning "Что обвязка моделирует, а что нет"
    Обвязка гоняет **внутрипроцессный транспорт** брокера: публикация разводит сообщение по
    подписчикам, у которых совпал субъект, прогоняет ваш обработчик по настоящему пути
    диспетчеризации и записывает исход вместе со всеми публикациями вниз по потоку. Она **не**
    моделирует durable-курсоры JetStream, повторную доставку по `ack_wait`, `max_ack_pending`,
    retention, офсеты и consumer-группы Kafka, обменники и dead-letter-маршрутизацию RabbitMQ. Это
    забота настоящего брокера; проверяйте это в
    [интеграционном наборе](#integration-tests-against-a-real-broker).

    Что такое `MemoryBroker` и что он не заменяет, сказано на его собственной странице:
    [брокер в памяти](../brokers/memory.md).

## Юнит-тестирование сервиса через `TestApp` {#unit-testing-a-service-with-testapp}

`TestApp` берёт собранное приложение `RustStream`, подключает его брокеры (для внутрипроцессной шины
это без ввода-вывода), монтирует обработчики и записывает каждую доставку. Вы публикуете вход, и
публикация доводит всю реакцию (обработчик, его публикации вниз по потоку, любой каскад между
брокерами) до полной остановки, прежде чем вернуть управление, - а дальше вы проверяете.

Тестируемый обработчик (в настоящем сервисе он лежит в вашем модуле обработчиков, а тест его
импортирует):

=== "Макросы"

    ```rust
    --8<-- "tests/doc_testing_memory.rs:handler"
    ```

=== "Вручную"

    ```rust
    --8<-- "tests/manual_doc_testing_memory.rs:handler"
    ```

Сам тест:

=== "Макросы"

    ```rust
    --8<-- "tests/doc_testing_memory.rs:test"
    ```

=== "Вручную"

    ```rust
    --8<-- "tests/manual_doc_testing_memory.rs:test"
    ```

!!! info "Этот тест выполняется в CI этого репозитория"
    Код выше подтянут из
    [`tests/doc_testing_memory.rs`](https://github.com/powersemmi/ruststream/blob/main/tests/doc_testing_memory.rs),
    а `cargo test --all-features` прогоняет его на каждое изменение, так что пример не может молча
    протухнуть.

Включите фичу `testing` в dev-зависимостях:

```toml
[dev-dependencies]
ruststream = { version = "0.7", features = ["testing", "memory", "macros", "json"] }
```

### Как адресовать брокеры

`tb.broker::<MemoryBroker>()` адресует брокер по типу; `tb.broker_named("ingress")` - по метке из
[`with_broker_labeled`](asyncapi.md), когда сервис монтирует несколько брокеров и их субъекты
пересекаются. Внеобластной `tb.message(&value).to(name)` - удобство для приложений с одним брокером:
он сообщает `TestError::Ambiguous`, если зарегистрирован больше чем один брокер.

Вход приходит через тот же билдер публикации, которым публикует сам сервис: `message(&value)`
отправляет значение с `#[derive(Outgoing)]` тем способом, который выбрал его тип,
`with_headers(&meta)` прикрепляет типизированный контракт заголовков, а `to(name)` называет
субъект, когда тип значения его не объявляет. Байты, которые моделью не являются, -
недекодируемая нагрузка для политики декодирования или вход обработчика, который
[десериализует байты сам](subscribers.md#raw-subscribers), - едут через ту же точку входа в
newtype с `#[derive(Outgoing, Serialized)]`, поэтому тест называет то, что вбрасывает, а не
роняет анонимные байты на субъект.

### Проверки обработчика

`tb.broker::<B>().subscriber(name)` возвращает текучий билдер по тому, что получил этот обработчик:

| Метод | Что проверяет |
|---|---|
| `assert_called_once()` / `assert_called(n)` / `assert_not_called()` | число вызовов |
| `with(&value)` | единственная доставка последнего вызова декодируется в `value` (кодеком по умолчанию) |
| `with_raw(bytes)` | единственная сырая нагрузка последнего вызова |
| `settled(HandlerOutcome::ack())` | чем завершилось всё, что нёс последний вызов |
| `assert_page_sizes(&[2, 1])` | какие страницы получило тело, в порядке прихода |
| `assert_outcome(Outcome::Drop)` | классифицированный исход (ack / nack / drop / ошибка декодирования / паника) |
| `panicked()` | обработчик упал в панику на последнем вызове |
| `assert_last_failed_to_decode()` | полезная нагрузка не декодировалась |

Считают эти проверки ВЫЗОВ обработчика, а не сообщение. Обработчик одиночных сообщений вызывается
на каждую доставку, поэтому одно совпадает с другим; пакетный обработчик вызывается на страницу,
поэтому `assert_called_once()` означает, что пришла одна страница любого размера, `settled(..)`
охватывает каждый её элемент, а `received_raw()` по-прежнему перечисляет элементы поштучно. Две
проверки, называющие одну ожидаемую нагрузку (`with`, `with_raw`), сообщают размер страницы, а не
молча проверяют один её элемент. Элемент, который политика декодирования отвергла до тела, эта
политика и завершает: в странице, которую увидел обработчик, его нет.

Страница доходит до тела целиком - поэтому одна страница и есть один вызов. Где проходят границы
страниц, решает брокер в ответ на [`batch(n)`](subscribers.md#batch-subscribers) точки
монтирования, и `assert_page_sizes` как раз это показывает: журнал из трёх записей, переигранный
при `batch(2)`, доходит до тела как `[2, 1]` - два вызова, потому что брокер собрал две страницы.
Обработчик одиночных сообщений вызывается на каждую доставку, поэтому тот же прогон даёт
`[1, 1, 1]`.

`tb.broker::<B>().published::<T>(name)` проверяет то, что обработчик опубликовал дальше, читая журнал
публикаций брокера: `.assert_called_once()` / `.assert_called(n)` / `.assert_not_called()`
фиксируют число публикаций, `.with(&Receipt { id: 1 })` / `.with_raw(bytes)` - последнюю нагрузку,
`.with_header("x-app", b"1")` - заголовок, который проставил на выходе middleware публикации или
[`PublishTransform`](publishing.md).

Помимо готовых проверок, сами сообщения можно достать и проверить по-своему:
`subscriber(name).received::<T>()` / `.received_raw()` отдают то, что получил обработчик, а
`published::<T>(name).decoded()` / `.messages()` - каждое сообщение, опубликованное в канал; и то и
другое по порядку.

Ещё два представления сохраняют то, что теряет плоский список. `subscriber(name).pages::<T>()` /
`.pages_raw()` группирует доставки по ВЫЗОВУ - один вложенный вектор на вызов, - поэтому тест
фиксирует, как поток нарезан на страницы; `received::<T>()` эту границу стирает.
`subscriber(name).outcomes()` отдаёт классифицированный исход каждого вызова по порядку - с ним
сравнивают последовательность передоставки (nack, затем ack на повторе), тогда как `settled(..)` и
`assert_outcome(..)` читают только последний вызов.

Декодирующие помощники (`with`, `received`, `decoded`) работают кодеком по умолчанию. Если обработчик
или издатель смонтирован с другим кодеком (`with_broker_codec`, `Router::with_codec`), передайте его
явно через варианты `_with` / `with_codec` - `subscriber(name).with_codec(&CborCodec, &expected)`,
`.received_with(&CborCodec)`, `published::<T>(name).with_codec(&CborCodec, &expected)`,
`.decoded_with(&CborCodec)`, - а `with_raw` / `received_raw` / `messages` кодека не касаются.

### Проверки слотов Out {#asserting-on-out-slots}

Слот [`Out`](publishing.md#named-slots) обработчика служит заодно его тестовой идентичностью:
`tb.out::<Marker>()` возвращает ровно те сообщения, которые опубликованы через этот внедрённый
издателя, - вместе с адресатами и заголовками, по всем брокерам сразу - и с тем же набором
проверок, что у `published` (`assert_called_once`, `with_raw`, `messages`; для типизированного `with`
добавьте в цепочку `.decoded_as::<T>()`). Взгляд через слот добавляет только атрибуцию: те же
сообщения видит и поканальный журнал публикаций брокера.

```rust
--8<-- "tests/out_slots.rs:slot_capture"
```

Публикации, которые уходят из задачи обработчика (порождённая соседняя задача, буфер завершённой
собственной транзакции), слоту не приписываются: проверяйте их по журналу публикаций брокера.

### Политика ошибок, паника и остановка

Обвязка выполняет диспетчеризацию под настоящей `FailurePolicy` приложения, поэтому негативный тест
здесь полноправен. При умолчании `panic = fail_fast` паника обработчика роняет сервис ровно так же,
как в бою:

```rust
--8<-- "tests/testing_harness.rs:panic"
```

При `on_failure(panic = skip)` паника завершается через ack, потребление продолжается, и
`tb.assert_running()` держится. `run_result()` возвращает то же, что вернул бы настоящий
[`run`](lifespan.md): `Ok`, пока всё здорово, и ошибку, как только сбой в режиме fail-fast остановил
сервис.

!!! note "Чтобы ловить панику, нужна раскрутка стека"
    Обвязка работает через `catch_unwind` рантайма, поэтому намеренная паника не убивает тестовый
    поток. Сборка, скомпилированная с `panic = "abort"`, панику обработчика поймать не может.

### Отложенная повторная доставка (`retry_after`)

Обработчик, вернувший `retry_after(delay)`, планирует отложенную повторную доставку. `publish`
записывает немедленное завершение `NackAfter` и возвращает управление, а сама повторная доставка
запускается отдельно - сдвигом остановленных часов:

=== "Макросы"

    ```rust
    --8<-- "tests/testing_harness.rs:retry_after"
    ```

=== "Вручную"

    ```rust
    --8<-- "tests/manual_testing_harness.rs:retry_after"
    ```

## Интеграционные тесты против настоящего брокера {#integration-tests-against-a-real-broker}

Поведение, которое зависит от семантики настоящего брокера, вынесено в отдельный набор, включаемый
переменной окружения, - чтобы обычный `cargo test` оставался быстрым и офлайновым:

<!-- inline-rust: integration-test skeleton with a pseudocode body; it drives a real NatsBroker (external crate) behind an env gate, so it has no compiled home here -->
```rust title="tests/integration_nats.rs"
fn test_url() -> Option<String> {
    std::env::var("NATS_TEST_URL").ok()
}

#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
async fn durable_consumer_resumes_after_restart() {
    let Some(url) = test_url() else {
        eprintln!("skipping: set NATS_TEST_URL to run");
        return;
    };
    // connect NatsBroker::new(url), drive the real JetStream consumer ...
}
```

Запускайте его явно против живого сервера:

```bash
docker run -d -p 4222:4222 nats:latest -js
NATS_TEST_URL=nats://127.0.0.1:4222 cargo test --test integration_nats
```

Логику обработчика проверяет внутрипроцессный путь, семантику брокера - настоящий. Держите оба
набора над одними и теми же модулями обработчиков, чтобы у боевого кода был один источник истины.

!!! note "Пишете крейт брокера?"
    Машинерия, благодаря которой `TestApp` работает с брокером, - внутрипроцессный транспорт и
    контракт `TestableBroker` - это сторона автора брокера. Она описана в
    [Авторам брокеров: поддержка тестов](../broker-authors/index.md#test-support) и
    [Conformance](../broker-authors/conformance.md).
