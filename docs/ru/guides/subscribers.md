# Подписчики

Подписчик связывает обработчик с одной подпиской. Удобный способ объявить его - макрос
`#[subscriber]`; это руководство разбирает контракт обработчика, формы макроса и то, как
обработчики монтируются. Про группировку обработчиков по модулям рассказано в
[Роутинге](routing.md), а про декодирование полезной нагрузки - в [Кодеках](codecs.md).

## Контракт обработчика

Обработчик - это `async fn`, первый параметр которой - ссылка на декодированную полезную нагрузку:

=== "Макросы"

    ```rust
    use ruststream::runtime::HandlerOutcome;
    use ruststream::subscriber;

    --8<-- "examples/subscribers.rs:contract"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/subscribers.rs:contract"
    ```

Макрос превращает функцию в значение с тем же именем (здесь `handle`), которое реализует контракт
монтирования. Это значение вы и передаёте в `include`.

### Приём контекста

Объявите необязательный второй параметр `&mut Context`, чтобы читать заголовки, имя подписки и
общее состояние или публиковать прямо из обработчика:

=== "Макросы"

    ```rust
    --8<-- "examples/subscribers.rs:context"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/subscribers.rs:context"
    ```

Тип контекста макрос выводит сам, поэтому имя `Context` не нужно импортировать, пока оно
встречается только в сигнатурах `#[subscriber]`. Полная поверхность контекста - рабочая копия
заголовков, доступ к состоянию, поля брокера, привязанные к конкретной доставке - разобрана в
[Контексте и состоянии](context.md).

### Параметры-экстракторы

Любой следующий параметр, после сообщения и необязательного `&mut Context`, - это **экстрактор**:
рантайм получает его из доставки до того, как выполнится тело, а неудачная выборка завершает
доставку, не запуская тело. Бывает четыре вида:

- `State<T>` - поле состояния приложения (выведите `FromRef` на типе состояния).
- `Ctx<K>` - поле брокера для конкретной доставки, читается по своему ключу.
- `Headers<T>` - заголовки доставки, разобранные в типизированный контракт; нарушение
  контракта завершает доставку по политике `on_failure(decode = ..)` (см.
  [типизированные заголовки](headers.md)).
- любой тип, реализующий `FromContext`, - свой экстрактор (auth guard, резолвер в области одного
  запроса).

Механика описана в разделах
[Внедрение зависимостей](context.md#injecting-dependencies-extractor-parameters) и
[Поля контекста как параметры](context.md#context-fields-as-parameters).

Есть ещё одна форма параметра, и это не экстрактор, а **внедрение**: `Out(out): Out<impl
Publisher>` получает живого издателя, которого рантайм собирает из политики, прикреплённой в месте
`include` (`b.include(handler).publisher(..)` или `.out(marker, ..)` для именованного слота);
конкретный тип издателя в сигнатуре не появляется никогда. Необязательная третья позиция
объявляет набор сообщений, которые обработчик публикует, - `Out<impl Publisher, Marker, (A, B)>`, -
и тем самым включает типизированный путь публикации по словарю
([типизированные заголовки](headers.md)). См.
[Публикацию изнутри обработчика](publishing.md#publishing-from-inside-a-handler).

### Подтверждение {#acking}

Возвращать можно всё, что преобразуется в [`HandlerOutcome`] (единица завершения доставки: статус
для брокера плюс необязательное продолжение после завершения):

| Возвращаемое значение | Что происходит |
|---|---|
| `HandlerOutcome::ack()` | подтвердить; брокер удаляет сообщение |
| `HandlerOutcome::retry()` | nack с возвратом в очередь (повторная доставка позже) |
| `HandlerOutcome::retry_after(delay)` | nack с просьбой доставить повторно не раньше, чем через `delay` |
| `HandlerOutcome::drop()` | nack без возврата в очередь (отбросить или отправить в dead-letter) |
| `()` | всегда подтверждает |
| `Result<(), E>` | подтверждение при `Ok`, отбрасывание при `Err` |
| `Result<HandlerOutcome, E>` | внутренний исход при `Ok`, отбрасывание при `Err` |
| `HandlerOutcome::ack().and_after(..)` (любой исход) | завершить доставку этим исходом, затем выполнить продолжение |

У самого сообщения `ack` поглощает `self`, поэтому система типов не даёт сделать ack дважды.

### Продолжения после завершения доставки {#post-settle-continuations}

`HandlerOutcome::ack().and_after(fut)` прикрепляет к возвращаемому исходу продолжение: некритичное
уведомление, медленную доработку, прогрев кеша. Подходит любой исход (`drop().and_after(..)` тоже
корректен, нейтральное прочтение - «после завершения доставки»):

=== "Макросы"

    ```rust
    --8<-- "examples/post_settle.rs:single"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/post_settle.rs:single"
    ```

Продолжение подчиняется общей семантике post-settle (at-most-once, выполняется только после того,
как ack или nack завершил доставку, дорабатывает при мягкой остановке); см.
[Хуки после завершения доставки](context.md#post-settle-hooks).

В пакете каждый элемент завершается отдельно, поэтому продолжение задаётся поэлементно - такого
хук в контексте одного сообщения дать не может:

=== "Макросы"

    ```rust
    --8<-- "examples/post_settle.rs:batch"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/post_settle.rs:batch"
    ```

Пакетная *публикация* (пакетный обработчик с `publish(..)`) завершает всё целиком, одной
транзакцией, поэтому поэлементный `and_after` там не складывается; он работает только в обычной
пакетной и одиночной формах.

### Отложенная повторная доставка

`retry_after` закрывает случай «ещё не готово» (зависимость ещё не появилась, апстрим ограничивает
частоту запросов), когда немедленная повторная доставка крутилась бы вхолостую:

=== "Макросы"

    ```rust
    --8<-- "examples/retry.rs:retry_after"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/retry.rs:retry_after"
    ```

Внутри рантайм соблюдает задержку так:

- Брокер с нативной отложенной повторной доставкой (in-memory брокер доставляет повторно по
  таймеру, брокер на NATS JetStream мог бы послать `NAK` с задержкой) отдаёт это транспорту
  напрямую.
- На брокере без нативной поддержки рантайм планирует **отложенную повторную публикацию**
  сообщения в его же исходный субъект через `delay`, а оригинал отбрасывает. Опубликованная заново
  копия несёт увеличенный на единицу фреймворковый заголовок со счётчиком повторов
  ([`RETRY_COUNT_HEADER`](https://docs.rs/ruststream/latest/ruststream/runtime/constant.RETRY_COUNT_HEADER.html));
  обработчик может его прочитать и ограничить число повторных доставок.

  Включается в пределах области через
  [`BrokerScope::retry_via(publisher)`](https://docs.rs/ruststream/latest/ruststream/runtime/struct.BrokerScope.html#method.retry_via)
  (издатель должен указывать на тот же брокер). Без издателя задержка отбрасывается, и
  сообщение немедленно возвращается в очередь. Отложенная повторная публикация даёт
  **at-most-once** на окне задержки: если процесс завершится до срабатывания таймера, копия
  потеряется.

Форма `batch_retry_after` складывается с
[выборочным завершением пакета](#selective-acknowledgement): `Vec<HandlerOutcome>` несёт задержки
поэлементно, так что неготовые записи отходят на паузу, не задерживая остальной пакет:

=== "Макросы"

    ```rust
    --8<-- "examples/retry.rs:batch_retry_after"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/retry.rs:batch_retry_after"
    ```

## Выбор источника подписки

Атрибут всегда фиксирует *вид* подписки: субъект, консьюмер JetStream, поток Redis, канал pub/sub и
список - это разные типы. Опустить можно *значение*, которым вид заполняется: его тогда даёт точка
монтирования. Форм четыре, от самой короткой:

| Форма | Вид | Значение |
|---|---|---|
| `#[subscriber]` | источник по имени | из точки монтирования |
| `#[subscriber(RedisStream)]` | назван здесь | из точки монтирования |
| `#[subscriber("orders")]` | источник по имени | зафиксировано здесь |
| `#[subscriber(RedisStream::new("orders").group("w"))]` | назван здесь | зафиксировано здесь |

### По имени

`#[subscriber("orders")]` подписывается по имени. Это работает с любым брокером, реализующим
трейт-совместимость `Subscribe`, - а её реализуют все крейты брокеров семейства: имя отображается в
тот вид подписки, который брокер считает у себя основным, а всё, что этому виду нужно сверх имени,
настраивается один раз на самом брокере.

`#[subscriber]` - тот же источник, но без значения: имя, которое сервис узнаёт только в момент
собственного связывания, субъект, собранный из номера шарда, топик, прочитанный из конфигурации:

=== "Макросы"

    ```rust
    --8<-- "examples/subscribers.rs:deferred_name"
    ```

    ```rust
    --8<-- "examples/subscribers.rs:name_mount"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/subscribers.rs:deferred_name"
    ```

    ```rust
    --8<-- "examples/manual/subscribers.rs:name_mount"
    ```

Там, где виду для существования действительно нужно больше одного имени (источник Pulsar принимает и
топик, *и* имя подписки), `FromName` не реализуется, и эта форма для него не скомпилируется. Такие
виды пишите полностью.

### Дескрипторы, специфичные для брокера {#broker-specific-descriptors}

Когда подписке нужны опции конкретного брокера (consumer group, durable-имя, политика доставки),
крейт брокера предоставляет тип-дескриптор. Вызывайте его конструктор прямо в декораторе:

<!-- inline-rust: illustrative descriptor sketch; OrdersStream is a stand-in for a broker crate's SubscriptionSource type, which lives in another crate and has no in-repo compiled home (the real NATS form is pulled in just below) -->
```rust
#[subscriber(OrdersStream::new("orders", "workers"))]
async fn handle(order: &Order) -> HandlerOutcome {
    HandlerOutcome::ack()
}
```

Тип дескриптора макрос читает из вызова конструктора, поэтому компилятор сверяет дескриптор с тем
брокером, на который его смонтировали. Дескриптор - это любой тип, реализующий
`SubscriptionSource<B>`; см. [Авторам брокеров](../broker-authors/index.md#subscription-sources).

Источником может быть и цепочка билдера поверх этого конструктора, так что опции остаются на месте.
Например, у брокера с билдером опций обработчик называет конкретный стрим и консьюмер прямо в
декораторе:

<!-- inline-rust: illustrative builder-chain source; the concrete options type lives in a broker crate, so there is no in-repo compiled home -->
```rust
#[subscriber(StreamOptions::new("orders").durable("audit"))]
async fn handle(order: &Order) -> HandlerOutcome {
    HandlerOutcome::ack()
}
```

Чтобы назвать тип источника, макрос спускается по цепочке до базового `Type::new(..)`, поэтому
каждый метод цепочки обязан возвращать `Self`. Свободные функции отвергаются: их тип макросу не
виден.

Собранный так источник пересобирается для каждого монтирования, поэтому тип-дескриптор брокера
реализует `Clone`. Одно определение можно смонтировать на два брокера.

## Настройки в точке монтирования

Имя, политика воркеров, политики обработки ошибок и стартовая позиция - это значения, поэтому каждое
можно задать в атрибуте, в точке монтирования или частично там и там. Атрибут разворачивается ровно
в те вызовы, которые вы написали бы руками:

=== "Макросы"

    ```rust
    --8<-- "examples/subscribers.rs:builder_settings"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/subscribers.rs:builder_settings"
    ```

Настройка, названная в атрибуте, зафиксирована в типе определения, и её метод билдера больше не
применим, так что никаких правил приоритета помнить не нужно:

<!-- inline-rust: two compile-fail one-liners; a compiling example cannot host code that must not compile (the pinned diagnostics live in tests/ui) -->
```rust
#[subscriber("orders", workers(4))]
async fn handle(order: &Order) -> HandlerOutcome { HandlerOutcome::ack() }

b.include(handle.name("other"));    // does not compile: the name is already given
b.include(handle.on_failure(..));   // fine: the attribute said nothing about failures
```

Методы приходят из трейта `SubscriberSettings`, который реализует каждое сгенерированное
определение; чтобы до них добраться, импортируйте его (или
[prelude](https://docs.rs/ruststream/latest/ruststream/prelude/index.html)).

Настройки, специфичные для брокера, передаются тем же путём и в терминах самого брокера. Ядро не
может знать, что у подписки есть стрим JetStream или durable-имя консьюмера, поэтому оно даёт один
крючок - преобразование над собираемым источником, - а крейт брокера кладёт сверху свой трейт,
привязанный к своему типу источника; см.
[Авторам брокеров](../broker-authors/index.md#subscription-sources). Порядок в цепочке следует из
того, что делает каждый шаг: имя идёт первым, потому что оно конструирует источник, дальше настройки
брокера его преобразуют, а буфер, о котором ниже, оборачивает результат последним.

## Монтирование обработчиков

Внутри `with_broker` определение монтируется через `include`:

<!-- inline-rust: minimal include mount fragment with placeholder info/broker; the full compiled program is examples/subscribers.rs (its app is pulled in via other anchors on this page) -->
```rust
RustStream::new(info).with_broker(broker, |b| {
    b.include(handle);
});
```

`include` декодирует полезную нагрузку кодеком, взятым с самого конкретного уровня, который вы
задали: для обработчика, для области или выбранный фичами по умолчанию. См.
[откуда берётся кодек](codecs.md#where-the-decode-codec-comes-from).

Чтобы сгруппировать обработчики по модулям и смонтировать их разом, соберите их в `Router`; см.
[Роутинг](routing.md).

## Пакетные подписчики {#batch-subscribers}

Обработчик, принимающий срез, потребляет пакеты целиком: он выполняется один раз на каждый пакет,
доставленный брокером, - один поход в базу, один массовый вызов API. Форма читается из сигнатуры,
поэтому в атрибуте про неё ничего не пишут.

=== "Макросы"

    ```rust
    --8<-- "examples/subscribers.rs:batch"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/subscribers.rs:batch"
    ```

Монтируется он через `include`, как и любая другая форма, - пакетную форму несёт само определение:

=== "Макросы"

    ```rust
    --8<-- "examples/subscribers.rs:batch_mount"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/subscribers.rs:batch_mount"
    ```

Сигнатура говорит, что обработчик хочет получать по несколько сообщений сразу; а придут ли они так -
свойство брокера, поэтому решается это там, где определение монтируется. Подписчик этой подписки
обязан реализовать трейт-совместимость `BatchSubscriber`: брокеры, клиенты которых нативно отдают
сообщения пакетами (poll в Kafka, pull-консьюмеры JetStream), дают её напрямую, а размер пакета
настраивается в их опциях подписки; in-memory брокер тоже собирает пакеты нативно. Если подписка
пакетов не собирает, компилятор попросит буфер
фреймворка, а точка монтирования его даёт; буфер закрывает пакет по размеру или по сроку,
отсчитанному от первой доставки в нём:

=== "Макросы"

    ```rust
    --8<-- "examples/subscribers.rs:batch_buffered"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/subscribers.rs:batch_buffered"
    ```

Пакеты приходят либо от брокера (и настраиваются его собственными настройками), либо от этой
обёртки; настройка названа по имени адаптера, чтобы эти два источника не смешивались. Обёртка меняет
тип подписки, поэтому идёт последней - настройки брокера, привязанные к незавёрнутому типу, после
неё уже не применяются.

От обработчиков одиночных сообщений семантика отличается в нескольких местах:

- Элементы, которые не удалось декодировать, получают nack поштучно (по политике обработки ошибок
  декодирования) и до обработчика не доходят; остальные приходят одним срезом.
- Возвращённое значение завершает весь пакет. Одиночный `HandlerOutcome` (или `()` /
  `Result<_, E>`) одинаково завершает **каждое** сообщение: `ack()` подтверждает все, `retry()`
  возвращает в очередь все.
- Заголовки отдельных сообщений в форме `&[T]` недоступны, и контекст начинается с пустыми
  заголовками.
- Контекст один на пакет, и поля брокера в нём - те, что относятся ко *всей подписке*: пакетное
  тело называет пакетный тип контекста брокера (`ctx: &mut Context<'_, MemoryBatchContext>` для
  in-memory брокера) и читает его ключи через `ctx.context(..)`. Это значение рантайм строит один
  раз на пакет, по первой доставке пакета, через реализацию `BuildBatchContext` брокера; брокер,
  которому нечего дать на уровне подписки, не реализует ничего, и пакет остаётся на умолчании `()`.
- Данным отдельной доставки места там нет, потому что пакет охватывает много доставок: позиция или
  заголовок едут на самих элементах, и пакет `&[Message<H, T>]` читает их поэлементно. Это разные
  типы, поэтому пакетное тело, запросившее контекст отдельной доставки, не компилируется.
- Глобальные для приложения и роутерные middleware оборачивают обработчики отдельных сообщений и к
  пакетным регистрациям не применяются.

### Выборочное подтверждение {#selective-acknowledgement}

Частый случай - частичная готовность: часть сообщений пакета обработана, а остальные ещё не готовы и
должны быть доставлены повторно, не утаскивая за собой уже удавшиеся. Верните `Vec<HandlerOutcome>`,
чтобы элемент `i` среза завершился исходом `i`:

=== "Макросы"

    ```rust
    --8<-- "examples/subscribers.rs:batch_selective"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/subscribers.rs:batch_selective"
    ```

Со стороны брокера семантика ровно та же, что у `nack(requeue = true)` для одного сообщения: брокеры
с повторной доставкой отдельных сообщений поддерживают выборочный повтор нативно, а позиционный
брокер деградирует так же, как и на nack одиночного сообщения (крейт такого брокера это описывает).
Вернуть вектор, длина которого не совпадает с пакетом, - ошибка в обработчике: несопоставленный
остаток отправляется на повторную доставку, а расхождение попадает в лог.

## Перемотка {#seeking}

Брокеры поверх воспроизводимого лога (Kafka, потоки Redis, журнал публикаций in-memory брокера)
реализуют трейт-совместимость `Seekable`: живую подписку можно передвинуть на другую позицию
- переиграть поток после починки бага в обработчике, переобработать с известной точки, перескочить
через ядовитый участок - не разрывая подписку. Такой брокер публикует ключи перемотки поверх
своего контекста доставки; брокер без воспроизводимого лога ключей не даёт, и монтирование ниже
на нём не скомпилируется, а не упадёт в рантайме.

Обработчик передвигает собственную подписку через ключи контекста брокера: контекст доставки несёт
позицию и живую ручку перемотки (её брокер резолвит один раз, при открытии подписки), а обработчик
читает их по ключу - экстрактором `Ctx` на пути атрибута, вызовом `ctx.context(..)` над типом
контекста брокера на ручном. В месте `include` ничего прикреплять не нужно:

=== "Макросы"

    ```rust
    --8<-- "examples/seek.rs:handler"
    ```

    ```rust
    --8<-- "examples/seek.rs:mount"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/seek.rs:handler"
    ```

    ```rust
    --8<-- "examples/manual/seek.rs:mount"
    ```

Клауза навязывает позицию при каждом старте; без неё подписка открывается на умолчании брокера.
Условное умолчание - применять, только если у брокера нет сохранённого курсора для группы (сброс
смещения в Kafka, deliver policy в JetStream), - остаётся на собственном дескрипторе подписки
брокера, который выражает его нативно.

Пакетное тело перематывает свою подписку так же, только уровнем выше: ручка перемотки относится ко
всей подписке, поэтому едет в пакетном контексте брокера, а цель - позиция, с которой продюсер
просит продолжить, - едет на элементах самого пакета.

Что именно захватывает одна перемотка, у брокеров различается: перемещение экземпляра консьюмера
(Kafka) двигает только этот экземпляр, а перемещение общего курсора группы (потоки Redis) двигает всю
группу. Кроме того, перемотка делает недействительным весь учёт ack, который брокер вёл по этой
подписке; и то и другое описывает крейт брокера. Авторы брокеров доказывают контракт
[набором conformance `capabilities::seeking`](../broker-authors/conformance.md#capability-suites).

## Сырые подписчики {#raw-subscribers}

Когда полезная нагрузка вообще не сериализованное значение (двоичный кадр, чужой формат передачи,
который вы разбираете сами), тип нагрузки десериализует себя сам, и кодек уходит с пути. Что
именно произойдёт, решает сам тип, а мнемонику дают имена трейтов: `Deserialize` означает, что
значение собирает кодек фреймворка, `Deserialized` - что тип собирает себя сам.
`#[derive(Deserialized)]` покрывает обычный newtype над `&'a [u8]`, а параметр `&Frame<'_>` и
ставит обработчик на эту дорожку: байты приходят ровно в том виде, в каком их отдал брокер,
взаймы из его буфера, ничего не копируется, и кодека на пути нет.

=== "Макросы"

    ```rust
    --8<-- "tests/raw_subscriber.rs:raw"
    ```

=== "Вручную"

    ```rust
    --8<-- "tests/manual_raw_subscriber.rs:raw"
    ```

Форма без макросов выписывает ту пару impl-ов, которую пишет derive: `Deserialized` для
конструкции и написание `Input`, которое направляет тип на эту дорожку. Голый параметр `&[u8]`
входом обработчика вообще не является, и ошибка компиляции называет derive как исправление: срез
байтов - это ещё и пакет декодированных элементов `u8`, поэтому различить их может только
именованный тип.

Правило формы от дорожки не зависит: `&T` - одно сообщение, `&[T]` - пакет. Значит, пакет кадров -
это `&[Frame<'_>]`, и написание для пакета приходит вместе с derive: второй impl пакетному телу не
нужен. Его элементы заимствованы у сообщений самого пакета на время вызова, так что и здесь ничего
не копируется, а правила завершения доставки - те же, что и на пакетном пути.

=== "Макросы"

    ```rust
    --8<-- "examples/subscribers.rs:raw_batch"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/subscribers.rs:raw_batch"
    ```

Конструкция, которая проверяет содержимое (корень flatbuffers, читатель capnp, проверка длины),
сообщает о плохой нагрузке через `Err` из `from_payload`, и доставку завершает политика
`on_failure(decode = ..)`: та же ступень, на которую попадает ошибка декодирования кодека, и та
же, на которую попадает типизированный контракт `Headers`. Экстракторы, `&mut Context`,
`workers(..)`, `on_failure(panic = ..)` и внедряемые
параметры `Out` работают на форме одиночной доставки без изменений (пакет кадров `Out`
пока не принимает), а сам такой подписчик монтируется тем же `include`, что и любое другое
определение, - кодек области, если он задан, к нему просто не применяется. Это ещё и
единственная форма подписчика, доступная вообще без включённых фич кодеков.
Если же для своего формата сериализации вам нужны *типизированные* обработчики, реализуйте
[`Codec`](codecs.md) и оставайтесь на типизированном пути.

Обработчик на этой дорожке отвечает через ту же единственную клаузу `publish("dest")`, что и любая
другая форма ответа, а выбор между двумя способами отправки делает сам тип ответа - по зеркальной
мнемонике. Ответ, реализующий `serde::Serialize`, кодек ответа кодирует, а newtype с
`#[derive(Serialized)]` несёт собственные байты (`fn bytes(&self) -> &[u8]`) и уходит байт в байт,
ровно таким, каким его вернул обработчик. Возвращайте его напрямую или как
`Result<Export, HandlerOutcome>` - это то же явное управление ack, что и в кодирующей форме
ответа. Издателя даёт место `include`: ответ `Serialized` получает обычную политику публикации
(`b.include(relay).publisher(MemoryPublish)`), а кодируемый ответ оборачивает ту же политику в
`TypedPublisher::new(..)`; без этого вызова ответ уходит через политику публикации брокера по
умолчанию. На пути без макросов оба способа отправки идут по одной цепочке
`.reply().to(dest).publisher(..)` - по той же причине: тип ответа уже сказал, каким он уходит.
Неудачная публикация ответа даёт доставке nack с возвратом в очередь - ровно как на
кодирующем пути:

=== "Макросы"

    ```rust
    --8<-- "tests/raw_subscriber.rs:raw_reply"
    ```

=== "Вручную"

    ```rust
    --8<-- "tests/manual_raw_subscriber.rs:raw_reply"
    ```

Стороны друг друга не ограничивают: тип входа выбирает декодирование, тип ответа - кодирование, и
обе диагонали свободно сочетаются. Декодируемый вход с ответом `Serialized` - это форма шлюза:
принимаем структурированные сообщения и отдаём формат передачи, который обработчик собрал сам, а
вход при этом декодируется кодеком области и сохраняет свою политику обработки ошибок
декодирования:

=== "Макросы"

    ```rust
    --8<-- "tests/raw_subscriber.rs:raw_reply_typed"
    ```

=== "Вручную"

    ```rust
    --8<-- "tests/manual_raw_subscriber.rs:raw_reply_typed"
    ```

Вторая диагональ читается так же: вход `Frame<'_>` с ответом `Serialize` кодирует ответ кодеком
ответа, а сам вход кодека не касается вовсе. Два случая, однако, за типом не следуют. Ответ
`Vec<u8>` сырым ответом не считается - это обычное значение `Serialize`, поэтому оно уходит
закодированным, и нагрузке, которая обязана уйти нетронутой, нужен newtype. А пакетного ответа
`Serialized` не существует: ответы на пакет публикуются через кодек ответа.

## Пулы воркеров

Цикл диспетчеризации у подписчика последовательный: доставка обрабатывается и завершается до того,
как подписчик вытянет следующую, поэтому один медленный обработчик тормозит всю подписку. Клауза
`workers(n)` обрабатывает до `n` доставок этого подписчика одновременно, каждую в своей задаче на
многопоточном рантайме:

=== "Макросы"

    ```rust
    --8<-- "examples/subscribers.rs:workers"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/subscribers.rs:workers"
    ```

Обратное давление сохраняется: пока `n` доставок в работе, поток не опрашивается, и это хорошо
уживается с ограничениями на стороне брокера вроде `max_ack_pending` в JetStream. **Глобальный
порядок обработки при этом теряется, и так задумано**: если порядок доставки хоть где-то важен,
либо оставайтесь последовательными, либо используйте полосы по ключу:

=== "Макросы"

    ```rust
    --8<-- "examples/subscribers.rs:workers_by_key"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/subscribers.rs:workers_by_key"
    ```

`workers(n, by_key)` запускает `n` последовательных полос. Доставка попадает на ту полосу, в
которую хешируется её ключ партиционирования, поэтому сообщения с одним ключом никогда не
пересекаются и не меняют порядок - внутрипроцессный аналог семантики партиций Kafka. Ключ берётся из
`partition_key()` брокерского сообщения (его дают брокеры, у которых сообщения реализуют
трейт-совместимость `Partitioned`; in-memory брокер читает заголовок `partition-key`). Сообщения без
ключа раскладываются по полосам по кругу. `by_key` применим к подписчикам одиночных сообщений;
пакетные формы берут обычный пул `workers(n)` из пакетов.

На остановке подписчик перестаёт вытягивать новые доставки, а воркеры в работе дорабатывают в
пределах `shutdown_timeout` приложения.

## Правила композиции

Возможности подписчика сочетаются друг с другом; ниже - правила на каждом пересечении, и каждое
закреплено интеграционным тестом.

| Сочетание | Правило |
|---|---|
| `workers(n)` × пакетный обработчик | Пул держит в работе до `n` **пакетов**. `by_key` к пакетным формам не применяется: полосы упорядочивают одиночные сообщения по ключу, и макрос отвергает такое сочетание на этапе компиляции. |
| `retry()` / `retry_after` × `workers(n)` | Повторно доставленные сообщения снова попадают в пул и завершаются как любая другая доставка. |
| `retry()` / `retry_after` × `workers(n, by_key)` | Повторы отрабатывают, но порядок внутри ключа через повтор **не** гарантируется: возвращённое в очередь сообщение встаёт в поток с конца. Если сообщения ключа обязаны сохранять порядок даже через сбои, обработчик должен поглощать сбой сам, а не слать nack. |
| `.transactional()` × `workers(n)` | Одна транзакция на пакет, ровно как в последовательном цикле. Параллельные пакеты выполняют параллельные независимые транзакции; каждая остаётся атомарной (на пакет: сначала коммит, потом ack). |
| `Buffered` × `workers(n)` | Пакеты по-прежнему закрываются только по `max_size` / `max_wait`; пул ограничивает лишь то, сколько закрытых пакетов обрабатывается одновременно, и на границы пакетов не влияет никогда. |
| `publish(..)` × `workers(n)` | Ответы формируются параллельно, поэтому порядок ответов между доставками не гарантируется. Неудачная публикация ответа повторяет только свою доставку. |
| middleware × пакетный обработчик | Глобальные для приложения и роутерные слои оборачивают обработчики отдельных сообщений и к пакетным регистрациям не применяются (слой на одно сообщение не может обернуть обработчик целого пакета). |

## Макрос или вручную

`#[subscriber]` - это сахар над обобщённым API. Макрос генерирует типизированный обработчик и его
метаданные; ту же регистрацию можно написать руками: именованный тип, чей `impl Handle` несёт тело,
привязывается к источнику через `subscriber(source, body)` и запечатывается вызовом `.build()`. Обе
формы ниже регистрируют один и тот же обработчик.

=== "Макрос"

    ```rust
    use ruststream::subscriber;

    --8<-- "examples/subscribers.rs:contract"

    // inside with_broker(...):
    b.include(handle);
    ```

=== "Вручную"

    ```rust
    use ruststream::prelude::*;

    // inside with_broker(...):
    --8<-- "examples/subscribers.rs:manual"
    ```

Браться за ручную форму стоит, когда обработчику нужно состояние, которое макрос выразить не может
(обработчик-структура с полями), или чтобы задать неумолчальную
[политику обработки ошибок декодирования](codecs.md#decode-failures). В остальных случаях макрос
дешевле в сопровождении.

## Издатели

Обработчик, который формирует ответ, - это издатель. См. [Публикация и ответы](publishing.md).
