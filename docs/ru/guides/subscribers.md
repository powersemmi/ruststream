# Подписчики

Подписчик связывает обработчик с одной подпиской. Объявите его макросом `#[subscriber]`. Про
группировку обработчиков по модулям рассказано в [Роутинге](routing.md), а про декодирование
полезной нагрузки - в [Кодеках](codecs.md).

## Контракт обработчика

Обработчик - это `async fn`, первый параметр которой - ссылка на декодированную полезную нагрузку:

=== "Макросы"

    ```rust
    use ruststream::runtime::HandlerOutcome;
    use ruststream::subscriber;

    --8<-- "examples/subscribers.rs:contract"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/subscribers.rs:contract"
    ```

Макрос превращает функцию в определение подписчика с тем же именем (здесь `handle`), которое
реализует контракт монтирования. Это определение вы и передаёте в `include`.

### Приём контекста

Объявите необязательный второй параметр `&mut Context`, чтобы читать заголовки, имя подписки и
разделяемое состояние или публиковать прямо из обработчика:

=== "Макросы"

    ```rust
    --8<-- "examples/subscribers.rs:context"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/subscribers.rs:context"
    ```

Тип контекста макрос выводит сам, поэтому имя `Context` не нужно импортировать, пока оно
встречается только в сигнатурах `#[subscriber]`. Остальное - рабочая копия заголовков, доступ к
состоянию, поля брокера для конкретной доставки - разобрано в
[Контексте и состоянии](context.md).

### Параметры-экстракторы

Любой следующий параметр, после сообщения и необязательного `&mut Context`, - это **экстрактор**.
Рантайм получает его из доставки до того, как выполнится тело. Если получить его не удалось,
доставка завершается, а тело не выполняется. Бывает четыре вида:

- `State<T>` - поле состояния приложения (выведите `FromRef` на типе состояния).
- `Ctx<K>` - поле брокера для конкретной доставки, читается по своему ключу.
- `Headers<T>` - заголовки доставки, разобранные в типизированный контракт; нарушение
  контракта завершает доставку по политике `on_failure(decode = ..)` (см.
  [типизированные заголовки](headers.md)).
- любой тип, реализующий `FromContext`, - свой экстрактор (проверка прав доступа, поиск
  зависимости в пределах одного запроса).

Механика описана в разделах
[Внедрение зависимостей](context.md#injecting-dependencies-extractor-parameters) и
[Поля контекста как параметры](context.md#context-fields-as-parameters).

Есть ещё одна форма параметра, и это не экстрактор, а **внедрение**. `Out(out): Out<impl
Publisher>` получает живого издателя, которого конструирует политика, указанная в месте `include`
(`b.include(handler).out(marker, policy).build()`). Конкретный тип издателя в сигнатуре не
появляется никогда.

Необязательная третья позиция, `Out<impl Publisher, Marker, (A, B)>`, объявляет набор сообщений,
которые обработчик публикует, и включает типизированный путь публикации по словарю
([типизированные заголовки](headers.md)). См.
[Публикацию изнутри обработчика](publishing.md#publishing-from-inside-a-handler).

### Подтверждение {#acking}

Возвращать можно всё, что преобразуется в
[`HandlerOutcome`](https://docs.rs/ruststream/latest/ruststream/runtime/struct.HandlerOutcome.html)
(единица завершения доставки: статус для брокера плюс необязательное продолжение после завершения):

| Возвращаемое значение | Что происходит |
|---|---|
| `HandlerOutcome::ack()` | подтвердить; брокер удаляет сообщение |
| `HandlerOutcome::retry()` | nack с возвратом в очередь (повторная доставка позже) |
| `HandlerOutcome::retry_after(delay)` | nack с просьбой доставить повторно не раньше, чем через `delay` |
| `HandlerOutcome::drop()` | nack без возврата в очередь (отбросить или отправить в dead-letter) |
| `()` | всегда подтверждает |
| `Result<(), E>` | подтверждение при `Ok`, отбрасывание при `Err` |
| `Result<HandlerOutcome, E>` | внутренний исход при `Ok`, отбрасывание при `Err` |
| `HandlerOutcome::ack().and_after(..)` (любой исход) | завершить доставку этим исходом, затем выполнить продолжение |

У самого сообщения `ack` поглощает `self`, поэтому система типов не даёт сделать ack дважды.

### Продолжения после завершения доставки {#post-settle-continuations}

`HandlerOutcome::ack().and_after(fut)` прикрепляет к возвращаемому исходу продолжение: некритичное
уведомление, медленную доработку, прогрев кеша. Подходит любой исход, `drop().and_after(..)` в том
числе:

=== "Макросы"

    ```rust
    --8<-- "examples/post_settle.rs:single"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/post_settle.rs:single"
    ```

Продолжение подчиняется общим правилам шага после завершения доставки: at-most-once, выполняется
только после ack или nack, дорабатывает при мягкой остановке. См.
[Хуки после завершения доставки](context.md#post-settle-hooks).

В пакете каждый элемент завершается отдельно, поэтому продолжение задаётся поэлементно:

=== "Макросы"

    ```rust
    --8<-- "examples/post_settle.rs:batch"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/post_settle.rs:batch"
    ```

Пакетная *публикация* (пакетный обработчик с `publish(..)`) завершает весь пакет целиком, одной
транзакцией, поэтому поэлементный `and_after` с ней не сочетается.

### Отложенная повторная доставка

`retry_after` закрывает случай «ещё не готово»: зависимость ещё не появилась, внешний сервис
ограничивает частоту запросов. Немедленная повторная доставка в таком случае снова ничего не даст:

=== "Макросы"

    ```rust
    --8<-- "examples/retry.rs:retry_after"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/retry.rs:retry_after"
    ```

Задержку рантайм соблюдает так:

- Брокер с нативной отложенной повторной доставкой получает задержку напрямую. Так работает
  in-memory брокер, который доставляет повторно по таймеру; брокер на NATS JetStream мог бы
  послать `NAK` с задержкой.
- Брокер без нативной поддержки получает **отложенную повторную публикацию**: рантайм через
  `delay` публикует сообщение заново туда же, откуда оно пришло, а оригинал отбрасывает. В новой
  копии фреймворковый заголовок со счётчиком повторов
  ([`RETRY_COUNT_HEADER`](https://docs.rs/ruststream/latest/ruststream/runtime/constant.RETRY_COUNT_HEADER.html))
  увеличен на единицу, и обработчик может ограничить по нему число повторных доставок.

  Включить её в пределах области можно вызовом
  [`BrokerScope::retry_via(publisher)`](https://docs.rs/ruststream/latest/ruststream/runtime/struct.BrokerScope.html#method.retry_via);
  издатель должен указывать на тот же брокер. Без издателя задержка отбрасывается, и
  сообщение немедленно возвращается в очередь. Отложенная повторная публикация даёт
  **at-most-once** на время задержки: если процесс завершится до срабатывания таймера, копия
  потеряется.

Форма `batch_retry_after` сочетается с
[выборочным завершением пакета](#selective-acknowledgement): `Vec<HandlerOutcome>` задаёт задержки
поэлементно, поэтому неготовые записи ждут, не задерживая остальной пакет:

=== "Макросы"

    ```rust
    --8<-- "examples/retry.rs:batch_retry_after"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/retry.rs:batch_retry_after"
    ```

## Выбор источника подписки

Атрибут всегда фиксирует *вид* подписки: субъект, консьюмер JetStream, поток Redis, канал pub/sub и
список - это разные типы. Опустить можно *значение*: тогда его даёт точка монтирования. Форм
четыре, от самой короткой:

| Форма | Вид | Значение |
|---|---|---|
| `#[subscriber]` | источник по имени | из точки монтирования |
| `#[subscriber(RedisStream)]` | назван здесь | из точки монтирования |
| `#[subscriber("orders")]` | источник по имени | зафиксировано здесь |
| `#[subscriber(RedisStream::new("orders").group("w"))]` | назван здесь | зафиксировано здесь |

### По имени

`#[subscriber("orders")]` подписывается по имени. Форма работает с любым брокером, который
реализует трейт-совместимость `Subscribe`, а это все крейты брокеров семейства. Брокер отображает
имя в тот вид подписки, который считает у себя основным. Всё, что этому виду нужно сверх имени, вы
настраиваете один раз на самом брокере.

`#[subscriber]` - тот же источник, но без значения: имя, которое сервис узнаёт только при запуске,
субъект, собранный из номера шарда, топик, прочитанный из конфигурации:

=== "Макросы"

    ```rust
    --8<-- "examples/subscribers.rs:deferred_name"
    ```

    ```rust
    --8<-- "examples/subscribers.rs:name_mount"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/subscribers.rs:deferred_name"
    ```

    ```rust
    --8<-- "examples/manual/subscribers.rs:name_mount"
    ```

Есть виды, которым одного имени мало: источник Pulsar принимает и топик, *и* имя подписки. Такой вид
не реализует `FromName`, поэтому формы, которые берут имя из точки монтирования, для него не
компилируются. Пишите такие виды полностью.

### Дескрипторы, специфичные для брокера {#broker-specific-descriptors}

Когда подписке нужны опции конкретного брокера (группа консьюмеров, durable-имя, политика
доставки), крейт брокера даёт тип-дескриптор. Вызывайте его конструктор прямо в атрибуте:

<!-- inline-rust: illustrative descriptor sketch; OrdersStream is a stand-in for a broker crate's SubscriptionSource type, which lives in another crate and has no in-repo compiled home (the real NATS form is pulled in just below) -->
```rust
#[subscriber(OrdersStream::new("orders", "workers"))]
async fn handle(order: &Order) -> HandlerOutcome {
    HandlerOutcome::ack()
}
```

Тип дескриптора макрос читает из вызова конструктора, поэтому компилятор сверяет дескриптор с тем
брокером, на который его смонтировали. Дескриптор - это любой тип, реализующий
`SubscriptionSource<B>`; см. [Авторам брокеров](../broker-authors/index.md#subscription-sources).

Источником может быть и цепочка настроек поверх этого конструктора:

<!-- inline-rust: illustrative builder-chain source; the concrete options type lives in a broker crate, so there is no in-repo compiled home -->
```rust
#[subscriber(StreamOptions::new("orders").durable("audit"))]
async fn handle(order: &Order) -> HandlerOutcome {
    HandlerOutcome::ack()
}
```

Чтобы назвать тип источника, макрос спускается по цепочке до базового `Type::new(..)`, поэтому
каждый метод цепочки обязан возвращать `Self`. Свободные функции отвергаются: их тип макросу не
виден.

Такой источник пересобирается для каждого монтирования, поэтому тип-дескриптор брокера реализует
`Clone`. Одно определение можно смонтировать на два брокера.

## Настройки в точке монтирования

Имя, политика воркеров, политики обработки ошибок и стартовая позиция - это значения. Каждое можно
задать в атрибуте, в точке монтирования или частично там и там. Атрибут разворачивается ровно в те
вызовы, которые вы написали бы руками:

=== "Макросы"

    ```rust
    --8<-- "examples/subscribers.rs:builder_settings"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/subscribers.rs:builder_settings"
    ```

Настройка, названная в атрибуте, зафиксирована в типе определения, поэтому точка монтирования не
может назвать её повторно - никаких правил приоритета помнить не нужно:

<!-- inline-rust: two compile-fail one-liners; a compiling example cannot host code that must not compile (the pinned diagnostics live in tests/ui) -->
```rust
#[subscriber("orders", workers(4))]
async fn handle(order: &Order) -> HandlerOutcome { HandlerOutcome::ack() }

b.include(handle.name("other"));    // does not compile: the name is already given
b.include(handle.on_failure(..));   // fine: the attribute said nothing about failures
```

Методы объявлены в трейте `SubscriberSettings`, который реализует каждое сгенерированное
определение. Импортируйте его или
[prelude](https://docs.rs/ruststream/latest/ruststream/prelude/index.html), чтобы до них добраться.

Настройки, специфичные для брокера, вы задаёте тем же путём и в терминах самого брокера: стрим
JetStream, durable-имя консьюмера. Ядро такого словаря не знает, поэтому даёт одну точку
расширения - преобразование над собираемым источником. Крейт брокера добавляет поверх свой
трейт, привязанный к своему типу источника; см.
[Авторам брокеров](../broker-authors/index.md#subscription-sources).

Порядок в цепочке следует из того, что делает каждый шаг: имя идёт первым, потому что конструирует
источник, настройки брокера его преобразуют, а буфер, о котором ниже, оборачивает результат
последним.

## Монтирование обработчиков

Внутри `with_broker` монтируйте определение вызовом `include`:

<!-- inline-rust: minimal include mount fragment with placeholder info/broker; the full compiled program is examples/subscribers.rs (its app is pulled in via other anchors on this page) -->
```rust
RustStream::new(info).with_broker(broker, |b| {
    b.include(handle);
});
```

`include` декодирует полезную нагрузку кодеком с самого конкретного уровня, который вы задали: для
обработчика или для области. Если вы не задали ни одного, работает кодек по умолчанию, выбранный
фичами. См. [откуда берётся кодек](codecs.md#where-the-decode-codec-comes-from).

Чтобы сгруппировать обработчики по модулям и смонтировать их разом, соберите их в `Router`; см.
[Роутинг](routing.md).

## Пакетные подписчики {#batch-subscribers}

Обработчик, принимающий срез, получает пакет целиком: он выполняется один раз на каждый пакет,
доставленный брокером. Один запрос в базу, один массовый вызов API. Пакетную форму макрос читает из
сигнатуры, поэтому в атрибуте её не объявляют.

=== "Макросы"

    ```rust
    --8<-- "examples/subscribers.rs:batch"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/subscribers.rs:batch"
    ```

Монтируйте его через `include`, как любую другую форму. Пакетная форма уже задана в определении, а
точка монтирования добавляет одно число - размер пакета:

=== "Макросы"

    ```rust
    --8<-- "examples/subscribers.rs:batch_mount"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/subscribers.rs:batch_mount"
    ```

`batch(n)` - единственный пакетный параметр самого фреймворка, и он обязателен: пакетный
обработчик без него не компилируется. Рантайм передаёт размер брокеру, и тот собирает пакеты под
него: `XREADGROUP COUNT`, pull-пакет JetStream, лимит poll в Kafka. Тело видит ровно тот пакет,
который отдал брокер, и никогда его срез. Пакет бывает короче `n`, когда у брокера больше ничего
не было.

Всё остальное, из чего складывается пакет, - таймаут блокировки, группа консьюмеров, окно
предвыборки, - это словарь самого брокера. Такие настройки идут в цепочке после размера, на
источнике подписки брокера:

<!-- inline-rust: этот шаг принадлежит крейту брокера, а от него репозиторий зависеть не может -->
```rust
// на Redis-брокере: размер - слово ядра, `.block(..)` - слово брокера
b.include(reconcile.name("orders").batch(nonzero!(6)).block(Duration::from_secs(5)));
```

Размер задаётся одинаково на любой пакетной форме, в том числе когда обработчик отвечает или
публикует через слот `Out`. У обработчика одиночного сообщения пакета нет, поэтому `batch(n)` на
нём не компилируется. Сколько доставок такой обработчик берёт разом, задаёт `workers(n)`.

Пакеты даёт любой брокер. Брокер с нативной пакетной выборкой реализует трейт-совместимость
`BatchSubscriber` напрямую: poll в Kafka, pull-консьюмеры JetStream, `XREADGROUP` в Redis,
in-memory брокер. Брокер, транспорт которого отдаёт по одному сообщению, собирает пакеты на
клиенте адаптером `Buffered` из ядра, внутри своего крейта. В точке монтирования не видно, какой
из двух путей выбран. Как это устроено у брокера, описано в разделе
[Пакеты](../broker-authors/index.md#batches-batchsubscriber) руководства для авторов брокеров.

От обработчика одиночного сообщения семантика отличается в нескольких местах:

- Элемент, который не удалось декодировать, получает nack отдельно, по политике обработки ошибок
  декодирования, и до обработчика не доходит. Остальные приходят одним срезом.
- Возвращённое значение завершает весь пакет. Одиночный `HandlerOutcome` (или `()` /
  `Result<_, E>`) одинаково завершает **каждое** сообщение: `ack()` подтверждает все, `retry()`
  возвращает в очередь все.
- Заголовки отдельных сообщений в форме `&[T]` недоступны, и заголовки в контексте пусты.
- Контекст один на пакет, и поля брокера в нём - те, что относятся ко *всей подписке*. Пакетное
  тело называет пакетный тип контекста брокера (`ctx: &mut Context<'_, MemoryBatchContext>` для
  in-memory брокера) и читает его ключи через `ctx.context(..)`. Брокер без полей уровня подписки
  оставляет пакеты на умолчании `()`.
- Данных отдельной доставки в этом контексте нет: пакет охватывает много доставок, поэтому позиция
  и заголовок хранятся в самих элементах, а из пакета `&[Message<H, T>]` их читают поэлементно.
  Контекст доставки и контекст пакета - разные типы, поэтому пакетное тело, запросившее контекст
  отдельной доставки, не компилируется.
- Глобальные для приложения и роутерные middleware оборачивают обработчики отдельных сообщений и к
  пакетным регистрациям не применяются.

### Выборочное подтверждение {#selective-acknowledgement}

Частый случай - частичная готовность: часть сообщений пакета обработана, остальные ещё не готовы.
Повторной доставки требуют только неготовые. Верните `Vec<HandlerOutcome>`, чтобы элемент `i` среза
завершился исходом `i`:

=== "Макросы"

    ```rust
    --8<-- "examples/subscribers.rs:batch_selective"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/subscribers.rs:batch_selective"
    ```

Со стороны брокера семантика та же, что у `nack(requeue = true)` для одного сообщения. Брокер с
повторной доставкой отдельных сообщений поддерживает выборочный повтор нативно, а позиционный
брокер деградирует так же, как на nack одиночного сообщения; крейт такого брокера это описывает.
Вектор, длина которого не совпадает с пакетом, - ошибка в обработчике: несопоставленный остаток
отправляется на повторную доставку, а расхождение попадает в лог.

## Перемотка {#seeking}

Повторить обработку потока после починки ошибки в обработчике, перечитать его с известной точки,
перескочить через ядовитый участок: каждый случай называет позицию в потоке. Позиция задаёт точку,
с которой подписка открывается, или точку, на которую переходит работающая подписка, не
прерываясь.

Брокер поверх воспроизводимого лога (Kafka, потоки Redis, журнал публикаций in-memory брокера)
реализует трейт-совместимость `Seekable`, владеет типом позиции и даёт ключи перемотки в своём
контексте доставки. На брокере без воспроизводимого лога монтирования ниже отвергаются во время
компиляции, а не в рантайме.

### Открытие с выбранной позиции

Новая подписка открывается там, где решит брокер: в хвосте для обычного консьюмера, на сохранённом
курсоре для долговечного. Всё, что опубликовано до этой точки, сервис не увидит. Журналу аудита
нужна вся история, а монитор, наоборот, не должен разбирать накопленное отставание.

Позиция открытия - свойство точки монтирования, а не обработчика, поэтому её и задают там: клаузой
`start_at(<position>)` в атрибуте или шагом настроек `.start_at(..)`:

=== "Макросы"

    ```rust
    --8<-- "examples/seek.rs:start_at"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/seek.rs:start_at"
    ```

    ```rust
    --8<-- "examples/manual/seek.rs:start_at_mount"
    ```

Позиция - значение собственного типа позиций брокера, поэтому назвать можно ровно то, что брокер
умеет выразить. In-memory лог даёт `MemoryPosition::start()` для всей истории,
`MemoryPosition::end()` - для всего начиная со следующей публикации, `MemoryPosition::sequence(n)` -
для одной записи лога.

Клауза задаёт позицию при каждом старте. Без неё подписка открывается на умолчании брокера.
Условное умолчание - применить позицию, только если у брокера нет сохранённого курсора для группы
(сброс смещения в Kafka, deliver policy в JetStream), - задаётся на собственном дескрипторе
подписки брокера: он выражает такое умолчание нативно.

### Перемотка из обработчика

Обработчик передвигает собственную подписку через ключи контекста брокера. В контексте доставки
лежат позиция и живой дескриптор перемотки, который брокер создаёт один раз, в момент подписки.
Обработчик читает их по ключу: экстрактором `Ctx` на пути атрибута, вызовом `ctx.context(..)` над
типом контекста брокера на ручном. В месте `include` ничего прикреплять не нужно:

=== "Макросы"

    ```rust
    --8<-- "examples/seek.rs:handler"
    ```

    ```rust
    --8<-- "examples/seek.rs:mount"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/seek.rs:handler"
    ```

    ```rust
    --8<-- "examples/manual/seek.rs:mount"
    ```

Пакетное тело перематывает свою подписку так же, только уровнем выше. Ручка перемотки относится ко
всей подписке, поэтому лежит в пакетном контексте брокера. Цель перемотки - позиция, с которой
издатель просит продолжить, - хранится в элементах самого пакета.

Область действия одной перемотки у брокеров различается: перемещение экземпляра консьюмера (Kafka)
двигает только этот экземпляр, а перемещение общего курсора группы (потоки Redis) двигает всю
группу. Перемотка также делает недействительным весь учёт ack, который брокер вёл по этой подписке.
И то и другое описывает крейт брокера. Авторы брокеров доказывают контракт
[набором conformance `capabilities::seeking`](../broker-authors/conformance.md#capability-suites).

## Сырые подписчики {#raw-subscribers}

Иногда полезная нагрузка - не сериализованное значение, а двоичный кадр или чужой формат передачи,
который вы разбираете сами. Тип нагрузки убирает кодек из пути обработки:

```text
обычный путь: брокер -> байты -> кодек -> &Order     -> обработчик
сырой путь:   брокер -> байты ->          &Frame<'_> -> обработчик
```

Мнемонику пути дают имена трейтов: `Deserialize`/`Serialize` - работу делает кодек фреймворка,
`Deserialized`/`Serialized` - тип сделал её сам.

Тип `Deserialized` - это `&[u8]` с именем: одно поле, ничего не копируется. Объявление сводится к
`#[derive(Deserialized)]` на newtype над `&'a [u8]`, а параметр `&Frame<'_>` выбирает для
обработчика сырой путь. Байты приходят ровно такими, какими их отдал брокер, заимствованными из
его буфера.

=== "Макросы"

    ```rust
    --8<-- "tests/raw_subscriber.rs:raw"
    ```

=== "Вручную"

    ```rust
    --8<-- "tests/manual_raw_subscriber.rs:raw"
    ```

Голый параметр `&[u8]` не компилируется: нагрузка всегда приходит в именованном типе самого
сервиса, а ошибка компиляции называет нужный derive. Вкладка «Вручную» показывает пару impl-ов,
которую пишет derive: конструкцию из байтов и объявление, которое направляет тип на сырой путь.

Правило формы от пути не зависит: `&T` - одно сообщение, `&[T]` - пакет. Пакет кадров - это
`&[Frame<'_>]`, и тот же derive даёт объявление для пакета: второй impl пакетному телу не нужен.
Элементы пакета заимствованы у его сообщений на время вызова, поэтому и здесь ничего не копируется.
Правила завершения доставки - те же, что и на пакетном пути.

=== "Макросы"

    ```rust
    --8<-- "examples/subscribers.rs:raw_batch"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/subscribers.rs:raw_batch"
    ```

Конструкция, которая проверяет содержимое (корень flatbuffers, читатель capnp, проверка длины),
возвращает `Err` из `from_payload`. Доставку тогда завершает политика `on_failure(decode = ..)` -
та же, что и при ошибке декодирования кодека или нарушении типизированного контракта `Headers`.

Всё остальное складывается как обычно. Экстракторы, `&mut Context`, `workers(..)`,
`on_failure(panic = ..)` и внедряемые параметры `Out` работают на форме одиночной доставки без
изменений; пакет кадров параметра `Out` не принимает. Монтируется такой подписчик тем же `include`,
что и любое другое определение.

Кодек области к нему не применяется: этот путь кодек не вызывает. Поэтому сырая форма -
единственная, которая работает вообще без включённых фич кодеков. Для собственного формата
сериализации с *типизированными* обработчиками реализуйте [`Codec`](codecs.md) и оставайтесь на
типизированном пути.

Обработчик на этом пути отвечает через ту же клаузу `publish("dest")`, что и любая другая форма
ответа. Способ передачи выбирает *тип* ответа, по той же мнемонике: ответ с `serde::Serialize`
кодируется кодеком ответа, а ответ с `#[derive(Serialized)]` производит собственные байты, и они
публикуются ровно такими, какими их вернул обработчик. Ответ можно вернуть напрямую или как
`Result<Export, HandlerOutcome>`: это то же явное управление ack, что и в кодирующей форме.

Издателя конструирует политика, указанная в месте `include`, и оба способа передачи называют её
одинаково: `b.include(relay).out(Reply, Publish)`. Без вызова `.out(..)` издателя конструирует
политика публикации брокера по умолчанию.

Дальше цепочки расходятся: кодируемый ответ принимает `.codec(..)`, `.transform(..)` и
`.transactional()`, а байты `Serialized` публикуются нетронутыми, поэтому таких шагов на этом пути
нет. Неудачная публикация ответа даёт доставке nack с возвратом в очередь, ровно как на кодирующем
пути:

=== "Макросы"

    ```rust
    --8<-- "tests/raw_subscriber.rs:raw_reply"
    ```

=== "Вручную"

    ```rust
    --8<-- "tests/manual_raw_subscriber.rs:raw_reply"
    ```

Стороны друг друга не ограничивают: тип входа выбирает декодирование, тип ответа - кодирование, и
сочетаются они свободно. Декодируемый вход с ответом `Serialized` - это форма шлюза: сервис
принимает структурированные сообщения и отдаёт формат передачи, который обработчик собрал сам. Вход
при этом декодируется кодеком области, и политика обработки ошибок декодирования у него своя:

=== "Макросы"

    ```rust
    --8<-- "tests/raw_subscriber.rs:raw_reply_typed"
    ```

=== "Вручную"

    ```rust
    --8<-- "tests/manual_raw_subscriber.rs:raw_reply_typed"
    ```

Обратное сочетание читается так же: ответ `Serialize` кодируется кодеком ответа, а вход
`Frame<'_>` кодека не касается.

Из этого правила выпадают два случая. Ответ `Vec<u8>` сырым не считается: это обычное значение
`Serialize`, оно публикуется закодированным, и нагрузке, которая обязана остаться нетронутой, нужен
newtype. Ответ на пакет всегда публикуется через кодек ответа: способ передачи `Serialized`
работает для одиночных ответов.

## Пулы воркеров

Цикл диспетчеризации у подписчика последовательный: доставка обрабатывается и завершается до того,
как подписчик возьмёт следующую. Поэтому один медленный обработчик задерживает всю подписку.
С клаузой `workers(n)` подписчик обрабатывает до `n` доставок одновременно, каждую в своей задаче
на многопоточном рантайме:

=== "Макросы"

    ```rust
    --8<-- "examples/subscribers.rs:workers"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/subscribers.rs:workers"
    ```

Обратное давление сохраняется: пока `n` доставок в работе, поток не опрашивается. Это согласуется
с ограничениями на стороне брокера вроде `max_ack_pending` в JetStream. **Глобальный порядок
обработки при этом теряется, и так задумано.** Если порядок доставки важен, оставайтесь
последовательными или партиционируйте обработку по ключу:

=== "Макросы"

    ```rust
    --8<-- "examples/subscribers.rs:workers_by_key"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/subscribers.rs:workers_by_key"
    ```

`workers(n, by_key)` разбивает обработку на `n` последовательных партиций. Доставка попадает в
партицию, на которую хешируется её ключ партиционирования, поэтому сообщения с одним ключом не
обрабатываются одновременно и не меняют порядок. Это внутрипроцессный аналог семантики партиций
Kafka.

Ключ берётся из `partition_key()` брокерского сообщения: его дают брокеры, у которых сообщения
реализуют трейт-совместимость `Partitioned`, а in-memory брокер читает заголовок `partition-key`.
Сообщения без ключа раскладываются по партициям по кругу. `by_key` применим к подписчикам одиночных
сообщений, а пакетные формы берут обычный пул `workers(n)` из пакетов.

При остановке подписчик перестаёт вытягивать новые доставки, а воркеры в работе дорабатывают в
пределах `shutdown_timeout` приложения.

## Правила композиции

Возможности подписчика сочетаются друг с другом. Ниже - правило на каждом пересечении; каждое
закреплено интеграционным тестом.

| Сочетание | Правило |
|---|---|
| `workers(n)` × пакетный обработчик | Пул держит в работе до `n` **пакетов**. `by_key` к пакетным формам не применяется: партиционирование упорядочивает одиночные сообщения по ключу, и макрос отвергает такое сочетание на этапе компиляции. |
| `retry()` / `retry_after` × `workers(n)` | Повторно доставленные сообщения снова попадают в пул и завершаются как любая другая доставка. |
| `retry()` / `retry_after` × `workers(n, by_key)` | Повторы отрабатывают, но порядок внутри ключа через повтор **не** гарантируется: возвращённое в очередь сообщение встаёт в поток с конца. Если сообщения ключа обязаны сохранять порядок даже через сбои, обработчик должен справиться со сбоем сам, а не отвечать nack. |
| `.transactional()` × `workers(n)` | Одна транзакция на пакет, ровно как в последовательном цикле. Параллельные пакеты выполняют параллельные независимые транзакции; каждая остаётся атомарной (на пакет: сначала коммит, потом ack). |
| размер пакета × `workers(n)` | Пакеты по-прежнему закрываются по `batch(n)` или, если брокер собирает их на клиенте, по его сроку; пул ограничивает лишь то, сколько закрытых пакетов обрабатывается одновременно, и на границы пакетов не влияет никогда. |
| `publish(..)` × `workers(n)` | Ответы формируются параллельно, поэтому порядок ответов между доставками не гарантируется. Неудачная публикация ответа повторяет только свою доставку. |
| middleware × пакетный обработчик | Глобальные для приложения и роутерные слои оборачивают обработчики отдельных сообщений и к пакетным регистрациям не применяются (слой на одно сообщение не может обернуть обработчик целого пакета). |

## Макрос или вручную

`#[subscriber]` - это сахар над обобщённым API. Макрос генерирует типизированный обработчик и его
метаданные. Ту же регистрацию можно написать руками: тело обработчика кладут в `impl Handle`
именованного типа, тип привязывают к источнику вызовом `subscriber(source, body)`, а цепочку
завершают вызовом `.build()`. Обе формы ниже регистрируют один и тот же обработчик.

=== "Макрос"

    ```rust
    use ruststream::subscriber;

    --8<-- "examples/subscribers.rs:contract"

    // inside with_broker(...):
    b.include(handle);
    ```

=== "Вручную"

    ```rust
    use ruststream::prelude::*;

    // inside with_broker(...):
    --8<-- "examples/subscribers.rs:manual"
    ```

Ручное тело возвращает `Result`. В `Ok` лежит то, что произвёл обработчик: ответ или ничего. В
`Err` лежит завершение доставки, поэтому `Ok(())` подтверждает, а `Err(HandlerOutcome::retry())`
возвращает сообщение в очередь. Пакетное тело завершает доставки поэлементно через
`Err(Vec<HandlerOutcome>)`.

Между `subscriber(..)` и `.build()` цепочка принимает те же настройки, что и клаузы атрибута:
`.name`, `.workers`, `.on_failure`, `.batch`. Там же вы управляете документацией: с фичей
`asyncapi` регистрация документируется по умолчанию, `.describe(..)` задаёт её описание, а
`.undocumented()` выводит её из документа (см. [AsyncAPI](asyncapi.md#payload-schemas)).

Ручная форма нужна, когда обработчику требуется состояние, которое макрос выразить не может
(обработчик-структура с полями), или когда фича `macros` выключена. В остальных случаях атрибут
дешевле в сопровождении.

## Издатели

Обработчик, который формирует ответ, - это издатель. См. [Публикация и ответы](publishing.md).
