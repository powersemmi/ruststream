# Публикация и ответы

Обработчик публикует одним из двух способов. Вернуть ответ - способ короче, и он верен по умолчанию,
когда обработчик отвечает по одному объявленному адресату. Издателя параметром `Out` берут, когда
адресат определяется динамически или когда сообщение уходит сразу нескольким адресатам, в том числе
в разные брокеры. В обоих случаях обработчик не видит неподключённого издателя: при регистрации вы
указываете *политику* публикации, а она на старте инстанцирует издателя на подключённом брокере.

Явная публикация - это всегда один и тот же билдер: он начинается с `message(..)` и заканчивается
`publish()`. Публикуется значение объявленного типа, и способ передачи выбирает сам тип:

```text
message(&order)   -> кодек -> байты -> брокер    (значение Serialize кодируется)
message(&export)  ->          байты -> брокер    (значение Serialized выдаёт байты само)
```

Байты, которые сервис уже держит закодированными, публикуются через newtype с выводом `Serialized`,
и имя вносит их в сгенерированный документ. Тип сообщения объявляет, какие позиции остаются точке
вызова: адресат, типизированные заголовки, кодек. Недоопределённая публикация не компилируется.

## Ответ из обработчика

Тип ответа объявляют через `#[derive(Outgoing)]`. Атрибут `#[outgoing(name = "..")]` на типе - это
адресат. Верните значение ответа и напишите `publish` у подписчика:

=== "Макросы"

    ```rust
    use ruststream::Outgoing;

    --8<-- "examples/publishing.rs:reply_declared"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/publishing.rs:reply_declared"
    ```

Тип ответа без объявленного имени берёт имя в точке монтирования: `publish("responses")` в
атрибуте, `.to("responses")` в цепочке. Тип, который задаёт имя сам, публикуется по этому имени, и
имя из точки монтирования к нему не применяется.

=== "Макросы"

    ```rust
    use ruststream::subscriber;

    --8<-- "examples/publishing.rs:reply"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/publishing.rs:reply"
    ```

Монтируется такой обработчик обычным `include`. Если больше ничего не сказано, ответ публикуется
через политику публикации брокера по умолчанию и кодек по умолчанию. Вызов `.out_reply(Publish)`
называет политику, которую экспортирует прелюдия брокера, а следующие шаги цепочки достраивают
связывание ответа: `.codec(..)` задаёт кодек ответа, `.transform(..)` - статическое преобразование
публикации, `.transactional()` - одну брокерскую транзакцию на пакет ответов. Кодек называют один
раз: второй `.codec(..)` - ошибка компиляции.

Определение обработчика не называет издателя: оно объявляет, чем обработчик отвечает и куда.
Политика публикации принадлежит брокеру, поэтому её указывают там же, где брокер, - в точке
монтирования, тем же вызовом `.out(marker, policy)`, которым связывают слот `Out`. `Reply` - это
маркер позиции, через которую публикуется возвращённое обработчиком значение.

=== "Макросы"

    ```rust
    --8<-- "examples/publishing.rs:reply_mount"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/publishing.rs:reply_mount"
    ```

Входящий запрос декодируется кодеком области, заданным через `with_broker_codec`, иначе кодеком по
умолчанию. Кодек ответа задаётся связыванием, которое построила цепочка. См.
[Кодеки](codecs.md#the-publish-side).

Оба способа отправки обслуживает один и тот же `publish(..)`: выбор принадлежит типу ответа. Ответ
с `serde::Serialize` кодируется, как выше. Ответ с `#[derive(Serialized)]` производит собственные
байты и публикуется байт в байт, поэтому его `.out_reply(..)` берёт только политику: кодек на этом
пути называть негде, и `.codec(..)` после него не компилируется. См.
[сырые подписчики](subscribers.md#raw-subscribers).

## Управление подтверждением

Простая форма ответа всегда публикует и делает ack. Чтобы взять управление на себя, возвращайте
`Result<Reply, HandlerOutcome>`. Тогда `Ok(reply)` публикует и делает ack, а `Err(outcome)` не
публикует ничего, и диспетчер действует по возвращённому `HandlerOutcome`
(`HandlerOutcome::drop()` - отправить в dead-letter, `HandlerOutcome::retry()` - запросить повторную
доставку):

=== "Макросы"

    ```rust
    --8<-- "examples/publishing.rs:reply_result"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/publishing.rs:reply_result"
    ```

Форма `Result` распознаётся по написанной сигнатуре, поэтому выпишите её явно: псевдоним типа,
скрывающий `Result`, считается обычным типом ответа. Публикующий обработчик, как и любой другой,
может объявить необязательный второй параметр `&mut Context` и прочитать состояние приложения или
опубликовать что-то вручную.

Если сама публикация ответа вернула ошибку (брокер отверг её, соединение потеряно), входящее
сообщение получает nack с `requeue = true`, и брокер доставляет его повторно. Делайте публикующие
обработчики идемпотентными относительно повторной доставки.

## Публикация изнутри обработчика {#publishing-from-inside-a-handler}

Когда адресат определяется динамически или сообщение уходит сразу нескольким адресатам, в том числе
в разные брокеры, принимайте издателя параметром обработчика через `Out`. Шаблон
`Out(out): Out<impl Publisher>` связывает `out` с живым издателем внутри тела. Сигнатура называет
только ту совместимость, которая обработчику нужна, а конкретный тип издателя выводится из политики,
указанной в точке монтирования. Один и тот же обработчик без правок монтируется и на боевой брокер,
и на его внутрипроцессный тестовый транспорт.

=== "Макросы"

    ```rust
    use ruststream::runtime::Out;

    --8<-- "examples/publishing.rs:forward"
    ```

=== "Вручную"

    ```rust
    use ruststream::runtime::Out;

    --8<-- "examples/manual/publishing.rs:forward"
    ```

Вызов `message(&value)` публикует тем способом, который выбрал тип значения. Значение с
`serde::Serialize` кодируется кодеком области; для одного вызова другой кодек называют через
`.with_codec(..)`. Значение с `Serialized` публикуется байт в байт и позиции для кодека не имеет.
У обоих способов есть позиция заголовков: вызов `.with_headers(..)` принимает объявленный контракт
сообщения по ссылке (`&meta`) или уже собранный `HeaderMap` по значению. Публикация заканчивается
вызовом `publish()`.

Точка монтирования называет источник; для собственного брокера области это его политика публикации:

=== "Макросы"

    ```rust
    --8<-- "examples/publishing.rs:forward_mount"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/publishing.rs:forward_mount"
    ```

Несвязанный слот `Out` - это ошибка компиляции: регистрация не собирается, пока у каждого слота нет
политики.

### Именованные слоты {#named-slots}

Обработчик, принимающий несколько издателей, называет на каждый параметр **маркер слота**: пустую
структуру с выводом `OutSlot`, записанную вторым типовым аргументом
(`Out<impl Publisher, Primary>`). Точка монтирования связывает каждый маркер вызовом
`.out(marker, policy)` и фиксирует регистрацию завершающим `.build()`. Вызовы связывают по маркеру,
поэтому их порядок неважен. Связать один и тот же слот дважды или назвать маркер, которого
обработчик не объявлял, - ошибка компиляции. Сам `.build()` существует, только когда связаны все
слоты, поэтому забытая привязка тоже не компилируется, и слот назван прямо в типе
(`MissingSlot<Audit>`). Единственный безымянный параметр `Out<impl Publisher>` связывается с неявным
`DefaultSlot` (`.out(DefaultSlot, Publish).build()`).

Вызов `.transform(..)` после `.out(..)` относится к той позиции, которую назвал этот `.out(..)` (см.
[конвейер публикации](#the-publish-pipeline)), поэтому регистрация, которая и отвечает, и
раздаёт копии, называет преобразование на каждой:
`.out_reply(Publish).transform(StampSource).out(Audit, Publish).transform(Envelope)`.

=== "Макросы"

    ```rust
    use ruststream::OutSlot;

    --8<-- "examples/publishing.rs:slots"
    ```

    ```rust
    --8<-- "examples/publishing.rs:slots_mount"
    ```

=== "Вручную"

    ```rust
    use ruststream::OutSlot;

    --8<-- "examples/manual/publishing.rs:slots"
    ```

    ```rust
    --8<-- "examples/manual/publishing.rs:slots_mount"
    ```

Совместимость в ограничении можно уточнить: `Out<impl OwnedTransactions, Ledger>` скомпилируется
только с политикой, живой издатель которой поддерживает владеющие транзакции. Ограничение
проверяется в точке монтирования, и ошибка компиляции называет недостающую совместимость.
Ограничение называет трейт брокерской совместимости - `Publisher`, `TransactionalPublisher`,
`OwnedTransactions`, `RequestReply` или тот, что объявил крейт брокера, - а не тип брокера, поэтому
тело не зависит от брокера. На ручном пути то же ограничение стоит на живом значении записи,
`where L: OutEntry<Ledger, Wire: OwnedTransactions>`. Под каждым таким ограничением запись отдаёт
типизированную форму этой совместимости (билдер публикации, область транзакции, владеющую
транзакцию) поверх кодека точки монтирования и списка маркера. Маркер слота служит и тем именем, по
которому [тестовая обвязка](testing.md#asserting-on-out-slots) записывает публикации.

Необязательная третья позиция параметра `Out` объявляет, что именно публикует этот обработчик:
`Out<impl Publisher, Marker, (A, B)>`, один тип или enum-набор с `#[derive(OutMessages)]`.
Собственный список маркера `#[publishes(A, B)]` задаёт, что слоту разрешено публиковать, и для
обработчика, оставившего третью позицию без ограничения, сгенерированный документ показывает именно
его. Типизированная публикация типа, которого маркер не называет, - ошибка компиляции. Маркер, не
перечисливший ничего, не публикует ничего: у каждой публикации есть тип сообщения, поэтому список
распространяется на все публикации. У неявного `DefaultSlot` единственного безымянного
`Out<impl Publisher>` нет места объявления, где перечислять типы, поэтому он допускает любое
объявленное сообщение. См. [типизированные заголовки](headers.md).

Тип с `#[derive(Serialized)]` публикуется в слот байт в байт, без кодека на пути. Всё остальное
подчиняется обычным правилам: дайте типу `#[derive(Outgoing)]` и перечислите его в
`#[publishes(..)]`, как любую модель. Документ покажет его под собственным именем и без схемы
нагрузки, потому что формат тут и есть сами байты. Адресат берётся из объявления, а словарь,
объявленный набор сообщений и позиции заголовков проверяют такой тип так же, как кодируемую модель.

=== "Макросы"

    ```rust
    --8<-- "tests/lanes.rs:serialized_out"
    ```

=== "Вручную"

    ```rust
    --8<-- "tests/manual_out_slots.rs:serialized_out"
    ```

### Объявление адресата сообщения {#declaring-where-a-message-goes}

Тип сообщения объявляет всё, что касается его отправки, одним derive, и параметры записываются в
форме `key = value`. Параметр `name` - это адресат, а `headers` называет тип контракта заголовков;
сам контракт остаётся обычной serde-структурой, derive её не трогает:

=== "Макросы"

    ```rust
    use ruststream::Outgoing;

    --8<-- "examples/publishing.rs:declared"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/publishing.rs:declared"
    ```

Объявление решает, какая позиция адресата остаётся точке вызова:

- **Фиксированное имя** задаёт адресата, поэтому писать `to(..)` негде: такой тип публикуется
  только по адресу из объявления.
- **Шаблон имени** (`"orders.{tenant}.placed"`) открывает `to()`, который возвращает билдер с одним
  сеттером на каждую подстановку. Вызов `publish()` компилируется, только когда связаны все
  подстановки, а несвязанная остаётся прямо в типе билдера, поэтому ошибка компиляции сообщает, что
  адрес не достроен, и называет забытый сегмент. Адрес собирается заново на каждую публикацию, а
  фиксированное имя публикация берёт из `&'static str`.
- **Отсутствие `name`** означает, что имя называет точка вызова: `.to("orders.archived")` принимает
  `&str` или вычисленный `String`.

Сообщение, объявившее `headers = Meta`, публикуется только через `.with_headers(&meta)`: забытые
заголовки или другой тип не компилируются. В сгенерированном документе фиксированное имя становится
каналом сообщения, а шаблон - адресом с параметрами, блок которых заполняется из подстановок. Тип,
не объявивший адресата, в документ не попадает.

Публикуемым через билдер значение делает именно derive, включая третий случай. Тип с `Serialize` из
чужого крейта вывести `Outgoing` не может: такое значение можно завернуть в newtype с выводом
`Outgoing` или, внутри транзакции, опубликовать через `publish(name, &value)` у области.

=== "Макросы"

    ```rust
    --8<-- "examples/publishing.rs:declared_mount"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/publishing.rs:declared_mount"
    ```

Параметр `Out` сочетается с любой формой подписчика: рядом с экстрактором `Ctx`, на обработчике,
который десериализует вход сам, и на пакетных обработчиках
(`b.include(f).out(marker, policy).build()` - на вход целый пакет, на выход адресаты на каждый
элемент). В формах ответа, `publish(..)` и его пакетном аналоге, ответ становится ещё одной позицией
той же цепочки. Поэтому шлюз называет обе позиции и одновременно отвечает по фиксированному адресату
и рассылает побочные копии через внедрённого издателя:

=== "Макросы"

    ```rust
    --8<-- "examples/publishing.rs:publish_out"
    ```

    ```rust
    --8<-- "examples/publishing.rs:publish_out_mount"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/publishing.rs:publish_out"
    ```

    ```rust
    --8<-- "examples/manual/publishing.rs:publish_out_mount"
    ```

### Публикация в другой брокер

Когда обработчик потребляет из одного брокера, а публикует в другой (потребляет Kafka, пересылает в
Redis), оберните целевой брокер вызовом `.bindable()` и выпустите **связывающий токен** ещё до
регистрации. Дальше токен служит источником в точке монтирования. Форма одинакова для любой пары
брокеров, здесь она показана на двух in-memory брокерах:

=== "Макросы"

    ```rust
    --8<-- "tests/out_injection.rs:cross_broker"
    ```

=== "Вручную"

    ```rust
    --8<-- "tests/manual_out_injection.rs:cross_broker"
    ```

Токены существуют до того, как отработает хоть один `with_broker`, поэтому порядок регистрации не
имеет значения: двунаправленный мост связывает оба направления заранее.

Токен делит слот с обёрткой `Bindable`, из которой он выпущен, поэтому регистрируйте ту же обёртку
(`with_broker(bindable, ..)`), чтобы старт заполнил слот подключённым брокером. Токен, брокер
которого так и не зарегистрировался, возвращает внятную ошибку сразу на связывании. Та же форма
работает и для публикации ответов (`.out_reply(token)` на обработчике с `publish("dest")`), и для
пакетных форм.

Вне регистрации токен связывает себя сам, как только старт подключил его брокер:
`running.publisher(token)` выдаёт соседней задаче живого издателя - см.
[Работа рядом с другим сервером](http.md). Для самой первой публикации на старте токен не нужен
вовсе: `b.after_startup(policy, hook)` на уровне области запускает хук с уже связанным издателем,
как только подписки открыты (см. [Жизненный цикл](lifespan.md#lifecycle-hooks)). На нём выполняется
и начальное заполнение данными в примере публикации.

## Откуда берутся заголовки {#where-the-headers-come-from}

Заголовки публикации складываются из двух источников. Место вызова задаёт их через
`.with_headers(..)`: объявленным контрактом сообщения по ссылке или готовым `HeaderMap` по
значению. Издатель может добавить к ним собственную основу: в `base_headers` он хранит заголовки,
одинаковые в каждом его сообщении (арендатор, имя продюсера, идентификатор схемы). Так же поступает
и транзакция, открытая от этого издателя.

Билдер собирает исходящие заголовки один раз: сначала основу, затем поверх неё, ключ за ключом,
заголовки места вызова. Значение ключа определяется в следующем порядке:

- ключ, названный в **месте вызова**, берёт значение оттуда;
- ключ, которого место вызова не касается, берёт значение из основы **издателя**;
- издатель без собственной основы оставляет заголовки места вызова ровно такими, как их написали.

Обе формы сливаются одинаково: готовый `HeaderMap` дописывается запись за записью, а объявленный
контракт `headers = Meta` сериализует свои поля поверх основы, поэтому сообщение с контрактом
получает и основу издателя.

`.with_headers(..)` заполняется однажды: второй вызов - ошибка компиляции.

Ответ собирается так же, хотя `.with_headers(..)` на нём не пишут: издатель, созданный политикой,
которую точка монтирования назвала для позиции `Reply`, кладёт свою основу первой, а шаги
`.transform(..)` той же цепочки пишут поверх неё. Поэтому заголовок из основы издателя оказывается и
в ответе обработчика `publish("dest")`, и в каждом ответе пакета, и в том, что тело отправляет через
слот `Out`, - обработчик о нём не знает.

## Настройки брокера на сообщение {#broker-settings-per-message}

Брокер позволяет одному сообщению отличаться от следующего не только полезной нагрузкой: QoS,
приоритет, ключ упорядочивания, срок жизни. Это собственные настройки брокера, а не заголовки, и в
публикацию они приходят из двух мест.

Одно место - политика публикации: умолчания вы задаёте в точке монтирования, и каждое сообщение
через этот слот уходит с ними:

=== "Макросы"

    ```rust
    --8<-- "tests/publish_options.rs:mount"
    ```

=== "Вручную"

    ```rust
    --8<-- "tests/manual_publish_options.rs:mount"
    ```

Та же политика в позиции `Reply` задаёт умолчания для того, чем отвечает обработчик
`publish("dest")`. У ответа нет места вызова, поэтому задать их можно только в политике:

=== "Макросы"

    ```rust
    --8<-- "tests/publish_options.rs:reply_mount"
    ```

=== "Вручную"

    ```rust
    --8<-- "tests/manual_publish_options.rs:reply_mount"
    ```

Другое место - вызов: одну настройку для одного сообщения вы можете изменить шагом, который ваш
брокер добавляет к билдеру публикации. Настройка, которую ни один шаг не назвал, сохраняет умолчание
политики:

=== "Макросы"

    ```rust
    --8<-- "tests/publish_options.rs:handler"
    ```

=== "Вручную"

    ```rust
    --8<-- "tests/manual_publish_options.rs:body"
    ```

Остальное в публикации по-прежнему принадлежит точке монтирования: кодек, который назвала запись, её
преобразования и слот, на который обвязка запишет отправку. Шаги есть на любой поверхности
публикации - на слоте `Out`, на транзакции, открытой от него, на обычном издателе из состояния
приложения или из стартового хука.

В тесте вы можете прочитать настройки, с которыми ушла публикация через слот `Out`, включая те, что
брокер превращает в поле протокола, а не в заголовок: см.
[проверки слотов Out](testing.md#asserting-on-out-slots).

Тело, которое меняет настройку, импортирует прелюдию этого брокера ради шага и называет тип настроек
брокера в ограничении (`Out<impl Publisher<Options = MqttOptions>, Telemetry>`). Это единственное
место, где тело обработчика импортирует что-то помимо прелюдии фреймворка, и сигнатура тогда
называет брокер, к которому привязан обработчик. Какие шаги существуют - отвечает документация
вашего брокера.

## Конвейер публикации {#the-publish-pipeline}

Опубликованное сообщение проходит два уровня, прежде чем покинуть процесс, и они сочетаются:

- **Статический `PublishTransform`** на одной позиции, добавляемый через `.transform(..)` сразу
  после того `.out(..)`, который эту позицию назвал. Zero-cost преобразования на конкретного
  адресата: конверт, фиксированный content type, trace / correlation id доставки в ответе, конверт
  outbox или метка арендатора на слоте. Они выполняются ближе всего к значению, до общего для
  приложения конвейера.
- **Статический `PublishLayer`** на приложении, добавляемый через `.publish_layer(..)`. Сквозная
  функциональность (метрики публикации, обёртка dead-letter), применяемая к каждому опубликованному
  сообщению вокруг самой отправки, чтобы видеть её результат. Цепочка складывается в конкретный тип
  и становится частью типа приложения: билдер обычно возвращает `impl App` и никогда его не
  выписывает, а конкретный `RustStream<L, St, PublishStack<MyMiddleware, PublishIdentity>>`
  показывает конвейер прямо в записи типа; приложение без `publish_layer` сохраняет умолчание
  `PublishIdentity`. Каждый middleware обязан быть `Clone` (конвейер клонируется в каждый
  публикующий обработчик), а добавленный последним выполняется самым внешним. Умолчание
  (middleware нет) - это прямая отправка. Набор middleware, который определяется во время работы,
  можно завернуть в `PublishDynStack` (публикующий аналог `DynStack`) и добавить уже его.

### Что преобразование объявляет {#what-a-transform-declares}

Преобразование объявляет две вещи: что оно читает и что ему разрешено делать с адресатом.

Преобразование читает вид контекста этой позиции - тот самый `K` в
`apply(&mut Outgoing<'_>, &K::View<'_>)`, который выбирает точка монтирования:

| позиция | вид | что читает преобразование |
|---|---|---|
| ответ, после `.out_reply(..)` | `ForReply<C>` | `PublishContext<'_, C>`: доставка, на которую отвечают |
| слот `Out`, после `.out(marker, policy)` | `ForSlot` | `SlotContext<'_>`: имя самого слота |

Разрешённое задаёт `type Destination`: `Reads` для преобразования, которое адресата не трогает, и
`Names` для того, которое его задаёт. Эту строку пишет каждая реализация, и почти каждая пишет
`Reads`.

Преобразование, которое ничего не читает, пишет одну реализацию на все виды и монтируется на любой
позиции:

```rust
--8<-- "examples/publishing.rs:static_transform"
```

`ForReply` даёт доступ только на чтение к доставке, породившей ответ: к её каналу, входящим
заголовкам и типизированному контексту брокера на одну доставку, читаемому по ключу `Field`.
Поэтому преобразование может перенести значение из входящего сообщения в ответ. Этот вид задаёт и
место преобразования: смонтировать его на слоте - ошибка компиляции в точке монтирования.

`ForSlot` отдаёт имя слота и больше ничего. Публикацию в слот делает само тело обработчика, поэтому
оно может прочитать свой `Context` и положить в сообщение всё нужное из доставки.

```rust
--8<-- "examples/publishing.rs:slot_transform"
```

Ответы пакетного обработчика идут мимо стека `.transform(..)`, который работает на каждое
сообщение. Преобразование для них добавляют через `.batch_transform(..)`, а `PublishTransform`,
написанный на одно сообщение, переиспользуют через `for_batch(transform)`.

Ответы проходят через преобразование по одному, но `PublishContext` у них общий, и относится он к
пакету, а не к доставке: пакет охватывает много доставок, поэтому `name()` - это подписка,
`headers()` пуст, а `context(..)` читает пакетный контекст брокера. Преобразованию, которое читает
входящее сообщение, место на пути одного сообщения, где ответ и его доставка - одно и то же.

### Как преобразование задаёт адресата {#naming-a-destination-from-a-transform}

Адресат сообщения объявлен: на типе сообщения через `#[outgoing(name = "..")]`, в точке
монтирования через `publish("dest")` или в месте вызова слота через `.to(..)`. У некоторых ответов
объявлять нечего. В запросе AMQP очередь для ответа указана в заголовке `reply-to`, а `ROUTER` в
ZeroMQ адресует каждый ответ тому участнику, который спросил.

Преобразование с `Destination = Names` задаёт имя само:

```rust
--8<-- "examples/publishing.rs:naming_transform"
```

На цепочку его добавляют как любое другое:

```rust
--8<-- "examples/publishing.rs:naming_transform_mount"
```

Позиция даёт это право только там, где адресат не объявлен, а в остальных случаях вызов
`.transform(..)` не компилируется. Тип ответа с `#[outgoing(name = "receipts")]` права не даёт, и
ошибка компиляции называет этот тип. Ответы пакета права тоже не дают: пакет отвечает многим
доставкам сразу, и ни одна из них не говорит, куда уходит ответ. Право выдаётся один раз, поэтому
второе задающее преобразование на той же позиции не компилируется.

`publish("answers")` в точке монтирования остаётся объявленным адресатом ответа. Это имя попадает
в сгенерированный документ, и туда же уходит ответ, если преобразование имя не изменило.

Слот даёт это право только тогда, когда каждый тип в списке `#[publishes(..)]` его маркера
оставляет адресата открытым. Тело по-прежнему пишет `.to(..)` на каждой публикации, а задающее
преобразование переписывает это имя. Маркер без списка допускает любое объявленное сообщение, в том
числе те, что задают адресата сами, поэтому права он не даёт никогда. Неявный `DefaultSlot`
одиночного безымянного `Out<impl Publisher>` - один из таких маркеров. Отзывается только право
задавать адресата: обычное преобразование такой слот принимает как любой другой.

Слот, отдавший право, даёт только обычную отправку: транзакция и цикл запрос / ответ доходят до
брокера мимо пути публикации слота, поэтому обработчик, который просит любую из них, не
компилируется.

`PublishLayer` реализует сигнатуру вида around/next, поэтому он может прервать цепочку, повторить
отправку или просто наблюдать:

```rust
--8<-- "examples/publishing.rs:app_layer"
```

Оба уровня складываются на приложении:

=== "Макросы"

    ```rust
    --8<-- "examples/publishing.rs:pipeline"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/publishing.rs:pipeline"
    ```

Общий для приложения слой оборачивает каждую публикацию обработчика: и ответ формы `publish(..)`,
и любое сообщение, которое уходит через внедрённый слот `Out`.

Преобразования точки монтирования действуют там, где их назвали:
`.out_reply(Publish).transform(StampSource)` наращивает стек ответа,
`.out(Audit, Publish).transform(OutboxEnvelope)` - стек этого слота. Регистрация с обеими сторонами
пишет оба вызова, а `.transform(..)` относится к позиции, названной перед ним. В конвейере первыми
выполняются преобразования позиции, в том порядке, в каком их написала цепочка, затем общий для
приложения middleware, затем отправка.

Мимо конвейера идут две публикации, и обе обработчик ведёт сам: транзакция, открытая на слоте
(`begin()`, `transaction()`), отправляет внутрь транзакции брокера, а обмен request / reply
(`request(..)`) ждёт ответа вместо того, чтобы завершиться отправкой.

На слотах роутера работают только собственные преобразования, но не общая для приложения цепочка:
`include_router` монтирует маршруты, типы которых сложились раньше самого приложения. Обработчик,
публикации которого из слота должны пройти эту цепочку, монтируют на области брокера через
`b.include(..)`. Полная программа -
[`examples/publishing.rs`](https://github.com/powersemmi/ruststream/blob/main/examples/publishing.rs).

## Пакетные ответы и транзакции

Обработчик `#[subscriber("in", publish("out"))]`, принимающий `&[T]`, потребляет целый
декодированный пакет и возвращает ответы на него - шаблон consume-transform-produce. `Ok(replies)`
публикует каждый ответ объявленному адресату и делает ack всего пакета; `Err(outcome)` не публикует
ничего и завершает доставку всего пакета значением `outcome` (всё или ничего: выборочные исходы на
каждый элемент с транзакцией не сочетаются):

=== "Макросы"

    ```rust
    --8<-- "examples/publishing.rs:batch_publishing"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/publishing.rs:batch_publishing"
    ```

Монтируйте его через `include`, добавляя в цепочку связывание ответа через `.out_reply(..)`:

=== "Макросы"

    ```rust
    --8<-- "examples/publishing.rs:batch_publishing_mount"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/publishing.rs:batch_publishing_mount"
    ```

Без `.transactional()` каждый ответ публикуется независимо. Сбой в середине пакета отправляет на
повтор весь пакет, поэтому при повторной доставке ранее опубликованные ответы могут уйти ещё раз
(at-least-once).

Шаг `.transactional()` после `.out_reply(..)` переводит связывание на одну транзакцию брокера на
пакет: рантайм начинает транзакцию, публикует все ответы, фиксирует её и только потом делает ack
входящего пакета. Любой сбой откатывает транзакцию, поэтому ответы никогда не бывают видны
наполовину.

Смонтировать такое связывание можно только с политикой, живой издатель которой
транзакционен, поэтому с брокером без транзакций программа не скомпилируется. В ответе на одно
сообщение нет пакета, который нужно сделать атомарным, поэтому `.transactional()` есть только на
пакетных формах.

## Ручные транзакции

Вне пути пакетных ответов транзакцией управляют вручную: `begin()` на любом транзакционном издателе
открывает `TransactionScope`, который владеет транзакцией. Публикации идут через эту область, а
`commit()` / `abort()` её поглощают, поэтому фиксация без начатой транзакции, вторая фиксация или
публикация после завершения - ошибки компиляции, а не сюрпризы во время работы:

```rust
--8<-- "examples/publishing.rs:manual_transaction"
```

У области тот же билдер, что и у любой другой поверхности (`scope.message(&value).publish()`), но
отправляет он в открытую транзакцию, а не прямо брокеру. Значения область кодирует кодеком издателя
и отправляет напрямую: преобразования на конкретного издателя и общий для приложения middleware
`publish_layer` принадлежат пути диспетчеризации (они читают породившую доставку) и здесь не
выполняются. Область, уничтоженная незавершённой, пишет предупреждение в лог и оставляет транзакцию
брокера на этом дескрипторе открытой - завершайте её явно.

Слот `Out` открывает ту же область: ограничьте слот через `Out<impl TransactionalPublisher,
Journal>` (на ручном пути - `where W: TransactionalPublisher`), и `begin()` на записи вернёт
область, которую ведут ровно как выше.

Область, открытая на слоте, принимает то же, что и собственный `message` слота: список маркера,
суженный объявленным набором параметра. Поэтому транзакция не опубликует того, чего сгенерированный
документ не объявлял, а её публикации в тестовой обвязке записываются на слот.

Область - это заимствующая разновидность транзакции: она занимает единственную транзакцию
дескриптора на стороне брокера, поэтому на одном дескрипторе в каждый момент открыта одна область.

Брокеры, у которых транзакция - это буфер клиента, а не состояние продюсера, реализуют ещё и
владеющую разновидность, `OwnedTransactions`: каждый вызов открывает независимую транзакцию с
буфером внутри возвращённого `TypedTransaction`, поэтому один дескриптор держит сколько угодно
транзакций сразу, и завершение одной никогда не задевает другую. `message(..).publish()`
буферизует в это значение, а `commit()` / `abort()` его поглощают - та же дисциплина «завершение
через поглощение», что и у области, - тогда как уничтоженное значение просто выбрасывает свой буфер
(с предупреждением) и не оставляет транзакцию брокера открытой. Брокеры вроде Kafka, где клиент
держит ровно одну транзакцию на продюсера, реализуют только заимствующую разновидность.

Владеющая разновидность на обеих поверхностях читается одинаково: у издателя, который буферизует
транзакции на стороне клиента, есть `owned_transaction()`, а у слота с ограничением
`Out<impl OwnedTransactions, Ledger>` - `transaction()`. Оба вызова открывают `TypedTransaction`,
который владеет транзакцией брокера и кодирует кодеком поверхности:
`let mut txn = publisher.owned_transaction().await?;`, затем `txn.message(&value).publish().await?;`
и `txn.commit().await?;`. Там, где `begin()` даёт заимствующую область (по одной на дескриптор),
один издатель держит сколько угодно `TypedTransaction` сразу. Буфер владеющей транзакции
завершается вне слота, поэтому её публикации попадают в журнал публикаций брокера, а не
записываются на слот.

## Пакетная публикация

Много сообщений публикуйте в цикле: у большинства брокеров (NATS, Kafka) клиент сам объединяет
записи, поэтому цикл даёт ту же пропускную способность, что и отдельный пакетный вызов. Там, где у
брокера есть настоящий примитив конвейеризации (Redis), его крейт отдаёт этот примитив как
совместимость, специфичную для брокера.
