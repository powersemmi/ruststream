# Кодеки и сериализация

Кодек превращает байты сообщения в типизированную полезную нагрузку и обратно. С брокером он не
связан. На приёме конвейер выглядит так:
`байты -> Codec -> типизированная полезная нагрузка -> обработчик`. На публикации тот же конвейер
работает в обратную сторону. Кодек фиксируется в точке монтирования обработчика, поэтому на пути
доставки он ничего не стоит.

## Встроенные кодеки

| Кодек | Фича | Подключает | Формат передачи |
|---|---|---|---|
| `JsonCodec` | `json` *(по умолчанию)* | serde_json | JSON |
| `MsgpackCodec` | `msgpack` | rmp-serde | MessagePack |
| `CborCodec` | `cbor` | ciborium | CBOR |

Фичи кодеков строго аддитивны: включить можно столько, сколько нужно. Типу сообщения достаточно
вывести `serde::Deserialize`, а типу ответа - ещё и `Serialize`.

## Кодек по умолчанию {#the-default-codec}

`DefaultCodec` - псевдоним, который выбирается по включённым фичам: `json`, если он включён, иначе
`cbor`, иначе `msgpack`. Когда кодек не назван нигде, его берут `include(def)` и цепочка ответа,
которая останавливается на `.out(Reply, policy)`. Аргумента-кодека ни та, ни другая запись не
принимает.

Без единой фичи кодека кодировать и декодировать нечем. Всё, чему потребовался бы кодек по
умолчанию, становится ошибкой компиляции, и она перечисляет выходы: включить фичу кодека, назвать
кодек явно или перевести сообщение на байтовый путь.

Байтовым путям кодек не нужен никогда: [вход `Deserialized`](subscribers.md#raw-subscribers)
строит себя из байтов доставки, а значение `Serialized` производит свои байты само. Сервис, который
использует только собственные форматы передачи, работает без фичи кодека и ничего не теряет.

## Двоичные протоколы - не кодеки {#binary-protocols-are-not-codecs}

Позиция кодека означает «значение, которое кодирует кодек, выбранный точкой монтирования».
Сгенерированное сообщение Protobuf в эту позицию не встаёт: оно само задаёт свою кодировку и
владеет раскладкой байтов от начала до конца. В позиции кодека одно монтирование отправило бы
`Order` в JSON, а другое - в Protobuf; ровно от этой путаницы байтовые пути и защищают. Поэтому
двоичный протокол работает на байтовых путях, где между типом и байтами передачи нет кодека.

Сгенерированный код не правят руками, зато любой генератор умеет добавить атрибуты к тому, что
выдаёт. `prost-build` принимает `message_attribute`, поэтому весь рецепт - два атрибута на каждом
сгенерированном сообщении:

<!-- inline-rust: the service's own build script, which has no compiled home in this repository -->
```rust
// build.rs
prost_build::Config::new()
    .message_attribute(
        ".",
        "#[derive(ruststream::Serialized, ruststream::Deserialized, ruststream::Outgoing)]",
    )
    .message_attribute(".", "#[wire(prost)]")
    .compile_protos(&["proto/orders.proto"], &["proto"])?;
```

Третий derive объявляет, куда отправляется сообщение: это объявление читают и типизированная
публикация, и ответ.

После этого каждое сообщение схемы само оказывается на байтовых путях, как будто его написали
вручную. Вкладка «Вручную» - то же сообщение с раскрытым `derive`:

=== "Макросы"

    ```rust
    --8<-- "examples/protobuf.rs:message"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/protobuf.rs:message"
    ```

Обработчик не называет кодек ни на входе, ни на выходе:

=== "Макросы"

    ```rust
    --8<-- "examples/protobuf.rs:handler"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/protobuf.rs:handler"
    ```

`#[wire(prost)]` - сокращение для пары функций одного генератора. Общая форма называет функции
сама: `#[wire(encode = <path>, decode = <path>)]`, где `encode` - это `fn(&Self, &mut BytesMut)`,
которая возвращает либо ничего, либо `Result`, а `decode` - `fn(&[u8]) -> Result<Self, E>`.

Cap'n Proto, FlatBuffers и самодельный кадр используют тот же механизм. Отдельная фича cargo на
каждый формат не нужна: крейт вызывает то, что назвал атрибут, и ни от одного из этих форматов не
зависит, а зависимость объявляет сервис.

Формат, который не укладывается ни в одну из этих форм, пишут так же, как написано на вкладке
«Вручную»: `wire_bytes` и `from_payload` - методы публичных трейтов, поэтому байтовый путь доступен
и без фичи `macros`.

Тип модели остаётся виден там, где это важно: его называет точка монтирования, его перечисляет
словарь слота `Out`, о нём сообщает сгенерированный документ `AsyncAPI`. Newtype с заранее
закодированными байтами скрыл бы тип во всех трёх местах. Эти сервисы -
[`examples/protobuf.rs`](https://github.com/powersemmi/ruststream/blob/main/examples/protobuf.rs)
и
[`examples/manual/protobuf.rs`](https://github.com/powersemmi/ruststream/blob/main/examples/manual/protobuf.rs).

## Откуда берётся кодек декодирования {#where-the-decode-codec-comes-from}

Кодек декодирования фиксируется во время компиляции. `include` не принимает кодек аргументом, а
берёт его с самого конкретного уровня, на котором вы кодек назвали: от самого узкого к самому
широкому.

### На один обработчик {#per-handler}

Переопределить кодек одного монтирования:

=== "Router"

    <!-- inline-rust: standalone Router-builder fragment; the compiled form is the with_broker tab below (codecs.rs:per_handler), which mounts the same chain via include_router -->
    ```rust
    router.with_codec(CborCodec).include(handle);
    ```

=== "with_broker"

    === "Макросы"

        ```rust
        --8<-- "examples/codecs.rs:per_handler"
        ```

    === "Вручную"

        ```rust
        --8<-- "examples/manual/codecs.rs:per_handler"
        ```

### На область

Задать один кодек для всех обработчиков в области `with_broker`:

=== "Макросы"

    ```rust
    use ruststream::codec::CborCodec;

    --8<-- "examples/codecs.rs:scope"
    ```

=== "Вручную"

    ```rust
    use ruststream::codec::CborCodec;

    --8<-- "examples/manual/codecs.rs:scope"
    ```

### По умолчанию

Когда кодек не назван ни на одном из уровней выше, `include` берёт
[`DefaultCodec`](#the-default-codec).

## Сторона публикации {#the-publish-side}

Издатели подчиняются тем же правилам: `.out(Reply, policy)` кодирует ответы кодеком по умолчанию, а
`.out(Reply, policy).codec(codec)` называет кодек явно, как и `.out(marker, policy).codec(codec)`
для отдельного слота `Out`.

Входящий запрос декодируется кодеком области, заданным через `with_broker_codec`, или кодеком
цепочки роутера из `Router::with_codec`, иначе кодеком по умолчанию. Кодек ответа задаёт цепочка
монтирования, поэтому форматы запроса и ответа свободно расходятся.

Кодек - свойство монтирования, а не типа сообщения: один и тот же тип декодируется как JSON на одной
подписке и как CBOR на другой, а точка монтирования - единственное место, где это сказано.

## Ошибки декодирования {#decode-failures}

Что делать с сообщением, которое не удалось декодировать, решает политика отказов. По умолчанию
сообщение отбрасывается: nack без возврата в очередь. Свою политику для подписчика можно задать
через `on_failure(decode = ..)`:

=== "Макросы"

    ```rust
    use ruststream::subscriber;

    --8<-- "examples/codecs.rs:decode_failure"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/codecs.rs:decode_failure"
    ```

Значения политики (`Drop`, `Retry`, `RetryAfter(..)`, `Skip`, `FailFast`), умолчания и оговорки про
повторы описаны в разделе [Политика отказов](failure-policy.md). Примеры с кодеками выше взяты из
[`examples/codecs.rs`](https://github.com/powersemmi/ruststream/blob/main/examples/codecs.rs).

## Свои кодеки

Кодек - любой тип, который реализует трейт `Codec`. Свой кодек можно передать везде, где
принимается встроенный.

Если обобщить его по другому кодеку, он станет составным: внутренний кодек задаёт формат полезной
нагрузки, а обёртка только преобразует байты вокруг него. Кодек ниже добавляет к байтам внутреннего
кодека двухбайтовый заголовок с версией. Ту же форму имеют конверт реестра схем и шифрующая
обёртка.

```rust
--8<-- "examples/custom_codec.rs:codec"
```

Обе стороны обёртки возвращают ошибку `CodecError`. Ошибка внутреннего кодека уже имеет этот тип, и
`?` передаёт её наверх без изменений. Ошибка самой обёртки становится `CodecError::Decode` (или
`CodecError::Encode`), а её источником - ваша собственная ошибка. Поэтому текст ошибки называет
слой, который отверг полезную нагрузку, и причину:
`decode failed: not an envelope: leading byte 0x7b`.

Свой кодек монтируется на тех же трёх уровнях, что и встроенный, и пример ниже задаёт все три
сразу:

=== "Макросы"

    ```rust
    --8<-- "examples/custom_codec.rs:mount"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/custom_codec.rs:mount"
    ```

## Синхронная граница {#the-synchronous-boundary}

`Codec::encode` и `Codec::decode` синхронны, и это задаёт границу того, что помещается в кодек:
только то, что определяют константа и уже полученные байты, как тег версии выше. Интеграция,
которой для сериализации нужен ввод-вывод (найти идентификатор схемы в реестре, взять ключ из KMS),
в кодек не помещается. Блокирующий вызов внутри кодека останавливает задачу доставки.

Такие интеграции ставьте вокруг кодека, на асинхронных участках: входящие полезные нагрузки
перекодируйте на пути доставки подписки, до того как их увидит кодек, а исходящие обрамляйте через
[`PublishLayer`](middleware.md#publish-side-middleware). Оба участка асинхронны и могут вернуть
ошибку. Ту же границу со стороны брокера описывает раздел
[Авторам брокеров](../broker-authors/index.md#middleware-on-the-async-edges).

Этот кодек - [`examples/custom_codec.rs`](https://github.com/powersemmi/ruststream/blob/main/examples/custom_codec.rs).
