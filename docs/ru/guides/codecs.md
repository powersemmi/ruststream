# Кодеки и сериализация

Кодек превращает байты из сети в вашу типизированную полезную нагрузку и обратно. Это отдельный шов,
не связанный с брокером: на стороне потребления конвейер выглядит как
`байты -> Codec -> типизированная полезная нагрузка -> обработчик`, а на стороне публикации тот же
путь проходится в обратном порядке. Кодек фиксируется в точке монтирования обработчика, поэтому на
пути доставки он ничего не стоит.

## Встроенные кодеки

| Кодек | Фича | Подключает | Формат передачи |
|---|---|---|---|
| `JsonCodec` | `json` *(по умолчанию)* | serde_json | JSON |
| `MsgpackCodec` | `msgpack` | rmp-serde | MessagePack |
| `CborCodec` | `cbor` | ciborium | CBOR |

Фичи кодеков строго аддитивны: включайте столько, сколько нужно. От типов сообщений требуется только
вывести `serde::Deserialize` (и `Serialize`, если тип уходит в ответах).

## Кодек по умолчанию {#the-default-codec}

`DefaultCodec` - это псевдоним, выбираемый по фичам: `json`, если он включён, иначе `cbor`, иначе
`msgpack`. Именно его берут `include(def)` и цепочка ответа, остановившаяся на
`.out(Reply, policy)`, когда кодек нигде не назван; ни тот, ни другая не принимают аргумент-кодек.

Когда не включена ни одна фича кодека, кодировать и декодировать нечем, поэтому всё, чему
потребовался бы кодек по умолчанию, оборачивается ошибкой компиляции - и она перечисляет выходы:
включить фичу кодека, назвать кодек явно или перевести сообщение на байтовый путь обработки.
Байтовым путям кодек не нужен никогда: [вход `Deserialized`](subscribers.md#raw-subscribers)
строит себя из байтов доставки, а значение `Serialized` производит свои байты само. Сервис, который
говорит только на собственных форматах передачи, работает вообще без фичи кодека и ничего при этом
не теряет.

## Двоичные протоколы - не кодеки {#binary-protocols-are-not-codecs}

Позиция кодека означает «значение, которое кодирует кодек, выбранный точкой монтирования».
Сгенерированное сообщение Protobuf в эту позицию не встаёт: оно и есть своя кодировка и владеет
раскладкой байтов от начала до конца. В позиции кодека одно монтирование отправило бы `Order` в
JSON, а другое - в Protobuf; ровно эту путаницу байтовые пути и предотвращают. Поэтому двоичный
протокол едет по байтовым путям, и между типом и проводом ничего не разрешается.

Сгенерированный код не правят руками, но украшать то, что он выдаёт, умеет любой генератор.
`prost-build` принимает `message_attribute`, поэтому весь рецепт - две строки конфигурации сборки:

<!-- inline-rust: the service's own build script, which has no compiled home in this repository -->
```rust
// build.rs
prost_build::Config::new()
    .message_attribute(".", "#[derive(ruststream::Serialized, ruststream::Deserialized)]")
    .message_attribute(".", "#[wire(prost)]")
    .compile_protos(&["proto/orders.proto"], &["proto"])?;
```

Дальше каждое сообщение схемы приходит уже на путях, как будто его выписали руками. Вкладка
«Вручную» - то же сообщение с раскрытыми деривами: два импла путей, выбранные ими способы передачи
и декларация исходящего:

=== "Макросы"

    ```rust
    --8<-- "examples/protobuf.rs:message"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/protobuf.rs:message"
    ```

Обработчик не называет кодек ни на входе, ни на выходе: для этого типа кодек не разрешается вовсе.

=== "Макросы"

    ```rust
    --8<-- "examples/protobuf.rs:handler"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/protobuf.rs:handler"
    ```

`#[wire(prost)]` - сокращение для двух путей одного генератора. Общая форма называет функции сама:
`#[wire(encode = <path>, decode = <path>)]`, где `encode` - это `fn(&Self, &mut BytesMut)`,
возвращающая либо ничего, либо `Result`, а `decode` - `fn(&[u8]) -> Result<Self, E>`. Cap'n Proto,
FlatBuffers и самодельный кадр едут по тому же механизму, и отдельная фича cargo на каждый формат
не нужна: этот крейт вызывает то, что назвал атрибут, и ни от одного из них не зависит, а сервис
зависит от того, который использует. Формат, который не укладывается ни в одну из этих форм,
пишется так же, как вкладка «Вручную» пишет этот: `wire_bytes` и `from_payload` - методы
публичных трейтов, поэтому весь путь доступен вообще без фичи `macros`.

Тип модели остаётся виден там, где это важно. Его называет точка монтирования, его перечисляет
словарь слота `Out`, о нём сообщает сгенерированный документ `AsyncAPI` - и все три поверхности
newtype с заранее закодированными байтами прячет за мешком байтов. Эти сервисы -
[`examples/protobuf.rs`](https://github.com/powersemmi/ruststream/blob/main/examples/protobuf.rs)
и
[`examples/manual/protobuf.rs`](https://github.com/powersemmi/ruststream/blob/main/examples/manual/protobuf.rs).

## Откуда берётся кодек декодирования {#where-the-decode-codec-comes-from}

Кодек декодирования фиксируется во время компиляции. `include` не принимает кодек аргументом: он
разрешает его по самому конкретному уровню, на котором вы кодек задали, от самого узкого к самому
широкому.

### На один обработчик {#per-handler}

Переопределить одно монтирование:

=== "Router"

    <!-- inline-rust: standalone Router-builder fragment; the compiled form is the with_broker tab below (codecs.rs:per_handler), which mounts the same chain via include_router -->
    ```rust
    router.with_codec(CborCodec).include(handle);
    ```

=== "with_broker"

    === "Макросы"

        ```rust
        --8<-- "examples/codecs.rs:per_handler"
        ```

    === "Вручную"

        ```rust
        --8<-- "examples/manual/codecs.rs:per_handler"
        ```

### На область

Задать один кодек для всех обработчиков в области `with_broker`:

=== "Макросы"

    ```rust
    use ruststream::codec::CborCodec;

    --8<-- "examples/codecs.rs:scope"
    ```

=== "Вручную"

    ```rust
    use ruststream::codec::CborCodec;

    --8<-- "examples/manual/codecs.rs:scope"
    ```

### По умолчанию

Когда ни один из уровней выше кодек не назвал, `include` берёт
[`DefaultCodec`](#the-default-codec).

## Сторона публикации {#the-publish-side}

Издатели подчиняются тем же правилам: `.out(Reply, policy)` кодирует ответы кодеком по умолчанию, а
`.out(Reply, policy).codec(codec)` называет кодек явно - как и `.out(marker, policy).codec(codec)`
для одного слота `Out`. Декодирование входящего запроса следует
области (кодек области, заданный через `with_broker_codec`, или `Router::with_codec` цепочки
роутера, иначе кодек по умолчанию), а кодек ответа едет на связывании, которое построила цепочка, -
так что форматы запроса и ответа спокойно расходятся.

Кодек - свойство монтирования, а не типа сообщения: один и тот же тип декодируется как JSON на одной
подписке и как CBOR на другой, а точка монтирования - единственное место, где это сказано.

## Ошибки декодирования {#decode-failures}

Когда декодирование не удалось, судьбу сообщения решает политика отказа; по умолчанию сообщение
отбрасывается (nack без возврата в очередь). Политика задаётся для каждого подписчика клаузой
`on_failure(decode = ..)`:

=== "Макросы"

    ```rust
    use ruststream::subscriber;

    --8<-- "examples/codecs.rs:decode_failure"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/codecs.rs:decode_failure"
    ```

Значения политики (`Drop`, `Retry`, `RetryAfter(..)`, `Skip`, `FailFast`), умолчания и оговорки про
повторы описаны в разделе [Политика отказов](failure-policy.md). Примеры с кодеками выше взяты из
[`examples/codecs.rs`](https://github.com/powersemmi/ruststream/blob/main/examples/codecs.rs).

## Свои кодеки

Кодек - это любой тип, реализующий трейт `Codec`, поэтому можно подставить свой и передать его
всюду, куда идёт встроенный кодек. Обобщите его по другому кодеку - и он станет составным:
внутренний кодек задаёт формат полезной нагрузки, а обёртка только преобразует байты вокруг него.
Кодек ниже обрамляет вывод внутреннего двухбайтовым заголовком с версией - ту же форму принимают и
конверт для schema registry, и шифрующая обёртка.

```rust
--8<-- "examples/custom_codec.rs:codec"
```

Обе стороны обёртки сообщают об ошибках через `CodecError`. Сбой внутреннего кодека - это уже
`CodecError`, и он уходит наверх через `?` без изменений. Сбой самой обёртки становится
`CodecError::Decode` (или `CodecError::Encode`) и несёт ваш собственный тип ошибки как источник,
поэтому сообщение называет слой, отвергнувший полезную нагрузку, и причину:
`decode failed: not an envelope: leading byte 0x7b`.

Свой кодек монтируется на тех же трёх уровнях, что и встроенный, - здесь все три сразу, чтобы
область, цепочка и ответ читались каждый своей строкой:

=== "Макросы"

    ```rust
    --8<-- "examples/custom_codec.rs:mount"
    ```

=== "Вручную"

    ```rust
    --8<-- "examples/manual/custom_codec.rs:mount"
    ```

## Синхронная граница {#the-synchronous-boundary}

`Codec::encode` и `Codec::decode` синхронны, и это задаёт границу того, что может находиться в
кодеке: только то, что уже решают константа и байты под рукой, - как тег версии выше. Интеграция, которой
для сериализации нужен ввод-вывод (разрешить идентификатор схемы в реестре, взять ключ из KMS),
сюда не помещается, а блокирующий вызов внутри кодека останавливает задачу доставки.

Место таких интеграций - асинхронные края: перекодируйте входящие полезные нагрузки на пути
доставки подписки, до того как их увидит кодек, а исходящие обрамляйте через
[`PublishLayer`](middleware.md#publish-side-middleware). Оба края асинхронны и умеют вернуть
ошибку. Ту же границу со стороны брокера описывает раздел
[Авторам брокеров](../broker-authors/index.md#middleware-on-the-async-edges).

Этот кодек - [`examples/custom_codec.rs`](https://github.com/powersemmi/ruststream/blob/main/examples/custom_codec.rs).
